Sources: Microsoft AI's LinkedIn post and the technical blog RL infrastructure at Microsoft AI (2026-11-23; a PDF version is linked from the page). Rocket was first described in the MAI Thinking 1 technical report and is now post-training MAI Base 2, a roughly three-trillion-parameter MoE base model.

The regime it is built for

The blog's opening point is that RL infrastructure depends on the training recipe. A model distilled from a stronger teacher starts RL near its ceiling, so RL is a short refinement phase: a failed run can be restarted and small sampler/learner mismatches have little time to compound. MAI instead climbs from the base model through RL itself, with no distillation, over many thousands of steps across weeks to months on thousands of GPUs. In that regime hardware failures are certain, numerical drift accumulates, and the best data mix and GPU split change as the policy improves. They name verl and slime as strong open foundations but say these long climbs push past where those are usually exercised.

MAI owns all three systems involved (learner and training framework, Rocket, and an inference engine on an MAI-maintained SGLang fork), so it can co-design their interfaces. Kubernetes or Slurm still allocate nodes, and Ray runs the job.

Architecture: the async GRPO loop

  1. A controller picks a problem from the curriculum and sends it to a problem worker.

  2. The problem worker fans a GRPO group of rollout requests out to a rollout worker pool.

  3. For agentic tasks, an agent loop calls the sampler and routes tool calls through a tool dispatcher to the task environment: sandboxed execution environments, search, or MCP servers.

  4. Per-rollout graders score each trajectory (and environment state where needed); trajectories go to a rollout store.

  5. The problem worker runs group graders and computes GRPO advantages once the group is in, then returns them to the controller, which packs segments into learner batches.

  6. The learner pulls token IDs and sampling log-probs from the store by reference and trains.

The post gives scale figures: the median software-engineering rollout runs 93 minutes and 249 turns, and one day of a production run handled 1.13 million rollouts.

Controlling staleness

Because the learner keeps updating while rollouts run, each token is generated by an older policy than the one that trains on it. The blog measures staleness in policy versions and shows sampler/learner log-prob gaps grow with it. With roughly constant step times, a token's staleness is about the sampler lag plus (time trained minus time generated) divided by time between steps. Each term gets its own control:

  • Sampler lag: two-stage weight broadcast (some sampler engines pull packed chunks from the learner, then fan out to peer replicas), so the learner's cost does not grow with fleet size. A weight transfer takes 15 seconds in the current run.

  • Finish old rollouts first: a request inherits priority from its rollout's start time, and in-flight concurrency autoscales to inference capacity. Waiting before a rollout's first token adds no staleness; once generation starts, every pause does. In their example, rollouts still waited 24 minutes before the first request, so timeouts must allow for it.

  • Drop failed rollouts rather than retry, because in their example the fastest rollout in a group already waits 7.6 hours for the slowest. The cost: dropped failures may share traits, which biases the GRPO baseline.

  • Stay inference-bound: over-allocate learner GPUs so finished groups wait seconds (12 in the example), not minutes, in the controller queue. The learner partly idles as a result.

  • A counter-intuitive one: adding inference servers at a fixed batch size can increase staleness, because steps come faster while a long rollout's wall-clock time doesn't change.

Numerical precision and bitwise parity

  • MoE experts are over 95% of parameters. Rocket stores them in MXFP8 but computes in BF16, because MXFP8 matmuls widened sampler/learner log-prob gaps. The learner fake-quantizes (to MXFP8 and back) so it sees the same weights as the sampler.

  • KV cache uses the same storage/compute split. Quantizing local-attention KV hurt parity much more than global, so local layers and the last three global layers stay BF16. The rest of global attention in MXFP8 gives about 67% more global-context tokens.

  • Bitwise parity between sampler and learner on identical checkpoint and input, with no noticeable slowdown. They observed the discrepancy growing later in training, which suggests optimization exploits numerical differences. On a 7B-active, 180B-total model, the bitwise-matched run scored higher at comparable steps than a run from before the fixes.

  • How they got there: replicate attention output-projection weights and all-gather head outputs, so the projection doesn't do a cross-GPU reduction (the learner runs without tensor parallelism to match the summation order). Combine experts with all-to-all and a local FP32 weighted sum. Use a shared FlashAttention-4 implementation with aligned tiling, KV splits and sliding-window block boundaries across learner forward, sampler prefill and sampler decode.

Fault tolerance and elasticity

  • Smallest-scope recovery. A separate job-management layer supervises the learner, controller and inference workers, and health checks treat a stall as a failure. If the learner fails, new admissions pause, its ranks are killed rather than left to hit NCCL timeouts, and it is rebuilt from the last checkpoint and reattached. The controller, curriculum, and in-flight rollouts keep going. This takes about 5 minutes and saved over 7% of GPU hours in a recent run.

  • A failed inference replica is replaced alone. Below a live-worker threshold, recovery escalates to in-job recovery inside the existing Ray job (about 0.42% compute saved), then to a cluster-level requeue.

  • Control plane on CPU-only nodes, which have been more stable than GPU nodes.

  • Elasticity: the learner, inference and controller scale independently; the learner resizes only after a checkpoint. Placement respects rack-scale Blackwell topology. A spare node group sized for one learner slice speeds up replacement. Typed, validated runtime settings (concurrency, admission, staleness limits, batch packing, mixture weights) take effect at defined boundaries. The blog credits runtime elasticity with a 9.88% gain in training compute.

Caveats

  • This is a vendor engineering blog. Benchmark claims (passing one frontier model on an internal aggregate, closing on another) rest on an aggregate of public and private evals and cannot be checked.

  • The parity comparison runs were launched about a month apart, so other changes may have contributed.

  • Dropping failed rollouts trades staleness for possible bias, and the blog says so without quantifying it.

Review checklist for long-running async RL

  • Do you measure staleness per token, and do you know which term (sampler lag, in-flight time, group wait, queue wait) dominates?

  • Are storage precision and compute precision separated, and does the learner reproduce the sampler's quantization?

  • Have you tested sampler/learner log-prob parity on identical inputs, both at initialization and late in training?

  • Can the learner fail and recover without killing in-flight rollouts?

  • Are runtime knobs typed, validated, and applied only at safe boundaries?

  • Is supervision isolated from GPU-node failures?
