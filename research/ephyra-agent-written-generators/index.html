Ephyra, a property-based testing library in Rust from Datadog. Repository public 16 Oct 2026 (MIT, 415 stars); paper arXiv:2611.23282v1, Alperen Keles, 23 Oct 2026, to appear at the Future of Property-Based Testing workshop at POPL'27; results write-up 24 Nov 2026.

The division of labour, which is the actual idea

Property-based testing has always had one bottleneck, and it is not the property. Stating a rule the software must keep — sorting preserves the multiset, a parser round-trips, two logically equivalent queries return the same rows — is usually easy. Writing a generator that produces inputs interesting enough to break the rule is the hard part, and it is where most PBT efforts quietly stall: the generator produces valid-but-shallow inputs, the property passes forever, and the suite becomes decoration.

Ephyra's split puts the human on the easy half and the agent on the hard one. An engineer writes the property. A coding agent writes the generator, measures code coverage, and rewrites the generator to reach further. The project describes this as inductive, in contrast to coverage-guided fuzzing's deductive mutation of a seed corpus: rather than mutating inputs toward new coverage, the agent edits the program that produces inputs.

The mechanism is worth stating precisely because it is the transferable part. On the headline case study, a database engine, the loop ran 37 rounds, over which the generator's coverage of the engine's instrumented counters went from 35.9% to 74.1% and the SQL features it could emit went from 79 to 261. That run found 26 bugs. The generator did not get luckier; it got broader, and breadth is a property of source code that an agent can read, diff and extend.

The numbers, and the cost line nobody quotes

Across 26 well-tested open-source systems the project reports 535 unique, previously unknown bugs, every one validated with a minimal reproducer and reported upstream, of which 373 have been confirmed and 313 already fixed. Targets include database engines, query planners, a URL parser, a policy engine, an SQL equivalence prover, Rust reimplementations of standard Unix tooling, and compilers. Bug ages run from under a day to 24 years.

The individual findings are a good advertisement for differential and metamorphic oracles. A 24-year-old compiler bug where a non-exhaustive match crashed instead of raising the language's own match-failure exception. A ~13-year-old case where three deletes corrupted a database file. A 670-byte query that needed close to 100 GB to parse, in a system at least 21 years old. An SQL equivalence prover that proved 0.1 and 0.100000001 equivalent, because it read constants as 32-bit floats. A LIMIT 1 that returned three rows.

But the number to carry into a planning conversation is in the paper's closed-loop table, and it is a cost:

Agent spend for those 80 bugs: $67 setup, $195 triage, $68 write-up, $330 total. About $4 per previously-unknown bug in mature, heavily-tested software.

Two readings follow. First, at that price the economics of finding bugs in your own system have changed category, not degree — this is below the cost of a single engineer-hour per several bugs. Second, and more useful for designing your own loop: triage is 59% of the spend. Generation is cheap, coverage is cheap, deciding what a finding means is where the money goes. Any plan that budgets for discovery and not for adjudication has the proportions backwards.

Note also what the oracles are. Three of the five closed-loop targets are differential against a mature reference implementation, and the other two use metamorphic relations over query plans (partitioning a query three ways and requiring the parts to sum to the whole; toggling optimiser rules and requiring identical results). Neither requires anyone to know the right answer in advance. That is why this works on systems nobody has a specification for.

Two things the authors say about their own work that coverage of it drops

The results do not validate the library. From the paper's discussion: the experimental contribution is not unique to Ephyra, any PBT library could be set up with a similar optimisation loop, and similar results would be expected. The 24 November write-up agrees that the work does not yet validate the library's design choices, with reliability, cost and generality still to be measured.

This is unusually honest and it changes what the number is evidence for. 535 bugs is evidence that agent-optimised generators work, not that this library is the way to get them. A team already invested in an existing PBT library should read this as a result they can reproduce in their own stack, and the library as a convenient set of primitives rather than a prerequisite.

Reward hacking is the named open problem. Also from the discussion: given a metric, an agent can optimise the metric rather than the testing power it stands for; designing metrics that resist gaming, and detecting when gaming is happening, remains open. Coverage is the metric here. An agent can raise line coverage with inputs that exercise paths shallowly, or that reach code through degenerate values, without improving the chance of falsifying anything. There is no published measurement of how often this happened, only the statement that it did.

The practical consequence: coverage is a usable optimisation target precisely because bugs found provides the outer check. Coverage alone, with no downstream bug count to validate it, would be the wrong metric to hand an agent and walk away from. The loop is sound because it is two-level — and if you adopt the technique, keep the second level.

Provenance discipline worth copying

The paper publishes a per-bug table: every bug with its upstream report identifier and its status. The status vocabulary includes the unflattering outcomes — fixed, reported, not yet reported (write-up ready but unfiled), won't report (decided against), duplicate (an existing issue already covers it), and declined (upstream closed it as not planned).

A headline bug count is cheap to produce and nearly impossible to evaluate. A per-bug table with upstream ids, duplicates admitted and declined reports counted is a claim a reader can audit. This is the standard to hold any "our agents found N bugs" claim to, including your own: if the declined and duplicate columns are missing, the number is not yet a result.

Tradeoffs and failure modes

  • No published false-positive rate. Not in the paper, the write-up or the README. The loop clearly expects them — its diagram routes a false positive to "narrow the oracle or generator", and the automated variant performs a harness fix and re-gates — so bad oracles are a designed-for case, but their frequency is unknown. Budget triage time without a prior.

  • A wrong property is indistinguishable from a bug until someone looks. The architecture's answer is to tighten the oracle or the generator, which is correct, and which is also human work. This is the same reason triage dominates the cost line.

  • A human is still in the filing path. Every report was personally validated and submitted. The closed loop automates pre-triage, minimisation, re-verification and write-up; it does not automate the decision to tell a maintainer their software is broken. Keep that boundary.

  • Coverage is a proxy, and the agent knows it. See reward hacking above. The defence is the outer bug count, plus metrics designed over the input distribution rather than only over reached lines — which is what this library's observability concept is for: generators declare a validity predicate and a set of metrics computed across generated inputs, checked over 10,000 inputs by default.

  • Differential oracles need a reference. The strongest results come from targets with a mature implementation to disagree with. Greenfield systems get metamorphic relations instead, which are weaker and require more thought per property.

  • Maturity. Version 0.0.1, explicitly experimental, "almost all of the code... subject to change", and standalone packaging still under study. Which model drives the agent, whether an API key is required, and whether any of it runs offline are not stated. Nor is any determinism or sandboxing requirement on the system under test, which matters for differential testing against a real binary.

  • No comparison against the incumbents. Hypothesis, QuickCheck and proptest appear nowhere with numbers. Given the authors' own claim that the loop is library-independent, this is the most important missing experiment: the same agent loop on an existing library, measured the same way.

Review checklist for an "agents found N bugs" claim

  1. Is there a per-bug table with upstream report identifiers, or only a count?

  2. Does the status vocabulary include duplicate, declined and won't-report? How many fall in each?

  3. How many reported bugs are confirmed, and how many are merely filed? Confirmed and fixed are different numbers.

  4. What is the oracle — differential against a reference, metamorphic over the system's own behaviour, or a human-written assertion? The first two scale without a specification; the third does not.

  5. What is the optimisation metric, and what prevents the agent from gaming it? Is there an outer check that the metric is still buying what it stands for?

  6. What is the cost per bug, split into discovery and triage? If triage is not the larger half, ask what is not being triaged.

  7. Who validates a finding before a maintainer hears about it, and is that step automated?

  8. What is the false-positive rate, and if it is not published, what is the plan for absorbing it?

  9. Would the result survive on a different testing library? If the authors say yes, treat tool choice as a convenience rather than a finding.

  10. For a differential setup: is the reference implementation's behaviour deterministic, and is the comparison sandboxed?

Related reading

  • Grading a reimplementation against the real service, and shadow-diffing a rewrite against the system it replaces, are the same oracle strategy applied to migration rather than to bug-hunting; this work shows the cost per finding when that strategy is pointed at mature upstream software.

  • Work on harnesses that enforce rather than propose is the structural counterpart: here the human-written property is the enforcement surface and everything above it is agent-generated and disposable.

  • Acceptance-gate designs for self-improving loops address exactly the failure this project names as open — an agent optimising a metric past the point where the metric means anything — and the two-level structure (coverage inner, bugs outer) is the cheapest version of that defence.

  • Port-and-gate workflows that keep a change only if replayed real behaviour still matches share the reliance on a reference oracle, and run into the same question of what to do when the oracle itself is wrong.
