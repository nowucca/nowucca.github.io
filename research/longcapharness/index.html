LongCapHarness: a written harness instead of long-context training

Elvis Saravia (DAIR.AI) on Zhang and He, Microsoft Research AsiaPublished 2026-11-07Summarized 2026-11-11

Read the original

long-documentsretrievalagent-harnessself-improving-agentscontext-engineeringsmall-models

TL;DR

LongCapHarness (Zhang and He, Microsoft Research Asia, arXiv 2611.10463, 7 Nov 2026; surfaced by Elvis Saravia) replaces long-context data synthesis and post-training with a harness. A strong model (GPT-5.6-Sol) decomposes each task type into capability primitives, implements each as code or a bounded LLM call, and refines them by recursive self-improvement on a development set. The frozen harness then runs a small model with an 8K or 32K window.

  • HELMET plus RULER average: Llama3-8B rises from 15.14 to 79.32 (+64.18), above NExtLong-128K (70.15); Qwen2.5-3B reaches 78.73, above PolicyLong-128K (64.10).

  • Recall hits 100 and RULER about 94 with both models, because keyword matching, lookup, counting and state tracking run as code.

  • Gains are small or negative on ICL, RAG and LongQA, and on LongBench-v2's longest subset it trails PolicyLong (27.85 vs 31.50).

  • Estimated development cost $541 in API tokens vs $1,859 to $3,696 of H100 time for the training baselines.

How it works

A capability is an abstract input-to-output transformation shared by many questions (for example, reranking). The harnessing agent splits it into primitives with defined inputs and outputs (relevance judgement, then ordering), writes control logic that schedules them, and defines a capability state: how a new question is converted into records the primitives can use and which intermediate results to keep. Explicit rules (assignment, counting, sorting) become code; judgements become an LLM call with a bounded prompt.

The agent runs each harness on development questions, compares its answers with the references, and revises primitives, control logic and state until the gap is small. Finished harnesses are frozen into a library with a text description. At test time the small model picks a harness by description and the harness runs as a program, keeping intermediate results outside the model's context so total input length is decoupled from any one call's window.

The reranking case shows the loop's value: BM25 plus sort (40.35), then LLM scores plus sort (38.95 to 40.50), then pairwise LLM comparison with group merge (56.28 on Qwen, best at every length).

Tradeoffs and failure modes

  • Task-type exposure. The development split deliberately covers every evaluated task type (2,242 dev vs 59,826 test examples, no overlap). The harness is fitted to the benchmark's task families, so the comparison with general-purpose context-extended models is not like for like.

  • Code wins where code is the answer. Perfect Recall and high RULER scores come from deterministic lookup and counting. That is a fair engineering result, but it measures program synthesis as much as long-context reasoning.

  • Semantic tasks stay model-bound. ICL, RAG and LongQA barely move; the harness organizes the work but cannot replace judgement.

  • Needs a frontier developer. Results drop sharply when the small models build their own harnesses, so the cost comparison assumes access to a strong model.

  • Inference cost can rise. Input tokens roughly double versus the RRSI baseline; on Qwen the estimated inference cost is $53.74 vs $29.39.

  • Two authors, estimated costs. Training costs are rental estimates, not measured runs.

Implications

Before post-training a small model for a long-context workload with a known set of task types, try a decomposed harness first: it is cheaper, inspectable and transfers across models for its code parts.

  • List the task types the workload actually contains; the method depends on that

  • Push every rule-like step (lookup, counting, ordering) into code

  • Keep intermediate state outside the model's context

  • Hold out task types, not just examples, to measure real generalization

  • Budget input-token growth at inference
