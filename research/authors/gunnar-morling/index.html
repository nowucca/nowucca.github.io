  2. 2026-11-12R046Hardwood: a remote file reader is really a schedulerReading Parquet from S3, the hard part is not decoding but deciding what to fetch and decode next: tens of ms per request, footer at the end, pages gated on bytes plus dictionary plus batch position, sometimes no page index. Every step is a job keyed by the first row it serves (lowest first); IO jobs on Java 21 virtual threads, CPU decode on a sized pool or the caller's thread; separate read-ahead bounds for fetched bytes and decoded values; the consumer's next need always runs (progress guarantee); zero-copy decode with reference-tracked buffers. Goal: run at the slowest resource's speed, never slower due to scheduling. Caveats: author's design note, no scheduler benchmarks yet, fairness and request coalescing not detailed.
