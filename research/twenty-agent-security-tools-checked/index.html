20 open-source tools for AI agent security, checked

TL;DR

A sound five-layer map for agent security (guardrails, red teaming, authorization, isolation, data and supply chain), but treat it as a category map, not a shopping list. Checked against GitHub on 2026-11-19: 16 of the 20 are healthy, widely used projects. LLM Guard is archived (Protect AI stopped maintaining it and its Hugging Face models), two names (AgentGuard, Guardian) are ambiguous low-traction projects with several unrelated repos sharing each name, and Trivy, Semgrep and ModelScan protect the code and model supply chain rather than the running agent.

The post's own closing point is the one to keep: assume the model will be manipulated, and make the outer layers (authorization and sandbox) hold anyway. Guardrail classifiers are probabilistic and belong inside that envelope, not in place of it.

Source: Maryam Miradi's LinkedIn post, posted 2026-11-06 (about 300 reactions, 46 reposts).

What the post lists

Five groups of four, each with a one-line "best when" rule:

  1. Prompt injection and guardrails (LLM Guard, NeMo Guardrails, AgentGuard, Guardian): when untrusted text can steer the agent.

  2. Red teaming and security testing (PyRIT, garak, Promptfoo, Giskard): break the agent before an attacker does.

  3. Identity and permissions (Open Policy Agent, OpenFGA, Casbin, Cedar): control which users, agents and tools can do what.

  4. Sandboxing and runtime security (E2B, gVisor, Firecracker, Kata Containers): when agents run code or cause real side effects.

  5. Data and secrets protection (Presidio, Trivy, Semgrep, ModelScan): when agents touch sensitive data, credentials, code or dependencies.

The post gives no links per tool, no versions and no evaluation; it promises a benchmark later. It ends with a link to the author's free course guide. The best comment thread adds the failure the list misses: the policy service goes down at 3 AM and the agent treats a missing approval as a yes. Authorization has to fail closed.

Where each layer sits

The five groups are not peers. They sit at different points on one tool call's path, and only some are deterministic. Read from the outside in:

  1. Build time (Semgrep, Trivy, ModelScan). Scan the agent's own code, images, dependencies and model files before deploy. These guard the supply chain, not the running agent.

  2. Input and output filters (NeMo Guardrails, LLM Guard, Presidio). Classify or rewrite text entering and leaving the model. Probabilistic: they lower the hit rate of injection and leakage but can be evaded, so they never stand alone.

  3. Authorization at the tool boundary (OPA, OpenFGA, Cedar, Casbin). A policy decision point checks each proposed call against who the user is, which agent is acting and what resource it touches. Deterministic, and the layer that still holds when the model is fully compromised. It must fail closed when the policy service is down.

  4. Isolation (gVisor, Kata, Firecracker, E2B). Contains whatever an allowed call does: file system, network egress, credentials. Stronger isolation costs startup latency and density (gVisor syscall overhead; Firecracker and Kata need KVM).

  5. Pre-deploy and continuous testing (Promptfoo, garak, PyRIT, Giskard). Attack the whole stack, in CI and on a schedule. They measure the layers above; they enforce nothing.

The design rule that follows: put decisions you must be able to audit in layers 3 and 4, and treat layer 2 as noise reduction. Most of the 20 tools are general infrastructure (OPA, Firecracker, Trivy) rather than agent-specific, which is a strength: they are mature and already run in production.

Gaps and corrections

Corrections:

  • Replace LLM Guard. It is archived. For a maintained input/output filter look at NeMo Guardrails or Meta's PurpleLlama (Prompt Guard, LlamaFirewall; 4.5k stars, pushed 2026-11-13). Protect AI's older Rebuff is archived too.

  • Skip AgentGuard and Guardian by name. Each name maps to several unrelated small repos. If tool poisoning is the worry, snyk/agent-scan (3.3k stars, Apache-2.0, formerly Invariant's mcp-scan) scans MCP servers and skills for poisoned descriptions.

  • Trivy, Semgrep and ModelScan are build-time tools. They belong in the pipeline that ships the agent, not in its runtime. Semgrep is LGPL-2.1, and its rule licensing changed in 2024, which some teams route around with the Opengrep fork.

  • Update repo homes: PyRIT moved to microsoft/PyRIT, NeMo Guardrails to NVIDIA-NeMo/Guardrails, Casbin to apache/casbin, Giskard to giskard-oss.

Missing layers a staff review would ask about:

  • Secrets brokering. The list detects leaked secrets but never keeps them out of the agent's reach. Inject credentials at an egress proxy outside the sandbox (as in OpenShell, R030, and Agent Substrate, R122) so the model never sees a token.

  • Egress control. No tool here limits where an agent can send data. Default-deny network policy is the cheapest control against exfiltration (see the F5 incidents, R112).

  • Audit trail. Nothing records who approved which action. Policy decision logs (OPA has them) plus per-call traces make incidents reviewable.

  • Fail-closed semantics. Raised in the comments: test that a down policy service or a timed-out approval denies the action.

Review checklist

  • Every tool call passes a deterministic policy check (OPA, Cedar or OpenFGA) keyed on user, agent and resource, and denies on timeout or error.

  • Code the agent runs executes in a VM-grade sandbox (Firecracker, Kata or gVisor), with default-deny egress.

  • Credentials are injected outside the sandbox; the model never holds a long-lived token.

  • Guardrail classifiers are treated as noise reduction, with their bypass rate measured, not assumed.

  • Promptfoo, garak or PyRIT runs in CI and on a schedule against the deployed stack, including indirect injection through tool output.

  • MCP servers and skills are scanned for poisoned tool descriptions before install.

  • Each dependency in the security stack is checked for archive status and maintainer activity at least quarterly.
