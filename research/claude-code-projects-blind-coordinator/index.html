Claude Code Projects: a coordinator that cannot read its own threads

Published 2026-09-17Summarized 2026-11-28

Read the original

Source: Anthropic's Claude Code Projects documentation and the launch post "Projects redesigned: from folder to conversation" (2026-09-17). Public beta, Pro and Max only.

What it is

A project is one long-running conversation in which a coordinator Claude turns what you send into threads. Each thread is a separate session with its own context window that does one piece of work and reports back. A cloud thread is Claude Code running in a cloud sandbox on its own branch, started from the repository's default branch, and it opens a pull request when the work calls for one. A thread can also run on your own computer through Remote Control, but only while that computer is awake.

That much reads like managed fan-out. The interesting part is the information boundary.

The one fact that shapes everything else

The documentation is explicit that the coordinator "sees what threads report back, not every step they take", and that "a thread's full results stay in the thread." The coordinator works from recent messages, recent threads and project memory — not from its own full history.

So the system has no shared transcript. Three consequences follow, and they are the whole design:

  1. Project memory is the only durable shared state. It is stored as files; every cloud thread reads an index file, MEMORY.md, at start and opens others as needed, and either the conversation or any cloud thread can be asked to remember or forget something. Anything a thread learns and does not write there is lost to the rest of the project the moment that thread goes idle.

  2. A thread's report is a summary written by the thing being summarised. There is no mechanism by which the coordinator can go and check. If a thread reports success on a partly-finished job, the coordinator has nothing to contradict it with.

  3. Writing to memory is an unprivileged action available to every thread. Any thread can write what every later thread will read as background. That is a coordination channel, and it is also the system's injection surface: text a thread wrote is peer-written text, not instruction, and nothing in the described design distinguishes the two.

What a thread inherits, and the omissions that matter

A new cloud thread starts with: the project's repositories and files, the project instructions, project memory, the CLAUDE.md in each project repository, the connectors on the account, and a cloud environment.

It does not start with skills, .claude/settings.json, or .mcp.json. And separately, cloud threads do not apply .claude/settings.json permission rules at all — approvals happen inside the thread, in auto mode where supported.

This is the sharpest practical finding in the documentation, and it cuts against the usual advice. The settings file is the layer that gives mechanical guarantees: a permissions.deny entry is checked before any classifier and refuses regardless of what the model decides. That is precisely the layer that does not travel into a project thread. Checked-in denies protect your terminal sessions and not your project's cloud threads, and the protection you are left with is the environment — network policy, secrets, setup script — plus in-thread approval.

A second asymmetry: local threads start with the project's instructions but not with memory files loaded. The same project, briefed the same way, behaves differently depending on where the thread runs, with nothing in the brief to say so.

Instructions have a ceiling

Project instructions go to each new thread and to the coordinator, up to 16,000 characters.

That cap is worth dwelling on, because the characteristic failure of hand-rolled agent fleets is a rule file that grows without bound — prose every agent is asked to read, which nobody can prove is read, where a rule present but unread is indistinguishable from one never written. A hard numeric ceiling does not fix that, but it bounds it, and it forces the question the prose never forces: which of these rules could be a check that refuses instead of a sentence that asks?

The thread lifecycle, and where it spends your money

The Overview pane groups threads into six states: Ready for review (PR open, awaiting review), Waiting on you (needs a reply or approval, or failed), Working, Landing (PR approved or queued to merge), Idle (finished, waiting on nothing), and Resolved — marked done by you, by Claude after a last step such as merging, or automatically after a week with no activity. Resolved threads can be reopened from the thread menu.

Once a thread opens a pull request it watches that PR with auto-fix on, regardless of your settings for other cloud sessions. It pushes fixes when CI fails, addresses review comments, and replies when checks pass. The consequence is stated plainly: an idle thread wakes and uses your plan when CI fails or a review comment arrives.

Read that as a billing and trust boundary, not a convenience. An open PR is a standing claim on your quota that is triggered by events you do not control, and the set of people who can trigger it is the set of people who can comment on the PR. The thread also acts on the content of those comments. Repository content, PR descriptions and review comments are external input; an agent that wakes on them and pushes code in response needs to treat them as information rather than instruction, and nothing in the product description says it does.

Prerequisites for any of this: code on github.com, push access, and the Claude GitHub App installed. A web-setup token is explicitly not enough.

Sandbox durability is best-effort

Each cloud thread clones its repositories into its own sandbox. The sandbox pauses between turns and resumes when the thread continues. If it cannot resume, the thread continues from a fresh clone, and uncommitted changes can be lost. The documentation's own mitigation is to commit and push work in progress on long tasks.

This is the right design for cost — idle sandboxes are not held — but it means the working tree is not the place to keep state across turns. Git is. For a long agentic task, treat "commit early" as a durability requirement rather than hygiene.

Scheduled tasks

Asking for recurring work in a project creates a cloud scheduled task that runs as threads in that project. One behaviour is worth planning around: a scheduled task's thread does not wait on a usage limit — its turn stops with a limit error and needs a message after the limit resets. A schedule that fires while you are over your limit does not queue; that occurrence is simply gone, and nothing retries it. Any schedule whose value depends on not missing an occurrence needs its own catch-up logic.

First-project setup can suggest scheduled tasks, switched on by default. Pausing or archiving a project stops them; deleting turns them off. Scheduled tasks created outside a project keep working independently.

Usage counts against the same plan limits as any other Claude Code session; a project cannot exceed them on its own, and work continues past them only with usage credits enabled. Because each thread is a full session, the launch post notes that projects reach limits faster. You can set model and effort level separately for the coordinator and for worker threads.

Availability, and what it is not

Public beta on Pro and Max, rolling out gradually; not on Team or Enterprise. Available at claude.ai/code and in the desktop and mobile apps — not in the terminal CLI, the VS Code extension, the JetBrains plugin, Amazon Bedrock, Google Cloud's Agent Platform or Microsoft Foundry. One user per project, no sharing, and no organisation-level controls during the beta. Threads cannot be moved or copied between projects and projects cannot be merged. Local threads cannot run while "Require trusted devices" is on.

The no-sharing constraint is doing more work than it looks. A single-user project has no identity problem: there is no fleet of agents posting under a shared login, so there is no question of which agent wrote which coordination record. Hand-rolled boards that put coordination state in a shared, writable artifact run into exactly that, and solve it with a convention rather than a credential. Projects sidesteps it by having nothing to share — which also means none of this generalises yet to a team.

What to take from it

  • Design for the blind coordinator. If a result must survive the thread that produced it, it goes in project memory or in git. A thread's report is the only thing the coordinator ever sees, so write reports as though they are the artifact.

  • Do not assume your deny list travels. Re-establish refusal at the environment boundary — network policy, secrets, setup script — because the settings file that enforces it locally is not applied to cloud threads.

  • Price the open pull request. Auto-fix on an idle thread converts third-party PR activity into spend on your plan, and converts comment text into an input your agent acts on.

  • Commit, don't rely on the sandbox. Resume is best-effort and the documented recovery loses uncommitted work.

  • Give schedules catch-up logic. A missed occurrence is dropped, not deferred.
