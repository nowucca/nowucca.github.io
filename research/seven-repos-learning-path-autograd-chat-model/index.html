Why this matters

There is a well-known gap between engineers who can call a language model API and engineers who understand how one is built. The usual advice for closing it is a reading list, which is why most attempts stall: a paper tells you what a transformer is, not what breaks when you implement one.

A different framing is circulating: treat a specific set of seven open-source repositories, all by Andrej Karpathy, as an ordered curriculum rather than a bag of resources. The claim worth taking seriously is not that these are good repos, which is uncontroversial, but that the order carries the pedagogy. Each stop is sized so that one person can read all of it, and each one answers the question the previous stop leaves open. That is a property of the sequence, not of any single repo.

The sequence

1. micrograd. A scalar-valued autograd engine in roughly 100 lines, plus a small neural-network library on top of it in about 50 more. Backpropagation stops being a formula you trust and becomes a graph of scalars you can print. The open question it leaves: this is one value at a time, so how do real systems do it on tensors, at scale?

2. nn-zero-to-hero. Eight video lectures that answer that. Lecture one builds micrograd from scratch, which is why micrograd comes first rather than being skipped as a toy: the sequence deliberately has you read the code before watching it being written. Later lectures work up through language models and the practical failure modes of training them.

3. minbpe. Byte-pair encoding, minimally implemented. This is the stop most self-taught engineers never make, and it is the one that explains a disproportionate share of odd model behaviour — token boundaries, arithmetic failures, why some strings cost more than others. The implementation is checkable against a known target: it reproduces GPT-4's token IDs, matching tiktoken.

4. nanoGPT. A transformer in about 300 lines of model code and about 300 lines of training loop. Worth being precise about its current status: the README is now deprecated and points readers onward to stop six. The guidance is to read nanoGPT for clarity, not to use it to train something. It is the clearest short statement of a GPT, and it has been superseded as a thing to run.

5. llm.c. GPT-2 in plain C and CUDA, with a CPU reference implementation of roughly 1,000 lines in a single file. This is where the framework disappears. Everything PyTorch was doing for you — allocation, kernel launches, the backward pass — is now written out in front of you, and the single-file constraint means there is nowhere for complexity to hide.

6. nanochat. The end-to-end one: training a GPT-2-class chat model for roughly $48, about two hours on eight H100s. The comparison that makes the point is historical rather than technical — training GPT-2 in 2019 cost on the order of $43,000. The same curve that made this repo possible is what makes the whole path teachable in a weekend rather than a semester.

7. autoresearch. The most interesting stop and the least like the others. It edits train.py, trains for five minutes, and keeps the change only if validation loss improves. One GPU, left running overnight, gets through roughly 100 experiments. It is a tiny, legible instance of automated research: a search loop over code changes with a cheap, honest objective.

What a staff engineer should take from this

Three things are worth separating out from the enthusiasm.

First, the ordering rule is the transferable artifact. "Each stop answers the question the previous one leaves open" is a usable test for any curriculum you build for your own team, and it is why a list of the same seven repos in a different order would teach less. If you are writing onboarding material, that rule is more valuable than the repo list.

Second, checkable milestones matter more than completeness. minbpe matching tiktoken IDs, llm.c's single-file CPU reference, nanochat's dollar figure: each stop has an unambiguous "it works" signal. Curricula without those produce the familiar outcome where a learner finishes every module and still cannot tell whether they understood any of it.

Third, the path has a deprecation in the middle of it, and that is a feature of how it should be read. nanoGPT's README now sends you to nanochat. Treating the sequence as fixed would have you train on a repo its own author has moved past. The honest version of the recommendation is: read four, run six.

The limitation worth stating plainly is scope. This path takes you from autograd to a small chat model. It does not cover post-training at scale, serving and inference economics, evaluation design, or anything about running a model in production. It closes the gap between calling a model and knowing how one is built, which is exactly what it claims and no more.

Open questions

  • Does the ordering rule survive the next repo? autoresearch is the newest stop and does not obviously "answer a question nanochat leaves open" so much as open a new direction.

  • The cost figures are the most load-bearing and the most perishable claim here. The $48 and the two-hours-on-eight-H100s numbers reflect a particular configuration at a particular price; anyone quoting them a year from now should re-derive them.

  • For hiring, the useful question is whether completing this path actually predicts the judgement the screening is trying to find, or only the vocabulary.
