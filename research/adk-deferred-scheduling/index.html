Deferred scheduling for agent runs: off-peak model capacity in Google ADK

What it is

Many agent workloads don't need an immediate answer: summarisation jobs, bulk eval runs, document pipelines. Google's Agent Development Kit (ADK) now lets a run ask for off-peak model capacity at a discount. When capacity is tight, the call waits in a queue instead of failing.

The setting is RunConfig(service_tier=ServiceTier.DEFERRED). It sits on the run, not the model or agent, so one agent definition can serve live users at standard tier and overnight batches at deferred tier.

Tiers: DEFERRED (queued off-peak), FLEX (best-effort, cheaper, no latency guarantee), STANDARD (default), PRIORITY (reserved capacity for latency-sensitive calls). The enum is a string, so new backend tiers can be passed before ADK names them.

How it works

  • The model must be a Gemini model with use_interactions_api=True.

  • On a deferred call the backend queues the request and returns an interaction ID at once. ADK polls it internally with exponential backoff, tolerates transient read failures (it gives up after 5 consecutive failures) and turns the final result into a normal response event. Application code reads events exactly as in a standard run.

  • Polling adds a few seconds on top of the queue wait, so it is wrong for short interactive calls.

  • Over HTTP, adk api_server accepts service_tier in the body of /run and /run_sse; deferred with streaming returns HTTP 422.

  • For long waits, the docs recommend Agent Runtime on Google Cloud rather than holding an HTTP connection open.

The sharp edges

  • Per-turn queuing. Every model turn in a tool-using agent is its own interaction and queues separately. Total latency is the sum of every turn's wait, so a 20-turn agent waits 20 times.

  • No client deadline by default. The backend's completion timeout is the only bound.

  • Timeouts don't cancel. An asyncio.timeout() or a client disconnect stops ADK polling, but the backend still runs the request, bills it, and the output can't be retrieved. A timed-out turn is paid for and lost.

  • Silent fallback. If the model isn't on the Interactions API, ADK drops the tier, logs one warning per run, and runs at standard price. The run succeeds, so the log line is the only signal. This is deliberate for mixed multi-agent runs.

  • Not everywhere. Custom model classes ignore the tier, streaming is incompatible, and some agent classes run their own loop and ignore it.

Review checklist

  • Is deferred used only for runs with no user waiting?

  • Are agents in deferred runs designed for few model turns (batched tool calls, larger steps)?

  • Is there an alert on the "has no effect for agent" warning, so fallback to standard pricing is visible?

  • Are client timeouts treated as cost, not as a spending cap?

  • Are long deferred runs hosted somewhere that doesn't hold an HTTP connection open?

  • Is the batch path tested end to end with the tier actually applied?
