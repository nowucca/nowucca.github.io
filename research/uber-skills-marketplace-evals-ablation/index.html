Uber's skills marketplace: evals, ablation and agent-filed papercuts

Source: Uber Engineering blog, How Uber Evals 1 Million Agent Skill Invocations a Month (Andrew Mager, Jason Varbedian, Uday Kiran Medisetty, 23 Nov 2026), shared on LinkedIn by Uber Engineering and by co-author Jason Varbedian. Figures below are Uber's own; no raw data or code is published.

What it is

Uber runs one Git-backed marketplace of agent skills (SKILL.md folders) that serves Claude Code, Codex, OpenCode, Cursor and its internal and hosted agents. It grew from one skill in October 2025 to more than 5,000, with over a million recorded invocations in one month. The post is less about the format than about the operating system around it: tiers, distribution, telemetry, evals, cost measurement and a bug-reporting loop in which agents report their own friction.

Architecture

Tiers. Skills live in three tiers with rising bars. Domain areas let any team publish after one peer approval and CI. Core skills are widely used, team-maintained and reviewed by the platform team. About 100 always-on skills (PRs, code review, tool access, data analysis, chat) are enabled for everyone. Graduation runs the eval system plus quality checks.

Distribution through one CLI. The aifx CLI starts each agent and translates skills, plugins (groups of skills), MCP access and sign-in into each agent's native config. Config merges six layers (company, team or program, repo, working directory, user, local override). Layers only add plugins and never remove them, so a repo can require a plugin set. Personas set defaults by role.

Discovery. A find-skills skill searches and installs a ranked skill for the current prompt. Ranking uses evals, run counts and a quality score. An internal context graph answers "skills my peers use that I don't."

Telemetry. Agent hooks emit OpenTelemetry events (session start, tool call, skill invoked with version, and whether the agent chose it or the user typed it). Events carry no prompt text or file contents. Twelve per-skill measures (users, retention, cost, latency, errors and others) appear on the skill's page in Skill Workshop, the authoring tool.

Spec-first authoring. Each skill has a spec covering its goal, outputs, required and forbidden tool actions, and target agents and models. Skill Workshop compiles SKILL.md and test prompts from it, and recompiles when a model or harness changes. A linter encodes the house style: numbered steps with one objective each and some verification, a concrete command whose result is checked before the next step, and an error-recovery table ("try again" doesn't count).

Evals

  • Suite mix: about 5% golden cases (fixed input, expected output, tool mocks), 80% real prompts graded on trajectory (right skills and tools in the right order), and 15% author-judged cases.

  • Three clean-room runners: a background-agent platform, a managed agent sandbox, and remote dev machines. Running away from the author's laptop exposed hidden dependencies on local paths, cached documents and OS tools.

  • Pass-rate stance: an eval passing 70 to 90% of runs can be more informative than one at 100%, which may be insensitive to meaningful changes. LLM judges need a human-annotated set that authors keep regrading.

  • Ablation: real prompts are replayed with and without a skill (and with parts removed), and a blind judge picks the winner. Results are reported against a per-skill noise band (how much two identical runs differ). Most skills helped and cost less. The biggest wins gave the agent something it couldn't find itself, such as internal docs or warehouse query access. For one warehouse skill, sessions without it made 13% more tool calls, had six times the tool errors and took 31% longer, and the with-skill answer won 87% of comparisons. Uber also tests deleting words, since stronger models can do worse with more instruction.

Cost per invocation

Agents report a running session-cost total in periodic snapshots. A skill call's cost is the last total before the call subtracted from the first total after it, summed per day and divided by calls. That window includes any other tool calls that land in it. Levers they report:

  • Code Mode: deterministic flows (queries, Slack, email, code search) moved into scripts that call tools through a gateway and write results to files. A default MCP install with over 100 tools had cost 50k to 70k tokens of definitions before the first user turn. .mcp.json files are now blocked inside skills and plugins.

  • Worker subagent on a cheaper model that returns a bounded summary: a tracing skill's cost per call fell 46%, while a deployment skill showed no drop in its first week. So they measure each change.

  • Run the script at load time when its output is small and always needed: one search skill went from four turns to three, with mean cost down 32%.

  • Move polling to a background agent. Notification turns were about a third of spend in the 20 most expensive sessions.

Papercuts: agents file their own bugs

An always-on log-papercut skill lets any agent report friction: what it tried, what it expected, what happened, and a suggested fix. Reports are grouped by skill on one dashboard, then triaged, root-caused, fixed, evaluated, approved and measured for regressions, with humans at two steps. Thousands were filed in three months and hundreds fixed. Examples:

  • a shared temp file let concurrent sessions overwrite each other's PR commit messages

  • seconds were passed where an API expected milliseconds

  • a config lookup silently returned a different key

  • a PR skill waited on CI in a repo with none until it timed out

Human signals also feed the loop. PRs from a maintenance factory that draw iteration or rejection become eval cases.

Tradeoffs and failure modes

  • Additive config layers are simple to reason about but can't subtract. A noisy company-wide plugin can't be switched off per repo, and the always-on tier's description cost is paid in every session.

  • The cost window is approximate. Snapshot granularity and unrelated tool calls in the window blur per-skill attribution, so it suits before/after comparison more than absolute accounting.

  • Trajectory grading assumes one right path. It can penalize a better route the author didn't anticipate, and it needs maintenance as tools change.

  • Judge and noise. Blind pairwise judging still inherits judge bias. The noise band is the right guard, but it needs repeated identical runs, which cost money.

  • Papercuts are agent self-reports. They can be wrong, duplicated or gamed by a struggling agent. Grouping and human triage carry the load, and the volume (thousands in three months) needs owners with capacity.

  • Spec-to-SKILL.md compilation adds a build step whose output authors may stop reading. Per-model compilation (listed as future work) would multiply the artifacts to evaluate.

  • What isn't solved: the post says the open problem is evaluating rare, high-stakes, hard-to-judge workflows. Its evals favor frequent ones.

Review checklist

  1. Does every shared skill have an owner, a tier and a graduation bar tied to an eval, not just to review?

  2. Is skill telemetry scoped to skill, version and selection mode, with prompt text and file contents excluded?

  3. Do eval suites mix golden, trajectory-graded real prompts and human-judged cases, with a measured noise band?

  4. Has each heavy skill been ablated (with vs without, and trimmed) against real prompts?

  5. Is cost per invocation measured before and after each efficiency change, rather than assumed?

  6. Are deterministic steps in scripts, and are large tool results kept out of the main context?

  7. Can agents report friction in a structured form, and does someone own triage and closing the loop?

  8. Do evals run in a clean environment that matches where the skill will actually run?
