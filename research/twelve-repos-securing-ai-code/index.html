The claim

Coding agents now produce code faster than humans can review it, so security checks have to be automated and layered. Beliaev lists 12 open-source repos (vendors include OpenAI, Anthropic, NVIDIA, Microsoft, Cloudflare and Cisco) that together cover code, dependencies, secrets, running services, and the agents and skills themselves.

The list is a listicle, not an evaluation: no head-to-head results, no false-positive rates. Its value is the taxonomy, and the fact that half the entries are now LLM agents rather than rule engines.

What the agent-native tools share

The four LLM-based scanners share a converging design.

  • Separate finder from checker. Cloudflare's skill gives every candidate finding to a fresh verifier that tries to disprove it, and a second set of fresh agents re-verifies the final records. Its principle: the agent that checks a finding is never the agent that found it. Codex Security has a separate validate step; Strix validates by exploit.

  • Evidence beats opinion. Strix requires a working proof of concept. Cloudflare's skill only confirms a finding with a complete source trace and an observed result; anything blocked stays needs_validation with the exact unresolved fact, and gets no severity.

  • Coverage is an artifact. Cloudflare writes a coverage-ledger.json and validates it with a zero-dependency script after every update; repeat runs target gaps in the ledger. Codex Security reports exclusions and coverage limits alongside findings.

  • Repeat runs are additive. Cloudflare reports that one run found about half of what repeated runs found in total. Codex Security's Deep mode repeats Standard scans and dedupes. Treat a single LLM scan as a sample, not a census.

  • Structured, schema-checked output. findings.json against a JSON schema (Cloudflare); SARIF, JSON and CSV (Codex Security, SkillSpector).

  • Sandboxing is a precondition. Cloudflare requires an OS-enforced sandbox with no external network to run target code; without it the lead stays unverified. Strix runs everything in a Docker image.

Agent and skill supply chain

Two entries treat the agent itself as attack surface. SkillSpector scans skills before installation: 71 patterns across 17 categories (prompt injection, data exfiltration, privilege escalation, memory poisoning, tool misuse and more), a fast static stage, an optional LLM stage, a 0 to 100 risk score, and baselines so re-scans show only new findings. Its README cites a research dataset in which 26.1% of 31,132 skills had vulnerabilities and 5.2% looked malicious. It is part of NVIDIA's Verified Skills pipeline, which scans, evaluates and signs skills before publication. PyRIT attacks the deployed LLM app from outside.

Anthropic's own action carries a warning worth repeating: it is not hardened against prompt injection and should only review trusted PRs. Any LLM reviewer that reads attacker-controlled diffs with write tokens is itself a target.

Gaps and caveats

  • Authorization logic. A commenter points out that none of these reliably catch broken object-level authorization (BOLA), where the exploit is a valid request for someone else's object id. Rule scanners can't see it; LLM scanners can only if they know the intended access model. Codex Security's README suggests focusing scans on authentication and authorization, which helps but needs a written threat model.

  • Omissions. Commenters add Gitleaks (pre-commit secret blocking, complementary to TruffleHog's history scan) and Wazuh (runtime log analysis and threat detection). Runtime detection is missing from the list generally.

  • BLA is the odd one out. It is obfuscation against AI reverse engineering, not vulnerability finding, and its claimed 300x to 2,800x token amplification is the project's own modeled estimate.

  • Cost and nondeterminism. LLM scanners need API keys, minutes per scan and repeat runs to approach coverage; results differ run to run. Keep the deterministic tools (Semgrep, Trivy, TruffleHog) as the always-on floor.

  • Dual use. Strix and PyRIT are attack tools; run them only against systems you own, inside a sandbox.

Review checklist

  1. Is there a deterministic floor on every PR: SAST rules, dependency and IaC scanning, secret scanning (history plus pre-commit)?

  2. Does an LLM reviewer run only on trusted PRs, with read-only tokens, given that it can be prompt-injected?

  3. Is every LLM finding checked by a separate agent or by an exploit before it is filed?

  4. Is coverage recorded, so a clean report can be told apart from an unexamined area?

  5. Are repeat or deep scans scheduled for high-value code, since one run finds about half?

  6. Are agent skills, MCP servers and plugins scanned before install and pinned after?

  7. Is there a written authorization model that a scanner or reviewer can check BOLA-type bugs against?

  8. Is target code executed only in a sandbox with no external network?
