Java4Shell (CVE-2026-114938): when the CPU, not the image, decides exposure

Sources: Oracle Critical Security Patch Update Advisory, November 2026 (published 2026-11-17); Horizon3 vulnerability summary; a platform-engineering write-up by Deepak Kumar shared 2026-11-19. Reported by Quang Luong (Calif.io) and Albert Yang.

The bug

HotSpot replaces the Java loop in java.util.Base64 with a hand-written x86-64 AVX-512 intrinsic once the decode method runs hot. When handling the final partial block, the routine computes an output length from the block size and subtracts one byte per trailing =. A one-to-three-byte tail produces a negative length; the store mask built from it is read as full width, and the routine writes 62 or 63 bytes past the end of the destination array, corrupting the next heap object. The decoder still throws on the malformed input, but the corruption has already happened.

  • Weakness: CWE-122 heap overflow, in JIT-generated code (Oracle files it under Compiler).

  • Attack vector: any service that Base64-decodes attacker-supplied data with the basic or URL decoder. No authentication, no user interaction.

  • Impact: memory disclosure and, with careful exploitation, remote code execution. The reporters say they demonstrated pre-auth RCE in default configurations of Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate.

  • Scores: Oracle CVSS 3.1 8.1 (high attack complexity); a CVSS 4.0 9.2 circulates in public write-ups. Exploitation attempts were reported by 2026-11-18; none confirmed successful, and it was not in CISA KEV at that point.

Why it is an operations problem, not just a patch

The vulnerable path runs only on x86-64 CPUs with AVX-512 VBMI (reported as Intel Xeon Ice Lake through Granite Rapids, AMD Zen 4 and newer). On Linux the check is avx512f, avx512bw, avx512vbmi and bmi2 all present in /proc/cpuinfo. ARM64 is unaffected. A container inherits its host's processor, so one image can be exploitable on one node pool and safe on the next. Image scanners that look only at the JDK version will report the same verdict for every replica; the real exposure is per node type.

Version confusion adds a second trap: builds patched in October are still affected. Fixed builds are 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1 (Oracle also lists a Java 8 perf build). Affected OpenJDK ranges start at 17.0.6. Downstream distributions (Temurin, Corretto, Red Hat builds) and JREs bundled inside appliances and vendor images ship on their own schedules. Sources disagree on whether OpenJDK itself published an advisory, so confirm ranges against your distributor.

Response plan

  1. Inventory by JVM and by CPU. List every running JVM with its version and the processor it actually runs on, including CI runners and build agents, which decode a lot of untrusted Base64 (artifact metadata, tokens).

  2. Prioritise internet-facing identity, build and collaboration servers.

  3. Patch everywhere, including ARM nodes, since the same update carries other fixes.

  4. Restart every JVM. A new image changes nothing until the old pod or process is replaced.

  5. Stopgaps only where patching must wait, tested first:

    • -XX:-UseBASE64Intrinsics disables the vulnerable intrinsic and costs decode performance.

    • -XX:UseAVX=2 keeps the JVM off AVX-512 entirely, can slow other vectorised code, and prevents an ARM JVM from starting, so it must not be applied fleet-wide blindly.

    • Verify with jcmd <PID> VM.flags -all. Neither flag is a vendor-supported workaround.

Failure modes

  • Per-image risk scoring misses mixed instance generations; a safe-looking service hides a vulnerable replica.

  • Patched image, unrestarted pods. The deploy pipeline reports success while old JVMs keep running.

  • Bundled runtimes in third-party appliances that you cannot rebuild.

  • Fleet-wide JVM flags breaking ARM nodes or degrading throughput.

  • Autoscaling onto newer hardware silently turning an unaffected service into an affected one before the patch lands.

Review checklist

  • Does your SBOM or scanner record the host CPU features, not just the JDK version?

  • Do you know which node pools have AVX-512 VBMI?

  • Can you list every JVM process (not image) and its uptime since the fix?

  • Are CI runners and build agents in scope?

  • Are vendor appliances with embedded JREs tracked with their own patch dates?

  • Is any stopgap flag scoped by architecture?
