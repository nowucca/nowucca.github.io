TrustGraph: access control before the model reads

TL;DR

TrustGraph is an open-source "ontology runtime": it extracts a knowledge graph from documents, guided and checked by your OWL ontology, stores it as RDF with provenance, and serves it to agents over MCP, SPARQL, REST and GraphRAG. The idea worth taking away is where access control sits. Policies written as SHACL-AF shapes are evaluated per node on every query, so restricted facts are filtered out of the result before any model sees them. Redacting a model's answer afterward is not access control, because the model has already read the data and can paraphrase, infer or leak it.

Architecture

Three stages, all on W3C standards:

  1. Extract (OntologyRAG). A similarity selector picks the relevant slice of the ontology for each chunk (with a bypass for small ontologies). The LLM emits triples, which are validated against domain, range and subclass constraints; triples that violate them are rejected. Entity types are stored with the graph embeddings so vector search can filter by type. Schema-free GraphRAG and hybrid BM25-plus-vector DocumentRAG with cross-encoder reranking are also available.

  2. Ground (context graph). Knowledge is stored as RDF (including RDF-star) in named graphs, with PROV-O lineage from document to page, chunk and edge. Query-time reasoning traces for GraphRAG, DocumentRAG and agent queries go into a separate named graph and are themselves queryable.

  3. Govern (SHACL-AF policies). Policies live in their own named graph. Each graph query is evaluated node by node against a per-request user context and gets one of three results: Allowed, Filtered or Violation. The same policies apply across REST, SPARQL and GraphRAG, and every evaluation emits a structured audit event. With no policies loaded the system runs in open mode.

Around that: guided traversal (seed nodes, per-hop restrictions by type, relationship, named graph or language), an agent orchestrator (ReAct, plan-then-execute, supervisor), an MCP server with bearer-token auth, small fast classifiers for decision scoring, and portable bundles for moving a workspace between deployments. It runs as a set of containers on Pulsar or RabbitMQ, Cassandra, Qdrant and S3-compatible storage. The README is explicit that it checks OWL constraints but is not a full OWL reasoner.

Tradeoffs

  • Filter at retrieval vs. redact at output. Filtering before the model reads is the only version that actually enforces access, but it puts policy evaluation on the hot path of every query and makes policy bugs silent: a fact that should have been visible simply isn't there.

  • Standards vs. simplicity. RDF, OWL, SHACL and PROV-O buy portability and auditability, and avoid lock-in to a warehouse vendor's object model. They also bring a steep learning curve; few application teams write SHACL fluently.

  • Ontology-checked extraction. Rejecting triples that break domain or range rules keeps the graph clean, but extraction recall depends on how complete the ontology is; facts the ontology doesn't model are dropped rather than flagged.

  • Self-hosted stack. Full control and on-prem deployment, at the cost of operating a message bus, Cassandra and a vector store.

  • Open mode by default. Easy to start, but a deployment that never loads policies is wide open, and nothing forces the switch.

Failure modes to watch

  • Inference around the filter. Hiding a node doesn't hide what can be inferred from its visible neighbors, counts or edges. Node-level filtering needs thought about aggregates and paths.

  • Leaks through other channels. Vector search, document-chunk retrieval and cached reasoning traces must honor the same policies as the graph; a trace graph that records a restricted fact is a side channel.

  • Stale user context. Policies are only as good as the per-request identity passed in; an agent running under a shared service token sees what the token sees.

  • Silent over-filtering. A too-broad shape quietly starves the model of context, which shows up as worse answers rather than an error. The Filtered vs. Violation distinction and audit events are how you'd catch it.

  • Ontology drift. As the ontology changes, previously valid triples may become invalid, and policies written against old classes may stop matching.

Review checklist

  • Is access enforced at retrieval, before content reaches the model, on every path (graph, vector, document, trace)?

  • Does every request carry the real end-user identity, not a shared agent credential?

  • Are policies tested with both allow and deny cases, including inference through neighbors and aggregates?

  • Is "open mode" impossible to ship to production by accident?

  • Are policy evaluations audited, and is over-filtering visible in metrics?

  • Is provenance kept from each fact back to its source chunk, so answers can be traced and retracted?

  • Is it clear which ontology changes require re-extraction or policy updates?
