DESIGN.md: a plain-text design system for coding agents

VoltAgentPublished 2026-11-24Summarized 2026-11-24

Read the original

docs-as-codeagent-codingtoolingopen-source

Source: the README of VoltAgent/awesome-design-md (MIT), surfaced by a practitioner post the same day. The convention itself originates with Google Stitch; everything below about the format comes from the collection's README, which cites that spec.

The convention

DESIGN.md is a markdown file at the project root that states a design system in prose and tables: colors, typography, spacing, components, layout rules. A coding or design agent reads it like any other repository file. The README's framing is the clearest statement of the idea:

FileWho reads itWhat it defines
AGENTS.mdcoding agentshow to build the project
DESIGN.mddesign agentshow the project should look and feel

The argument is narrow and plausible. An agent asked to build a page has no visual context, so it invents one, and the result is inconsistent across sessions and contributors. The existing fixes — Figma exports, JSON token pipelines, a configuration layer the agent must be taught to read — all put a parsing step between the agent and the intent. Markdown removes that step, at the cost of everything a schema would have guaranteed.

The format

The collection's files follow the Stitch format with extensions, in nine sections:

  1. Visual theme and atmosphere — mood, density, design philosophy

  2. Color palette and roles — semantic name, hex, functional role

  3. Typography rules — font families and a full hierarchy table

  4. Component stylings — buttons, cards, inputs, navigation, with states

  5. Layout principles — spacing scale, grid, whitespace philosophy

  6. Depth and elevation — shadow system, surface hierarchy

  7. Do's and don'ts — guardrails and anti-patterns

  8. Responsive behavior — breakpoints, touch targets, collapsing strategy

  9. Agent prompt guide — quick color reference and ready-made prompts

Two of these are doing work a token file cannot. Section 7 states what not to do, which is the part of a design system that normally lives in a reviewer's head and is exactly what an agent gets wrong. Section 1 gives the intent behind the tokens, so an agent facing a component the system never specified has something to extrapolate from. A JSON token file answers "what is the accent color"; this format tries to answer "would a button look right here".

Section 9 is the honest tell about what this is: a file that ships prompts for reading itself is a prompt artifact, not a specification.

The collection

83 DESIGN.md files extracted from public websites, grouped by sector (AI platforms, developer tools, backend and DevOps, productivity, design tools, fintech, e-commerce, consumer, automotive), plus a series reconstructing the web of the 1990s from period screenshots. Each entry ships DESIGN.md, preview.html and preview-dark.html, the previews being visual catalogs of swatches, type scale, buttons and cards — a sensible inclusion, since it lets a human check whether the extraction actually captured the look before an agent builds on it.

Usage is two steps: copy a file to the project root, tell the agent to use it.

The repo states that the files are extracted from publicly visible CSS, provided as-is, with no claim of ownership over any site's visual identity. Treat that as the author's position rather than legal advice: shipping a file that reproduces a named company's brand system, and asking an agent to build UI that matches it, is a trademark and brand question regardless of how the values were obtained. The 1990s series is the safer illustration of what the format can carry; a file called "Stripe" is a different kind of artifact.

Where this is weak

  • No validation, by design. Markdown is the point, so nothing checks that the hex values are real, internally consistent, accessible for contrast, or still true after a redesign. A JSON token pipeline is annoying for exactly the reasons that make it checkable.

  • No link to the implementation. The file sits beside the code and nothing keeps the two in agreement. This is the drift problem that every natural-language project document has, and the usual answer — generate the document from the source of truth, or check it in CI — is unavailable here because the format's selling point is that there is no pipeline.

  • Extraction fidelity is unverified. The files describe what the extractor saw on a public page. There is no claim that they match the company's internal system, and third-party extraction of a living design system ages quickly. The preview.html files are the only check offered, and they check the file against itself.

  • Prose scales badly as the rules get specific. Nine sections of prose per project is a document someone has to maintain; the "do's and don'ts" section in particular is where a real design system accumulates hundreds of exceptions.

  • A file dropped in the project root is read by the agent on every task. That is the point, and also a cost: it is context the agent carries, and a third-party file with an "agent prompt guide" section is instructions arriving from outside the repository. Read what you copy.

Review checklist before adopting one

  1. Did you read the whole file, including its prompt-guide section, before putting it where an agent will read it?

  2. Do the stated colors and type match your actual implementation today, or just the extraction's snapshot?

  3. Is it your design system, or a named company's? If the latter, is anything you ship from it going to look like theirs?

  4. What keeps the file in agreement with the code after the next UI change — a human habit, or something that fails loudly?

  5. Are the do's and don'ts specific enough to refuse a wrong output, or general enough to permit anything?

  6. Does the contrast of the stated palette pass accessibility checks? Nothing in the format verifies that.

  7. Does the agent actually honor it? Build the same component twice in separate sessions and compare.

Why it is worth watching anyway

The convention is doing the same thing AGENTS.md did for build instructions: moving knowledge that lived in people, tools and pipelines into a plain file the agent reads without configuration. That pattern has repeatedly won against better-structured alternatives, because the cost of a parser or a schema is paid every time the format changes, and the cost of prose is paid only when it drifts. Design is a reasonable next candidate, since the thing being communicated — intent and taste — was never well served by tokens alone.

The open question is whether a design system can tolerate drift the way build instructions can. A wrong build instruction fails visibly. A wrong color is shipped.
