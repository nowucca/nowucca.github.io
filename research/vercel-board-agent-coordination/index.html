Vercel Board: a message board as the coordination layer for coding agents

The claim in one paragraph

Agents now open pull requests faster than teams can merge them, so the bottleneck has moved from writing code to coordinating around it. Vercel Board gives each piece of work a thread on a team message board. GitHub reviews and check results, Slack replies and board posts all land in the same thread, and a watcher wakes an agent when an event matches. In the factory template, the agent reproduces a bug before fixing it, opens the PR, stays with it on a schedule, and merges only once a person approves on GitHub and checks pass. Vercel reports that its own factory now merges over half of its PRs.

Architecture

  • Board in the platform's API. Channels, threads, labels and files live in Vercel's API, so there is no database to run. A local board (serve on 127.0.0.1, optionally shared on a tailnet) and an in-memory board for tests use the same handle.

  • Identity from tokens, not accounts. People are who their CLI login says; deployments and CI runs are who their OIDC token says. A coding agent posts under its own name together with the person whose credentials it holds ("claude via julian"). Every message, reaction and label records its author from a verified token, giving one audit log.

  • Watchers instead of polling. A watcher is a filter over the event stream that the platform evaluates; matching events wake a route with retries and nothing held open. A PR's thread root carries its state as labels (open, approved), so an agent can wait on GitHub without polling it.

  • Sync with outbound restraint. Slack, GitHub and Linear sync into threads through a connector that holds their credentials, so the board stores no platform secrets. Nothing goes back to GitHub unless your sync function sends it, because GitHub is often public.

  • Tasks as leased threads. A task is a thread with state: who holds it, what it waits for, how it ended. A claim is a lease (for example 15 minutes) so two agents never hold one task.

  • Idempotent posts. Each post can carry a stable id so a retried delivery lands once.

The factory loop

  1. A bug report arrives from an issue, Slack or the board; the agent acknowledges it.

  2. The agent reproduces it in a sandbox of the thread's own and reports what it found. It fixes only confirmed bugs; feature requests get a proposal and wait for agreement; RFCs get a critique, not a build.

  3. It opens a PR and replies with the link, with a screenshot or video for visible changes.

  4. It checks back on the PR on a schedule and does what the team asks in the thread: fix, push, mark ready, merge or close.

  5. It marks the thread done when the settling PR merges.

Tradeoffs

  • Conversation as the control plane. Threads are legible to humans and agents alike and keep evidence next to decisions. The cost is that state is implicit in messages and labels; a structured queue gives stronger guarantees for ordering and retries.

  • Platform lock-in. The default board lives in one vendor's API and relies on its OIDC and connectors. The local and custom-backend options reduce but do not remove this.

  • Human approval stays the merge gate. Merging on approval plus green checks keeps a person in the loop; the over-half merge rate says nothing about how much review effort each merge took.

  • Pull versus push. In the hosted Factory integration the board is pull-only: posting does not wake an idle agent, and event delivery needs its own runtime. Watchers cover the push case only where you deploy them.

Failure modes to expect

  • Over-broad grants. A project grant can read and post on the whole board; channel names organize but do not restrict access. The guide's advice is separate boards when callers must not trust each other.

  • Shared principal within an environment. Every run in an environment is one principal, so a raw API client in any run could edit or delete what another run posted.

  • Preview environments. A preview runs any branch's code; granting it board access extends trust to every branch.

  • Watcher loops. A watcher that posts into a channel it tails can wake itself; the guide keeps factory channels out of watcher tails and sync for this reason.

  • Lease expiry mid-task. A slow agent can lose its claim and have another agent start the same task.

Review checklist for an agent coordination board

  1. Does every agent post carry its own identity and the human whose credentials it uses?

  2. Are grants scoped to named projects and environments, with no preview access unless intended?

  3. Can a watcher's own output re-trigger it?

  4. Is outbound sync to public platforms opt-in per event?

  5. Do tasks use leases, and is a lost lease detected before work is duplicated?

  6. Are posts idempotent under retry?

  7. Is merging gated on a human approval and passing checks, and is review effort per merged PR measured, not just merge rate?
