Borrowing a document genre as a prompt scaffold, and grounding it in the repository

Source: a practitioner's account of drafting an AWS-style PR/FAQ with a language model, plus primary-source checks on the two document formats it invokes (adr.github.io; Amazon's hosted excerpt from Bryar and Carr's Working Backwards*). No artifact, baseline or comparison accompanies the account — see "What this does and does not establish" before acting on it.*

The practice described is small enough to state in two sentences. Instead of prompting a model with a description of the document you want, name a published document genre the model already knows — here Amazon's PR/FAQ — and let its structure carry the prompt. Then, rather than describing the product yourself, point the session at the repository and its open issues and have it derive the actual feature set, mapping that to the goals of the release.

The practitioner's analogy is to Architecture Decision Records: a known framework "makes the model do much better work" by cutting the task into discrete, named pieces. That analogy is the useful part, and it is worth taking apart carefully, because one half of it holds up at the source and the other half does not.

What the two formats actually are

PR/FAQ. "Short for press release/frequently asked questions." The press-release portion is "a few paragraphs, always less than one page"; the FAQ "should be five pages or less". Its stated purpose is not documentation but reorientation: "The primary point of the process is to shift from an internal/company perspective to a customer perspective", as "a systematic way to vet ideas and create new products".

Note where that description comes from: an excerpt of Bryar and Carr's book hosted on Amazon's news site, rather than Amazon's own blog post on working backwards. It is a credible account of the practice, not a first-party specification of it.

ADR. An Architectural Decision Record "captures a single AD and its rationale", and helps a reader "understand the reasons for a chosen architectural decision, along with its trade-offs and consequences". The reference site does not name an originator — of Michael Nygard's 2011 post it says only that it "popularized the concept".

And here is the gap. That site does not publish a section list for an ADR. It points instead at the Y-statement format and at Zdun et al.'s Sustainable Architectural Decisions; concrete templates live elsewhere. So the claim "an ADR has a standard structure the model can follow" is weaker than it sounds. What the ADR genre reliably supplies is a defined scope and purpose — one decision, with rationale, trade-offs and consequences — not a fixed set of headings.

That distinction matters for the technique rather than undermining it. Both genres work as scaffolds because each carries a constraint and a point of view: the PR/FAQ forces a customer perspective and a hard length budget; the ADR forces exactly one decision and demands its consequences. Length limits and a mandated perspective are the parts a model cannot satisfy by writing more, which is the usual failure mode of an under-specified drafting prompt.

The grounding step is the part to copy

Strip away the document genre and the procedure still has a spine:

  1. Name a genre with a stated purpose and a stated budget, and let the model supply the form.

  2. Do not describe the feature set. Point the session at the repository and the open issues, and have it derive what the system actually does today.

  3. Map that derived feature set against the goals of the release, which is the one thing only a human has.

  4. Iterate by nudging, not by rewriting the prompt.

Step 2 is the engineering content. A product document drafted from a human's recollection of the feature set inherits that recollection's errors; one derived from the repository and the issue tracker is grounded in artefacts that can be re-read and disagreed with. The issues matter as much as the code — they carry the intended and the broken, which the code alone does not distinguish.

Step 3 is where this stops being automation. The release's goals are not in the repository. The division of labour is clean and worth stating explicitly in any process built on this: the model supplies form and derives current state; the human supplies intent.

What this does and does not establish

The honest summary of the evidence is short. The author reports that the model knew the format without examples, produced "a pretty good first pass", and that "the framework makes the model do much better work". There is no artifact, no comparison against a free-form prompt, no second attempt, and no measurement. The document itself is held back pending a release.

So: the procedure is concrete and repeatable, and the effectiveness claim is a single practitioner's impression of a single document. The appealing generalisation — that an established document genre is a better scaffold than a bespoke prompt — is a hypothesis this account illustrates, not a result it demonstrates. It is also the kind of hypothesis that is cheap to test yourself, which is the right response to it.

Two failure modes are predictable enough to name in advance:

  • Genre fluency without genre substance. A model that knows a format well can produce something that reads correctly and contains nothing, and a PR/FAQ is especially exposed here because polished marketing prose is exactly what the genre looks like. The customer-perspective requirement is the test: a draft that explains the system rather than the customer's changed situation has failed, however well formed it is.

  • Hollow derivation. Pointing a session at a repository guarantees grounding only if it actually reads enough of it. A feature set derived from a README and three file names will be confidently wrong, and a document in the right shape makes that harder to notice than a scrappy one would.

A short review checklist

For any document drafted this way, before it circulates:

  • Does each claim about present behaviour trace to a file, an issue or a test? Spot-check three.

  • Does the length budget hold without the content being thinned to meet it?

  • Is the perspective the genre demands actually present — customer outcomes in a PR/FAQ, consequences and trade-offs in an ADR — or only its vocabulary?

  • Which parts came from the release goals rather than the repository, and are those marked? Those are the parts the model could not have derived and the only parts a reviewer must supply judgement on.

  • Does the draft state anything the issue tracker contradicts, for instance describing as working something with an open bug?
