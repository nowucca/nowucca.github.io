Spec-driven development gaps: rules that drift, expensive search, and lost intent

Source: Oscar Benedek (IBM), "Spec-Driven Development: Let's Get Situated", shared in his LinkedIn post, November 2026. Describes an internal SDD framework being rolled out to IBM ALM teams with IBM Bob, IBM's coding assistant.

Context

Spec-driven development (SDD) frameworks such as GitHub's Spec Kit and OpenSpec put spec and rule files next to the code so agents have the who/what/why that code alone doesn't carry. The post credits them with reducing knowledge drift and names four gaps they leave: rule/validation drift, agent efficiency, multi-repo understanding, and intention drift.

Architecture of the proposed framework

  • Stacked RULES.md. Like a constitution file, but layered: org-level rules in a central repo, repo-level rules at the root, optional sub-folder rules. Higher levels always win.

  • Lifecycle hooks as the main fix for rule drift. Rules stated once at the start of a session get buried. The team injects short reminders and hard checks at events such as after tool use and at stop ("validate against RULES.md", run tests on uncommitted files). They report the agent treats hook-injected text as top-level instructions, and that hooks were the main source of improvement. Deterministic shell/Python validators at end of turn are in limited testing.

  • An SDD agent mode with extra system-prompt reminders; AGENTS.md is kept for behavioural guidance (interaction, note-taking).

  • Yellow-paging for efficiency. The SDD docs are condensed into one agent-oriented index file, with a navigation skill and a prompt-submit hook that says to use it before grep or glob. Results on their own diagnostic questions:

    • small repo, 3 questions: cost down 45%, time down 30%, tool calls down 56%, 1 expensive search vs 13;

    • larger multi-level repo, 3 questions: cost down 17%, time down 22%, tool calls down 58%, 3 vs 17;

    • same repo, 7 questions in one session: cost down 18%, time down 18%, tool calls down 33%, 14 vs 25.

  • Multi-repo understanding via a dependency map built at install and the GitHub Enterprise MCP server: the agent fetches related repos' index files and org-level rules remotely.

  • Intention drift. A PM-to-dev template feeds planning; after human review gates, the plan is compacted into a historical-changes entry the agent consults before touching that code.

Tradeoffs

  • Hooks cost tokens and attention every turn. Re-injecting reminders works because it is repetitive; too many reminders become their own noise.

  • Index files go stale. A yellow-pages file is only as good as its last regeneration; stale indexes steer the agent confidently to the wrong file.

  • Rule precedence by level is simple but blunt. Legitimate repo-specific exceptions to org rules need an escape hatch.

  • Remote context over MCP widens what the agent reads, and with it the latency and the prompt-injection surface.

Failure modes to watch

  • Small, self-run evaluations (a handful of questions, one assistant, internal cost units); no correctness measure is reported, only cost, time and search counts.

  • "Nearly guarantees" that checks run is a statement about tool calls happening, not about the checks being right.

  • Compacted plan history can drift from the code if later changes skip the process.

Review checklist

  • Are non-negotiable rules enforced by hooks or deterministic checks, not only stated once in a prompt?

  • Is there a cheap index the agent must consult before broad search, and is it regenerated in CI?

  • Do org-level rules have an explicit override process?

  • Is cross-repo context fetched from a trusted, read-only source?

  • Is the "why" of past changes stored where the agent will find it before editing that code?

  • Do efficiency claims come with a correctness measure?
