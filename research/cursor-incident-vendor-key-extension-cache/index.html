Cursor's incident: a read-only vendor key, credentials in agent traces, and a poisoned extension cache

Cursor incident update, 2026-11-13; analysis by Steve ZenonePublished 2026-11-13 (Cursor); 2026-11-17 (write-up)Summarized 2026-11-20

Read the original

Sources: Cursor, An update on our recent security incident, 2026-11-13; Cursor's 2026-10-30 security notice about the Claude Code extension; Fireworks' October security bulletin and Microsoft's 2026-10-30 analysis of the malicious extension (both cited by the commentary). Commentary: Steve Zenone, From a Vendor Key to Cursor's Extension Store, 2026-11-17, and his post.

What happened, per Cursor

  1. Vendor key exposed. Cursor had issued an access key to Fireworks, its training and inference vendor. Fireworks exposed the key. It was read-only, scoped to a storage bucket Cursor used to share data with the vendor.

  2. Old agent traces copied. The bucket held a limited set of coding-agent traces, mostly from 2025. They came from sessions not in Privacy Mode, which Cursor was allowed to use for training.

  3. Credentials inside the traces. A small number of traces contained credentials that had never been redacted. Under 0.01% of customers had API credentials exposed, and traces were exposed for under 0.05% of users.

  4. Lateral movement. Using those credentials, the attacker reached SaaS tools Cursor uses. From there they got archived non-production repositories, some support data and email, usage metrics and contact details, summaries of some agent conversations, and credentials users had sent to support.

  5. Supply-chain step. On 29 October, with another stolen credential, the attacker placed malicious copies of the Claude Code extension (versions 2.1.312 and 2.1.313) directly on the cache that serves Cursor's VS Code extension marketplace. The upstream Open VSX source was never tampered with, and it was not a flaw in the extension's real publisher. At most 5,000 users who requested those cached versions may have received the build, which was live for about 11 hours. Microsoft's analysis describes a persistent SSH backdoor.

  6. Containment. Cursor reports the last attacker activity on 1 November, and it was blocked. Production systems, the Cursor app and its updates, customer repositories and live traffic were not affected.

The core lesson

A read-only credential is only as safe as the data it can read. Agent traces are an especially dangerous dataset: agents read config files, environment variables and terminal output, so secrets end up in transcripts as a matter of course. Once traces are retained, shared with vendors and kept for training, they become a store of live credentials with weak access control.

Remediation Cursor lists

  • Moved inference off the vendor and revoked its key and data access.

  • Rotated every exposed credential, highest risk first, then all internal credentials as a precaution.

  • Verified the other marketplace extensions and rebuilt the marketplace.

  • Network-location restrictions on service-provider credentials, so a stolen credential fails outside its intended location.

  • Secret scanning across repositories, extended to other internal data sources.

  • Redeployed production and reviewed each internal service before restoring it, with external forensics engaged.

Failure modes this exposes

  • No redaction at capture. Secrets were scrubbed neither when traces were written nor when they were exported for training.

  • Retention without review. Year-old data stayed in a shared bucket.

  • Long-lived, location-free credentials. Keys worked from anywhere, and some were still valid long after they were captured.

  • The cache as a trust boundary. The marketplace verified its source, but the cache in front of it could be written with an internal credential and clients trusted it.

  • Support channels as credential stores. Users pasted secrets to support, and those messages were reachable from SaaS tools.

Review checklist for AI coding tools and their vendors

  • Do agent traces pass through secret detection and redaction before storage, and again before any export?

  • What trace data is shared with model vendors, under which key, for how long, and with what retention limit?

  • Can a vendor-held credential be used from outside the vendor's network?

  • Are extension or plugin artifacts signed end to end, so a cache cannot serve something the publisher did not sign?

  • Do clients verify the signature or hash on install and on update?

  • Are support tickets scanned for pasted secrets, with users told to rotate them?

  • If a trace leaks, can you list the customers affected and the keys to rotate within hours?
