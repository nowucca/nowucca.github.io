CSPD: add RL-trained skills to a frozen model as stackable soft prompts

Source: Zhang, Yang, He et al. (28 authors including Alkesh Patel, Zhe Gan and Xin Eric Wang; the post credits Apple, NVIDIA and university researchers), Composable Soft-Prompt Distillation of RL Experts: Toward Continual Post-Training, arXiv 2611.27376, submitted 2026-11-20. Surfaced by Pascal Biese's post.

The problem

RL post-training produces domain experts (math, code, agents). Shipping one model means consolidating them, usually by weight merging or multi-teacher on-policy distillation (MOPD). When experts keep arriving, consolidation becomes a continual process: every new expert forces a re-merge or re-distill of the whole model, and each round can erode capabilities outside the target domains.

The method

  • Keep the pre-RL base model frozen.

  • Distill each RL expert independently into a soft prompt: a short block of learned embedding vectors placed in the input.

  • Compose skills by concatenating their soft prompts, with no joint training. Add a skill by training its block; remove one by dropping it.

Results (from the abstract)

  • One soft prompt recovers at least 90% of the RL teacher's gain in 22 of 23 math, code and agent settings, across several open backbones.

  • Independently trained prompts compose: with experts added one at a time, the average score rises with each addition, and the full composition matches MOPD (67.83 vs 67.79).

  • The composition generalizes best on six held-out benchmarks.

  • Serving cost: throughput stays within 1.5% of the unadapted backbone, about 2.4x a rank-4 LoRA.

Limits to keep in mind

  • The multi-expert composition result is on one base model with few domains and, per the post's reading, a single run. Variance across seeds and orders is not established.

  • Each prompt uses context window. Stacking many skills adds memory and prefill cost and competes with the user's input.

  • Prompts are tied to one backbone, so a model upgrade means re-distilling the whole library.

  • Soft prompts need embedding-level access to the model, so this works for open weights you serve yourself, not closed APIs.

Engineering takeaways

  • A skill library on a fixed backbone becomes plausible. Teams that self-host can treat RL-tuned skills as deployable artifacts, versioned and toggled per request, without re-releasing the model.

  • Order and interaction tests matter. If skills compose by concatenation, CI should test combinations and orderings, not each skill alone.

  • Budget the context. Track the token cost of each skill prompt the way you would track adapter memory.

Review checklist

  • Has composition been tested across seeds, orders and more than one backbone?

  • What is the token length per skill, and how many fit before quality or latency drops?

  • Does adding a skill degrade held-out general tasks?

  • What is the re-distillation cost when the base model changes?
