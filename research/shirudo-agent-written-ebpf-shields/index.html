Shirudo: agent-written eBPF shields that hold the line until the patch lands

TL;DR

Shirudo is an open-source Linux runtime from OpenAI and Cisco for temporary, targeted mitigations ("shields") that block an exploit's code path on a running system while a real patch is tested and rolled out. Shields are eBPF programs, so they attach to a live process or kernel hook without a restart. The pitch is that AI agents can investigate a vulnerability, write a candidate shield, and validate it against both the exploit and real traffic, while humans approve what gets deployed. In a controlled demo, a Codex-generated shield added an input check to Java's Base64 decoder inside a running Elasticsearch and rejected a Java4Shell exploit attempt without downtime. BSD-2-Clause, with the BPF programs dual BSD/GPL.

The problem it targets

The window between disclosure and full patch rollout is days to weeks. Blunt mitigations (block a syscall, firewall a port) often break the service because the exploit and legitimate requests use the same operation. A shield aims to be narrow enough to stop the malicious input pattern and let everything else through.

How it works

  • Live protection: eBPF shields attach to specific points in the OS or a process and can block vulnerable paths without restarting. A shield can first run in a monitoring mode to show which requests it would affect before enforcement.

  • Agent-driven development: agents get programmable controls to investigate a vulnerability, draft a shield, and test it against the exploit and representative workloads. Operators approve deployment.

  • Trusted deployment: shields are cryptographically signed and verified before loading; the kernel's eBPF verifier enforces its safety rules; kernel security controls restrict unauthorized changes.

  • Hardware-backed evidence: a TPM records shield loads and removals, giving operators an attestable history of which protections were in force.

  • Getting started paths: a VM quickstart to sign, load and verify a test shield; a hands-on lab from Isovalent; a Linux Plumbers Conference walkthrough.

Engineering read

  • A virtual patch layer, now agent-authored. The concept is old (WAF rules, IPS signatures, live-patching), but moving it into eBPF at the process level gets much closer to the vulnerable code path. What is new is the claim that an agent can write and validate the shield fast enough to matter.

  • The validation step is the product. A shield that blocks the exploit but also blocks a rare legitimate pattern is an outage. Test coverage against real traffic (replay, shadow mode) is what turns a generated shield into something deployable. Ask how representative the validation workload is.

  • eBPF verifier proves safety, not correctness. The verifier guarantees the program won't crash the kernel or loop forever; it says nothing about whether the filter logic is right. Signed and verified is a supply-chain property, not a semantic one.

  • New privileged surface. A runtime that can load kernel-attached programs is a high-value target. Signing keys, who can approve, and audit via TPM records need the same rigor as production deploy credentials.

  • Lifecycle risk. Temporary shields have a way of becoming permanent. Track each shield with its CVE, owner and expiry, and remove it when the patch lands; otherwise you accumulate untested filters in the hot path.

  • Performance cost. Per-call checks in hot functions (like a decoder) add latency. Measure overhead under load before enforcing.

  • Sharing shields across organizations (the stated goal of publishing tested shields alongside disclosures) raises a trust question: who signs a community shield, and how do you validate it against your own workload?

Review checklist before adopting

  1. Who can generate, approve and load shields, and how are signing keys protected?

  2. Is there a mandatory observe-mode period with metrics on what would have been blocked?

  3. How is the validation workload built, and does it include rare but legitimate request patterns?

  4. Does every shield carry a CVE reference, owner and expiry, with alerts when the patch has shipped?

  5. What is the measured latency overhead on the hooked path?

  6. Are TPM attestations actually checked by something, or just recorded?

  7. What is the rollback path if a shield causes errors in production?
