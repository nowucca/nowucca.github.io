Inside an AI-run AWS intrusion: 56 API calls in 141 ms and 78 alerts nobody escalated

Sources: Elastic Security Labs, "56 AWS API calls in 141 milliseconds: Inside an AI-run intrusion" (Bousseaden, Porras Blanch and DeJesus, 13 Nov 2026), shared by Elastic on LinkedIn, 2026-11-19.

What happened

Between 30 September and 16 October 2026, one server running the CyberStrikeAI attack interface used stolen credentials for eight AWS identities in four accounts. Five were IAM users and three were EC2 instance roles. The researchers attributed the IP from internet-scan data: the server presented a self-signed "CyberStrikeAI" certificate on port 8080 a day before the first alert. Two sibling IPs share the same certificate.

The phases, from CloudTrail:

Sep 30   validate stolen keys          GetCallerIdentity / GetSessionToken
         harvest secrets               Secrets Manager reads
         harvest EC2 user data         56 DescribeInstanceAttribute(userData) calls in 141 ms
Oct 2    read encrypted SSM parameter  -> SSM SendCommand 29 s later
         (CloudTrail shows neither the command nor whether it succeeded)
...      14 quiet days, sporadic reuse
Oct 16   last activity

It produced 78 alerts, 65 of them on day one, across six detection rules that between them covered every phase. Every alert was medium or low severity, and each looked routine alone: a first-time GetCallerIdentity, a GetSessionToken, a SendCommand from a rare user. Only correlating by shared source IP showed one intrusion.

Why it matters

  • Machine speed is the tell. Fifty-six user-data reads in 141 milliseconds is not a human with a console. AI-driven tooling pursues objectives and enumerates everything it can, so it is noisy, but the noise is spread across many low-severity signals.

  • Severity-based triage fails. If the SOC escalates only high-severity alerts, this intrusion never surfaces. The fix is correlation, not more rules.

  • Credentials are the entry, user data is the prize. Secrets left in EC2 user data and readable SSM parameters turned one stolen role into lateral movement.

  • Audit gaps. CloudTrail records that SendCommand ran but not what it ran, so SSM command history has to be checked separately.

Detection lessons from the write-up

  • Add high-signal, low-false-positive behaviour rules that justify acting at once. Two examples are bulk EC2 user-data enumeration, and three or more distinct non-role identities calling GetCallerIdentity from one external IP and ASN within 10 minutes.

  • Correlate medium and low alerts by source IP and ASN, with flexible matching, since attackers rotate within a range.

  • Automate containment of compromised IAM identities once a high-signal rule fires.

Response checklist (from the write-up, condensed)

  • Assume anything an affected role could read is compromised, and work outward from the credentials.

  • Rotate every identity that touched the indicator IPs and revoke active sessions, including temporary credentials.

  • For instance roles, replace the instance profile or the instance. Stolen role credentials expire, but a compromised host can reissue them.

  • Treat all secrets in EC2 user data as exposed and move them to Secrets Manager or Parameter Store.

  • Review SSM command history for any unexpected SendCommand, including abuse of the AWS-RunShellScript and AWS-RunPowerShellScript documents.

  • Restrict ec2:DescribeInstanceAttribute for userData to the roles that need it, through IAM or a service control policy.

  • Enable GuardDuty and alert on credentials used from outside expected IP ranges.

  • Hunt for how the credentials leaked: exposed web apps, SSRF, code repositories, IMDS.

Tradeoffs and caveats

  • One vendor's telemetry. The analysis is from Elastic's own detections and shows its product's workflows. The lessons generalise to any SIEM, but the rule names are Elastic's.

  • Attribution is infrastructure-level. The link to CyberStrikeAI rests on certificate and page-title matches. That is strong for linking the servers, but it says less about who operated them.

  • Unknown outcome. The SendCommand payload and result are not in the logs, so the full impact is unknown.
