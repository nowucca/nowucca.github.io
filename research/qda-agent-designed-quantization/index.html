QDA: an agent designs the quantization recipe, scored by KL in minutes

Li, Zhao, Han et al., MIT and NVIDIA, arXiv 2611.23388; shared by Elvis SaraviaPublished 2026-11-17 (paper); 2026-11-19 (post)Summarized 2026-11-19

self-improvementquantizationevalsinference

Sources: Li, Zhao, Han et al. (MIT and NVIDIA), "QDA: Closed-Loop LLM Quantization Design with Agents", arXiv 2611.23388, 17 Nov 2026; Elvis Saravia's LinkedIn post on the paper.

The claim in one paragraph

Post-training quantization (PTQ) recipes do not transfer: the best mix of methods, calibration data and per-layer choices changes with each model and precision, so experts redesign it by hand. QDA hands that design loop to a coding agent. The agent proposes a recipe, a shared library builds the checkpoint, a fast evaluator scores it, and the agent uses the scores to decide what to change next. Each search gets 8 GPUs for 8 hours (64 GPU-hours) and roughly $19 to $75 of agent tokens. On four reasoning models QDA beats the strongest public recipe by 0.9, 1.4 and 2.2 accuracy points at W4A16, W4A8 and W3A16. On the 320B-parameter MoE GLM-5.3-Flash at NVFP4 (W4A4) it recovers 98.3% of FP8 accuracy, against 96.9% and 96.3% for the NVIDIA and Red Hat AI vendor checkpoints. Every output runs on existing serving kernels with no inference overhead.

Architecture

  • The loop. Each round has four steps: propose a recipe, build it with the library, score every checkpoint by KL in minutes, and run long-generation checks on a few promising candidates (hours). The agent ranks by KL and folds in the generation checks before proposing again.

  • Fast proxy evaluator. Scoring a quantized reasoning model on real benchmarks takes tens of GPU-hours. QDA instead measures the KL divergence between the candidate's next-token distributions and the original model's on about a million positions of reference reasoning traces. The original model's top-k distributions are cached once (about 1 GB); the candidate side is reduced inside vLLM's workers so only running sums leave the engine. The paper reports a score is 350 to 990 times cheaper than a full evaluation.

  • Generation checks catch what KL misses. Low KL does not rule out repetition loops in long outputs, so a few candidates get long generations. In one reported search this check caught looping on code answers, and the agent responded by distilling on long answers.

  • Composable library. Public PTQ methods are wrapped so they compose and run on new architectures, which removes the hand-porting step that normally limits what an expert tries.

  • Isolated evaluator. The agent runs in a sandbox with no GPU and no network except the model API, and a supervisor logs every tool call. The evaluator runs outside the sandbox from a read-only copy of its code, reads a frozen copy of each checkpoint, and returns only KL values (overall, per domain, and on human-written text). Every file the agent can read is scanned for test items first.

Why it matters beyond quantization

The pattern generalizes to any expert tuning loop: an agent can search a design space well only if each candidate can be scored cheaply, the scorer is out of the agent's reach, and an occasional expensive check guards against the cheap proxy's blind spots. Evaluation rate, not agent cleverness, sets how many rounds fit in the budget.

Tradeoffs

  • Proxy versus target. KL to the original model measures fidelity, not task accuracy. It is the right target for quantization (you want the original model back), but the same trick does not transfer to tasks where you want to beat the reference.

  • Agent harness versus vendor tooling. The paper reports that the same agent given NVIDIA ModelOpt's workflow and tools instead of QDA's library falls 0.5 to 1.3 points behind, so most of the gain is attributed to the library and evaluator design, not the model alone.

  • Budget. 64 GPU-hours per model-precision pair is cheap relative to expert time but not trivial; it pays off for models served at scale.

  • Starting point. The agent may start from a public checkpoint, as an expert would, so results are improvements over the best available start, not from scratch.

Failure modes to expect

  • Reward hacking the proxy. If the agent could read the reference traces it could calibrate on them and lower KL without improving the model. QDA's isolation exists for this reason; a reimplementation that shares a filesystem loses that guarantee.

  • Contamination. Calibration data or prompts that contain test items inflate results; the scan of every readable file is load-bearing.

  • Proxy blind spots. Repetition loops and long-horizon degradation can hide under a good KL; skipping the generation checks to save time reintroduces them.

  • Single search per model. Most models got one search; only the ablation model got three (standard deviation 0.1 to 0.2 points). Expect run-to-run variance on others.

Review checklist for an agent-driven tuning loop

  1. Can each candidate be scored in minutes, and is the cheap score validated against the expensive one?

  2. Is the scorer, its reference data and the test set physically out of the agent's reach (separate process, read-only code, frozen inputs)?

  3. Is there a periodic expensive check for failure modes the proxy cannot see?

  4. Are all agent tool calls logged by a supervisor outside the sandbox?

  5. Is every file the agent can read scanned for test items?

  6. Is the final result compared against the strongest public baseline and the vendor's own tooling, not only a naive baseline?

  7. Is the per-search budget (GPU-hours and tokens) reported alongside the gain?
