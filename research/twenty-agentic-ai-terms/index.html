20 agentic AI terms, checked for teaching

Read the original

Alok Sharan's LinkedIn post (12 Nov 2026) is a one-page glossary of 20 agent terms with a small diagram per term. It is a good first map for newcomers, but about a third of its one-liners are loose enough to mislead, and it leaves out the harness ideas (context management, permissions, tracing, idempotency) that decide whether an agent works in production. Use it as a vocabulary warm-up, then correct and extend it.

The 20 terms

The post groups the terms into five sets. The middle column paraphrases the post and its tile captions; the right column is the definition a staff engineer would want a learner to leave with. Rows marked * are corrected in the next section.

#TermThe post's gistSharper definition
1AI agentAn LLM in a loop that uses tools until the goal is doneA loop where the model picks the next action from the current context, and code outside the model runs it and feeds back the result. The loop, its stop condition and its budget are the design, not the model.
2Tool callingThe model emits a structured call; your code runs itSame. Add: the tool schema is a prompt, the arguments are untrusted input, and every call needs a permission decision.
3ReActThought, action, observation, repeatThe 2022 prompting pattern that interleaves reasoning text with tool calls. Native tool use in current models made it the default loop, so it is now more history than technique.
4PlannerBreaks a goal into ordered steps before actingEither an explicit plan the loop executes (plan-and-execute) or a plan the model keeps and revises. Plans go stale; the useful question is when to re-plan.
5*ReflectionThe agent critiques and fixes its own draftSelf-critique without new information helps little and can make answers worse. It works when the critique has an external signal: a test run, a linter, a checker, a second model with a rubric.
6Agent memoryShort-term in the context window, long-term in a storeRight split. Add: what gets written, when it is recalled, and how stale or wrong memories are corrected are the hard parts.
7Agentic RAGThe agent decides when and what to retrieveRetrieval as a tool the agent calls, often with several queries and a judgement of whether the results suffice. Coding agents often use grep and file reads instead of a vector index.
8StateThe shared object every step reads and updatesThe full record needed to resume or audit a run: messages, plan, tool results, pending approvals. Distinct from memory, which outlives the run.
9RouterClassifies a request and sends it down a pathSame. A router is usually a small classifier or a cheap model call, and often the place to use code instead of an LLM.
10*OrchestratorA lead agent splits work and delegates to workersOne pattern among several. Orchestration can also be plain code (a workflow) that calls models at fixed steps, which is often the better choice.
11*Multi-agent systemSpecialist agents collaborate, each with a roleSeveral model loops with separate contexts. The real benefit is context isolation and parallelism, not personas; the cost is tokens and coordination failures.
12HandoffOne agent passes control and full context to anotherTransfer of the conversation to another agent's instructions and tools. Passing the full context is a choice; a summary or a structured brief is often better.
13CheckpointerSaves state after each step so a crash can resumeSame. Resuming safely also needs idempotent or deduplicated side effects, or a resumed step repeats an email or a payment.
14Human-in-the-loopThe agent pauses for approval on risky actionsSame. Design questions: which actions gate, how the approver sees enough to judge, and what happens while nobody answers.
15*GuardrailChecks inputs and outputs and blocks unsafe contentInput and output filters are one layer. The stronger guardrails are on actions: tool permissions, scopes, rate and spend limits, and allowlists.
16Prompt injectionHidden instructions in a page, email or file hijack the agentRight, and the most important row on the page. No filter reliably stops it, so the defence is limiting what an agent that has read untrusted content can do.
17SandboxAgent code runs in an isolated box with no host accessSame. The tile says no network; real sandboxes often need some network, so egress control (an allowlist proxy) is the usual design.
18*MCPOne standard plug between AI apps and tools or dataAn open protocol where servers expose tools, resources and prompts to a client. It standardizes the connection, not the trust: a server is code you run or a remote you rely on.
19A2AAgents from different vendors discover and talk to each otherAn open protocol for agent-to-agent tasks, with an Agent Card that lists skills and an endpoint. MCP connects an agent to tools; A2A connects agents to agents.
20*Agent evalsScore outcome and steps on test tasks before shippingOutcome, trajectory, tool use and cost, measured on a fixed task set and re-run on every change. The post's scorecard is right; the missing part is that evals are continuous, not a ship gate.

Where the post is loose

Six one-liners teach a habit that causes trouble later. Fix these before handing the page to learners.

  1. Reflection implies the model can check itself. Research on self-correction finds little gain, and sometimes loss, when the model re-reads its own answer with no new evidence. Teach reflection as "critique against a signal": run the tests, then revise.

  2. Orchestrator and multi-agent are presented as the mature design. The list moves from single agent to orchestrator to multi-agent as if that were a progression. In practice most production systems are workflows (code calls the model at fixed steps) or a single agent with subagents for isolated side tasks. Teach "start with the simplest loop that works" and make multi-agent earn its token cost.

  3. Multi-agent is framed as roles. The Researcher, Writer, Coder and Critic tile suggests personas are the point. The engineering value is separate context windows: each worker sees only what it needs, and the parent sees only a summary.

  4. Guardrails are drawn as content filters. The shield tile blocks PII, toxic and off-topic text. That misses the guardrails that stop real incidents: least-privilege tools, scoped credentials, spend limits and egress rules.

  5. MCP reads as plug-and-play. "One standard plug" hides that every MCP server is a trust decision. A tool description can carry an injection, and a server can be swapped or updated under you.

  6. Evals sit last, as a ship gate. Placing evals at #20 under "before you ship" teaches them as a final exam. They are the regression suite you run on every prompt, model or tool change.

Two smaller points. ReAct (#3) is shown as a current technique; it is the ancestor of native tool use. The sandbox tile says "no network", which most real agents cannot live with, so the lesson is controlled egress rather than none.

What the list leaves out

The 20 terms describe the parts of an agent. They say little about the harness that keeps those parts working, which is where most engineering time goes. Add these eight to make it a course vocabulary.

TermWhy a learner needs it
Context engineeringChoosing what goes into the window each turn. Most agent failures are context failures, not model failures.
CompactionSummarizing or dropping old turns as the window fills. Long runs depend on it, and it silently loses facts.
SubagentA child loop with a fresh context for one side task, returning a summary. The practical form of multi-agent.
SkillsInstructions and scripts loaded only when a task needs them, so the base prompt stays small.
Permissions and approval modesWhich tools run without asking. This is the main safety control, more than any output filter.
Tracing and observabilityA record of every model call, tool call and token count. Without it you cannot debug or build evals.
IdempotencyMaking side effects safe to repeat. Retries and checkpoint resumes break without it.
Workflow vs agentThe choice between code-driven steps and model-driven steps. Most tasks with a known shape should be workflows.

The post also has no failure modes. A useful companion slide pairs each group with its typical failure: loops that never stop, wrong tool arguments, stale memory, lost context at handoff, double side effects on resume, approval fatigue, injected instructions, and evals that pass while users fail.

How to teach with it

The infographic works best as a map learners fill in, not a page they memorize. A 90-minute session for engineers new to agents:

  1. Warm-up (10 min). Show the grid with the captions hidden. Learners guess each term from its small diagram, then compare with the caption.

  2. Build the loop (25 min). Write a 30-line agent: one model call, two tools, a step limit. Point at terms 1, 2, 3 and 8 in the code as they appear.

  3. Break it (20 min). Give the agent a web page that contains an injected instruction (#16). Learners watch it obey, then add a permission check on the dangerous tool (#14, #15) and see that a content filter alone does not stop it.

  4. Resume it (15 min). Kill the run mid-task and restart from a checkpoint (#13). The tool that sends a message fires twice. Fix it with an idempotency key.

  5. Measure it (15 min). Write five test tasks and score outcome, tool choice, steps and cost (#20). Change the prompt and re-run.

  6. Correct the map (5 min). Hand out the six corrections and eight missing terms above. Ask which terms they used today and which they never needed.

Other uses:

  • Interview screen. Ask a candidate to explain the difference between memory and state, or MCP and A2A, and when not to use multi-agent. The post's one-liners are the shallow answer; the right column above is the strong one.

  • Team onboarding. Pair the page with R006 (six harness terms) and R022 (a reading list) as week-one material.

  • Critique exercise. Give senior learners the original post and ask them to find what it gets wrong. The six items above are the answer key.

Caution for reuse: the image is the author's work and the post ends in a book promotion. Link to the post rather than copying the graphic into slides, or redraw the grid in your own words.
