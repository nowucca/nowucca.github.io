Stretch evals: a practitioner's Gemini 4 Neon result on incident-investigation tasks

Source: Shahram Anver (Cleric, an agent that investigates production incidents), LinkedIn post, 2026-11-20. Trial run by Peter Richens. Short post, no eval details published.

What the post says

  • Cleric keeps a subset of its eval suite called stretch evals: cases its agent fails today. When models catch up, the team makes the cases harder, so the set always sits just past the frontier and tells them how ambitious the agent can be.

  • On that stretch set, Opus 5.5 and GPT-6.2 Sol both score 78.8% recall. Sol gets there about 1.5x faster and about 30% cheaper than Opus.

  • Gemini 4 Neon scores 98.1% on the same set.

  • The catch: without caching, Neon is "way too slow and costly to be usable". The author says Gemini 4 models add a request attribute that turns on an in-memory cache, and the team is tuning it to bring latency and cost to parity with or below Opus 5.5 and Sol 6.2.

  • Next step: a shadow experiment in production to see whether the eval gain holds on live incidents, with results promised for Monday 2026-11-23.

Why it matters

This is the first independent, domain-specific number for Neon after the vendor launch (R149), and it points the same way: Neon is strong on long agentic investigation. It also comes from a team whose task (root-causing production incidents from telemetry) is close to the SRE workloads in R155 and R031, where recall of the true cause is the metric that matters.

The more durable idea is the eval design. Most eval suites saturate: once every model passes, they stop separating candidates (R078). A stretch set is a deliberately unsaturated slice you keep moving, so each new model release gets a test it can actually fail.

How to read the numbers

  • A 20-point jump on a set built from failures is expected to look dramatic. The set was selected because the incumbent models fail it. Any model with different failure modes will look better on it than on a random sample (selection effect, a cousin of regression to the mean). The fair comparison is the full suite plus the stretch set, and the post only gives the stretch set.

  • Identical 78.8% for Opus and Sol suggests a small set (a few dozen cases would produce matching scores easily) or cases both models fail the same way. Size, run-to-run noise, and number of runs are not stated. Treat one-run gaps under a few points as noise (R039 on measuring the noise floor).

  • Recall only. For incident investigation, precision matters too: an agent that lists every plausible cause scores high recall and wastes an on-call engineer's time. No precision, false-positive, or confidence calibration figure is given.

  • Cost and latency are the open question. R149's list price is $3 in / $15 out per million tokens with cached input at $0.15, so long incident contexts that repeat across turns are the case caching is built for. Whether the cached configuration still scores 98.1% is not yet shown. The specific "in-memory cache" attribute is the author's description.

  • Evals vs production. The shadow run is the right next step. Live incidents differ from curated ones in noise, missing telemetry, and novelty. Watch for the follow-up post.

Practices worth copying

  1. Keep a stretch tier in every agent eval suite. Seed it from real failures (failed investigations, escalations, incidents the agent missed). When a tier saturates, promote it into the regression set and build a harder one.

  2. Report the stretch tier beside, never instead of, the main suite, so a model that is better on hard cases but worse on routine ones is visible.

  3. Compare models at equal harness and settings, and state thinking level and caching. Neon's own launch showed the harness alone can triple a coding score (R149).

  4. Gate a model switch on a shadow run, not on the eval: run the candidate on live traffic with its output hidden, and compare it to what the production agent and the human responder concluded.

  5. Price per solved task, with caching on, not price per token.

Review checklist when someone cites a stretch-eval result

  • How many cases, how many runs, and what is the run-to-run spread?

  • How was the set built, and was the new model involved in building it?

  • What happened on the full suite?

  • Recall and precision, or only one?

  • Same harness, prompts, tools and thinking level for every model?

  • Latency and cost per task, with and without caching?

  • Did it hold in a shadow or canary run?
