First-hand account from the vendor's own team; the one quantitative claim (up to 10 points from a separate grader) is internal and unpublished.

TL;DR

When about 90% of a team's code is written and reviewed by an agent, the bottleneck is no longer writing or reading diffs; it is verification you can trust without reading. The article's answer is to treat the verifier as a system in its own right: give the agent a real way to run the change end to end, keep the rules that judge a change out of that change's reach, route only persistent failures to humans, and grade the reviewer against the bugs that actually shipped. The parallelism claim is the point: without verification loops you can supervise one or two agents; with them, dozens.

What the system looks like

Three test types worth investing in.

  • End-to-end tests are the priority because they are hard to fool: the feature either works or it doesn't, and the failure arrives as evidence (a screenshot plus a description), not a timeout. A unit test can pass while the feature is broken because neither the agent nor the test understands the whole task. A feature map, written from the user's point of view with paths, shortcuts, selectors and expected results, doubles as guide and grading rubric.

  • Property tests (fast-check, Hypothesis, proptest) state something that must never fail (round-trip encoding, invariants, idempotency, optimized-equals-naive) and let a generator search for counterexamples. The key benefit is independence: generated edge cases do not share the bias of the agent that wrote the code.

  • Differential tests use the old system as the oracle during migrations: same random or production-sampled inputs to both, normalize irrelevant differences, keep an allowlist of intended changes.

How the team runs it.

  • A verify skill per area. A repo-local skill (in .claude/skills/, placed near the code) codifies how to boot and drive the app: browser extension for web, iOS/Android tooling for mobile, computer use for desktop, a local service for backend. It is treated as the smoke-test harness and hardened accordingly.

  • Failures decide what needs a person. The agent runs checks and attempts fixes; after three failed rounds on the same check it stops and escalates.

  • Owners write the checks. Code owners tune checks until they flag what the owner would flag, and every escalation states why.

  • Diff-triggered reliability checklist. 39 items, each with a trigger readable from a diff, a check, and the incidents behind it. Only matching items run (typically 3 to 10). Example: when session storage or message types change, confirm a new field loads safely from old transcripts.

  • One reviewer, tuned, multiple rounds. Rather than stacking a second, pricier reviewer, the team tunes the primary with a per-area REVIEW.md, and each round is handed context from earlier rounds and past failures.

  • Checks live out of the change's reach. The reviewer reads REVIEW.md from the base branch, never from the PR. Reviews attach to a specific commit; a pass on a stale commit is void.

  • Cheap checks first. Tests, build and lint run locally before a PR, enforced by a hook or a goal of a passing suite.

  • Gates roll out in observe mode. Every commit is stamped with how it was verified, including "none". A commit gate has off, observe and enforce modes; observe logs would-be blocks to find false positives. Enforce allows an explanation in the message and lets the third attempt through after two blocks so the agent can't deadlock.

  • Review the reviewers. Track reverts, maintainer rejections, and a size-matched clean control. The formal eval rebuilds the repo at review time for past incidents, scores only findings matching a one-sentence answer key, uses stable merges to penalize over-flagging, keeps tuning and test sets separate, and measures recall separately at raw findings, post-verification, and final review so it can see where found bugs are lost. Findings carry severity (Important, Nit, Pre-existing). Recall is tuned up to the point of overfitting the eval.

  • Misses become rules, and rules get pruned. Candidate rules come from human review comments and reverts (must recur in at least two PRs and be detectable from a diff; three agents try to disprove each; a human approves), or from replaying three bug finders against incident PRs (two of three finding it means detectable; a miss on a small diff is a REVIEW.md gap). Flaky tests may not be skipped, slept or retried; without a root cause they are deleted with a written reason. Rules, steps and suites are pruned on a schedule.

Tradeoffs

  • E2E over unit. More realistic and harder to game, but slower and flakier; the article's mitigation is to run heavy checks before commit and invest heavily in making the verify skill fast and reliable.

  • One tuned reviewer vs. many reviewers. Cheaper and easier to evaluate, but correlated blind spots stay correlated; the article compensates with property tests and independent bug finders rather than a second reviewer.

  • Escalate after three rounds. Bounds token spend and human load, but a fix that needs four honest rounds gets escalated, and a determined agent can still "fix" by weakening code within three.

  • Deleting flaky tests. Removes a training signal for retry-until-green behavior, at the cost of coverage; the written reason is the only record of what was lost.

  • Bypass after two blocks. Prevents deadlock, but makes the gate advisory for anyone willing to try three times; the verification stamp is what makes that queryable afterward.

Failure modes to watch

  • The verifier drifts into the change. Any check, rubric or REVIEW.md readable from the PR branch can be edited by the change it judges.

  • Stale reviews. A result tied to a branch rather than a commit SHA silently covers later pushes.

  • Flaky checks train retries. If re-running is cheaper than fixing, agents learn to re-run.

  • Checklist bloat. Every incident adds a rule; without pruning, matching items stop being 3 to 10 and become noise.

  • Eval overfitting. Tuning recall against a fixed incident set eventually optimizes for those incidents; the separate test set and clean control are the guardrails.

  • Same-bias tests. Agent-written tests for agent-written code share blind spots; property generators and differential oracles are the independent sources.

Review checklist

  • Does each area have a runnable verify path (skill, script or harness) that drives the real app, and is it fast and reliable enough that agents actually use it?

  • Are review rules, rubrics and gating config read from the base branch, never from the PR?

  • Is every review and verification result bound to a commit SHA?

  • Is there a bounded retry count before a human is pulled in, and does the escalation say why?

  • Are reliability rules triggered from the diff rather than run wholesale, and does each cite the incident behind it?

  • Is every commit stamped with how it was verified, including "none"?

  • Do new gates start in observe mode, with false positives reviewed before enforcement?

  • Is the reviewer evaluated against past incidents with a clean control and recall measured per stage?

  • Do flaky tests have a policy other than retry (root-cause or delete with a reason)?

  • Is there a scheduled pruning pass for rules and checks?
