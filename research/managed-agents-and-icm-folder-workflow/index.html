The reel

Jake Van Clief's 2 min 23 s reel (posted 2026-04-09, the day after Anthropic's post) makes one claim: Managed Agents makes custom agent harnesses a waste of time, and vindicates building on files and process instead. Paraphrased from the burned-in captions, in order:

  1. A "lawyer agent", "marketer agent" or "finance agent" is usually just a harness wrapped around someone else's model, and startups sell those wrappers.

  2. As models improve, those harnesses go stale or get in the way. Managed Agents "cancels all that out".

  3. On paper he draws the split: one brain, many hands. Hands are tools (data, MCP servers, plain SQL calls); "legs" are security, cloud and scale. Anthropic "took the brain and removed it from the hands".

  4. He says he made the same move earlier by "using file architecture as my harness", and points at the post's opening (harness assumptions "go stale") as Anthropic saying what he has been saying.

  5. The payoff: what matters now is "the process and the structure". Most people do not even need Managed Agents; a couple of tables and markdown files do most of the work. The hard part is breaking down the process and the workflows the agents read.

The captions are paraphrased; treat the quotes as close, not exact.

Managed Agents at a glance

Managed Agents is Anthropic's hosted service for long-running agents, launched April 2026 and still in beta. It splits an agent into three parts behind stable interfaces: the brain (Claude plus the harness loop), the hands (sandboxes and tools), and the session (an append-only event log). Any part can fail or be swapped without the others noticing.

Read it from the accent box: the log is the only thing that must be durable. Everything else is cattle, rebuilt on demand.

The interfaces and the API objects

Managed Agents is two layers: a handful of internal interfaces that the engineering post names, and the public REST objects you program against. The internal interfaces are the design; the REST objects are how you reach it.

Two details matter more than they look. Agents are versioned, so a prompt change never mutates a running session. And memory stores and repo skills are both folders of markdown mounted into the sandbox: the platform's own persistence model is files the agent reads with ordinary tools.

Why it is built this way

The design starts from one observation: a harness encodes assumptions about what the model cannot do, and those assumptions go stale. Anthropic's example is context resets added because Sonnet 4.5 wrapped up early near its context limit ("context anxiety"); on Opus 4.5 the behaviour was gone and the resets were dead weight. So Managed Agents commits to interfaces (session, harness, sandbox) and stays unopinionated about what runs behind them. The post's analogy is the operating system: read() outlived the disk pack.

The failure that forced it: the container was a pet. The first version put session, harness and sandbox in one container. File edits were syscalls and there were no service boundaries, but:

  • A dead container lost the session.

  • A harness bug, a dropped packet and a dead container all looked the same from the WebSocket stream.

  • Debugging meant a shell inside a container that also held customer data, so in practice they could not debug.

  • Customers who wanted Claude in their own VPC had to peer networks, because the harness assumed every resource sat next to it.

What decoupling bought

ChangeEffectNumber reported
Containers provisioned lazily by a tool callInference starts as soon as the orchestrator reads pending eventsp50 time to first token down about 60%, p95 down over 90%
Harness is stateless; the log is the stateA crashed harness is replaced with wake(sessionId)none given

Each hand is a toolOne brain drives many sandboxes, and brains can pass hands to each othernone given

The session is not the context window. Compaction, the memory tool and context trimming all make irreversible choices about which tokens survive. Managed Agents keeps the full log durable outside the model and lets the harness pull positional slices with getEvents(), then transform them (for cache hit rate, for summarisation) before they reach Claude. Storage is recoverable; context management stays swappable.

Failure modes that remain

  • Stream deadlock. SSE has no replay. If the client drops while a tool confirmation or custom tool result is pending, the session idles forever unless the client re-lists events on reconnect.

  • Prompt injection still has reach. Tokens are out of the sandbox, but bash, web_fetch and any repo-mounted .claude/skills content still give injected text real capability. Repo skills load with no review step.

  • Many hands is harder thinking. The post says outright that choosing among execution environments is a harder cognitive task than one shell; earlier models could not do it.

  • Cost is now runtime plus tokens. Sessions bill runtime, multiagent threads share one budget, and workflow runs multiply token spend. Set a session budget.

  • Lock-in moves up a layer. You no longer own the loop, the log or the scheduler. Portability lives in what you mount: the agent config, the skills, the files.

Clief's folder workflow (ICM)

Interpretable Context Methodology (paper, March 2026) says the folder is the agent. An agent is "tools in a loop toward a goal" (Simon Willison's line, which the course quotes); a lawyer agent and a marketer agent are the same model reading different files. So instead of a framework, you build a workspace whose structure tells one model what to read for each job.

The parts

PartWhat it isRule of thumb
The map (CLAUDE.md or AGENTS.md)Read every session: what this folder is for, where things go, naming rulesFits on one screen. A giant map "puts the whole drawer back on the desk"
Routing table (inside the map)One row per job: Read / Skip / Use (which skill) / Save toIf a fresh session reads the wrong files, tighten that row
Method / Facts / Work / OutputsFour kinds of file kept apart. Method travels to the next client; facts stay with this oneLabel each file as instructions, state, or both; a file that is neither is the first to question
StagesNumbered folders, each leaving exactly one file you can openNothing moves on until someone has looked at the last file
Stage contract (CONTEXT.md per stage)What the stage reads, what it makes, who checks itPlain English, in the stage's folder
Stop pointsWhere human judgment changes the resultThree strengths: a line in the map, the permission mode, and a hook for anything that must never happen
scripts/Steps done the same way three or four times"Same input, same output" is code; a map line says when to run it
_archive/Retired workThe map says: never read it

Three shapes, one method. Stages (his animation pipeline: voice, timed words, storyboard, scene, render), records (a folder per client), and a wiki the model maintains (Karpathy's raw-sources plus written-pages split). The ICM Architect skill drafts one of six shapes from a messy folder.

The 60/30/10 split. 60 is the data, the questions and the thinking (knowing what the client actually needs). 30 is tools that already exist: a calendar, a spreadsheet, a script. 10 is the AI. "Most people start with the ten." His psychometrics work had models answer the questions and a script score ten thousand responses; that script is the 30.

Keeping it alive. Three checks from lesson 3.3: the fresh-session test (a new session must say what the folder is, what is in progress and what is next), one home for every fact (three prices in three files will drift), and clearing generated clutter into _archive/. The hand-off test is the same: if the AI were switched off tomorrow, could a person still find their way and do the work?

Why folders. Files outlived every platform shift since Unix. "Next week some other company will have the better model"; your files, context and data are what stay yours. That is the thesis the reel applies to Managed Agents.

How the two fit

They solve different halves of the same problem. Managed Agents makes the runtime disposable (harness and sandbox are cattle, the log is durable). ICM makes the context durable and portable (the folder outlives the model and the vendor). Put together: the folder is what you own and version; Managed Agents is one place to run it.

The join is clean because Anthropic made the same bet: the session log is not the context window, and persistence is files mounted into a sandbox. What ICM adds is the curation Managed Agents leaves to you: which files, for which job, checked by whom.

Where the reel is right and where it overreaches

Right

  • Thin wrapper harnesses are exposed. A "lawyer agent" that is a prompt plus a loop plus a container has nothing a hosted meta-harness lacks. Anthropic's own framing (harness assumptions go stale) supports him.

  • The durable asset is process and context. Both designs put persistence in files and logs outside the model, so the investment that survives a model upgrade is the workflow, the files and the checks.

  • The split matches his drawing. Brain separate from hands, tools behind one call, security and scale as infrastructure: that is the post's architecture.

Overreaches

  • "Same methodology" conflates layers. Managed Agents decouples runtime components (log, loop, sandbox). ICM structures context for one model. They are complementary, not the same idea; neither needs the other.

  • Harnesses are not useless; they moved. The post says Managed Agents is a meta-harness that hosts harnesses, Claude Code among them, and that task-specific harnesses excel in narrow domains. What goes stale is a harness that encodes model weaknesses, not one that encodes your domain (tool contracts, approval rules, evals).

  • "Most of us don't need Managed Agents" depends on the job. For one person working in a desktop app on a folder, true. For unattended, scheduled, multi-tenant or VPC-bound work, you need what the post describes: durable sessions, credential isolation, lazy sandboxes, crash recovery. Files do not give you those.

  • No evidence offered. The reel cites no measurements. ICM's own paper rests on practitioner reports from 52 people, with no controlled comparison against a framework or a monolithic prompt.

Net: read it as "own your folder, rent your runtime". That holds up. The stronger claim, that harness engineering is now a waste of time, does not.

Review checklist

For a team proposing an agent built on Managed Agents, an ICM folder, or both:

  • Is the agent config created once and versioned (or kept as files synced with ant apply), with sessions pinned to a version?

  • Does the client re-list events and dedupe by ID on every reconnect, so a pending tool confirmation cannot deadlock the session?

  • Are all credentials in a vault, with nothing secret in the repo, the memory store or the prompt?

  • Is networking limited with an explicit host list, and web tools off unless the job needs them?

  • Who can commit to .claude/skills/ in any repo the session mounts? Is that path reviewed like code?

  • Does the folder have a one-screen map with a routing row per job, and does a fresh session open only the files that row names?

  • Does every stage leave one file with a stated reviewer, and is there a hard stop (permission policy or hook) before anything irreversible?

  • Are the deterministic steps scripts, not prompts?

  • Is there a session budget, especially with multiagent rosters or workflow runs on?

  • If the vendor changed tomorrow, what would you lose: the folder (should be nothing) or the hosted loop (should be replaceable)?
