Learn Quiz: make the agent prove you understood the session

Published 2026-11-22Summarized 2026-11-26

Read the original

comprehension-debthuman-oversighthuman-learningagent-skillspromptingteaching

A short from the Agentic Engineering channel argues that the danger in AI coding is the agent succeeding while you stop understanding the work. It points to a prompt by Suzanne at Anthropic, shared by Thariq Shihipar as a gist called "Learn Quiz". The prompt turns Claude into a teacher that keeps a running checklist of what the human must understand, has the human restate it first, quizzes them, and refuses to end the session until they have shown they understand every item. The useful idea is the direction of the check: it verifies the human, not the code.

The prompt, verbatim

This is the full text of the gist's only file, SKILL.MD (revision a6229891, created 2026-06-01). The video's creator says "the exact wording of their prompt matters here", so it is reproduced as published, lowercase and pronouns included. The file has no YAML frontmatter despite its name.

you are a wise and incredibly effective teacher. your goal is to make sure the human deeply understands the session. 

do this incrementally with each step instead of all at once at the end. before moving on to the next stage, you should confirm that she has mastered everything in the current one. this should be high level (e.g. motivation) and low level (e.g. business logic, edge cases).

keep a running md doc with a checklist of things the human should understand. make sure she understands 1) the problem, why the problem existed, the different branches 
2) the solution, why it was resolved in that way, the design decisions, the edge cases 
3) the broader context of why this matters, what the changes will impact. 
  
make sure she understands why (and drill down into more whys), make sure she understands what and how as well. understanding the problem well is imperative.

to get a sense of where she's at, proactively have her restate her understanding first. then help her fill in the gaps from there—she might ask you questions or ask to eli5, eli14, or elii (explain like she's an intern). 
  
quiz her with open-ended or multiple choice questions with AskUserQuestion (be sure to change up the order of the correct answer, and to not reveal the answer until after the questions are submitted). show her code or have her use the debugger if necessary!

/goal the session should not end until you've verified that the human has demonstrated that she understood everything on your list.

The path to it is one hop longer than the video implies. The channel's pinned YouTube comment links to Thariq's X post (2026-06-01, about 1.4M views), which shows a screenshot of the prompt; his first reply in that thread links the gist. A second reply adds that Suzanne uses it with voice mode "to make it easier to respond and more natural". Among the gist's 11 comments are three gender-neutral rewrites, a version for reviewing one PR's changes to a named file, and a generalised version for papers, strategies and onboarding.

How it works

The prompt is a teaching loop with a ledger and a stop condition. Each part closes a specific gap in the usual "let it work, then read the summary" pattern, where the agent has explored files, rejected approaches and changed assumptions that the human never saw.

  1. Teach as you go, stage by stage. Understanding is checked after each step, not once at the end, so the human never has to rebuild a long chain of decisions at once. A stage is not left until the human has "mastered" it.

  2. A running Markdown checklist is the ledger. The agent writes down what the human should understand. That turns an open-ended "do you get it?" into a finite list that can be ticked off, and it survives context compaction because it lives in a file.

  3. Three layers of content. The problem (why it existed, the branches explored), the solution (why this way, design decisions, edge cases), and the context (why it matters, what it will affect). These are the questions a reviewer or an on-call engineer will ask later.

  4. Diagnose before teaching. The human restates their understanding first, and the agent fills gaps from there. This is the step the video calls "the move": a restatement exposes thin understanding that a skimmed summary hides. Voice mode makes the restatement cheaper and more honest.

  5. Adjustable depth. The human can ask for ELI5, ELI14 or "explain like I'm an intern", so the agent adapts rather than lecturing at one level.

  6. Quiz with structured questions. Open-ended or multiple-choice questions through Claude Code's AskUserQuestion tool, with the correct option's position varied and answers withheld until submission. It can also show code or have the human step through a debugger.

  7. A completion condition. The last line invokes /goal, so the session should not end until the human has demonstrated understanding of every item on the list.

The design choice that matters most is the direction of verification. Most AI code review checks the artifact, and many workflows ask the model to explain itself. This one checks that knowledge reached the person who will own the change. The video's closing test states it well: can you explain what the agent did well enough to own the result?

Tradeoffs and failure modes

The idea is sound, but the prompt as published has two mechanical gaps and several ways to turn into theatre. Checked against the Claude Code docs for /goal, skills and AskUserQuestion on 2026-11-26.

IssueWhat happensMitigation
/goal inside skill text/goal is a command the user types. The docs describe no way for skill content to set a goal, so in a SKILL.md the last line most likely acts as an emphatic instruction, not a registered goal (inference, not tested).Run /goal <condition> yourself after loading the prompt, or give the skill a hooks entry with a prompt-based Stop hook, which is what /goal wraps.
Soft stop conditionThe /goal evaluator is the small fast model. It reads only the transcript and runs no tools, so "understood everything" is judged from what was said.Make the ledger the end state: every checklist item marked demonstrated, with the restatement or quiz answer quoted beside it.
No frontmatterA SKILL.md without name and description gives the model little to decide when to load it.Add frontmatter; set disable-model-invocation: true so it runs only when asked.
Same model teaches and gradesThe agent that did the work also writes the checklist and judges the answers. It tends to be lenient, and if its own rationale for an earlier decision is wrong or reconstructed after the fact, it teaches the wrong "why".Ground the checklist in recorded artifacts (spec, decision log, diff, test output), not in the agent's recollection. Treat a human answer that contradicts the agent as a possible defect, not only a wrong answer.
Multiple choice tests recognitionPicking the right option is easier than producing it.Lead with restatement and open questions; use multiple choice for edge cases and "which input breaks this?" checks.
Quiz auto-continueIf askUserQuestionTimeout is set, an unanswered question closes itself and Claude proceeds on its own judgment.Leave the timeout off for comprehension sessions.
Cost and fatigueEvery stage adds turns, tokens and human minutes. On trivial changes it becomes ritual.Scale by risk: full loop for changes someone must own on call, a three-question check for small ones, skip for mechanical edits.
Gendered pronounsThe text says "she" throughout, because it was written for one person.Use the gender-neutral rewrites in the gist's comments, or "the human".

The evidence that this kind of loop matters is in the index already. R012's randomized trial found that tutor-style AI use left a lasting learning gain while AI-written work left none, and R075 describes the same effect at work: delegating feels like being in the loop when it is not. Learn Quiz is a cheap way to force the tutor-style path on real work.

Review checklist for adopting it

  • Is it installed as a skill with frontmatter, invoked on purpose (disable-model-invocation: true), and worded for any user?

  • Is the stop condition registered for real (/goal typed by the user, or a skill Stop hook), rather than left as a line of text?

  • Is the end state measurable: a checklist file where each item records how it was demonstrated?

  • Is the checklist built from recorded artifacts (spec, decisions, diff, tests) rather than the agent's memory of the session?

  • Does the session start with the human's restatement, before any explanation?

  • Are at least some questions open-ended, and do multiple-choice ones vary the correct position and hide answers until submission?

  • Is a human answer that disagrees with the agent treated as a possible bug in the work?

  • Is the depth scaled to the change's risk, so small edits do not get the full loop?

  • Is askUserQuestionTimeout off for these sessions?

  • Is the checklist kept after the session (in the PR, the feature record or the team's docs) so the next reader inherits it?
