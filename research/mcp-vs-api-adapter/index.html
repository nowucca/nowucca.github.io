MCP vs API: an adapter in front of the same endpoints

Luís Rodrigues's whiteboard post, 2026-11-18Published 2026-11-18Summarized 2026-11-18

Read the original

Authors Luís Rodrigues

mcpagent-protocolsagent-authlearning-resources

The post's main claim holds: an MCP server is an adapter that lets a model call the same APIs your app already calls, not a replacement for them. Its "the agent worked it out" framing oversells discovery, though, and the current MCP spec (2026-07-28) makes MCP look more like an ordinary stateless HTTP API than the post suggests.

What the post says

Luís Rodrigues's post (18 Nov 2026, about 470 reactions; whiteboard credited as inspired by Rahul Agarwal) draws two call paths to the same three back ends: Google Drive, Postgres and GitHub.

  • API path. A web or mobile app sends a REST/JSON request; an API gateway validates the token and routes it; a service queries the data and returns JSON. Every hop is hand-built and someone operates it.

  • MCP path. An agent connects through "the MCP protocol" to MCP servers A, B and C, reads how each describes its capabilities, picks one, and gets results back in the same format.

Its thesis, in its own words: an API "expects the caller to know what to request", while MCP "shows the caller what it's able to request". MCP sits in front of the same endpoints; the API still does the work. Several commenters added the point the post skips: the hard engineering is in permissions, tool validation and reliable execution.

Corrections and missing pieces

The diagram is a fair first picture for a newcomer. Five points need fixing before it is used to teach engineers.

Two omissions are worth one line each. MCP exposes more than tools: resources (readable data) and prompts (templates) too. And discovery costs context: every tool's schema and description sits in the window, which is why large deployments page or filter tool lists (R082, R071).

The 2026-07-28 spec narrows the gap

The latest MCP revision moved MCP toward the shape of an ordinary HTTP API. A staff engineer comparing the two should start from this version, not from the 2025 stateful one.

  • Stateless requests. The initialize handshake and the Mcp-Session-Id header are gone. Each request carries its protocol version and client capabilities in _meta, and tools/list no longer varies per connection.

  • Routable at the HTTP layer. Streamable HTTP POSTs must carry Mcp-Method and Mcp-Name headers (for example tools/call and execute_sql), so load balancers, gateways and observability can route and log by tool without parsing JSON-RPC bodies.

  • Cacheable discovery. List results carry ttlMs and cacheScope, and servers SHOULD return tools in a deterministic order, which also helps the model's prompt cache.

  • server/discover. Servers must advertise versions, capabilities and identity up front.

  • Fewer server-initiated calls. Sampling, elicitation and roots requests now come back as an input_required result the client answers on a retry, rather than as requests from server to client.

  • Long-running work moved to a tasks extension with polling (tasks/get).

The practical result: the post's "two systems that met in advance" versus "enter a room and ask what's on offer" is now mostly a difference in the description layer. Transport, routing, caching and auth look like the API side. What remains distinct is that the caller is a model choosing from natural-language descriptions, which is the real source of both MCP's flexibility and its failure modes.

When to add MCP, and what breaks

Add an MCP server when a model, not code you control, is the caller and needs to choose among operations at run time. Keep calling the API directly when the call sequence is fixed: a workflow step, a batch job or a UI. A CLI is a third option many coding harnesses prefer for local tools, and one engine can serve both surfaces (R082).

Failure modes to plan for:

  1. Wrong tool picks from vague or overlapping descriptions; worse as the tool count grows.

  2. A second path to the data that skips the gateway's auth, quotas and audit.

  3. Over-broad tools (a generic execute_sql or run_command) that turn tool choice into arbitrary code execution; split read and write tools so the read path cannot write (R055).

  4. Context bloat from loading every schema on every turn.

  5. Prompt injection through tool results, which reach the model as text it may act on.

  6. Silent drift when the API underneath changes and the tool description does not.

Review checklist

  • Each tool maps to an existing, owned API operation, under the same authorization policy as its HTTP route.

  • Read and write tools are separate; destructive tools need confirmation.

  • Tool names, schemas and descriptions are versioned and covered by a tool-selection eval.

  • Remote servers follow the spec's OAuth flow; tokens are scoped per server and never passed through.

  • Gateway or proxy logs record Mcp-Method and Mcp-Name for every call.

  • Tool lists are filtered or paged for the task, not loaded whole.

  • Tool output is treated as untrusted input by the host.
