LeanRDF: untrusted search finds, a proven checker certifies knowledge-graph reasoning

What it is

LeanRDF is a set of Lean 4 libraries that writes the W3C semantics of RDF 1.2, RDFS, OWL 2 RL and EL, SPARQL 1.1 and SHACL Core as Lean definitions. The design splits reasoning into two parts:

  • Untrusted engines find answers. Elpi (a λProlog) saturates a graph and emits a proof certificate. A SQLite-based SPARQL store (oxilite) can also answer queries and materialise OWL closures.

  • A verified checker certifies them. The checker is proven sound against the semantics, so an accepted certificate becomes a theorem such as "graph g RDFS-entails query q". A bug in the search can only produce a rejected certificate, never a wrong accepted answer.

  • Where a certificate can't cover it, the engine itself is proven. A certificate shows something follows, not that nothing is missing, so the SPARQL evaluator and SHACL validator are proven to compute their semantics exactly.

What is claimed proven

  • Soundness of 80 RDFS rules, 60 OWL 2 RL rules, 10 EL rules and 12 OWL 2 RL clash rules (a checked clash certificate proves the data has no model).

  • RDF canonicalisation that never merges blank nodes; checked countermodels that prove non-entailment.

  • SPARQL evaluation equal to the SPARQL 1.1 semantics up to order; SHACL "conforms" exactly when the data conforms.

  • No sorry, no new axioms beyond Lean's standard three, no Mathlib dependency; tests pin the axioms of each main theorem.

  • W3C suites: RDF syntax suites pass, RDFC-1.0 86/86, SHACL Core 98/98, SPARQL 97 syntax and 257 evaluation tests; OWL 2 inconsistency tests 27 decided, 91 listed as not decided.

A standalone leanrdf-check tool verifies a certificate someone else produced, with the certificate bound to digests of its data, query and rules.

Why it matters for engineers

This is the same pattern as proof assistants checking AI-written proofs, applied to knowledge-graph reasoning: let a fast, fallible component (a solver, a database, or a model) propose, and accept only what a small verified kernel checks. For agents that answer from ontologies or policy graphs, it gives a way to say "this conclusion is proven from this data under these rules" rather than "the reasoner said so". Exit codes separate "proven", "not derived" (never a claim of falsehood, because the rules are sound but not complete), "certificate rejected" (a bug upstream) and input errors.

Tradeoffs and limits

  • Scale. Aimed at thousands of triples, not millions; certificate checking and proof terms are not built for warehouse-scale graphs.

  • Soundness, not completeness. "Not derived" means not found, not false. Many OWL tests are undecided.

  • Profile coverage. OWL 2 RL and EL fragments only; datatypes outside the supported set are not handled.

  • Toolchain cost. Lean 4 (pinned version), Elpi and a build step; a heavy dependency for teams without Lean experience.

  • Early project. Single-maintainer repo; README claims, not independent review.

Failure modes to watch

  • Trusting the RDF/OWL encoding: the theorems are only as good as the Lean definitions matching the W3C specs.

  • Treating "not derived" as "false" in downstream logic.

  • Certificates checked against the wrong data or rules if digests aren't verified.

  • Performance cliffs when graphs grow past the intended size.

Review checklist

  • Is the fast reasoner's output accepted only after an independent check?

  • Does the system distinguish "proven", "not found" and "checker rejected"?

  • Are certificates bound to the exact data, query and rule set they were made for?

  • Is the graph size within what the checker handles?

  • Who reviewed the formal definitions against the specs?
