Zed Delta: review the agent thread, not the pull request

Source: Zed Industries, Replace PRs with Delta – Now in Public Beta (zed.dev blog, 16 Sep 2026), and Introducing Delta (12 Aug 2026). Surfaced in a practitioner's LinkedIn post about using DeltaDB as a daily agent harness. Product claims are the vendor's own.

The claim

Agents produce diffs that are too large for pull-request review, and the diff alone loses the reasoning that produced it. A reviewer who pastes the diff into their own agent forces that agent to reconstruct decisions the author already made. Zed's answer is to make the agent conversation thread the unit of collaboration and review, and to version the work between commits so that history is kept.

The team says it turned off pull requests on its own Delta repository and landed 570 changes to main that way, with 33 people working in it daily, by the time of the public beta.

How it works

  • Shared threads. You invite teammates into your conversation with the agent. They see the same worktrees and can work with them on their own machine. They can ask the same agent why a choice was made, and can carry on with it if you log off.

  • Review subthreads. A review walks the reviewer through the branch's changes with access to the original agent's context. Each review gets an isolated copy of the parent thread's worktrees, so reviewers can explore and try fixes without disturbing the original work. Fixes made in review can be folded back into the parent thread before the agent lands the change.

  • DeltaDB. Extends Git's content-addressed versioning with incremental, delta-based versions. It records the edits between commits alongside the human and agent messages that caused them, so the thread's evolution is preserved. A commit is still the checkpoint you push, pull and build from; DeltaDB keeps what happened in between.

  • Git-compatible. Teammates who never open Delta still see a normal Git repository. Zed's own editor repo stays on GitHub; contributors are encouraged to attach Delta threads to their PRs.

  • CI. Not yet native. An agent can trigger an existing CI provider and check results before landing. Longer term they want content-based builds verified inside the thread.

  • Clients. macOS, Linux, Windows, web, and a mobile browser for following threads. Free during the beta.

Why this matters

The framing is that integration and delivery became continuous while design, implementation and review stayed batched around the PR. A thread that holds idea, implementation, review and landing in one place is the vendor's "continuous engineering". Whether or not that label sticks, the underlying move is real: the rationale becomes a reviewable, versioned artifact next to the code, instead of being lost in a local session.

Tradeoffs

  • Context vs signal. A full agent narrative is far longer than a PR description. Reviewers now have more to read, unless the tooling guides them to the decisions that matter.

  • Asking the author's agent. Convenient, but the agent's explanation of a choice is a reconstruction too, and may be confidently wrong. The recorded messages are evidence; the agent's later answer is not.

  • Lock-in. DeltaDB's between-commit history and thread structure live in a new system. Git compatibility covers the code, not the narrative. Exporting threads matters if you might leave.

  • Review gates. Without PRs, branch protection, required reviewers and audit rules have to be re-expressed in the new tool. Check what is enforced versus conventional.

  • Hybrid teams. Running Delta threads alongside GitHub PRs means two places where review discussion can happen.

Failure modes

  • Secrets or sensitive data pasted into a thread become part of persistent, shared history.

  • Reviews that skim the narrative and skip the diff, trusting the agent's account.

  • Fixes made in a review subthread that are not folded back, leaving forks of intent.

  • CI checked by an agent before landing, rather than enforced by a gate the agent cannot bypass.

Review checklist

  • What is the enforced landing rule (reviews, CI) and can an agent land without it?

  • Can threads and between-commit history be exported in an open format?

  • Who can see a thread, and how are secrets kept out of persistent history?

  • Does a review show the reviewer the key decisions, not only the full transcript?

  • When the team also uses GitHub, which system is the record of review?

  • Are review-subthread changes tracked until merged back or discarded?
