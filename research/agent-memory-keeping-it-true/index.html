Agent memory: capturing is easy, keeping it true is the hard part

Conor Bronsdon's survey (Chain of Thought, 22 Nov 2026) argues that agent memory products now retain and recall well, but rarely refine. Stale facts keep loading after the world changes. The fix he proposes is memory as maintenance: store each claim with its source and invalidation conditions, and let a background curator propose evidence-backed changes. The issue is sponsored by Walrus Memory. The numbers below are as the article cites them.

The model

  • Loop. Write, manage, read. Richmond Alake's four steps are Retain, Recall, Reuse and Refine, and most products skip Refine.

  • Types (from CoALA). Working, episodic, semantic and procedural memory. Procedural memory includes files like CLAUDE.md and AGENTS.md.

  • Arc. RAG in 2020 (memory as search), then MemGPT in 2023 (memory as an OS), then saved facts in products in 2024, sleep-time compute in 2025, and memory as maintenance in 2026.

Evidence cited

  • A survey of 435 papers on always-on agents found the field focuses on accumulating and retrieving state, not on governing or relinquishing it (arXiv 2606.30306).

  • In a full-reversal test (arXiv 2608.07429), append-only and last-write-win memory both score 0.210 and no memory scores 0.309. Retiring stale memories scores 0.950.

  • On STALE (arXiv 2605.06527, 400 scenarios), the best model reached 55.2%. A prototype, CUPMem, reached 68%.

  • Across 16 models (arXiv 2608.25553), agents re-checked a memory's source about one episode in five, and acted on the stale memory about three-quarters of the time.

  • On Anthropic's CL-Bench chart, a memory folder lifts Opus 5 from 0.564 to 0.828. Recording only failures reduces the gain.

  • Poisoning: GhostWriter reports injection rates around 98% (arXiv 2607.06595). A MINJA follow-up found that existing legitimate memories blunt such attacks.

Failure modes

  • Staleness. A trip that ended keeps loading as current. Deliberation about trips gets recorded as trips taken.

  • Newest-wins correction. A newer chat may be a proposal, not a decision, so "trust the latest record" is wrong.

  • Forgetting conflated. "Less relevant" (a retrieval score), "no longer current" (superseded, with a validity window) and "gone" (true deletion, including copies) are different operations. A retired record can resurface if default reads return history.

  • Integrity vs. truth. A hash shows a record is unchanged, not that it is still true. Provenance links the two.

  • Over-active curators that make many unwarranted edits.

Design recommendations

  • Store the claim, its source and the conditions that would invalidate it. For fast-changing facts, store a pointer, not a cached value.

  • The curator proposes changes with cited evidence and never edits what it reviews directly. Reject proposals without evidence. Keep history in version control and archive superseded facts with what replaced them.

  • Test by quietly changing a fact, then asking about the current state, asking a question that assumes the old state, and requesting an action that depends on it. Keep unchanged controls, and compare against memory off and fresh retrieval.

  • One person: a markdown folder with a small startup index. Teams: a database or managed layer. Neither settles which source wins on conflict.

  • Security: cite each source with its authority boundary, and keep permissions through summarization.

Review checklist

  • Does every stored fact carry a source and a validity window?

  • Are superseded facts excluded from default reads?

  • Are curator edits proposals, reviewed and reversible?

  • Is there a stale-fact regression test?

  • Is memory write access treated as an injection surface?
