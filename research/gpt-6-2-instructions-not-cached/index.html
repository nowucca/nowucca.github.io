GPT-6.2 stops caching the Responses instructions field: where harnesses put the system prompt

OpenCode v2.3.2 changelog, opencode issue #64550 and openai/codex issue #62312; surfaced by André LindenbergPublished 2026-11-18Summarized 2026-11-19

Sources: OpenCode v2.3.2 changelog (2026-11-18); anomalyco/opencode issue #64550 and the fixes in #64542 and #64544; openai/codex issue #62312, which has an independent reproduction. Surfaced by André Lindenberg on LinkedIn, 2026-11-19. Behaviour as reported by these sources.

What changed

On the Responses API, a request can carry a system prompt in two ways: in the top-level instructions field, or as a leading developer message at the start of input. With GPT-6.1 both are cached once the prefix repeats. With the GPT-6.2 family (Sol and Astra), the reports say the API now places top-level instructions at the end of the model's input and never caches it. OpenAI reportedly confirmed to OpenCode maintainers that this is deliberate. Its recommendation is to put static, reusable text in the first developer message of input, ahead of the user turn.

Any harness that sends its system prompt as instructions therefore pays the full input rate for it on every agent step.

The measurements

From the OpenCode issue, with each request sent twice, a 10.1k-token text and a unique prefix per pair:

model         text sent as        1st request       2nd request
gpt-6.2-sol   instructions        written 0         cached 0
gpt-6.2-sol   developer message   written 10,113    cached 10,113
gpt-6.1-sol   instructions        written 10,114    cached 10,114
gpt-6.1-sol   developer message   written 10,113    cached 10,113

In the reporter's code-review sessions, the uncached system prompt was about 12.9k tokens per request. That made GPT-6.2 Sol reviews 2.85 times the cost of identical GPT-6.1 Sol reviews. The LinkedIn post cites about 14k uncached tokens per step in a Copilot-routed session, falling to 3 after the fix.

The Codex issue reproduces the same pattern with streaming requests, a ~9.2k-token system prompt and five tools:

  • It holds for both API-key and ChatGPT sign-in auth, and for both 6.2 Sol and 6.2 Astra.

  • Cached tokens stay at 0 every step with instructions.

  • With a leading developer message, nearly the whole prefix is cached from step 2.

That issue also reports a diagnostics mismatch. OpenAI's cache-comparison diagnostics said cache_hit for the 6.2 instructions runs, while the usage fields showed zero cached and zero cache-write tokens.

The fix in OpenCode

Version 2.3.2 sends the system prompt as a leading developer message on every Responses route: OpenAI (API key and ChatGPT sign-in), GitHub Copilot, Zen, Azure and OpenRouter. The system prompt is then cached from the second step on. On the dev branch the change applies to all models, not only 6.2 and later, so there is one request shape rather than a per-model branch.

Why it matters beyond one harness

  • The request shape is now a cost control. Two semantically identical requests can differ by close to 3x in billed input, depending only on which field holds the static text.

  • Model upgrades can silently change cache economics. Nothing errored. The only signal was the cached-token count in usage data, and one diagnostics endpoint said the opposite.

  • Routers and gateways inherit the problem. Copilot, Azure and OpenRouter routes were all affected through the same harness code. A gateway that rewrites requests could reintroduce it.

Tradeoffs of the fix

  • Developer message vs instructions semantics. Moving text from instructions into input can change instruction priority or how the model treats it across turns. OpenCode applied it uniformly, and it is worth an eval pass on your own prompts.

  • Uniform shape vs per-model branches. One shape for all models is simpler and avoids the next model-specific surprise. It does assume older models cache developer messages equally well, which the measurements support for 6.1.

  • Stateless requests. The tests used store: false. Harnesses that use server-side conversation state should verify separately.

Failure modes to watch

  • A model upgrade raises cost per task with no change in output, and nobody notices until the monthly bill.

  • Cache dashboards built on diagnostics rather than usage fields show hits that are not billed as hits.

  • A gateway or SDK upgrade moves the system prompt back into instructions.

  • Per-session dynamic content (dates, IDs) placed before the static prompt breaks the prefix even after the move.

Review checklist for any harness on the Responses API

  • Log cached_tokens and input_tokens per step, and alert when the cached share drops after a model or SDK change.

  • Check where your system prompt is sent. For GPT-6.2 and later, it should be a leading developer message, not instructions.

  • Keep static text first and byte-identical across steps, with dynamic content after it.

  • Re-run a two-request cache probe whenever you change model, route or gateway.

  • Trust billed usage over diagnostics when they disagree.
