Mellum2.1 Instruct, and designing for the fast worker rather than the best score

A 12B mixture-of-experts coding model with 2.5B active parameters per token has shipped under Apache 2.0, in two variants — one that emits its chain of thought and one that does not — built on the same architecture and the same training run, differing only in whether the reasoning is produced.

The release is worth reading less for the model than for the argument around it, which is unusually honest about where it stands: a comparable open model scores higher on the benchmark everyone cites, and the vendor says so in the announcement. What it offers instead is a different operating point. That is the interesting engineering claim, and it is the one worth examining.

The two-model split, and what it is actually for

The pitch is that much of a coding agent's work does not reward reasoning. "A small fix, a command to run, or a question about the code" does not get better when the model deliberates first; it gets slower. The reasoning variant stays the right choice for hard algorithmic and mathematical problems, where the chain of thought is load-bearing, and the instruct variant takes everything else.

Two details make this more than a marketing segmentation:

  • It is the same model, trained identically. The instruct variant is not a smaller or cheaper architecture. It is the same weights' worth of capacity with the thinking suppressed and a tuned length penalty, which means the comparison between them isolates the cost of reasoning rather than confounding it with model size.

  • The motivating constraint is local inference. The release says it came from requests by people running models on their own hardware, where "every extra thinking token adds to the time you're waiting." That is a latency argument, not a quality argument, and it only bites when you own the GPU.

The reported effect is that the instruct variant emits roughly half the tokens of its reasoning sibling on agentic coding tasks while performing nearly as well on SWE-bench Verified. For a sub-agent invoked dozens of times inside a loop, halving output tokens is the whole economics of the loop.

Sparsity as the actual product

The comparison the vendor draws is the useful part. Against a similarly sized dense open model, it concedes the benchmark and claims the throughput: roughly 1.4x faster token generation for a single request, and roughly 1.8x faster under load, on the grounds that only 2.5B parameters activate per token.

That gap between the single-request and under-load figures is the detail to take away. Sparsity's benefit is not primarily per-request latency; it is how many concurrent requests the same hardware absorbs before queueing. A model that is 1.4x faster alone and 1.8x faster under load is telling you that its advantage grows with utilisation — which is exactly the regime a fleet of sub-agents creates, and exactly the regime a single-stream benchmark hides.

Separately, a multi-token prediction head ships alongside each variant, claimed at up to 1.8x faster generation. Note that this is a different 1.8x from the under-load figure above; they describe different mechanisms and should not be multiplied together or conflated, which is easy to do when reading the announcement and its predecessor side by side.

How it was trained, and why that is the credible part

The post-training recipe is described in enough detail to be assessed, which is rarer than it should be.

Two reinforcement-learning stages: first standalone tasks across code, mathematics, tool use and instruction following; then agent work in real repositories, using shell and file tools inside a sandbox, with reward given only when hidden tests pass. Hidden tests as the sole reward signal is the right choice and the expensive one — it resists the reward hacking that any proxy signal invites, at the cost of a sparse, delayed signal.

The scale figure is the one to remember: a single run collecting about half a million agent trajectories from ten thousand concurrent sandboxes, with generation and training running asynchronously and weight updates distributed across a large GPU cluster. That is a statement about infrastructure as much as method. The bottleneck in repository-level RL is not gradient computation, it is environment throughput — ten thousand sandboxes is the hard part, and the asynchronous split between generation and training is what keeps the trainers fed while those environments run.

Two adjustments were made for the non-reasoning variant: the length penalty was tuned for a model that answers directly, and generation and training were brought into closer agreement for stability. The second is quietly the more interesting: divergence between the sampling path used to generate trajectories and the path used to compute updates is a standard source of instability in asynchronous RL, and naming it as a fix suggests they hit it.

Where the release falls short

The benchmark numbers are in a picture. The announcement's prose gives only directional claims — the agentic score "doubled" against the previous instruct release, it "leads the group" on code generation, it is "level" with the dense competitor on multi-step tool use — and the actual figures live in a slide carousel. For an Apache-2.0 release aimed squarely at people who will self-host it and need to decide whether it fits their latency budget, numbers in text would cost nothing and would make every claim above checkable. As published, the three most quotable claims (half the tokens, almost as well, doubled) cannot be verified from the announcement at all.

"Doubled" is a statement about the baseline, not the model. A doubled score on an agentic benchmark usually means the previous release was poor at agentic work, which the framing confirms — the previous generation was positioned for routing, Q&A and sub-agent duty rather than for driving a repository. Doubling from a low base is a real improvement and a weak ranking signal.

Thinking suppressed is not thinking absent. A model trained with reasoning and then asked to answer directly is not the same thing as a model that never needed the reasoning. The honest reading of "almost as well" is that some of the reasoning benefit survives in the weights, which is a point in the approach's favour, but it also means the quality gap is likely to be task-dependent in ways a single aggregate score will not show.

Design consequences

Route by task shape, not by model preference. If a reasoning and a non-reasoning variant share an architecture, the routing decision is cheap to implement and cheap to reverse: same serving stack, same prompts, different endpoint. The split this release proposes — deliberation for diagnosis, direct answers for mechanical work — is a reasonable first cut, and worth measuring per task class rather than adopting wholesale.

Benchmark the operating point you will run at. A model whose advantage appears under load must be evaluated under load. Measuring a sparse model with one request at a time understates it by roughly the gap between the two speed figures above, and that is the easiest mistake to make when a local test precedes a fleet deployment.

Count tokens as a first-class metric alongside quality. The claim here is explicitly a token-count claim, and token count is what a tool loop multiplies. A sub-agent that is marginally worse per call but emits half the tokens can be better for the loop and worse on the leaderboard simultaneously.

Treat a permissive licence as part of the latency story. The reason the local-inference constraint is coherent at all is that the weights, the quantised builds and the prediction head are all obtainable. A model you cannot host has no local latency profile to optimise.

Review checklist

  1. For your own workload, what fraction of agent calls genuinely need a chain of thought? Measure it before buying a routing layer.

  2. Benchmark both variants at your real concurrency, not single-stream, and record tokens emitted as well as pass rate.

  3. Separate the two speedup mechanisms — architectural sparsity and multi-token prediction — and confirm each independently on your serving stack rather than assuming they compose.

  4. Before accepting a "doubled" improvement, find the baseline's absolute score. The multiple is uninformative without it.

  5. If benchmark numbers are published only as images, treat every derived claim as unverified until you reproduce it or find the figures in a model card or technical report.

  6. Check what the reward signal was during training. Hidden-test-only reward is a meaningful quality signal about the training process; a proxy reward invites the behaviour it measures.

  7. For a self-hosted sub-agent fleet, confirm the quantised build and any auxiliary head are available under the same licence as the base weights.

Related reading

The active-parameter question recurs: another recent small open release was described in circulation as having a higher active count than its own model page claims, and the discrepancy mattered for exactly the reason it matters here — active parameters, not total, set the throughput. Read any MoE release with that number in hand.

On the training side, work on RL for coding agents in real environments is the directly comparable literature, and the environment-throughput figure above is the number to compare against: methods are easy to publish, ten thousand concurrent sandboxes are not.

The serving-side counterpart to the under-load claim is the arithmetic of what a concurrent request actually costs in memory, since a sparse model's throughput advantage is only realisable while its cache still fits.
