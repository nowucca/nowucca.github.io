The error message is the next command: designing a CLI for agents that get it wrong

Sources: the Forge changelog (page 1, covering 13–25 Nov 2026), the Forge CLI reference and the @forge/cli npm page; surfaced by a post from someone on the product team. Version numbers could not be pinned down — see "What could not be established".

Most tooling work aimed at agents goes into giving them more to call: more commands, more MCP servers, richer schemas. This change goes the other way and is more interesting for it. It takes an existing CLI and alters two things about how it behaves when an agent is on the other end — what it does by default, and what it says when the agent gets a call wrong. Neither adds a capability. Both remove a failure.

Default by caller, not by flag

The CLI gains a non-interactive setting whose default value is auto. Under auto the mode turns on "when an AI coding agent that identifies itself runs the CLI" and stays off otherwise. The reference is explicit that in a terminal, in CI/CD or in scripts it "stays off unless you turn it on". The other values are on, off, and a per-command --non-interactive.

That tri-state is the design worth copying, and it is worth being precise about what it is not. It is not "non-interactive is now the default" — a blanket default would break every human at a terminal who relies on being prompted. It is a default that varies by who is calling, which is a different and better idea: the tool decides its own interaction model from the caller's identity rather than making every caller remember a flag.

The reason this matters is that a prompt is not a minor inconvenience to an agent. An interactive prompt on a non-TTY stdin is one of the classic ways an agent-driven command hangs forever or dies with an unhelpful EOF, and the agent has no way to distinguish that from the command being wrong. Removing the prompt removes a whole class of unexplainable failure.

The dependency to notice: detection is delegated to a library, @vercel/detect-agent, plus named handling for two agents the library does not cover. The documentation names Claude Code, Rovo Dev and Windsurf. It does not describe the mechanism beyond that — no environment variable, no TTY heuristic, nothing a reader can reason about.

This is the soft spot in the design. A detection list silently fails for every caller not on it, and the failure is invisible: an undetected agent gets the interactive behaviour, hangs, and nothing in the output says why. Any team adopting this pattern should ensure the tool can state which mode it chose and why — one line on stderr naming the detected caller, or a --print-mode — so an undetected agent produces a diagnosable symptom instead of a hang. And auto should be overridable by an environment variable, so a wrapper can assert the mode rather than hope detection works.

Worth noting also that the post which surfaced this named OpenAI's Codex as a detected agent. The documentation does not name Codex anywhere. Whether the underlying library covers it is not stated.

Errors that carry their own retry

The second change is the one to steal outright. On a call with missing arguments the CLI emits a MISSING_INPUT error that, per the reference, "lists all of them at once and ends with a Next: command that includes the options you already passed". The changelog adds that the error "starts with [MISSING_INPUT] and exits with code 1". The documented example:

Next: forge feedback --message <message> --non-interactive

Two separate properties there, and both are doing work.

All the missing inputs at once. The usual CLI behaviour is to fail on the first missing argument. An agent then supplies it and fails on the second, which turns a three-argument mistake into three round trips, each one burning a tool call and a slice of context. Reporting the full set collapses that to one.

The error is the next command. This is the real idea. Normally an agent recovering from a CLI error has to parse prose, work out what the tool wanted, and rebuild the whole invocation from scratch — and rebuilding is exactly where it drops an argument it had already got right, or re-invents one with a plausible wrong value. Emitting a runnable command line that preserves what was already supplied means the recovery path requires no reconstruction at all. The agent fills the placeholders and runs it.

Generalised: when your tool rejects a call, return the corrected call, not a description of what was wrong with it. That holds for CLIs, for API error bodies, and for MCP tool results. It is a small amount of work in the tool and it deletes the least reliable step in the agent's loop.

The honest caveat is in the docs' own hedge: "In most cases, the error lists every missing option." Not always, then. And the single documented example appends only the missing option, so the preservation of already-supplied arguments rests on the prose rather than on a demonstrated case.

What could not be established

  • Version numbers do not line up. The changelog says non-interactive mode requires "Forge CLI 16.0.0 or later" and that the feature arrived with 16.0.0 (entry dated 23 Nov 2026). The npm page showed 11.6.0 and no publish date. A separate changelog entry says CLI 13.2.0 and earlier stop working on 3 Feb 2027. These cannot all describe the same current state, so treat the npm reading as stale rather than concluding anything about which version a reader would install today.

  • Whether a --non-interactive flag already existed. The changelog presents the feature as new ("Introducing Forge CLI non-interactive mode"), and neither page says whether an earlier flag was replaced. So this may be a new capability or a repackaged one with a smarter default; the documentation does not settle it.

  • The detection mechanism, beyond the library name.

  • Whether the Next: line always preserves prior arguments.

  • MCP. Not mentioned on any of these pages. The reference's sidebar lists assistant and skills commands, and nothing describes them as agent integrations.

The upgrade instructions also disagree between pages: the changelog says npm install -g @forge/cli@latest, while the reference's upgrading section says to uninstall globally first and then install. Minor, but it is the kind of inconsistency an agent asked to "upgrade the CLI" will resolve by guessing.

A review checklist for any CLI agents will drive

  1. Can the tool hang waiting for input when stdin is not a terminal? That is the first bug to close, and it is usually present.

  2. Does the interaction model follow from the caller, or from a flag every caller must remember?

  3. If the tool detects its caller, can it say which mode it chose? An undetected caller should produce a diagnosable line, not a hang.

  4. Is the mode overridable by an environment variable, so a wrapper can assert rather than rely on detection?

  5. On a bad call, does the tool report every problem, or fail on the first?

  6. Does the error output contain a runnable corrected command that preserves the arguments that were already right?

  7. Is the failure machine-recognisable — a stable prefix or code, and a non-zero exit status — so the caller need not pattern-match prose?

  8. Do your upgrade instructions appear in more than one place, and do they agree?
