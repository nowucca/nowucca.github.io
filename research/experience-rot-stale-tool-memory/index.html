Experience Rot: agents with memory stop checking changed tools

Xu, Yin, Zhang, Zhao and Liu (eBay, University of Chicago), arXiv 2611.20922, 2026-11-16; shared by Pascal BiesePublished 2026-11-16 (paper); 2026-11-20 (post)Summarized 2026-11-20

Source: Zhen Xu, Hang Yin, Zitao Zhang, Kevin Zhao, Xuefeng Liu, "Experience Rot: Experienced Agents Fail Where Novices Succeed", arXiv 2611.20922, 2026-11-16 (eBay and University of Chicago). Shared by Pascal Biese on LinkedIn, 2026-11-20 (post).

TL;DR

Agents that reuse what worked before (conversation history, memory files, retrieved notes, skills) stop checking the tool when it changes silently. In a controlled study of six models on MCP-style tools, an agent that had done the task once before copied its earlier call after the interface changed, even when the tool definition in front of it showed the new field, and then told the user the task was done. With complete documentation, agents with no experience succeeded on 88 to 100% of tasks while agents with out-of-date experience succeeded on 26 to 49%. With incomplete documentation, out-of-date experience left agents at about 23%, below the 42% of agents with none. More experience made it worse. The one remedy that worked reliably was reading back the stored result before reporting completion.

Setup

  • Services. Three small synthetic services (calendar, task list, mail), each in two versions that differ in one interface detail. Changes include a renamed field (attendees to guests), a changed structure (end time to duration), a changed value set (urgent/low to p0 to p3), and changes in the meaning of a number that the schema can't show (which end of the priority scale is highest, whether weekday 0 is Monday or Sunday, whether months start at 0 or 1, minutes vs. seconds). Each service has read tools for stored state and a documentation search tool.

  • Episodes. An earlier task and a final task of the same kind in one conversation. Three arms: valid experience (earlier task on the same version), out-of-date experience (earlier task on the other version), no experience. The earlier task is done live by the agent and retried until its stored state is correct, so the experience is the agent's own.

  • Scale. Six models (open and hosted, including GLM, DeepSeek, MiniMax and Qwen variants) in the same simple loop, temperature 0.7, at most 16 model calls per task; 12,624 episodes; cluster-bootstrap standard errors over task instances; predictions preregistered.

Findings

  • Silent acceptance plus false success. Services accept the outdated call. In 347 of 348 failed runs with complete documentation, the agent's final reply said the task was done.

  • Experienced agents stop looking. Agents without experience searched the documentation when they needed it (every run when only the docs had the fields; 70% when a number's meaning changed). Agents with experience, valid or stale, searched in at most 6% of runs. Before writing, novices said they would check the docs; experienced agents cited the earlier task, equally often whether it was still valid or not.

  • The failure path is one sequence: no lookup, old usage, no read-back. Runs that wrote the old usage and then read back stored state almost always caught and fixed the error (94 of 97). Across models, success with stale experience tracked each model's read-back rate.

  • Every memory form is affected. When the earlier task carried information the final task needed, the experience gain held in conversation history, memory files and the other designs, and stale experience gave back much of it. Content carried over correctly; only the interface usage was stale.

  • More experience, more rot. With one, three or ten earlier tasks, success with stale experience fell from 46% to 33% to 26%, while valid experience stayed at 97 to 100%. Documentation lookups fell from 4% to 0%.

  • Hand-written histories hide the problem. Giving agents author-written histories that included a read-back step produced 88% success with stale experience, against 46% after the agent's own earlier task, because agents copy the procedure in the history. Memory evaluations built on curated histories overstate robustness.

What helped and what didn't

  • Version numbers and update notices: a version in every tool description plus an "the service was updated" notice raised success only to about 50%. Recording the version in a memory file barely moved it.

  • "Check the docs" in the system prompt: made things worse (29%). Agents followed it on the earlier task (98%) but not the final one (4%).

  • "Check the docs" in the task message: almost every agent searched, and success reached 99% with complete documentation, but this fails whenever the docs don't spell out the answer. Docs placed in the system prompt or tool description gave only 54 to 55%.

  • Read back before reporting: an instruction to read back the stored state and correct mismatches raised success to 91% with complete documentation and 69% with incomplete. Agents still wrote the old usage first; the check caught it, at the cost of extra model calls.

Tradeoffs

  • Memory gain vs. change risk. Experience is what makes agents succeed when documentation is incomplete, and the same experience is what makes them fail after a change. Turning memory off is not the answer.

  • Read-back cost. Verifying every write costs model calls and needs a read path for every write path; it is the only remedy here that worked without perfect docs.

  • Prompt placement. Instructions in the system prompt decay across turns; the same words in the current task message work. That pushes guidance toward per-task injection, which costs context.

Limitations

Synthetic, small services; one silent change per version pair, while real changes come in groups and sometimes produce partial errors; short tasks and one to ten earlier tasks; the documentation in the complete condition is always correct and one call away; experience was given as explicit rules rather than discovered by trial; mid-size models in one simple loop. Frontier models and production harnesses were not tested.

Failure modes to watch

  • Permissive tool servers. A server that accepts unknown fields or ignores them turns a schema change into silent data loss. Strict validation would have turned most of these failures into visible errors.

  • Success reported without evidence. Completion messages based on the call being accepted, not on the stored state.

  • Skills and memory files encoding interface details. A saved procedure that names field names or value encodings rots the moment the tool changes.

  • Changes the schema can't show. Meaning changes (0-based vs. 1-based, units, scale direction) pass even strict validation.

  • Evaluations with curated histories. They show the agent the right procedure and hide the problem.

Review checklist

  • Do tool servers reject unknown or deprecated fields instead of silently accepting them?

  • Does the agent read back stored state before telling the user a write succeeded?

  • Do memories and skills record intent and invariants rather than exact interface details, or carry the tool version they were learned on?

  • Is a tool's version or schema hash compared with the one a memory was recorded against, with stale memories flagged?

  • Is critical guidance placed in the current task message, not only in the system prompt?

  • Are meaning changes (units, numbering, scale direction) versioned explicitly, since a schema can't show them?

  • Do memory evaluations use the agent's own experience and incomplete documentation?
