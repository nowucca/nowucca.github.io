The claim

A Mixture-of-Experts model routes each token through only k of E experts per layer, so one decode step touches a small fraction of the weights. FreeToken treats a personal machine (GPU, CPU, host RAM, PCIe) as one elastic inference platform and schedules expert weights and agent state across it at runtime, instead of committing to a fixed offloading split. The result is that serving a large open-weight model locally becomes a memory-management and scheduling problem rather than a question of whether every weight fits in VRAM.

Reported results, against llama.cpp, Ollama, KTransformers and MoE-Infinity on six machines (8 GB RTX 4060 laptop to a single RTX PRO 6000) with four real agentic workloads:

  • RTX 5090: 77 to 83 tok/s on Qwen3.6-35B-A3B and 22 to 25 tok/s on DeepSeek-V4-Flash, 1.5 to 2.3x the decode throughput of the best edge baseline.

  • Decode rate stays within 12% of single-turn as workloads become more agentic; baselines degrade substantially.

  • Worst-case time to first token under 44 s on every workload; each baseline exceeds 150 s somewhere, long enough to time out real agent clients.

  • 8 GB laptop GPU: a 35B model at 39.3 tok/s, above the 33 tok/s median decode speed the authors cite for a production coding agent.

  • 32 GB gaming desktop: a 284B model interactively. Single workstation GPU: the 753B GLM-5.2 at twice llama.cpp's throughput.

  PREFILL: double-buffered          |        DECODE: per-step cache misses
  layer streaming (next layer's     |        split by q* policy between
  experts cross PCIe while the GPU  |        (a) fill GPU expert cache over PCIe
  computes the current layer)       |        (b) run expert directly on CPU
                                  |
        shared LRU expert cache in VRAM (inter-token routing locality)
                                  |

The key observation in decode is that PCIe transfer and direct CPU expert execution both draw on the same host-memory bandwidth, so the policy that splits misses between them has to be tuned to the bandwidth the specific machine sustains. The custom FTW weight format and graph-compatible execution keep the fast path compilable.

The semantic-anchor idea is the most agent-specific part. Harnesses routinely rewrite context at predictable boundaries: stripping old thinking blocks, replacing tool outputs, truncating turns. Checkpointing state at exactly those token boundaries means an edited context resumes from the nearest anchor instead of recomputing from the start, which matters most for hybrid models with recurrent state where prefix caching alone does not help.

Tradeoffs

  • Adaptivity vs predictability. A runtime that remaps work as conditions change gives better averages but makes per-request latency harder to reason about than a static split; the paper's tail-latency numbers are the reassurance, and they should be re-measured on your hardware.

  • Host bandwidth is the real budget. Gains depend on PCIe generation and RAM bandwidth as much as on the GPU. A fast GPU in a bandwidth-starved desktop will not reproduce the headline figures.

  • Custom weight format. FTW speeds loading but adds a conversion step and a format-specific failure surface (the repo already carries checkpoint repair and diagnosis docs).

  • Breadth vs depth. More than 20 MoE models and several quantization formats (MXFP4, NVFP4, FP8, BF16, GGUF) is wide coverage for a young engine; expect per-model rough edges compared with llama.cpp's maturity.

  • NVIDIA-first. Native support is RTX 30/40/50; Apple silicon and AMD are not in scope today.

Failure modes to watch

  • Routing locality collapses on workloads that hop topics or languages, raising LRU miss rates and pushing decode onto the CPU path.

  • Memory contention with the rest of the desktop (browser, IDE, games) shifts the bandwidth the policy was tuned for.

  • Anchor reuse that is wrong: if a harness edits context somewhere other than the boundaries the engine expects, the cache must detect it and fall back, or outputs drift.

  • Timeouts in agent clients during long cold prefills on very large models, even when steady-state decode is fine.

  • Quantization-format mismatches between the model card and what the engine actually loads.

Review checklist before adopting for local agents

  • Benchmark on your exact machine with your harness's real traces, including multi-turn tool use, not single prompts.

  • Record decode tok/s, worst-case TTFT and LRU hit rate together; any one alone misleads.

  • Check the harness's context-editing behaviour against the engine's anchor boundaries.

  • Keep llama.cpp or Ollama as a fallback path and compare output quality at the same quantization.

  • Pin engine and FTW checkpoint versions together.

  • Confirm the API compatibility layer covers the tool-calling features your client uses.
