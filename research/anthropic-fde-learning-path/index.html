Anthropic's Forward Deployed Engineer path: 9.5 hours, and the 100 minutes that make it FDE

TL;DR

Anthropic has published a Forward Deployed Engineer (FDE) learning path on its partner academy: 11 self-paced courses, about 9.5 hours, open to Claude Partner Network members (membership is free for organizations bringing Claude to market). Nine of the 11 courses are the same ones in the Claude Developer path. The two that are FDE-specific are about delivery, not code: qualifying a use case, designing a pilot, capturing a baseline, and driving adoption. The path ends with a pilot plan rather than a demo. It also prepares for the Claude Certified Developer - Foundations exam.

For a staff engineer, the useful signal is not the course list. It is that Anthropic's own definition of an FDE is "a Claude developer plus a pilot methodology," and that the methodology centres on agreeing success measures and a baseline before building.

"Public" means the course appears in the public Anthropic Academy catalog (anthropic.skilljar.com). The FDE path page itself requires a partner-academy sign-in; course lengths and contents are as the post describes them.

The shape of the role it implies

Read as a job description, the path splits an FDE's work into three layers:

  1. Set expectations. Explain limits up front, pick the entry point (chat, Claude Code, API, managed agents) and the model before writing prompts. This is the part most pilots skip and later pay for.

  2. Prototype in the customer's environment. Claude Code in the customer's repository, MCP to their systems, skills to leave behind reusable procedure. The emphasis on permission modes, hooks and verification in long sessions is the guardrail layer.

  3. Run the pilot as an experiment. Baseline first, success measures agreed before building, ship a first slice, onboard the first users, then scale adoption.

The third layer is what distinguishes the role. It is also the cheapest to learn (100 minutes) and the hardest to do well.

What is good about it

  • Baseline before build. Agreeing success measures and capturing a baseline before the prototype exists is the single habit that separates pilots that convert from pilots that end in "it seemed nice." Putting it in the official path makes it a default rather than a consultant's opinion.

  • Leave-behind as a deliverable. Ending the building block with agent skills frames the FDE's output as reusable, team-owned procedure, not a one-off demo.

  • Model and entry-point choice is taught as a decision. Treating "which surface, which model, which features, what context" as an explicit up-front decision matches how cost and reliability problems actually arise.

  • Mostly free to sample. Seven of the 11 courses are in the public academy, so a team can run most of the path without partner membership.

Gaps a staff engineer should notice

  • Evaluation is implied, not taught. "Capture the baseline" and "success measures" are there, but there is no course on building an eval set, grading outputs, or regression-testing prompts and skills. A pilot without a repeatable eval cannot be defended at scale-up.

  • Security and data handling are thin. Connecting Claude to customer systems via MCP and running long hands-off sessions in a customer repo are exactly where credential scope, data residency and prompt-injection risks live. The syllabus mentions permission modes and hooks but no threat-modelling course.

  • Cost is absent. Model choice is covered, but not token budgets, caching, batch versus interactive, or how to forecast run cost from pilot to production.

  • Operations after the pilot. "Activation to scale" is an adoption course. Monitoring, incident handling and ownership hand-off of what the FDE built are not listed.

  • Foundations-level certification. The path prepares for the Foundations exam, not the Professional one (see R130), so it is an entry credential.

How to use it

  • Already building with Claude: do the two delivery courses first (as the post suggests), then the two partner-only core courses on platform foundations and model choice.

  • Running a pilot next month: write the pilot plan the path ends with before touching code: baseline metric, success threshold, first slice, first ten users, and an eval set you can rerun. Add a one-page security and cost note the path does not ask for.

  • Teaching a team: the seven public courses make a reasonable two-week internal curriculum; pair Claude Code in Action with a hands-on exercise in your own repository.

Review checklist for an FDE-style pilot

  • Is the use case qualified (value, data access, tolerance for error) and written down?

  • Was a baseline measured before the prototype, with the same metric you will report?

  • Were success measures agreed with the customer before building?

  • Is there a rerunnable eval set, not just demo prompts?

  • Are tool and data scopes for MCP connections and Claude Code sessions least-privilege, and reviewed?

  • Is the cost per task estimated at production volume?

  • What does the customer's team own at the end: skills, configs, runbooks?
