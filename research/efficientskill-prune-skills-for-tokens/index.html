EfficientSkill: learn the skill for accuracy, then prune it for tokens

The problem

Reflective skill optimizers improve an agent by reading its failed and successful rollouts and rewriting its instructions, the "skill" file it loads each turn. The usual failure is bloat. Every failure adds an edge-case rule, the skill grows, every turn replays more tokens, and agents drift into long, error-prone loops that time out. The baseline compared here is EvoSkill, an unconstrained reflective optimizer.

How it works

Two phases, in a fixed order.

  1. Accuracy phase. Start from a minimal seed skill. Repair failed rollouts with no token penalty until the skill reaches a target accuracy.

  2. Accuracy-guarded pruning. Warm-start from that skill and shrink it under a constraint that accuracy stays near the target. The pruning has three levers:

    • Compress instructions: merge or delete rules.

    • Bound agent turns: replace open-ended loops with compact workflows.

    • Offload reusable code into workspace utilities, which the agent calls instead of re-deriving, so the code costs no prompt tokens.

Order matters. Pruning straight from the seed stalls; the optimizer needs a working skill before it can learn what is safe to cut.

Reported results

MeasureResult vs unconstrained EvoSkill
SetupFour models (frontier, mid-tier, open-weight) on MATH-500, ALFWorld and SpreadsheetBench, 12 configurations
Output tokensLower in 11 of 12 configurations, by up to 80%
AccuracyMean accuracy higher on every benchmark; +14.3 points (Gemini 3.8 Flash) and +17.5 points (Grok 4.1 Fast) on SpreadsheetBench
Serving costDown 25% to 67% according to the roundup; lower total tokens in every configuration, with or without full-prefix KV caching

The accuracy gain comes from the same change as the savings. Stalled loops were replaced with short workflows, so the cheaper agent was also the better one.

Tradeoffs

  • Two optimization budgets instead of one. Phase 1 is deliberately wasteful on tokens. Teams pay that once per skill, offline.

  • The target accuracy is a dial. Set it too high and pruning has no room; set it too low and the skill ships weaker. It needs a held-out set that represents production.

  • Utilities move complexity into code. Workspace helpers are cheaper per turn but need versioning, tests and a security review, like any other code the agent can execute.

  • Bounded turns trade flexibility for predictability. Good for repetitive task families (spreadsheets, household simulations), riskier for open-ended work.

Failure modes

  1. Overfitting the pruned skill to the optimization set: compact rules that only cover the benchmark's cases.

  2. Silent capability loss when a pruned rule handled a rare but important case the evaluation set missed.

  3. Utility drift: helper code changes and the skill's description of it doesn't.

  4. Turn bounds that truncate legitimately long tasks.

Review checklist for teams with growing skill files

  • Is token cost per task tracked next to accuracy for every skill revision?

  • Does the optimizer or reviewer have a pruning pass, not only an append pass?

  • Is pruning gated on a held-out accuracy floor?

  • Have repeated procedural instructions been moved into tested helper scripts?

  • Are turn limits set per task family, with a measured distribution of turns?

  • Is there a regression set of rare cases that pruning must not lose?
