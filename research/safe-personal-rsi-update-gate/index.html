Safe Personal RSI: an update gate for a self-improving personal assistant

The claim in one paragraph

Kicker is a personal health assistant that can propose changes to its own reusable instructions. Such edits can improve task handling while quietly changing what the assistant discloses, which requests it obeys and how it reports its actions. Safe Personal RSI is the update gate that decides whether a proposed edit is adopted. Recursive self-improvement is restricted to prompt updates: model weights and runtime code stay fixed. Across three models and two deliberately risky edits, the gate rejected 20 of 21 update attempts. An admitted repair for GPT-5.6 Luna cut attack violations from 10.7% to 0% and raised safe task completion from 89.7% to 100%. Under stronger attacks, a repair found on Qwen2.5-7B-Instruct and transferred to Qwen3-14B cut violations from 69.0% to 17.9% and raised safe task completion from 19.5% to 64.4%.

Architecture: the six-step gate

  1. Search. Run the proposed and current instructions on the executable benchmark: 29 email, calendar, health and marketplace cases, plus separate probes for authorization reuse, memory and tool-output injection.

  2. Replay. Repeat failing cases to separate real failures from noise.

  3. Investigate. Temporarily undo individual prompt changes and replay, to find which edit caused the failure (a bisection over the diff).

  4. Repair and verify. Revise the instructions and recheck both the failures and task utility.

  5. Decide. Check safety, task handling and complete execution together.

  6. Adopt or keep. Adopt a passing version; if none passes, the current instructions stay.

The default is conservative: no passing candidate means no change.

The caveat the headline omits

The paper reports that a broad handwritten authority rule matches the gate's outcomes in the GPT-5.6 Luna repair confirmation. In other words, for that case a single static instruction did as well as the full search-and-repair loop. The gate's value is that it finds such repairs and refuses bad edits automatically, not that it beats a careful human rule. The study's comparison arms make this explicit: the current harness, the harness plus a fixed handwritten rule, direct adoption of the edit (utility-only), and the gate's selected version. Authentication, allowlists and draft-only containment stay on in every arm, so the gate is a layer on top of those controls, not a replacement.

Tradeoffs

  • Prompt-only RSI is auditable. Restricting self-improvement to instructions makes every change a reviewable diff and keeps weights and code out of scope. It also caps what self-improvement can achieve.

  • Small benchmark, real execution. 29 executable cases are cheap to run on every update, but coverage is narrow; an edit that only misbehaves outside those cases passes.

  • Rejection rate as a feature. Rejecting 20 of 21 attempts is the intended behavior for deliberately risky edits; on benign edits, a gate this strict could also block useful improvements, and the paper's numbers come from stress updates.

  • Transfer across models. A repair found on a small model helped a larger one, but still left 17.9% violations under strong attacks.

Failure modes to expect

  • Benchmark overfitting. Repairs tuned to pass 29 cases can encode case-specific rules that do not generalize.

  • Gaps below the prompt. Runtime probes found missing local OAuth scope checks in the evaluated snapshot. No prompt gate fixes a missing authorization check in code.

  • Memory side effects. Separate probes for memory-entry deletion exist because instruction changes can alter what the agent remembers or forgets.

  • Injection through tools. Tool-output injection is tested separately; an edit that loosens how the assistant treats tool output is exactly the kind of change that looks like an improvement on utility metrics.

Review checklist for a self-modifying agent

  1. Is the scope of self-modification explicit (instructions only, or also code, tools, memory)?

  2. Does every proposed update run against executable cases for both utility and safety, including injection and authorization reuse?

  3. Are failing cases replayed before a verdict, and is the offending edit isolated by undoing changes?

  4. Is the default on failure to keep the current version?

  5. Are hard controls (authentication, allowlists, draft-only actions) enforced outside the prompt so a bad edit cannot remove them?

  6. Is the gate compared against a simple handwritten rule, so its added value is measured?

  7. Are code-level gaps (such as scope checks) tracked separately from prompt repairs?
