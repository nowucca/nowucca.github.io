Bottom line

The post is a usable vocabulary list for agent memory, and its third group is its best part. Its repo links are weak, though: 6 of 15 fit well, and the rest point at general infrastructure (Redis, Chroma, FAISS) or at the wrong tool (DSPy for conflict resolution).

Maryam Miradi's post (2026-11-13) lists 15 patterns in three groups. Types say what is remembered (working, episodic, semantic, procedural, long-term). Mechanisms say how it is processed (summarization, retrieval, consolidation, compression, graph memory). Control says what to trust, forget or isolate (decay, forgetting, conflict resolution, provenance, isolation). Each pattern gets a one-line definition and one GitHub repo.

Three things to know before you use it:

  • The groups mix axes. Some items are kinds of content, some are lifetimes, one is a data model, and three are the same write-path decision.

  • The write side is missing. The post never says what is allowed into memory, at what scope, or how you prove memory helps. Two commenters supply the best missing rules: store only facts the business can verify, and test that a one-off instruction doesn't become a standing preference.

  • The field is moving toward append-only. mem0's current README says v3 dropped write-time UPDATE/DELETE: memories accumulate and time-aware retrieval picks the current one. That matches R040 and R057, which keep raw evidence and resolve at read time.

Caveats: the post funnels to the author's course guide, and the "400+ agents" claim is unverified.

Corrections

The three groups mix four different questions, and sorting the 15 by question makes the design choices visible.

  • Content type: what is it? Episodic, semantic and procedural are real kinds of content. They need different stores and update rules: events are appended, facts get superseded, and procedures get versioned and reviewed.

  • Lifetime and placement: where is it, and for how long? Working memory is the context window. Long-term memory is anything persisted outside it. These are places, not types, and every content type can live in either.

  • Data model. Graph memory is a way to store facts and relations, not a mechanism. It sits beside a vector index or a set of Markdown files as a choice of store.

  • Write-path loss: how much of the raw event do you keep? Summarization, consolidation and compression are one decision at three strengths. Each throws away evidence. R059 measures this as a "memory tax" and finds that many memory systems do worse than plain retrieval over the raw history. The safer design keeps an append-only raw log and makes every derived note point back to it (R040, R057, Graphiti's episodes).

Two more corrections inside Group 3:

  • Decay and forgetting are one policy at two strengths: rank down, or delete. Keep both apart from deletion on request (a user or a regulation says remove it). That must be hard and verifiable, and must reach summaries, embeddings and graph edges derived from the item.

  • Conflict resolution depends on provenance and time. "Pick the trusted fact" needs to know where each fact came from and when it was true. Graphiti records validity times and marks a superseded fact invalid instead of deleting it, so you can still ask what was true last month. Asking a model which fact to believe, with no source or time, is a guess.

What's missing

The list is all about storing and processing memory, and silent on deciding what gets in and proving it helps.

  • An admission policy. Who may write (the user, the agent, a tool's output), and what qualifies. A commenter's rule is the right default: store facts the business can verify, not the agent's guesses. Tool and web output should not become "facts" without a source attached.

  • Scope at write time. Another commenter offers a test: after "use this address for this order", the next order should still use the usual address. Every memory needs a scope (this turn, this task, this user, this org) and an expiry, set when it is written.

  • Memory as an attack surface. Retrieved memory is untrusted input. Text planted once, through a document, a web page or a tool result, is replayed into every later session. Treat memory reads like any other untrusted context.

  • Proof that memory helps. Report gain and regression against a no-memory run, as R040 does; there, 52% of memory-caused failures came from following a stored item. Also compare against retrieval over the raw history at the same token budget (R059). LoCoMo and LongMemEval are the common benchmarks.

  • Cost and latency. Write-path model calls add up on every turn. R057's SoMem costs about 34 times as much as Mem0 per LoCoMo run, and beats the best baseline by 2 to 3 points.

  • Several writers. Two agents updating the same memory need a merge rule. R074 gives each agent a branch and merges on review.

  • A way for the user to see and fix it. A memory the user can't inspect or correct turns a wrong fact into a permanent one.

A memory pipeline to design against

Put the 15 patterns on five stages in order, and each stage gets a test you can run. Stage 1 is the one the post leaves out.

StageWhat it decidesPatterns from the postTest it with
1. AdmitWhat may enter, from whom, at what scope and expiryNoneA one-off instruction does not persist. An unsourced claim from a tool is rejected.
2. RecordAn append-only raw log, with a source on every entry14 ProvenanceEvery derived memory resolves to a log entry.
3. DeriveNotes, facts, procedures and graph edges built from the log3, 4, 6, 8, 9, 10A/B against retrieval over the raw log at the same token budget.
4. RetrieveWhat goes into context for this step1, 7, 9, 11Recall at k and answer accuracy. Regressions against a no-memory run, reported separately.
5. GovernTrust, expiry, deletion, tenancy11, 12, 13, 15A planted contradiction resolves to the newer sourced fact. A delete removes every derived copy. No cross-tenant hits.

Patterns 2 and 5 (episodic, long-term) are not stages: episodic memory is mostly stage 2, and long-term describes stages 2 to 5 together.

Failure modes and review checklist

Most memory failures are a missing step around the store, not a bad store.

FailureWhat you seeStage that should catch it
A one-off becomes a rule"Use this address for this order" sticks for every later order1 Admit
A guess stored as a factThe agent's own inference comes back later as ground truth1 Admit
Poisoned memoryText from a page or tool result steers every later session1 Admit, 5 Govern
Summary driftA note no longer matches its sources, and nothing checks2 Record, 3 Derive
Stale fact winsAn old preference outranks a newer one4 Retrieve, 5 Govern
Memory hurtsThe agent fails tasks it solves with memory off3 Derive, 4 Retrieve
Delete misses copiesA removed item survives in a summary or embedding5 Govern
Cross-tenant leakA shared index without a tenant filter returns another user's memory5 Govern

Review checklist for any agent memory design:

  1. Who can write to memory, and is tool or web output kept apart from user-stated facts?

  2. Does every memory carry a scope and an expiry, set at write time?

  3. Is there an append-only raw log, and does every derived memory link back to it?

  4. Which steps throw away evidence (summarize, consolidate, compress), and has each been A/B tested against raw-history retrieval at the same token budget?

  5. Are gain and regression against a no-memory run reported separately?

  6. How are contradictions resolved, and does the rule use source and time rather than a model's opinion?

  7. Does a delete reach every derived copy, and is there a test that proves it?

  8. Is tenant isolation enforced in the store, not just in the prompt?

  9. Can the user see and correct what is remembered?

  10. What do memory writes cost per turn in model calls and latency?
