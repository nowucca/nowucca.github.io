Exact: Expo's all-platform app framework built around the agent loop

What it is

Exact is a new open-source app framework from Expo. One source tree builds native apps for web, iOS, macOS, Linux and Android, with Windows early and tvOS, watchOS and terminal hosts included. It is designed so a coding agent can build, run, see and test the app on every platform through one deterministic loop. That addresses the usual gap: agents write UI code but can't observe what it renders.

Architecture

  • Contract, a declarative UI language. It is compact and strictly typed, uses CSS property names, and keeps JavaScript and I/O out of views. Expressions are pure, actions have no loops or await, and async work lives in data sources. A whole app is meant to fit in a model's context window. App logic lives behind a typed data seam in TypeScript (precompiled to Hermes bytecode), in Rust (native or Wasm), or in declarative HTTP/GraphQL sources that need no JS engine at all.

  • Compiler to a plan. Four passes (syntax, types, analysis, lowering) turn .contract files into a plan of tables and bytecode, with constant data baked in so the first frame needs nothing else. The compiler reports up to 20 independent errors per build, each with a stable ID, a line number and a suggested fix. That is aimed directly at agent self-correction.

  • Hosts. The web target compiles the plan into one ES module over a ~20 KB DOM runtime. Native hosts run the plan in a Rust VM with a patched Taffy layout kernel. They present through real UIKit and AppKit on Apple platforms, Android Canvas with Material 3 and native text fields on Android, and Exact's own GPU or CPU painter on Linux and Windows.

  • The agent driver. One script exposes the same ten operations on every host: tree, screenshot, tap, type, state, layout, logs, clock, prefer and perf. In driven mode time advances only when the driver moves the clock, so tests and agents never sleep on animations or timers and don't flake on timing. Motion can be filmed deterministically into a contact sheet. The driver also refuses to drive a build that is older than its sources.

  • One-command verification. A single verify command builds the app, runs the authored tests, and checks light and dark mode, several screen widths, accessibility trees, dynamic-type overflow and scroll feel. It returns one structured report.

  • Performance budgets as gates. Targets include a 100 ms p50 cold start, 100 ms save-to-present reloads and no app JavaScript before first paint. The budgets are checked continuously, and regressions are bisected automatically to the breaking commit. On the RealWorld (Conduit) benchmark, the README reports a 26 KB web build against React 19's 81 KB.

  • Opt-in friction notes. An app's AGENTS.md asks agents to log rough edges locally. Notes record no code or command output, and sending them to Expo is opt-in.

The post also describes a README test run in which a fresh agent, given one prompt for a todo app, finished in about 57 minutes with tests passing on web, macOS and the iOS Simulator. The README publishes that prompt; the timing is the README's own figure.

Tradeoffs and failure modes

  • Immaturity. It is pre-1.0 and changes daily. There's no packaged CLI, no API stability or backward compatibility, and you build from a checkout. Android polish and Windows control styling are still in progress.

  • No ecosystem bridge. There's no JSX or React layer, and React Native and Flutter plugins don't work. Teams lose npm and pub.dev breadth and rely on about 60 first-party packages plus native modules.

  • A new language. Contract is small and agent-friendly, but humans and models alike must learn it, and its deliberate limits (no loops in actions, no I/O in views) push complexity into the data seam.

  • Driver-observed reality isn't user reality. A seekable clock and an accessibility tree make tests deterministic, but they can hide bugs that only show under real timing, real network jitter or real devices. Android drives refuse filmed capture outside live mode.

  • Over-the-air updates. Signed updates are limited, for example to one module type per platform, and Windows has no update store yet.

Review checklist

  1. Can your coding agent observe the rendered UI (tree, screenshot, state) on every target platform, or only the code it wrote?

  2. Are UI tests driven by a controllable clock rather than sleeps, so failures are about behavior and not timing?

  3. Do compiler and test errors give the agent a location and a fix, not just a stack trace?

  4. Is there a single verification command covering themes, widths, accessibility and text scaling that an agent can run before it claims done?

  5. For a pre-1.0 framework, is the lack of release versioning and plugin compatibility acceptable for the project's lifetime?
