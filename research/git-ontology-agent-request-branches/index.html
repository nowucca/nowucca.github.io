The problem

A person adds a budget, corrects a city, or asks an unrelated question while an agent is mid-task. Most harnesses either queue the message, restart the task, or splice the new text into the prompt and hope the model reconciles it. None of those says which completed work is still valid. Git Ontology Agent (goa) is a small prototype that makes that question explicit.

Architecture

  • Work state is a list of typed claims, not prose. Each claim has an id (constraint.budget, plan.hotel), a type (Request, Constraint, Assumption, Finding, Decision, Progress), from (the request that produced it), depends_on, and status (confirmed, in_progress, invalid, superseded). It lives in state.yaml in a git repo.

  • One branch per request. main is what has been confirmed to the user; each request runs on req/<n> from a base commit. Every work step is one commit made with git plumbing (no checkout, no working tree), with a structured message: request, relation and confidence, branch, base, claims invalidated, decision model used.

  • A decision model classifies each new message against the open request into one of five neutral keys: supplement (k1), correction (k2), independent (k3), cancel (k4), progress (k5). Keys are deliberately neutral because decision models reportedly follow option names over definitions. Below 0.8 confidence the agent asks the user. With several open requests, a second choice picks the target.

  • Dependency-driven redo. A supplement commits a Constraint and invalidates only its dependents (the hotel, not the train). A correction retracts an Assumption and invalidates everything downstream of it. Nothing restarts from scratch.

  • Type-aware three-way merge. Claim by claim between base, main and branch: Constraints stack, Assumptions take the correction, Decisions recompute if a dependency changed, Findings take the later check, Progress never merges, Requests all kept. The only unruled case (two independent requests changing the same Assumption or Decision) goes to a 0-1 decision-model score; at 0.7 or more the later value wins, otherwise both are kept and the final answer asks. A branch with any invalid claim cannot merge.

  • Answers are generated from status. Interim answers read the branch tip and word claims by status (confirmed said plainly, in_progress as ongoing, invalid never said, superseded with which request changed it). The final answer reads the diff from base to merge commit, so it can say which request each part came from. Answers are themselves commits on an answers branch, so "why did it say that" replays with git show <sha>:state.yaml.

  • Packaging: standard-library Python 3.9+, zero dependencies, offline demo and a --mock mode that simulates every provider's request shape. Pluggable LLMs (OpenAI, Anthropic, Gemini, xAI, Meta, OpenRouter) and decision backends (Typesafe Jev, OpenAI Decisions API, Gemini enum schema, Cloudflare Workers AI, a local keyword heuristic). Thresholds in a versioned policy.yaml.

What is genuinely useful here

  1. The five-way relation taxonomy is a clean, reusable contract for mid-task user input. Any steerable agent (Slack-thread agents, background coding agents) needs some version of supplement/correct/fork/cancel/status, and naming it makes it testable.

  2. Status-aware wording directly addresses a common failure: interim updates that state half-finished work as fact. Tying the wording to a machine-readable status is cheap and checkable.

  3. Provenance per claim (from) gives you an answer that can explain itself, and an audit trail that replays exactly what the agent knew when it spoke.

  4. Merge rules by type move most conflict resolution out of the model. That is the same instinct as typed CRDT-style merges: semantics first, judgment only for the residue.

Tradeoffs and failure modes

  • Someone has to write the claims and their depends_on edges. The demo uses built-in trip skills; in open-ended work the LLM must emit correct dependencies. A missing edge silently keeps stale work (the budget never reaches the hotel); an overly broad edge (constraint.*) redoes too much. The whole value rests on graph quality, and the README doesn't say how it is checked.

  • Real side effects are out of scope. The top LinkedIn comment asks the right question: what if the invalidated step already booked a nonrefundable train? goa marks claims invalid; it has no notion of compensations, irreversible actions or approval before redo. In a real agent, a Decision that triggered a tool call needs a compensating action or a human check, not just a status flip.

  • Classification errors are expensive in different directions. A correction misread as a supplement keeps Busan results under a Daegu plan; an independent request misread as a supplement pollutes the main task. The 0.8 ask-threshold helps, but there's no evaluation data on relation accuracy.

  • Concurrency is single-agent. Parallel req/* branches are a fork-join within one conversation; swarms and long-term memory are explicitly out of scope. No locking story for two writers on the same repo.

  • Git as a database. Fine for a session's worth of commits; history growth, claim lookup cost and multi-user access aren't addressed. Plumbing-only commits avoid working-tree races but not ref races.

  • Maturity. A same-day prototype from one author (who also wrote auto-ontology-mcp, R028), no stars yet, model names in the defaults that will age fast. Treat it as a design sketch, not a dependency.

Review checklist if you adopt the pattern

  • Can you list every claim type and its merge rule, and is there a test per rule?

  • How are depends_on edges produced, and what catches a missing one (e.g. a post-hoc check that each Decision cites every Constraint in scope)?

  • Which Decisions have external side effects, and what happens when one is invalidated: compensate, ask, or block the merge?

  • What is the measured accuracy of the relation classifier on your traffic, and what does each confusion cost?

  • Do interim answers ever cite an in_progress or invalid claim as settled? Make that an automated check.

  • Can you replay any answer from its recorded commit?
