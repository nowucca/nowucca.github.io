In one paragraph

A 15-module Python course that grows one project from a single chat-completion call into a small harness: loop, tools, a registry, context compression, JSON memory, plan/execute/synthesize, retry limits plus a critic, async tool calls, guardrails with human confirmation and an audit log, tracing, sub-agents as tools, a packaged library with cost tracking and caching, and MCP tools. No framework; plain openai SDK against an OpenAI-compatible endpoint, tested on Ollama with gemma4:e4b. The new book is the useful part for experienced readers: every chapter runs the code against a small local model and records what actually went wrong, then traces each safeguard to that failure. The final chapter turns those runs into a ledger of failure to production practice.

Architecture of the course

  • Modules 0 to 3 are cumulative: one call, then a loop with a done marker and MAX_TURNS, then one tool, then a decorator registry with an executor that turns every tool error into a string the model can read.

  • Modules 4 to 11 are branches off the module 3 loop, each showing one feature alone (the book says so explicitly, so module 6 has no module 5 memory).

  • Module 12 folds the core into an importable agent_harness package: config, tools, prompts with versions, cost, cache, loop.

  • Module 13 moves tools into a separate MCP server process (official Python SDK MCPServer and Client), with a model-free inspector script first.

  • Module 14 is a production roadmap: security, reliability, evaluation, observability, scale and cost, UX, frameworks, in a suggested order.

The book's own summary: almost none of these failures was loud. Production work on agents is mostly making quiet failures visible.

Tradeoffs and limits

  • One small local model (gemma4:e4b, reasoning_effort="none"). Several failures (chat-format leaks, marker placement) are much rarer on frontier models; the lessons hold, the frequencies don't transfer.

  • Sample sizes are 2 to 7 runs per experiment. The book says so and asks readers to run cases several times; treat the tables as demonstrations, not measurements.

  • Teaching code by design: eval() calculator, secrets as constants, in-memory audit log, stub web search. The README's caveat lists what a production review must add.

  • No sandboxing, durable state, token-level budgeting, or evals are built; chapter 14 points to them only.

  • Module 13 pins an older openai version in a separate venv.

  • The author says AI helped write the code and book; the documented runs carry dates and versions, which makes them checkable.

Review checklist it implies for any harness

  1. Does the loop parse model output defensively, and fail loudly on an empty final answer?

  2. Is completed work tracked outside the model's context (a list the code owns)?

  3. Which prompt rules matter enough to enforce in tool code instead?

  4. Do stage boundaries pass tool evidence and reject empty or malformed outputs?

  5. Does any structured verdict put reasoning before the decision field?

  6. Are destructive tools behind an allowlist plus a human gate that the model cannot satisfy with text?

  7. Does every agent hop keep provenance, so a guess can't become a "finding"?

  8. Is output validated before it is cached, and are side-effecting tools safe to re-run on a cache hit?

  9. Are traces written as they happen, so a crash keeps them?

  10. Is each of the above a repeatable test case, run several times per prompt or model change?
