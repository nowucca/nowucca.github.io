Skills for Real Engineers: small, composable skills for coding agents

TL;DR

A collection of small agent skills that encode classic engineering practice (alignment interviews, a shared domain language, red-green-refactor, disciplined debugging, deep modules) as slash commands and model-invoked skills. It installs as a plugin for Claude Code, Codex and Copilot, or as editable files for other agents. The design choice that matters is the opposite of heavyweight agentic process frameworks: rather than owning the whole workflow, each skill is small, composable and meant to be edited for your stack, so failures stay debuggable.

What's in it

The README organizes the skills around four failure modes of coding agents:

  • Misalignment ("the agent didn't do what I want"). /grill-me and /grill-with-docs make the agent interview you about the change before writing code. The docs variant also maintains a project glossary and inline architecture decision records.

  • Verbosity and drift in naming. A shared domain language in a glossary file, following Domain-Driven Design's ubiquitous language, so agents use one precise term instead of twenty vague words, name code consistently, and spend fewer tokens.

  • Code that doesn't work. /tdd enforces red-green-refactor with guidance on good and bad tests; /diagnosing-bugs wraps debugging into a gated, phase-by-phase loop.

  • Ball of mud. /to-spec asks which modules a change touches before writing a spec; /improve-codebase-architecture surveys the codebase for "deepening" opportunities (in Ousterhout's sense of deep modules) and produces an HTML report, which the author recommends running every few days.

Planning flows into the issue tracker: /to-spec publishes a spec, /to-tickets splits it into tracer-bullet tickets with explicit blocking edges, and /triage moves issues through a labeled state machine. A one-time /setup-matt-pocock-skills records the tracker, triage labels and docs location per repo.

Invocation rule. Skills split into user-invoked (orchestrators you type) and model-invoked (reusable discipline the agent may pick up on its own). A user-invoked skill may call model-invoked ones, never another user-invoked one, which keeps orchestration flat.

Tradeoffs

  • Small and composable vs. an owned process. You keep control and can fix any step, but you also own the integration; nothing enforces that the pieces are used together.

  • Plugin vs. copied files. The plugin auto-updates; copied files can be edited but drift from upstream. The README warns against installing both.

  • Interview-first workflow. Grilling sessions improve alignment at the cost of human time on every change; it's a deliberate trade against rework.

  • Popularity isn't evidence. Star count reflects reach (the author has a large newsletter audience), not measured effect; the README offers no benchmark of outcomes.

Failure modes to watch

  • Glossary rot. A shared-language file that isn't maintained misleads agents with stale terms.

  • Tests written to pass. TDD skills help only if the failing test is committed and protected before the fix; otherwise the agent can weaken it.

  • Ticket graphs that don't match reality. Blocking edges inferred from a spec can be wrong; review them before parallelizing work.

  • Architecture surveys as busywork. Running the survey often produces candidates; it doesn't untangle legacy code by itself, as the README notes.

Review checklist

  • Are the skills you install pinned or reviewed when they update?

  • Is there a single glossary or domain doc, and is it kept current as part of normal changes?

  • Are failing tests committed before fixes, and protected from edits during the fix?

  • Do generated tickets have owners and verified dependencies?

  • Is there any measurement of whether the skills reduce rework or defects in your repo?
