Source: Claude product update, "MCP servers can now ship skills, run tasks, and more with Claude" (2026-11-24). Found via TLDR Dev 2026-11-25.

What shipped

  1. Skills over MCP (public beta). An MCP server can publish skills next to its tools. Claude loads a skill only when a task needs it, so idle skills cost no context, and a skill updates whenever the server does, with nothing separate for the user to install. It is on by default for Pro, Max and Ultra in Claude and Claude Code; Team needs an admin to enable it; Enterprise is "coming soon". Spec: MCP skills extension. Example servers: Shopify, HubSpot, Atlassian (Carta coming).

  2. Tasks (generally available). A server can run a slow operation or a whole agent loop in the background while Claude keeps working, and hand back the result when it is ready. Spec: MCP tasks extension. Example: ZoomInfo.

  3. Elicitation (generally available). A server can pause mid-call and ask the user for input through a form or a link, then carry on. Examples: confirming the cost before a paid action, or typing a repository's name before deleting it. Spec: 2026-07-28 client elicitation.

  4. File uploads (rolling out soon). Claude can send a PDF, spreadsheet or image to a server without passing it through the context window. It is still an experimental extension.

Tasks and elicitation are GA on Pro, Max and Ultra and rolling out to Team and Enterprise. All four are open MCP extensions or spec features, so other compatible clients can implement them.

Why it matters for a staff engineer

  • The server becomes the unit of distribution for know-how. Until now a skill was a folder you copied into a repository or a user's home directory. With skills over MCP, the team that owns an API also owns the instructions for using it, versioned with the server. That fixes drift between tool and instructions, and it moves a prompt-injection surface onto the server: a skill is instructions that the model follows, so treat a third-party server's skills with the same trust as its code.

  • Long work leaves the chat turn. Tasks let a server own a long-running job, with the model polling or being told when it finishes. This is the durable-execution pattern (R263, R273) pushed into the protocol.

  • A human gate in the protocol. Elicitation gives servers a standard way to require explicit confirmation for destructive or costly actions, instead of relying on the model to ask. That is the right place for a gate: in the code that performs the action.

  • Context economics. On-demand skills and the existing tool search (the article claims more than 85% less context for tool definitions across many servers) both follow the same rule: load what the task needs, when it needs it.
