No, not underneath. Federico Tomassetti (Strumenta) had Claude Code on Opus 5.5 translate about 600,000 lines of IBM i source (RPG, DDS, CL) into more than a million lines of Java, over 49 headless sessions. The result looks uniform on the surface. Underneath, it drifts: one date helper exists in 27 classes with 20 different bodies. The parts the agent produced with its own deterministic generators were the most uniform (article, 23 Nov 2026, part 4 of 5). Strumenta sells parser-based migration tooling, so read the comparison with that in mind.

Setup

  • Scope. About 600K lines of RPG, DDS and CL became about 5,737 Java files.

  • Prompt. "Organize the project as you see fit." The agent ran headless and could not ask questions.

  • Phasing. 49 phases, ordered by a dependency plan from Strumenta's tooling. Each session saw only files written by earlier phases.

  • No running IBM i. "Agrees with the RPG" was judged by reading the source, not by running both.

The generators

The agent wrote seven Python generators, about 5,000 lines in total. They use regex and fixed-column parsing, with no grammar and no tests. Rerun on 3,558 members, they failed on 15, and about 30 of roughly 3,700 generated files now behave differently from what was delivered. They are all-or-nothing: one unsupported line abandons the whole member. RPG itself had no generator; its only tool produced skeletons that were completed by hand.

Failure modes worth testing for

  • Behavioural divergence. A screen regenerated from DDS sets indicator 25 true for an input where the delivered Java sets it false.

  • Silently dropped semantics. About 70 DDS keywords are ignored. Cursor placement (CSRLOC), used in 16 display files, is lost with no error.

  • Hidden coupling. The CL generator reads a generated Java class with a regex. Run from another directory, 24 programs that should convert fail.

  • Hardcoded tables. Specific program names are baked into a generator.

Takeaways for large agent migrations

  • Per-session agents don't maintain conventions across sessions. Something has to own the architecture: rules, review, or a final consolidation pass.

  • Prefer generators for mechanical layers, but give them grammars and tests, and check that they reproduce what was delivered before anyone maintains them.

  • Expect to find every copy of a shared utility and merge them one at a time.

  • Measure consistency directly (duplicate bodies, helper adoption by phase, style indicators), not just compile success.

Review checklist

  • Is there a cross-session conventions file the agent must read and update?

  • Do later phases get a pass that refactors earlier code to new helpers?

  • Are generators deterministic, tested, and diffed against delivered output?

  • Are dropped constructs reported as issues instead of silently skipped?

  • Is equivalence checked by execution, not only by reading?
