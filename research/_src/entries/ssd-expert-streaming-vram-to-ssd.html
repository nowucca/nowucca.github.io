The claim

A widely-shared post this week argues that local inference has just changed shape. The old rule was: if the weights do not fit in GPU VRAM or unified memory, the model does not run — which is why running a very large open model has meant buying a workstation. The claim is that SSD expert streaming breaks that rule, and that an open-source engine shipping it moves the binding constraint from VRAM capacity to SSD bandwidth, at a fraction of the hardware cost.

The mechanism, as described, is worth understanding on its own merits, because the reasoning is sound even where the specifics turn out to be unverifiable.

Why sparse MoE invites this

Modern large open models are sparse mixtures of experts. Each layer holds many small sub-networks; a router selects a few per token. A model with a large total parameter count may activate only a small fraction of it on any given token — ratios of roughly 30:1 between total and active parameters are now common.

So on every token, the overwhelming majority of the weights sit idle. A conventional local runner nevertheless holds all of them resident, because it has no mechanism to fetch a layer's experts on demand at token speed.

The proposal: keep attention weights and the session's hottest experts in fast memory, leave the rest on NVMe, and read an expert only when the router actually selects it. Reads only, so no write amplification and no flash wear.

The four obstacles — and why they are the right four

This is the most valuable part of the argument. A naive implementation of the above runs at a couple of tokens per second. Four distinct reasons are named:

1. Cache eviction of imminently-needed experts. A conventional LRU or random-eviction cache does not know the router's near-future selections. Routers are far from uniform — expert selection is strongly skewed and strongly autocorrelated across adjacent tokens — so a policy blind to that structure evicts exactly what the next few tokens will ask for. The stated fix is to rank experts by observed reuse and pin the top set resident, so most tokens never touch storage at all.

2. Serialised layer-wise I/O. If you read layer n's experts, compute layer n, then read layer n+1's, the GPU idles during every read and the SSD idles during every compute. The device-level throughput is irrelevant when the pipeline alternates. The stated fix is to look ahead at upcoming tokens and prefetch their experts before the GPU stalls — which is only possible because of the autocorrelation that makes problem 1 hard.

3. Speculative decoding widens the per-step working set. A drafter proposes several tokens and the target model verifies them together. Each verified position may route to different experts, so one step touches a materially larger expert set than single-token decoding would. Speculative decoding is table stakes for local throughput, so this is not an optional interaction — any storage-streaming design has to assume it.

4. Prefill evicts the decode working set. A long prompt sweeps through experts across all layers, flushing whatever decoding had warmed. The result is a cold cache at exactly the moment the user starts waiting on tokens. This is the one most likely to be felt in agent workloads, where prompts are long and decode bursts are short.

Any engineer evaluating a storage-tiered inference engine should ask about these four by name. They are the real failure surface.

What the project's own documentation actually supports

The post attributes all of the above to a specific Apache-2.0 engine. Checked against its README, landing page, benchmarks, model catalog, docs index, hardware page, FAQ and models page, the result is worth stating carefully.

Confirmed. The project is real, Apache-2.0, free and local — prompts, files and models stay on the machine, with no internet needed once a model is downloaded. It profiles the host and estimates tokens per second for every model before download. It tunes kernels for the specific chip, spending up to a minute trying different ways to split the math and keeping the fastest combination that does not change the model's output — though this happens at download time, not at first launch. It ships a desktop app and a CLI, runs on macOS, Linux and Windows, and offers one-click connection for a list of agent clients longer than the post's, plus an OpenAI-compatible API for everything else.

Published performance. Against a popular local runner: 1.32x faster prefill and 2.19x faster decode on a mid-range 48 GB Mac, and 1.34x / 2.17x on a 128 GB developer box, across 11 models at a 64k-context workload. The largest model benchmarked goes from 47.2 to 122 tokens per second on decode. The project's own benchmark notes concede that some of the Mac decode gain "partly compare speculative decoding against almost none" — a creditable disclosure.

Not documented on any published page. No page mentions SSD, NVMe, disk offloading, streaming weights or experts from storage, or running a model whose weights exceed available memory. No expert reuse ranking, no prefetch of upcoming tokens' experts, no direct storage scheduling, nothing about flash wear, nothing about the prefill/decode cache interaction. There is no changelog or release-notes page, so the "shipping today" framing cannot be dated — and the project itself was being written about weeks earlier as a hardware-auto-tuning engine.

Pointing the other way. The documentation's memory language is fit-or-refuse, not stream: it advises using a fit assessment and closing memory-heavy applications if loading fails, says models are unloaded when memory is tight, and says only variants that fit with room to work are recommended. That is what an engine says when a model larger than memory does not run.

Contradicted. The demo model is listed in the project's own catalog at 180B total and 6B active — not the 300B the post states. Its smallest quantized download is 70.1 GB and the 4-bit variant is 115 GB. The catalog publishes no tokens-per-second figure for it, states no minimum memory beyond "the weights plus a few gigabytes for context", and the model does not appear in the benchmark tables.

How to read this

Two readings survive. Either the streaming feature is genuinely new and entirely undocumented, or the post describes a capability the project does not have. The published evidence cannot distinguish them, so the capability should not be assumed.

What is solid: the engine auto-tunes per chip and roughly doubles decode throughput against a common baseline on ordinary hardware, with an honest caveat attached. That is a real and useful result — and it is a different, smaller claim than the one the post makes.

The parameter-count error is not cosmetic. The entire argument is about fitting a model that should not fit; overstating the model by two thirds overstates the achievement by the same margin.

Review checklist

  1. Establish whether the engine streams weights from storage at all, from its documentation — not from a demonstration video.

  2. Check the model's real parameter count and active-parameter count in a primary catalog, not in the write-up.

  3. Compare the quantized download size against your actual memory. If the download exceeds memory, streaming is load-bearing, not incidental.

  4. Ask whether published throughput figures were measured with speculative decoding on both sides.

  5. Look for the specific model you care about in the benchmark tables; absence is informative.

  6. Measure time-to-first-token after a long prompt, separately from steady-state decode.

  7. Benchmark on your own storage — if the thesis is that SSD bandwidth is the new limit, your drive is now part of the model's performance envelope.

  8. Confirm the read-only claim before trusting the no-flash-wear argument, with an I/O counter rather than a sentence.

  9. Verify platform and packaging claims individually; a project's own pages can disagree with each other.

  10. Treat the per-chip kernel tuning as the reliably-delivered feature, and anything about storage as unverified until you reproduce it.

The broader lesson

The architecture reasoning in this post is better than most. The four obstacles are correctly identified and the proposed mitigations map onto them properly. And the specifics still did not survive a check against the project's own pages.

That combination — sound mechanism, unverifiable attribution — is the common case, not the exception. Read the design for the design. Verify every number, parameter count and capability claim against the primary source before you let it into a decision.
