Sources: ClickHouse engineering blog, "Detect, act, keep the evidence: node reliability across three clouds", Nov 2026; Roopa Tangirala's LinkedIn post; github.com/ClickHouse/node-problem-mitigator. First-hand operator write-up from the vendor's own SRE team.

The claim in one paragraph

At thousands of Kubernetes nodes across AWS, GCP and Azure, a node with a failed disk, a stuck kernel task or a half-working network is a daily event, and most such failures do not look like node failures: Kubernetes still says Ready and the cloud console says running. ClickHouse decided to own both detection and reaction rather than rely on each cloud's differing auto-repair. The system has three parts: Node Problem Detector as the sensor, their open-source Node Problem Mitigator as the actuator, and a Node Debug Collector that captures evidence before the node is gone.

The incident that started it

One of two NVMe drives behind a software RAID 0 array on an EC2 node failed. The kernel logged the missing member followed by a stream of EXT4 and I/O errors, and ClickHouse pods on the node failed writes for a long time. No data was lost and nobody was paged, because the Node object stayed Ready and the provider never flagged the instance. Node Problem Detector was running and had matched the EXT4 errors, but the upstream rule is marked temporary: it emits an Event that expires after an hour and sets no Node condition, so nothing reacted.

Architecture

  • Sensor: Node Problem Detector (NPD). A DaemonSet that turns kernel and system log lines plus a few active probes into Node Conditions and Events. The fix for the incident is making the failures that matter permanent conditions, not expiring events.

  • Actuator: Node Problem Mitigator (NPM). A controller that never decides whether a node is bad; it only acts on conditions NPD sets. Each condition maps to a ladder of steps, least to most aggressive: evaluate (dry run), drain (honoring PodDisruptionBudgets), terminate (drain with timeout, then delete the instance). An ongoing mitigation can escalate if a more severe condition fires, but never de-escalates.

  • Forensics: Node Debug Collector (NDC). A pre-mitigation job collects logs and system state, even when the node no longer answers. Collection is best-effort by default and does not block mitigation, because getting rid of the bad node comes first. Diagnostics go to cloud support without manual steps.

  • Safety gates. A kill switch, dry-run mode, a rate limit and exclusions bound what the mitigator can do.

Why not existing tools

The post surveys the alternatives: Medik8s operators (capable but a long chain of custom resources and DaemonSets), Draino (abandoned, drain only), Cluster API MachineHealthChecks (too large a change), node-readiness-controller with descheduler (loose coupling where a misconfigured descheduler leaves nodes tainted but never drained, and no control over termination), and Karpenter auto-repair (AWS-only). Their underlying point: the threshold for killing a node depends on workload statefulness, how well the software honors PDBs and SIGTERM, and the operators' risk appetite, so termination resists standardization.

Per-cloud behavior also differed. On AWS they had disabled auto-repair because a disk heuristic kept flagging healthy nodes, and repair was usually an in-place reboot that often left the same fault. GCP ships its own NPD with many custom checks. Kubernetes v1.37 Lifecycle Conditions help partly but were not production-ready for them.

Tradeoffs

  • Own the reaction or trust the provider. Owning it gives one consistent behavior on three clouds and faster eviction than waiting for repair; it also makes you responsible for every node you kill.

  • Evidence versus speed. Non-blocking collection means some bundles are incomplete, in exchange for never holding a bad node in service to debug it.

  • More automation, new failure modes. A broad detection rule can drain healthy nodes without fixing anything; a mitigator bug can drain too many at once or suppress errors. The gates turn these into bounded, observable events rather than eliminating them.

Failure modes to expect

  • Expiring signals. Detector rules that emit events instead of conditions leave nothing for a controller to act on.

  • Correlated false positives. A bad rule or a cloud-wide kernel issue can match many nodes at once; the rate limit is what prevents a fleet-wide drain.

  • PDB deadlock. Drains that honor disruption budgets can stall; the terminate step needs its timeout.

  • Reboot loops. In-place repair that does not replace hardware brings the same fault back.

  • Lost evidence. Without pre-mitigation capture, the node is gone before anyone can learn the failure mode.

Review checklist for automated node remediation

  1. Do the failures you care about set durable Node conditions, not hour-long events?

  2. Is detection separated from action, so the actuator never judges health itself?

  3. Does each condition have an explicit escalation ladder that starts in dry-run?

  4. Is there a kill switch, a global rate limit and an exclusion list?

  5. Do drains have timeouts, and is termination explicit?

  6. Is evidence captured before mitigation, without blocking it?

  7. Is behavior the same across clouds, and is provider auto-repair either trusted deliberately or turned off?
