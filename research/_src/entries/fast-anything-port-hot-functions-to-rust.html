Source: EL4CTEO/fast-anything on GitHub (MIT; created 21 Nov 2026, early stage), README. Surfaced in a LinkedIn post by André Lindenberg. Benchmarks are the author's own.

The claim

Rewriting a whole app in Rust takes months. Most runtime sits in a few functions. So profile the app, have a coding agent port only the hottest pure functions, prove each port behaves identically on real recorded calls, and swap it in behind a reversible switch.

How it works

StepWhat happens
scanProfiles the running app and ranks functions by time spent multiplied by how portable they are (top-level, deterministic, plain-data inputs). It says why a function cannot move.
portRecords up to 500 real calls of the chosen function and creates a one-function Rust crate plus a TASK.md for the agent.
agentClaude Code, Codex or any stdin-driven command writes the Rust.
verifyRelease-builds the port and replays every recorded call, plus derived edge cases answered by the original.
enable / disableSwaps the Rust in or out via one marked block that is removed byte for byte. An env var forces the original at any time.
bench, reportTimes the whole app, original against Rust in interleaved runs, and emits a Markdown and SVG summary for the PR.

It is distributed as a CLI (npm or cargo), a Claude Code plugin, an MCP server with eight tools, and a skill. Bindings: PyO3 for Python, napi-rs for Node and TypeScript. Ruby, Java, Go, PHP, C and C++ use one C entry point that takes and returns JSON.

The verification gate

  • Recorded calls are the authority. The agent cannot edit them.

  • Derived cases widen the recording: NaN, ±infinity, -0.0, zero and ±1, non-ASCII text, empty inputs, inputs up to 16x larger, and shrunk slices. The original answers each one.

  • Equality: values must match (floats within 1e-9), and the port must raise an error wherever the original does.

  • Performance gate: a correct port that is slower per call than the original (FFI overhead exceeding the work saved) is not enabled.

  • The README's example: a port that compared bytes instead of characters looked right, and 148 of 500 recorded calls caught it.

A design point worth keeping: it ports the outermost loop it can, so execution crosses into Rust once rather than millions of times. Porting only the inner Levenshtein function gave 35x and 1.9x instead.

Where it fits

This is a narrow instance of "pointable" agent work. The original function is the authority, its behaviour at a recordable boundary (arguments in, value or error out) is the check, the agent cannot edit that check, and the job ships one function at a time behind a fallback. It is the per-function sibling of whole-app port tools that gate each unit on replayed recordings.

Tradeoffs

  • Scope. Only top-level, deterministic, plain-data functions qualify. Anything touching I/O, global state, object graphs or callbacks stays put.

  • Recording coverage. 500 calls from one run reflect that run's inputs. Derived edge cases help, but rare production shapes may be missing.

  • Two implementations. You now maintain the Python and the Rust, and must keep them in sync when the original changes.

  • Toolchain. Every environment needs a Rust toolchain and a build step. Each port is a separate crate, sharing one cache.

  • Benchmarks. The showcase is string-heavy fuzzy matching, a best case for native code. Typical I/O-bound services will see far less.

Failure modes

  • Hidden non-determinism (dict ordering, locale, time) making the original's own recorded answers unstable.

  • Floating-point semantics that differ beyond the 1e-9 tolerance on untested ranges.

  • The original function changing later while the stale Rust port stays enabled.

  • Unicode or encoding edge cases outside the derived set, the class the README's own example caught.

Review checklist

  • Record from production-like inputs, not just a demo run.

  • Add a CI job that re-records and re-verifies the port when the original function changes.

  • Keep the kill switch documented and tested.

  • Benchmark the whole request path, not just the function.

  • Check the function really is pure: no hidden global, time or randomness.
