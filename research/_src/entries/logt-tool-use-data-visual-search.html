Why it matters

"Thinking with images" means a vision-language model (VLM) can call a zoom-in tool to crop part of an image and look again, the way o3-class models do. Recent open work gets there with supervised fine-tuning (SFT) followed by increasingly elaborate, tool-specific reinforcement learning (RL). LogT argues the bottleneck is upstream: the SFT traces are poor. They teach the model to call tools, but not when a call is worth it. Fix the data and a 7B model beats SFT+RL baselines with far less compute. The lesson generalizes to any agent that has to learn when to use a tool, not only vision.

How the data engine works

LogT is a fully automated pipeline in two stages.

  1. Object-oriented question synthesis.

    • Start from high-resolution SA-1B images, which come with unlabeled object boxes.

    • Discard boxes covering more than 1% of the image, so questions target small, hard-to-see objects.

    • A large generator VLM (Qwen2.5-VL-72B) writes questions about one or two specific objects.

    • A filter plus a separate ~106B-parameter judge model reject weak or ambiguous pairs.

  2. Logic-chain-driven trace synthesis. Each question gets a reasoning trace that follows one of three human strategies:

    • Direct answer, with no tool call, when the target is prominent. Questions the 7B base model already answers perfectly fall here.

    • Multi-hop: find an anchor (the person), then zoom to the target (their backpack).

    • Exhaustive search: split the scene into regions and inspect them systematically when nothing points to the target.

The base models (Qwen2.5-VL-7B and InternVL3.5-8B) are fine-tuned on these traces (LogT-SFT). Optionally, a plain RL recipe with no tool-specific design is applied on top.

Tradeoffs

  • Data engineering vs RL engineering. LogT moves effort from reward design and RL infrastructure into a synthetic-data pipeline with a generator, a judge and strategy templates. That is cheaper to run and easier to inspect, but it depends on very large teacher models.

  • It is partly distillation. The 72B generator and the 106B judge supply knowledge the 7B student lacks. Some of the gain is from teacher quality, not only from trace structure; the paper discusses this relationship directly.

  • Calibrated tool use. Including a "don't call the tool" path teaches restraint. Unnecessary tool calls are a known cost and latency problem in o3-style models.

  • Narrow tool surface. The method centres on a single zoom-in tool. Transfer to other tools is reported, but only on a limited set.

Failure modes to watch

  1. Judge-generator collusion. Synthetic questions filtered by another model can share that model's blind spots. Benchmark gains may not reflect real-world images.

  2. Template rigidity. Three fixed strategies may not cover cluttered documents, charts or video frames, where the right search pattern is different.

  3. Under-calling. A model trained to answer directly when confident may skip the zoom on hard cases it misjudges as easy.

  4. Benchmark overlap. SA-1B-derived questions and the evaluation sets can share image distributions, which inflates in-domain numbers.

  5. Teacher licensing and availability. The pipeline assumes access to 70B to 100B-class open VLMs.

Review checklist for teams copying the recipe

  • Do training traces include a no-tool path, with the threshold set by what the student already gets right?

  • Is the judge a different model family from the generator?

  • Are tool-call counts and latency measured, not just accuracy?

  • Is there an out-of-distribution test set (documents, charts, real user images)?

  • Has SFT-only been compared against SFT+RL before investing in RL infrastructure?

  • Are teacher-model licences compatible with the intended use of the student?
