Vendor releases, both public preview.

TL;DR

Two GitHub releases target the same gap: teams change skills, custom agents, tool descriptions and system prompts every week and judge the result by how the next few sessions felt. Copilot Evals is a runner for repeatable evals of that customization layer (not the model), with before-and-after run comparison. The Harnesses view on GitHub's benchmarks site compares Copilot CLI with Claude Code and Codex CLI on the same model at the same reasoning effort, with run-to-run variation and bootstrap intervals. The method is sound; the caveat is that GitHub runs and publishes the comparison of its own product. Treat it as a hypothesis to test on your own repo, which is exactly what Evals is for.

What shipped

Copilot Evals (public preview; Individual, Business and Enterprise plans).

  • Scope: skills, custom agents and MCP tools in your setup. It grades what you wrote around the model.

  • Workflow: ask in natural language or use /eval to create an eval (a realistic task plus a description of a good result), run it, inspect failed checks, and compare runs. Checks cover both the result and how the agent got there. You approve each run before it starts.

  • Engine: Vally, described as an extensible local eval tool. Installed through the VS Code extension, the Copilot CLI plugin or the Copilot app.

  • Intended use: rerun the same eval after changing a skill, agent or MCP tool to catch regressions, since one good answer from a nondeterministic agent proves little.

Harnesses view (public preview) and Terminal-Bench-Science 0.1.

  • Matches exact model pairs at medium reasoning effort across Copilot CLI, Claude Code and Codex CLI; Copilot-only configurations and unmatched results are excluded rather than compared across models.

  • Plots resolution rate against mean cost per task, with ellipses for run-to-run variation and approximate 95% bootstrap intervals on Copilot CLI's resolution advantage and cost savings per model.

  • A new benchmark, Terminal-Bench-Science 0.1, covers research workflows with tasks written and reviewed by domain experts across several sciences.

Tradeoffs

  • Evals measure what you thought to test. The runner and comparison are the easy part; the eval cases are the hard part, and cases written by the skill's author share its blind spots. The costly failures are the ones nobody wrote a case for.

  • A before-and-after delta is a narrow claim. It says whether a change moved the chosen metric on the kept cases, not that the harness is good. That narrow claim is still the first one you can put in a pull request.

  • Controlled design, self-published results. Holding model and effort constant and reporting variance is better practice than most vendor comparisons, but GitHub built the harness, chose the pairs and ran the study. No independent run or audit is claimed.

  • Per-run approval. Safe for evals that execute tools, but it adds friction that makes frequent regression runs less likely.

Failure modes to watch

  • Eval sets that never grow. Without adding a case for each real miss, the suite drifts away from the failures that matter.

  • Small samples. Agents are nondeterministic; a handful of runs per side can't separate a real change from noise. Repeat runs and report spread.

  • Grading only the result. A correct output reached by an unsafe path (wrong tool, skipped check) passes result-only checks; grade the trajectory too.

  • Vendor leaderboards used as procurement evidence. Self-run comparisons should be reproduced on your own tasks before they drive a decision.

Review checklist

  • Does every change to a skill, agent prompt or tool description come with a before-and-after eval run on a fixed case set?

  • Are new eval cases added from real incidents and review findings, not only from the author's expectations?

  • Are runs repeated, with variance reported, before a delta is called an improvement?

  • Do checks cover the agent's path (tools used, approvals, checks run) as well as the final output?

  • Are vendor harness comparisons reproduced on your own tasks before you rely on them?
