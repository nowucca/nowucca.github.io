TL;DR

Kumo Engine is NVIDIA's open-source library for predictive ML on relational data without hand-built features. You declare tables, keys and how they link; the engine stores them as an on-disk graph and, for each entity, samples the related records that existed before the prediction time. A predictive query in a SQL-like language (for example, "will this user place an order in the next 30 days") generates point-in-time-correct training examples, and a built-in graph neural network trains on the sampled neighborhoods. It handles classification, regression, forecasting and recommendation, runs on one machine over graphs larger than memory, and ships an agent skill so coding agents can drive it. Part of the NVIDIA Kumo family, alongside pretrained tabular and relational foundation models.

The workflow it replaces

The usual path for churn, propensity or fraud models is a feature pipeline: aggregate each customer's orders, events and tickets into one wide row, hand-write label logic, and carefully do point-in-time joins so no future data leaks into training. That pipeline is where most of the effort, bugs and leakage live. Kumo Engine removes it: the model reads the raw linked records directly.

How it works

  • Graph built once at ingest. Minimal perfect hashing maps each primary key to a compact integer; foreign keys are resolved once, so following a link while sampling is a lookup, not a join.

  • Bounded, recent context. Each hop samples at most a fixed number of related records, newest first. A binary search finds the prediction time and the sampler reads forward contiguously, so per-entity context has a fixed maximum size regardless of graph size.

  • Disk-friendly batches. Large batches expand one hop at a time, sorted by on-disk position so reads stream through files in order, spread across threads.

  • Larger than memory. Graph files are read-only and memory-mapped; the OS page cache keeps hot pages and threads read without locks. The README asks for local NVMe; network volumes make sampling much slower.

  • Predictive query. One statement (for example, PREDICT COUNT(orders.*, 0, 30, days) > 0 FOR EACH users.user_id) yields the labeled training table and the prediction table, with point-in-time correctness built in.

  • End-to-end: hyperparameter search, explanations, embedding export, batch prediction, MLflow/SageMaker tracking, and connectors for S3, GCS, ADLS, BigQuery, Snowflake and Databricks. Runs on Linux, macOS (Apple silicon) and Windows; production expects an NVIDIA GPU.

Engineering read

  • Leakage control is the real win. Making point-in-time sampling the default removes the most common silent error in tabular ML. Still verify that every table's timestamp means "known at" time, not "event" time; late-arriving data breaks the guarantee.

  • Bounded sampling is a modeling choice. Taking the most recent N links per hop caps cost but can drop older, important signals (a single large purchase a year ago). Check the model plan's sampling settings against the business question.

  • GNNs trade interpretability for less feature work. Built-in explanations help, but stakeholders used to feature importance on named aggregates may find graph explanations harder to act on.

  • Benchmark claims are vendor-reported. The README points to a separate benchmark report for sampling and end-to-end results; compare against a strong gradient-boosted baseline on your own data before switching.

  • Early repo, not accepting contributions, with a Studio UI still prerelease. Treat APIs as unstable.

  • Agent skill is a double-edged convenience. Letting a coding agent build and train models quickly is useful; it also makes it easy to ship a model nobody validated. Keep evaluation and promotion gates human-owned.

Review checklist

  1. Do timestamps on every table reflect when the data was actually available?

  2. Are sampling limits per hop appropriate for the signal you need?

  3. Have you compared against a well-tuned tabular baseline on the same split?

  4. Is the hardware right (local NVMe, NVIDIA GPU) for your graph size?

  5. How are models versioned and promoted, and who signs off before scheduled predictions use a new one?

  6. If an agent built the pipeline, who reviewed the query and the evaluation?
