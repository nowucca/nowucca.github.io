Source: "Turn artifacts into Mac and Windows apps", claude.com product-updates article, 24 November 2026.

What shipped

A generated HTML artifact can be installed as a real desktop application on macOS and Windows — own icon, own window, outside the chat client. No packaging step, no code signing, no API key, no separate login: the installed app authenticates as the user's existing account, and both the work of building it and any model calls it makes count against that account's usage limits. It can reach the user's configured connectors, can be shared with other people, and updates itself when the underlying artifact changes.

In beta on all plans. On by default for Team accounts with the highest permission tier disabled; off on Enterprise until an owner enables it. HIPAA-ready organisations and hybrid deployments are excluded entirely. The app requires the user to be online and signed in to open. Some artifact types — the document, slide and spreadsheet kinds — cannot be installed.

The permission model

Three tiers, each a superset of the last:

TierWhat the app may do
DefaultOnly what it could do in a browser tab
App permissionsAsk for specific host features described as ones the platform "can tightly control": always-on-top windows, listening for global keyboard shortcuts, sending notifications, adding a menu bar or tray item
Full computer accessRun programs, and read, change or delete files, without asking each time

Team and Enterprise administrators can disable the upper two tiers organisation-wide. Full access can only be granted to apps the user made themselves — or, inside Team and Enterprise, apps made by someone in the same organisation. The article states that apps are not reviewed before installation.

The design decision worth studying: consent is versioned

This is the part that generalises beyond this product. A permission grant covers the current version of the app only. After any update — including an edit the user makes themselves — the grant is re-requested.

That is a materially stronger property than the install-time permission model every app store uses, and it is the right answer to the specific risk here. An artifact is not a shipped binary: it is a living document that the model rewrites on request. If consent persisted across rewrites, then granting file-deletion access once would grant it to every future version of a program whose text can change in a single sentence of conversation. Tying the grant to a version makes the grant mean something.

The cost is friction proportional to iteration rate, which for generated software is high. A user who is actively refining an app re-approves on every pass. That is the correct trade, but it is a real one, and it is the kind of trade that erodes: the predictable failure is habituation, where a prompt that appears on every edit stops being read.

Where the guarantee stops, and why it matters most

The article is admirably direct about the hole: if part of an app comes from another website, that part can change without consent being re-requested.

This is the whole security story in one sentence. Versioned consent binds the grant to the app's own content. A script, stylesheet or font loaded at runtime from a third-party origin is not that content, so it sits outside the model. Concretely: an installed app with full computer access that pulls a script from a CDN has an update channel for privileged code that the consent mechanism does not see. The remote origin changes the file, the app runs the new file, and nothing is re-approved — because from the platform's point of view the app did not change.

That is not a flaw in versioned consent so much as the natural boundary of it, and the same boundary exists in browser extension review, in package ecosystems, and in any system that verifies an artifact rather than its transitive closure. It is worth naming because the mechanism's strength invites a false sense of coverage: "I get asked again after every change" is true of the app and false of what the app loads.

Failure modes to design around

  1. Remote subresources in a privileged app. The one above. An installed app that has been granted file or process access should ideally have no runtime dependency on a third-party origin. Nothing in the described model prevents one.

  2. Prompt habituation. Re-consent on every edit is correct and also the condition under which people stop reading prompts. The highest-risk grant is the one made during a fast iteration loop.

  3. Authorship as a trust proxy. Full access is restricted to apps you or your colleagues made. But "made" here means prompted into existence by a model, from an instruction that may itself have been copied from somewhere. Authorship is a weaker signal for generated software than for written software, and the restriction is doing less work than it appears to.

  4. Connector reach. Installed apps can use the user's connectors. An app with default (browser-equivalent) permissions and no file access can still read whatever the user's connected accounts expose. The permission tiers govern local capability; they are not the data-access boundary.

  5. Isolation is undocumented. The article says what each tier allows. It does not say how. There is no process model, no description of entitlements, no account of what "tightly control" means mechanically. For anything beyond personal use that is the first question to answer, and it is not answered here.

  6. Availability coupling. The app will not open unless the user is online and signed in. A locally-installed tool that fails when the network does is a different operational object from a normal desktop app, and worth knowing before someone builds a daily-driver workflow on one.

Review checklist before granting full access

  • Does the app load anything — script, style, font, data — from an origin you do not control? If yes, full access is not safe regardless of the consent model.

  • Does it need process or file access at all, or would browser-equivalent capability do? Most tools in the demo category (trackers, dashboards, viewers) do not need the top tier.

  • Which connectors does it touch, and what do those connectors reach? This is independent of the permission tier.

  • Who actually authored the instructions that produced it, as opposed to who pressed the button?

  • Is the re-consent prompt still being read, or has this app been edited twenty times today?

  • For organisational use: is the policy decision about the feature, or about the top tier? The two are separately controllable, and disabling only full access preserves most of the value.

Why this is interesting beyond the product

It is an unusually clean instance of a general problem: how to grant privilege to software whose text is rewritten on demand. The answer taken here — scope the grant to the exact version, re-ask on change, restrict the highest tier by authorship, and state plainly where the guarantee ends — is a reasonable template for anyone shipping model-generated code into a privileged position. The gap it leaves, remote subresources, is the gap every version-pinning scheme leaves, and it is the thing to close first in any adaptation of the pattern.
