Source: diggerhq/opencomputer (Apache-2.0, about 920 GitHub stars on 2026-11-21) and the makers' launch benchmark post (Zalutski, Habib and Nadiger, 30 Oct 2026), surfaced in a LinkedIn post by André Lindenberg. Vendor claims, not independently reproduced.

The claim

When one engineer runs a coding agent on a laptop for a team, that engineer becomes the relay: copying output into chat, carrying feedback back. OpenComputer moves the agent into the chat thread itself. Someone mentions the bot in a Slack thread with a task, the agent works on its own isolated computer, teammates watch each step, and anyone can steer it mid-task. The result lands as a pull request.

The makers' thesis is that cloud agents have been treated as fire-and-forget background agents only because they were too slow to be interactive. If the cloud session is as fast as a local one, you can keep the tight feedback loop of local work and still get isolation, shared visibility and parallelism.

Architecture

  • One VM per installation, recommended outbound-only network access. It dials out over a websocket to a control plane on Cloudflare Workers and Durable Objects, so nothing inbound needs to be opened.

  • A thin gateway on the VM listens for Slack events and starts one harness session per thread: Claude Code, Codex or OpenCode, chosen by configuration.

  • Per-session isolation with rootless Podman.

  • State goes to the VM's local disk first, then is persisted to a git-backed store.

  • Steering: a message posted in the thread mid-task is delivered to the agent after its current tool call finishes, rather than queued until the run ends.

  • Deployment: self-host on AWS, GCP or Azure, or use the vendor's cloud. Bring-your-own ChatGPT/Codex subscription is supported.

A separate side-by-side against a local Claude Code session on a laptop showed the cloud session as fast or faster, which the authors attribute to being closer to the inference provider.

Read it for what it is: a latency benchmark on a trivial, mechanical task, run by the vendor, with small samples and differing completion rates. It says the session start-up and tool-loop overhead is low. It says nothing about quality on hard tasks. The authors also note some agents refused to redo the task because a closed PR from an earlier round existed, which is memory interference between benchmark rounds and a reason to reset state between trials.

Why the interactivity argument matters

The post's strongest idea is not the speed number but the cost model of feedback. Work done after a wrong turn is wasted, and the waste grows with the time between the mistake and the correction. A slow agent you check rarely does not just cost proportionally more wall-clock; it lets more work pile up on a bad assumption. Making the agent visible to the whole thread and steerable at tool-call boundaries shortens that loop for everyone, not just the person who launched it.

Tradeoffs

  • Steering vs reproducibility. Mid-task messages make runs path-dependent. Two runs of the same task with different interjections will diverge, which complicates evals and post-incident review unless the thread is captured as part of the run record.

  • Shared thread vs single owner. Anyone in the thread can steer. That is the point, and also a governance question: who is accountable for the resulting PR, and can a drive-by comment redirect the agent?

  • Tool-call boundary latency. A steering message waits for the current tool call. A long test run or build delays correction by its full duration; there is no preemption.

  • Single VM simplicity vs scale. One VM is easy to lock down and reason about; concurrency is bounded by that machine unless you shard installations.

  • Harness-agnostic vs harness-specific features. Wrapping Claude Code, Codex or OpenCode keeps you portable, but the gateway can only expose what each harness supports for mid-run input.

Failure modes to plan for

  • Prompt injection through the thread. Slack is now an input channel to an agent with repo write access. Anyone who can post in the channel (including integrations and bots) can steer it.

  • Secret exposure in a shared view. Teammates watching each step will see tool output, including anything the agent prints from env files or logs.

  • State divergence. Local-disk-first then git-backed persistence implies a window where a VM loss drops recent session state.

  • Cross-run memory interference, as the benchmark itself observed: residue from earlier runs changing agent behaviour.

  • Outbound-only is a recommendation, not a default you can assume; verify egress policy on the VM.

Review checklist

  • Who can mention the bot, and in which channels? Is that list narrower than who can merge?

  • Is the full thread, including steering messages, stored with the PR as the run record?

  • Does the session see production secrets? What is redacted from the streamed view?

  • What is the egress policy on the VM, and is it enforced rather than recommended?

  • How are long-running tool calls bounded so steering is not starved?

  • How is session state recovered after VM loss, and what is the worst-case loss window?

  • Are branch protections and required reviews unchanged for agent-opened PRs?

  • If you benchmark it yourself, use your own non-trivial tasks, reset agent memory between trials, and record completion rate alongside latency.
