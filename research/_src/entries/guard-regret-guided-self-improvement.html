The problem

An agent is a frozen model plus an editable harness: prompts, skills, tool rules and memory. Recursive self-improvement (RSI) lets the agent rewrite that harness from experience, with no weight updates. Without an external grader this tends to backfire in three ways:

  • Local overfitting. An edit fixes the failure in front of it and quietly breaks something else.

  • Forgetting. Rules the agent had mastered get rewritten away.

  • Memory pollution. Stale or superseded clauses pile up, or aggressive rewriting adds wrong ones.

The root cause, per the authors, is that reflection and a single scalar score mix up two different things: what an edit newly broke and what was never solved. GUARD separates them.

How it works

During adaptation GUARD runs a four-stage loop. At test time the loop is switched off and one frozen harness runs each task in a single pass.

  1. Self-review via a pre-execution checklist. Before the solver acts, a reviewer reads only the task prompt, tool declarations and schema, and writes a fixed checklist of atomic yes/no predicates. Two classes: execution-verifiable ones (clean sandbox run, valid IDs and columns, idempotent mutations), checked deterministically on a throwaway sandbox copy; and semantic ones (every constraint, recipient, format and safety rule honoured, no superseded rules applied), graded one by one from the prompt, output and tool trace. Writing the checklist up front exploits the gap between generating a long answer and verifying one small claim.

  2. Analyze: paired regret. Compare the two most recent incumbent harnesses on the same tasks. Criteria that went from passing to failing are "hurt" and ranked first; criteria the agent already handles are pinned so later edits cannot drop them.

  3. Propose: group-relative candidates. Generate several candidate edits in parallel and score them on the same tasks, standardizing within the group (the GRPO idea, without a learned critic), so batch difficulty cancels out. The best and worst candidates are contrasted to steer the next proposal.

  4. Gate: Soft-HURT. Promote an edit only when its gains outweigh its regressions beyond a noise floor, scoping specialized fixes so they don't over-trigger. The authors prove non-regression on the gated buffer for their self-review objective.

Results reported

  • On 43 hosted SDK tasks: 80.8% accuracy, 8.89 points above the starting harness (p = 0.008), 6.28 points above Meta-Harness, with 54.5% fewer tokens per task.

  • On a cross-session memory benchmark, unscoped accumulators kept stale clauses on updates, and aggressive rewriters matched GUARD's update correctness (about 0.90) while tripling pollution. GUARD led procedural update correctness at 90.1% with zero procedural pollution.

  • Under hidden drift in continual task streams, pass@1 rose monotonically with no forgetting after each block.

Tradeoffs

  • Adaptation cost moves offline. Parallel candidates, replicates and two-layer grading make each improvement round expensive; the token saving is at deployment, from a tighter frozen harness.

  • Guarantees are relative to the checklist. Non-regression is proven against the self-review objective, not ground truth. A checklist that misses a requirement cannot protect it.

  • Frozen at test time. Good for predictability and audit; the harness only improves in explicit adaptation phases.

  • Needs a sandbox. Layer-1 execution checks assume you can replay tool calls safely on a copy of state.

Failure modes to watch

  • Checklist blind spots. If the reviewer derives the wrong predicates, the whole loop optimizes toward them confidently.

  • Grader drift. Layer-2 semantic grading is an LLM judge; an unparseable verdict counts as failed, which is conservative but can stall promotion.

  • Pinning stale rules. Pinned criteria protect mastered behaviour, but if requirements change, pins need an explicit retirement path.

  • Benchmark scope. Results are on SDK tool tasks, memory write paths and domain reasoning; long open-ended software tasks are not tested.

Review checklist for self-improving harnesses

  • Do you score what an edit broke separately from what it fixed?

  • Are mastered behaviours pinned so edits cannot silently remove them?

  • Is each candidate edit compared against others on the same task batch?

  • Is there a promotion gate with a noise floor, and does it log rejected edits?

  • Can memory updates remove superseded rules, and do you measure pollution, not just accuracy?

  • Is the harness frozen in production, with improvement confined to explicit rounds?
