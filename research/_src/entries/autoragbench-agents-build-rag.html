Source: Zhang, Pan, Zhong et al. (Tsinghua University and Sina Weibo), AutoRAGBench: A Benchmark for LLM Agents Automating RAG System Development, arXiv 2611.25582, 19 Nov 2026. Code and data released on GitHub (ZhanGHanG9991/AutoRAGBench). Surfaced by DAIR.AI.

The question

RAG pipelines are mostly tuning work: choosing indexes, rerankers, query rewriting and context assembly per task, then iterating. Can a coding agent do that job end to end, with no starter code and no prescribed design, and how does it compare with the best published human systems?

Benchmark design

  • Nine tasks spanning open-domain QA (NQ), multi-hop QA (HotpotQA, MuSiQue, MH-RAG), domain QA (PubMedQA, QASPER), fact verification (FEVER) and knowledge-graph QA (WebQSP and one more). Corpora range from a few hundred records to about 21 million passages. Up to 10,000 training and 1,000 test examples per task.

  • Budget: six hours and one H800 GPU per build, in a container. The agent analyses the data, writes the pipeline, installs libraries, downloads auxiliary models and iterates on its own experiments.

  • Rules: retrieve only from the supplied corpus; develop and validate only on the supplied Q&A examples. The test set never enters the container.

  • Audit before scoring: an LLM checks each trajectory and final system for rule violations (for example leaked test answers), with human review of flagged runs. Only runs that pass are evaluated.

  • Retrieval is what is scored. For each test question, five different answering models independently answer from the evidence the system retrieved. That separates the quality of the built retrieval pipeline from the strength of any one generator. Retrieval latency is reported too.

  • Process is measured, not just the final number: development-score curves over the six hours.

  • All nine agent configurations beat naive BM25; seven beat the reference system; all nine beat the composite human baseline. The best agent won seven of nine tasks and ranked first under every answering model.

  • Starting from a human-designed system instead of from scratch, the best agent added 16.6 points on average across seven tasks.

  • Latency is the cost. Every agent-built system retrieves more slowly than the reference: 0.50 to 2.01 seconds per question, 1.4 to 5.8 times the reference's 0.35 s (BM25: 0.10 s). Agents optimised for the score they were given, which did not include latency.

  • What the agents built (81 final systems): mostly classic components, sparse index (63), dense vectors (58), a reranker (58, of which 27 fine-tuned). LLM work at indexing time was rare (three systems), and 33 did no LLM query processing at all. Designs adapted to task: all knowledge-graph systems traversed the graph, QASPER systems ranked within the identified paper, most FEVER systems skipped dense vectors. Strategy labels are from a single coder, not yet cross-checked.

  • Iteration helps but plateaus late. Of 77 builds with at least two versions, median gain from first to last was 5.5 points; 72 improved by at least a point at some stage; median time to first peak was 4.0 of 6 hours. In 20 builds the final version was at least a point below the build's own peak.

How to read it

The strong number is less "agents are better RAG engineers" than "most published RAG systems are not tuned to each dataset, and an agent with six hours of GPU and a dev set is." The human baseline is a composite of published methods, not human engineers given the same six hours and the same dev data. The fair human comparison has not been run.

The design choices are the reusable part: a hidden test set outside the sandbox, an audit gate before scoring, several answering models to isolate retrieval quality, and process curves rather than one final score.

Failure modes

  • Metric tunnel vision. Latency rose up to 5.8x because it was not in the objective. Whatever you leave out of the score, the agent will trade away.

  • Regression at submission. About a quarter of multi-version builds submitted a version worse than their own best. Snapshot and select the best checkpoint by validation, not the last one.

  • Rule violations are common enough to need an audit stage. Without it, test leakage can masquerade as design skill.

  • Dev-set overfitting is likely with six hours of iteration on a few thousand examples. Here the hidden test set guards against it; in your own use, keep a held-out split the agent never sees.

Review checklist for agent-built retrieval

  • Is the test split physically outside the agent's environment?

  • Is latency (and cost per query) part of the acceptance criteria, with a hard budget?

  • Do you keep every version and pick the submission by held-out validation?

  • Does the evaluation use more than one answering model, so a retrieval win is not a generator quirk?

  • Is there an audit of the trajectory for data the agent should not have touched?

  • Is the baseline your current tuned system on the same data, not a published default?

  • Can someone else run the produced pipeline from the repo without the agent?
