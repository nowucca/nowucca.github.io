The problem

Early MCP use at Uber was team by team. Integrations were duplicated, tools were hard to find, and there were no shared security guarantees. Pointing every agent at every service directly would not scale for security or upkeep.

Architecture

Two parts:

  • Control plane: the MCP Registry. A catalog of MCP servers and tools, from no-code wrappers over existing APIs to native MCP servers. It is the single source of truth for what exists and who may use it.

  • Data plane: the Proxy Gateway. Receives MCP calls from agents and executes them against the back end.

Discovery: AutoCrawler

A scheduled Cadence workflow watches Uber's IDL registry and service signals for new services, APIs and schema changes. For each Protobuf or Thrift service it:

  1. Creates or updates a virtual MCP server for the service.

  2. Parses the IDL to get methods, request and response schemas, and doc comments.

  3. Uses an LLM to write tool descriptions, then registers the tools.

Native MCP servers and third-party MCP servers are registered alongside, and teams can author and enable tools in a UI.

Execution

For IDL-backed tools the gateway keeps an in-memory map to the downstream endpoint. It converts the JSON payload to Protobuf or Thrift, calls the service over HTTP, gRPC or TChannel, and translates the reply back to MCP.

Security

  • Authorization at tool granularity, through Uber's access-control system. Policies are set per server with optional per-tool overrides, and apply by caller type: human, service or agent.

  • Built-in redaction of PII and sensitive data from tool responses.

  • Calls are recorded.

Fixing context load

MCP has no cross-server search, and wiring hundreds of servers into an agent would fill its context. Three mechanisms address this:

  • Omni MCP: one proxy server with four tools, discover_server, discover_tools, get_tool_schema and invoke_tool. The agent finds servers and tools incrementally instead of loading every schema up front.

  • Response projection: a GraphQL-like field added to each tool's request schema. The model names the nested fields it needs, and the gateway trims the response to those fields.

  • Code Mode: coding agents call tools through aifx, Uber's CLI (aifx mcp list, search, call), without installing any MCP server, and write results to files they grep. This is now the company default for MCP use in coding agents.

Scale

The blog reports over 800 MCP servers and over 5,000 tools on the gateway.

What to take from it

  • Existing APIs are the fastest source of tools. Generating tools from IDLs, with LLM-written descriptions, beats asking teams to build MCP servers.

  • MCP is the interface, not the platform. Discovery, authorization, redaction and audit still have to be built, and a gateway is where they go.

  • Progressive discovery and output trimming are context controls. Four meta-tools plus field projection keep the agent's context small at any catalog size.

  • For coding agents, a CLI plus files beat in-context tool schemas. Uber made that the default.

Caveats

  • A vendor engineering blog: no numbers on latency, error rates, or how good the LLM-written tool descriptions are.

  • Tool-level policy depends on knowing which caller is which. The identity post Uber links covers that.
