TL;DR

Agents have made writing code fast, so the bottleneck moved to everything after the pull request opens: waiting for review, context-switching back to fix, re-running review, chasing an approver. Claude Ship is Anthropic's attempt to automate that post-PR loop with three cooperating agents on GitHub: Code Review (GA) finds problems, PR Steward (beta) fixes them and keeps the PR green, and Claude Approvals (beta) decides, from a policy file the team checks into the repo, which changes can merge without a human. The design choice worth studying is the separation of duties: the agent that fixes cannot approve, and approval authority lives in versioned policy, enforced through ordinary branch protection.

The three agents

ComponentJobBoundaries
Code Review (GA)Multi-lens review of the PR against the codebase; collects findings, adversarially verifies them, classifies them, posts commentsQuick / Standard / Deep depth chosen per repo; admin sets when it runs and spend limits
PR Steward (beta)Responds to failing CI, merge conflicts and review comments (from Code Review, other tools or humans); pushes fixesExplicitly not designed to approve or merge; comments after each push with what changed and how to undo it; steerable with @claude <instruction>, halted with @claude stop
Claude Approvals (beta)Applies an approval policy written as a file in the repo, like a smarter CODEOWNERS; approves routine changes or demands human sign-off for specified casesActivates only when a policy file exists on the default branch; can consume Code Review findings and natural-language classifiers; recommended to start in observe-only mode before making it a required check

Two entry points: a developer runs /ship in Claude Code (it pushes, opens the PR, reviews, and works feedback and CI), or an admin enables Ship per repository so it runs on every PR without invocation. In both cases what can actually merge is decided by the developer's permissions and the repo's existing branch protection and required checks.

Claimed results

  • On the Claude Code team, where Claude review is one layer of a broader process, merged PRs more than doubled from June to September while the share of PRs later reverted fell by more than 40%. This is a single in-house team, correlated with many other changes (new models, more agent-written code), so treat it as a directional signal, not a controlled result.

  • An anecdote: a PM saw a customer confused by API docs, asked an agent whether a fix was in flight, the agent opened a PR, review found nothing blocking, a docs reviewer signed off, the approval policy passed, and it merged the same evening.

  • Two customer quotes (TELUS Digital, Carvana) describe caught issues and less time spent on review feedback; no numbers.

Cost and availability

  • Team and Enterprise plans, GitHub repositories only.

  • Token-billed: cost scales with PR count and size, review depth, review frequency and how much PR Steward does. Approvals has no base charge, but policy classifiers bill tokens, and a policy that calls Claude's review triggers a billed Code Review even in observe mode.

  • Not available with Zero Data Retention, the HIPAA configuration or customer-managed encryption keys.

Engineering read

  • Separation of duties is the right primitive. Fixer and approver are different agents with different authority, and the approver's authority is a reviewed, versioned file. That keeps the audit question (who allowed this to merge?) answerable by git blame on the policy.

  • The policy file is now security-critical code. Anyone who can change it can widen what merges unattended. Protect it with CODEOWNERS and required human review, and require that policy changes themselves never qualify for auto-approval.

  • Self-review correlation. If the same model family writes the code, reviews it and evaluates the approval classifiers, errors can be correlated across stages. Adversarial verification of findings helps with false positives, not with shared blind spots. Keep independent signals in the policy: tests, static analysis, a second model or a human for risky paths.

  • Agent fix loops need a budget. PR Steward responding to CI and review comments can ping-pong with review. Spend limits cap cost; also watch for fix churn (many small pushes) and for fixes that make checks pass by weakening tests.

  • Reversibility is built in, but only per push. The undo comments are useful; the harder failure is a sequence of individually reasonable pushes that collectively change intent. Reviewers should read the PR diff, not the push log.

  • Observe mode is the rollout path. Run Approvals as an advisory check, compare its decisions to human approvals for a few weeks, and look specifically at false approves on changes that later reverted before making it required.

  • Metric to watch is reverts and incidents, not merge throughput. Throughput will go up by construction.

Review checklist before turning on auto-approval

  1. Is the policy file protected so its own changes always require a human?

  2. Which paths, file types and risk classes are excluded from auto-approval (auth, billing, migrations, infra, security config)?

  3. What independent signals (tests, coverage, static analysis, non-Claude reviewers) does the policy require besides Claude's own review?

  4. Has observe mode run long enough to measure false-approve rate against human decisions and later reverts?

  5. Are spend limits set per repo, and is there alerting on fix-loop churn?

  6. Does anyone audit PR Steward's pushes for test weakening or scope creep?

  7. Do data-residency or retention requirements (ZDR, HIPAA, CMEK) rule it out for some repos?
