The claim

Two practitioners land in the same place from different directions.

  • Iusztin: for most agent-written code, reading every line is wasted effort. Acceptance should rest on clear requirements and acceptance criteria, automated tests, static analysis, type and security checks, realistic environment testing, and investigation of failures. Line review is kept for unfamiliar territory and critical code, not by default.

  • Pocock: test-driven development (TDD) was designed around a human's small working memory, where one failing test reminds you where you are. Agents hold far more context, so the ritual matters less. What matters is the evidence: he asks the agent to prove that its change does what it claims, by showing a test that fails without the change and passes with it. He also warns that agents write tautological tests, which assert the implementation's own constants back at it.

Put together, the reviewer's job moves from reading diffs to auditing evidence. The reviewer checks that the checks are real.

The acceptance pipeline this implies

  1. Spec first. Acceptance criteria are written before the agent starts, so "does what I asked" can be checked.

  2. Fail-without-change proof. For each behavioural change, the agent shows the new or changed test failing on the base revision and passing on the branch.

  3. Test-quality gate. Tautological or implementation-mirroring tests are rejected. Mutation testing or a "revert the fix, does the test go red?" check catches them mechanically.

  4. Static, type and security analysis run as required checks, not suggestions.

  5. Realistic environment run. Integration or staging tests on production-shaped data.

  6. Risk-based human reading. Full line review is triggered by path (auth, payments, migrations, concurrency), by novelty, or by a failed check, not by default.

Tradeoffs

  • Throughput vs latent defects. Skipping line review frees senior time, but tests only catch what they assert. Design flaws, needless complexity and security problems that no check encodes pass silently.

  • Evidence quality is the whole game. If the agent writes both the code and its tests, it can satisfy the gate without solving the problem. A fail-without-change check helps, and independent or human-written acceptance tests help more.

  • Comprehension debt. Code nobody has read is code nobody understands at 3am. Teams that stop reading need another way to keep a mental model, such as architecture docs, generated maps or reviewing the agent's plan instead of its diff.

  • TDD as ritual vs TDD as evidence. Dropping red-green-refactor as a working method is reasonable for agents. Dropping the failing-first test as evidence is not.

Failure modes

  1. Tautological tests pass forever and prove nothing.

  2. Agent edits the oracle: it weakens or deletes a failing test to get green.

  3. Check coverage gaps: no check for performance, accessibility or data privacy, so regressions there are invisible.

  4. "Critical code" not defined in advance, so everything gets waved through.

  5. Flaky tests misread as proof in either direction.

Review checklist

  • Are acceptance criteria written before implementation, and linked from the PR?

  • Does each behavioural change come with a test shown failing on the base revision?

  • Is test-file editing during a fix blocked or flagged?

  • Is there a mechanical check for tautological tests (mutation testing, revert-and-rerun)?

  • Are static, type and security checks required, not advisory?

  • Is there a written list of paths that always get line-by-line human review?

  • Is there a way to keep a shared mental model of code nobody read?
