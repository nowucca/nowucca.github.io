The same newsletter also features Continuous Semantic Caching for Low-Cost LLM Serving (arXiv 2604.20021, MobiHoc 2026), summarized briefly below.

The problem

Mixture-of-Experts models save compute by routing each token to a few experts, but they save no memory: every expert must stay resident on the accelerator. Expert pruning cuts the footprint by dropping experts, but existing methods are static. They calibrate one mask offline and apply it to every request. That fails when one backbone serves a heterogeneous workload, and the clearest case is a multi-agent system, where the same model plays planner, coder, critic and tool-caller at once. The authors' analysis shows different tasks and roles recruit different experts, so one fixed subset is wrong for most of them.

The method

The key finding is that an agent's system prompt and task prompt are enough to predict which experts it will need. That text already says what the agent will do. DEP trains a lightweight predictor once, on transcripts of multi-agent workflows. At serve time it reads the prompts and emits a per-request expert mask in one forward pass, with no per-configuration calibration.

Reported results, across tasks, roles, model scales and MoE architectures:

  • Better overall accuracy than static pruning and expert-merging baselines.

  • Generalizes to workflows not seen in training, without retraining.

  • The margin is largest when few experts are kept. The authors read this as evidence that role specialization in multi-agent systems allows sparser serving than a static mask.

Why it matters for agent platforms

Multi-agent systems are often built on one shared backbone for cost and simplicity. DEP turns the role definition, which already exists in the system prompt, into a serving-time signal. In effect, it is routing at the request level, above the per-token router. Three practical consequences:

  1. Role prompts become capacity hints. Stable, well-scoped system prompts produce stable masks. Vague, catch-all prompts likely produce broad masks and save less.

  2. Placement and batching change. Requests with similar masks can be co-located, which suggests scheduling by role rather than only by arrival.

  3. Memory, not FLOPs, is the target. The win is fitting a large MoE on smaller hardware, or packing more replicas, rather than faster tokens.

Open questions and failure modes

  • Swapping cost. Per-request masks imply loading and evicting experts. The abstract doesn't say how mask changes are amortized across a batch, or what the latency cost is when consecutive requests need different experts.

  • Prompt drift. If an agent's behavior depends on tool results more than on its prompt (a generalist agent that discovers mid-task it needs to write SQL), a mask predicted from the prompt may miss experts needed later in the trajectory.

  • Predictor coverage. The predictor is trained on workflow transcripts. Prompt styles far from that data may degrade it, despite the reported generalization.

  • Evaluation scope. Accuracy is reported against pruning and merging baselines, not against the unpruned model at equal memory. The abstract doesn't give the gap to the full model.

Companion item: continuous semantic caching

The newsletter also features a theory-heavy paper on semantic response caching. Prior schemes assume a finite, known set of discrete queries. This one treats queries as points in a continuous embedding space. It uses a dynamic ε-net plus kernel ridge regression to estimate query costs with uncertainty and share them across semantic neighborhoods. Offline and online algorithms minimize the cost of changing what is cached, and the online one has a sublinear-regret bound. The authors report it approximates the continuous optimal cache with lower switching overhead. It matters for anyone running a semantic cache in front of an LLM, though the paper is from April.

Review checklist: serving many agent roles on one MoE backbone

  • Do you know which experts each role actually uses? Measure routing histograms per role before pruning.

  • Is the pruning mask per deployment, or per request?

  • What happens to latency when consecutive requests need different experts?

  • Does the mask adapt mid-trajectory, or only at the first turn?

  • Is the comparison against the full model at the same memory budget?
