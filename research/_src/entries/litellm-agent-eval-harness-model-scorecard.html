Source: a LinkedIn post by Hao Hoang (Senior AI Researcher, FWD) on a LiteLLM tool he calls Lens CLI, alongside LiteLLM's agent evaluation guide and its launch post by CTO Ishaan Jaffer (16 Nov 2026). Both docs mark the API as an unreleased preview: the code is on LiteLLM's main branch but not in a PyPI release.

What it is

Teams usually pick a model on purpose and inherit the agent harness by accident. LiteLLM's new evaluation layer makes the pair (harness, model) the unit you compare. You declare tasks with success checks once, list the targets, and get one scorecard with pass rate, cost and duration per target.

  • EvalTask: an id, a prompt, optional starting workspace directory and setup commands, and a check.

  • EvalTarget: a harness (Tool Loop, Claude Code, Codex and others; the post also lists OpenCode, Pi and Deep Agents, and a single run function for your own agent), a model routed through a LiteLLM gateway, and a label.

  • Checks: PredicateCheck (a Python function over the typed result, including tool calls), JudgeCheck (a rubric graded by a named judge model that returns JSON) and CommandCheck (a command run in the same sandbox after the agent; exit 0 passes).

  • Runner: litellm.agent_eval() or the async aagent_eval(), with trials, max_concurrency, per-stage timeouts and a mandatory sandbox factory (local or a Docker image per attempt).

The post describes a terminal front end (tasks in a CSV, checks and configurations in a Python file, one lens run command, reports written locally) and a saved demo run of 24 synthetic legal-QA tasks across 3 harnesses and 4 models. In it, the same small model passed 24 of 24 through one harness and 22 to 23 through two others, and the tool recommended the cheapest setup within five points of the best pass rate. That CLI and the demo numbers are the post's account; the public docs describe the Python SDK only, and the post itself says the CLI is a private preview needing a Lens-enabled gateway.

Design choices worth noting

  • Errors count against you. Pass rate is passed runs over scheduled runs, so a missing runtime, timeout or failed judge call stays visible instead of silently shrinking the denominator.

  • A run passes only if the agent stops with done and the check passes. Finishing a turn is not success; the runner skips grading if the agent hit a turn limit.

  • Fresh workspace per attempt, copied from the task's directory with .git excluded. Symlinks anywhere in the workspace are rejected before a sandbox is created, which closes an easy escape from the copy.

  • Cost honesty. Agent spend and judge spend are separate columns, and a metrics_complete flag says whether any usage was unavailable.

  • Gateway correlation. Every model request carries suite, run, task, target and trial metadata, so existing gateway logs can be joined to the scorecard.

Tradeoffs

  • Small task sets can't rank close setups. As the post notes, on 24 tasks one task is about 4.2 points, so 22 vs 24 passes is within noise. Hundreds of tasks and several trials are needed before a recommendation means much.

  • Changing harness and model together confounds the result. The launch post itself warns to hold one fixed where possible.

  • Judge-graded tasks inherit judge bias; the judge sees the prompt, answer and diff but not the rest of the workspace.

  • Local sandbox runs with your permissions; CLI harnesses belong in a container.

  • Gateway lock-in. Models go through a LiteLLM gateway; that is the point (one place for keys, routing and spend) but also a dependency.

Failure modes to watch

  • Synthetic tasks that don't resemble production work, producing a confident but irrelevant winner.

  • Checks that are too loose (predicate on a substring) or brittle (exact match on free text).

  • Flaky harness runtimes showing up as model failures; read the error rows first.

  • Comparing cost totals when metrics_complete is false.

  • Treating a one-off scorecard as permanent: a model or harness upgrade invalidates it.

Review checklist

  • Are tasks drawn from real work, with at least a few hundred cases for close calls?

  • Does each check verify the outcome (tests, file state) rather than surface text?

  • Are trials at least 2 to 3, and is variance reported?

  • Is only one variable changed per comparison?

  • Are error rows inspected before reading pass rate and cost?

  • Do CLI harnesses run in containers, not sandbox.local?

  • Is the scorecard JSON stored with the model and harness versions so it can be re-run on upgrade?
