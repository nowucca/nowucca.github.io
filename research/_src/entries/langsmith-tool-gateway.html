Source: LangSmith Tool Gateway: Secure, governed tool use for agents (LangChain blog, Karthic Subramanian, 2026-11-19). Public beta.

The problem it targets

Agents are moving from chat to scheduled and event-triggered work, running long tasks without a person checking each step. Tool use then becomes a governance problem with three parts: which tools an agent may call and with whose credentials (access), what each user may do with it and when a human must approve (control), and a record of what was called as whom (visibility).

The usual shortcut is to hard-code all three per agent: an OAuth flow per provider, tokens stored next to the agent, routing added for each new tool. The post's customer example shows why that breaks: a retailer with 50+ MCP servers exposing over a thousand tools, a store assistant acting with each associate's credentials, and a 3 a.m. inventory agent acting with its own. Handing either agent a whole tool server leaves no deterministic check against the wrong credential or an unapproved tool, and no audit trail.

Architecture

Agents, coding agents and backends call one URL. For each call the gateway resolves identity, applies access and policy, and logs a trace.

  • Register once. Add any MCP server by URL, or enable a built-in hosted server (Google, Microsoft, Salesforce, GitHub, Linear and others; some use LangSmith-managed OAuth, some an API key).

  • Tool kits. A curated subset of tools published at its own URL, shared to a workspace or kept personal. An agent connected to a kit sees only that kit's tools.

  • Search mode. For large kits the agent queries the kit and loads only relevant tool definitions, instead of every definition up front.

  • Two identities per call. As the user: the identity provider (Okta, Entra ID) identifies them, they connect an account once, and later calls use their access; if not yet connected, the call returns a sign-in link and resumes after auth. As the agent: agent auth or a shared-credential profile an admin connects once, for background agents.

  • Policies. Deny rules by user, service key or combination, at org or workspace level, with exceptions. Approval rules require the user to confirm a sensitive call (for example a data-warehouse write) in their MCP client before it runs.

  • Visibility. Each call's tool, server, user, outcome and duration is recorded inside the agent's own trace; call payloads are not stored. Enterprise plans add an audit log of which tool ran as whom.

Tradeoffs

  • Central choke point. One gateway makes policy consistent and auditable, and also becomes a dependency on every tool call: latency, availability and blast radius all concentrate there.

  • Managed OAuth removes per-provider plumbing but places long-lived user grants with a third party.

  • Payloads not stored protects sensitive data but limits forensics to metadata.

  • Kit scoping is only as good as the kit design; a broad kit recreates the original problem.

Failure modes to watch

  • Shared profiles for background agents drift toward over-privileged service accounts.

  • Approval fatigue if too many tools require confirmation; users start approving blindly.

  • Sign-in links returned mid-run can stall unattended agents or invite phishing-style prompts if links are surfaced carelessly.

  • Search mode can hide a needed tool or surface a risky one, depending on the query.

  • Beta status: behaviour and limits may change.

Review checklist for a tool gateway

  • Does each agent see a minimal kit, not a whole server?

  • Is every call attributed to a specific human or a named agent identity?

  • Which writes require approval, and is the approval recorded?

  • Can you answer "what did this agent call at 3 a.m., as whom" from one record?

  • What happens to agents when the gateway is down?

  • How are shared credentials rotated and scoped?
