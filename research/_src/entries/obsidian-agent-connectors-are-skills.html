Obsidian has published an official "Connectors" page offering its app to any AI agent, naming Claude, ChatGPT, Antigravity, Cursor, GitHub Copilot, Grok Bot, Hermes, Kiro, Muse and OpenCode among others, with official plugin listings in several of those directories. The interesting part for an engineer is what a connector turns out to be: not a server, not a protocol integration, but a bundle of seven Agent Skills — markdown instruction files following the Agent Skills specification — published open source.

Architecture

There is no daemon, no index and no network component. The bundle splits cleanly into two kinds of thing:

Format documentation (three skills). obsidian-markdown describes Obsidian Flavored Markdown: wikilinks, embeds, callouts, properties. obsidian-bases describes the .base file format with its views, filters, formulas and summaries. json-canvas describes .canvas files as nodes, edges, groups and connections. In the vendor's own words these "only describe file formats", so they work in any agent that can already read and write files in the vault. The skill contributes knowledge; the file access comes from somewhere else entirely.

Tool drivers (four skills). obsidian-cli drives the running desktop app through Obsidian CLI, including plugin and theme development. obsidian-headless syncs and publishes vaults without the desktop app. defuddle extracts clean Markdown from web pages. knap renders Markdown templates from JSON or CSV. Three of these four shell out to tools that are not bundled; the skill asks before installing one from npm.

Distribution is per-agent rather than universal: a plugin directory listing for some agents, a CLI install command for others (agy plugin install, hermes plugins install obsidian, kiro-cli powers install obsidian), npx skills add for the rest, and for a stubborn agent, copying the skill folders into its skills directory by hand. One release archive exists purely because one agent's CLI only picks an asset when a release has exactly one file attached.

The capability boundary, which the marketing crosses

This is the part worth being precise about, because enthusiastic write-ups of this release have claimed that every listed agent "can now read your vault". What the vendor's page actually establishes:

CapabilityWhat it actually requires
Read and write notes, bases, canvasesThe agent must already have filesystem access to the vault directory. The skill supplies syntax knowledge only.
Search and manage notes in the running appObsidian desktop running, Obsidian CLI turned on, and an agent that can run shell commands on that computer.
Sync and publish a vaultObsidian Headless, a separate tool, installed.
Web extraction, templatingDefuddle or Knap installed from npm.

A cloud-hosted agent with no filesystem and no shell gains nothing from the first three rows. The page says so directly about one of the named agents: it runs in a vendor's cloud, so the CLI skill does not work there, and using Headless means signing in and syncing the vault into that cloud instead.

Tradeoffs

Skills over a server. Shipping format knowledge as instructions means no process to run, no version to keep compatible and no transport. The cost is that every capability is borrowed: the agent's existing file access, the agent's existing shell, the user's existing desktop app. Nothing is enforced by the integration, because there is no integration — which also means no place to put a permission boundary.

The honest privacy position. The page states that connectors send nothing by themselves, and immediately states the consequence: when an agent uses them, the notes it reads become part of the conversation and are processed by whichever model the user chose. It tells readers to check their agent's privacy policy before pointing it at sensitive notes. A local-first app whose vendor writes that sentence down is being straight; a reader who summarises this as "total ownership of your data" has inverted it. Local storage of the file and local processing of its contents are different properties, and a vault-reading agent breaks the second while preserving the first.

No memory, no retrieval, no token saving. There is no store, no embedding, no index and no cache anywhere in the bundle. Claims that the connectors give an agent searchable local memory or reduce token use do not correspond to anything in the sources: instruction skills add tokens to a context window. The only search is the agent shelling out to the CLI against the live app.

Portability as the real product. The genuine win is that one open-source bundle targets ten-plus agents because they all consume the same skill format. That is a bet on an emerging specification rather than on a protocol, and it is a bet a document app can afford: the formats are stable, so the instructions age slowly.

Failure modes to design against

  • Assuming the skill grants access. Installing a skill in an agent that cannot touch the filesystem produces an agent that knows the syntax and can do nothing. Users read "connector" and expect a connection.

  • The full-vault blast radius. Once an agent has file access to a vault, skill-level scoping is advisory. A vault that mixes a public knowledge base with private material has no boundary an instruction file can enforce.

  • Write corruption in structured formats. Bases and Canvas are structured files. A model writing them from a format description, with no schema validation step, can produce a file the app refuses or silently misreads. There is no validator in the bundle.

  • Unbundled dependency installs. A skill that offers to install an npm package mid-task turns a documentation bundle into a supply-chain surface. The prompt before installing is the only gate.

  • Divergence across ten agents. One bundle, many host runtimes, each with its own skill loader, path conventions and tool permissions. A behaviour verified in one agent is not verified in the others, and the per-agent install instructions are already a sign of that drift.

  • Instruction files as an injection path. Skills are text the model follows. A vault whose notes are partly untrusted (clipped web pages, shared notes) is a directory of model-readable instructions sitting next to a model with write access.

Review checklist

Before adopting an agent-skill bundle for a local document store:

  • Which capabilities does the skill supply, and which does it assume the agent already has?

  • Is the vault path scoped to the subset the agent should see, by the agent's own permission system rather than by the skill text?

  • Is there a validation step for structured files the model writes, or does the app's parser serve as the only check?

  • Does any skill install software, and is that prompt actually surfaced to the user?

  • Which of these skills work in the hosted agent your team uses, with no shell and no filesystem?

  • Have the notes the agent will read been assessed as trusted input?

  • Is the privacy story about where the files live, or about where their contents are processed? Say which one your users are being promised.
