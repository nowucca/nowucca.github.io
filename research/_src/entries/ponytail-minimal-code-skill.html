What it is

Ponytail is one prompt, packaged as a skill (and a compact AGENTS.md for agents that read a rules file), that pushes a coding agent toward the smallest complete change. The rest of the repo is installers for about 20 agent hosts (Claude Code and Codex plugins, Cursor hooks, plain copy-in for others) plus commands: /ponytail-review (diff review), /ponytail-audit (whole-repo review, ranked), /ponytail-debt (collects deliberate shortcut: comments into a ledger) and, in Claude Code, a status band showing per-task cost, tokens, agent time, reuse rate and last test result, stored locally.

The mechanism: a reuse ladder after reading

The skill tells the agent to first read the task and the code it touches, list every place the change must reach (callers, tests, fixtures, config, exports), and only then pick the first rung that fully works:

1. Does it need to exist?          -> skip unrequested features, name them
2. Already in this codebase?        -> use the helper/component as neighbours do
3. Standard library / platform?     -> use it (house component beats native widget)
4. Installed dependency?            -> use it; never add a dep for a few lines
5. One readable line?               -> one line
6. Otherwise                        -> minimum code that works
   + one small test if it has a branch, loop, parser, money or security

Hard floor: never cut trust-boundary validation, data-loss error handling, security, accessibility, or anything the user asked for. Every reply ends with what was skipped or not checked. Deferred shortcuts get a structured comment (shortcut: <limit>, <when to upgrade>). Three levels: lite (build what was asked, name the smaller option), full (default), ultra (push back on the request itself).

The canonical example: asked for a date picker, an unprompted agent wrote about 335 lines (library or hand-built calendar); with the skill it combined the repo's existing Input component with the browser's native date input in about 10.

The benchmark, and how much to trust it

Same agent (Claude Code on Opus 5.5) with and without the skill, 39 tasks including a real FastAPI + React repo, 5 runs each. Reported deltas for v5: 53% less code, 41% less time, 26% lower cost, 45% fewer tokens, and 98% of risky logic shipped with a test versus 68% without. Task mix includes reuse tasks, six security tasks (SQL injection, path traversal, forged tokens, rate limiting, malformed CSV rows, caching), a privacy task, rename/format changes that must reach every caller, and open-scope "build me an app" requests.

What the results file itself concedes, which is to its credit:

  • On the security tasks all arms passed 30 of 30. Less code did not cost safety, but it did not add any either.

  • The privacy task was hard for every arm (2 of 5).

  • Completeness was scored by a blind LLM judge (0 stub to 3 full); one run was manually re-scored because the judge only saw the diff.

  • In a blind reply-quality comparison against no skill there was no significant difference (slight lean to the longer no-skill replies); the clear win was over the previous Ponytail version, mainly for the closing "what I skipped" line.

Staff-level read: this is a well-run self-benchmark, not an independent one. The maintainer chose the tasks, the hidden checks and the judges, and many tasks reward reuse by construction. The cost and code-size wins are plausible and mechanically explained; the test-coverage delta is the most interesting number and the one most worth reproducing on your own repo.

Tradeoffs

  • Reuse vs coupling. Rung 2 (use what the codebase already has) is right most of the time, but reusing a helper that is subtly wrong for the new caller spreads a bug. The skill's "grep every caller, fix the root cause once in shared code" rule cuts both ways: a shared-code fix has a larger blast radius.

  • Native platform vs product consistency. Native widgets (date input) are small and accessible but look and behave differently across browsers. The skill already says a house component beats a native one; check that your design system is discoverable enough for the agent to find it.

  • Smaller diffs vs hidden scope. "Skip what nobody asked for" is good against gold-plating, but under-specified prompts can yield an MVP when a fuller feature was implied. The lite level, which names the smaller option and lets the human choose, is the safer default for vague tickets.

  • One prompt, many hosts. Behaviour depends on how each host loads and prioritises skills; numbers from Claude Code need not transfer to Cursor or Codex.

Failure modes to watch

  • Over-reuse: the agent bends an existing abstraction to fit, adding flags to a shared function instead of writing ten clear lines.

  • Golfing despite the rule: dense one-liners that are short but slow to review.

  • Silent scope cuts: features dropped and only mentioned in the closing line, which busy reviewers skim.

  • Shortcut ledger rot: shortcut: comments accumulate if nobody runs the debt harvest.

  • Supply chain: the README warns that only the named GitHub repo and npm package are genuine; plugin marketplaces make typo-squats easy.

Review checklist for adopting a minimal-code skill

  • Run it on your own repo with and without the skill on 10 to 20 real tickets; compare diff size, review time, defects found later and test presence, not just tokens.

  • Check that reused code was actually fit for the new caller (read the reused function, not just the diff).

  • Make the "skipped / not checked" line a required PR-description field so it is not lost in chat.

  • Decide the default level per repo: lite for product work with vague specs, full for internal tooling.

  • Pin the plugin version and source; review the prompt diff on upgrade like any dependency.

  • Wire shortcut: comments into your existing tech-debt tracking or turn them off.
