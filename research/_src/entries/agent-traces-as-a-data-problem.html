Source: "The Agent Lake", Sam Crowder, LangChain blog, 24 November 2026. Vendor material describing the vendor's own product.

The premise

Agent traces are the system of record for what an agent did, and the volumes are now such that reading them one at a time has stopped working. The published figures: traces from billions of agent runs per month across the platform, with one named customer sending hundreds of millions of events per day, and the platform's automated issue-finder having analysed more than 60 million production traces.

That is a data-engineering problem rather than an observability one, and the post's framing — that this needs its own storage and its own compute, rather than being pointed at a general-purpose lakehouse — is the thesis. Be aware that the thesis is asserted rather than argued: the only alternatives named are two general data-lake vendors, and the stated reason is simply that they lack storage and compute "optimized for this agent data". No technical reason is given, and the post does not discuss warehouses, OLAP engines, observability vendors or vector stores at all.

The genuinely useful idea: outcomes beside traces

The clearest technical contribution is the data model, and it is worth separating from the product.

Three entity types. Traces, the record of a single run. Threads, grouping traces for multi-turn conversations. And outcomes — thumbs up and down, merged pull requests, judge scores, labels from an annotation queue — which map one-to-one or many-to-many onto threads and traces.

The argument is that outcomes belong in the same store as the traces, because every downstream use depends on joining them. Finding the best trajectories to fine-tune on, finding the failures worth fixing, and building an evaluation set out of real traffic are all "filter traces by outcome" queries. In most stacks the trace lives in the tracing tool and the outcome lives somewhere else — a product analytics table, the CI system, a spreadsheet of human labels — and that join is a manual export. Co-locating them is a small idea with a large effect on what is cheap to ask.

Query model

Structured queries and natural-language search, combinable. The natural-language path runs a small classification model over search results to apply a semantic filter; the examples given are "threads where the user got frustrated" and "traces that contain PII". The structured path filters on feedback that online evaluators have already written onto traces.

The post is explicit about the limitation this creates, and it is the right thing to be explicit about: online evaluators have to be defined up front, so anything you want to filter on structurally requires having decided in advance that it mattered. The post calls this "one downside". The semantic-search path exists precisely to cover the questions you did not anticipate, at the cost of running a model over the result set rather than using an index.

The improvement loop

Four named components, all described as shipped:

ComponentWhat it does
Online evaluatorsTuned prompts for hallucination, toxicity and user satisfaction; cheaper small classification models offered as an alternative to judge models
InsightsGroups recent traces into categories and keeps sorting new conversations into them, to surface traffic trends
EngineScans traces on a schedule, groups recurring failures into issues, and — with a repository connected — diagnoses root cause and proposes a fix as a pull request; since its second version it tests the fix against an evaluation set first
Tuning CLIFine-tunes a model on the best trajectories via one of two hosted training providers, then compares the result against the base model

The loop as claimed: filter traces and outcomes down to the high-signal items, then spend them on fixes, evaluations and fine-tuning. Note what is not claimed — the store does not generate datasets; the fine-tuning corpus is just the traces it already holds, filtered.

The eval-gated pull request is the piece most worth copying regardless of vendor. An automated fix proposal that has already been run against an evaluation set is a materially different artifact from one that has not, and the gate is cheap to add to any pipeline that already has both.

What is measured, and by whom

One benchmark is published: an internal benchmark for detecting and grouping issues in traces, run on a subset. A small open-weight model fine-tuned on the vendor's own tuning path scored 96; the same base model scored 90; a frontier model scored 87.

Every element of that comparison belongs to the vendor — the benchmark, the task definition, the training data (trajectories from one of its own agents), and the product being validated. The direction of the result is plausible, since a model fine-tuned on in-distribution trajectories for a narrow classification task beating a general frontier model is an ordinary finding. The magnitude should not be carried anywhere. There are no latency, throughput, storage-size or cost figures anywhere in the post.

Where the detail stops

For anyone evaluating this as an architecture rather than as a product, the gaps matter:

  • The storage layer is named but not described. The post attributes storage to a purpose-built trace database and links elsewhere for it. No format, no schema, no account of how deeply-nested trace data is laid out. No mention of columnar formats, table formats or object storage.

  • No query engine is named, and no query language or API is specified.

  • Indexing is unspecified — whether full-text, vector, both or neither.

  • Retention and tiering are not mentioned at all, which for a store taking hundreds of millions of events a day is the first question a platform team will ask.

So the post gives a data model, a component list and a workflow. It does not give a storage design. Both halves of the headline claim — storage optimised for traces, and intelligent compute over them — are substantiated only on the second half.

Review checklist, if you are building this yourself

  • Can you join a trace to its outcome in one query today, or is that an export? If it is an export, that join is the thing to fix first, independent of any product choice.

  • What are your outcome sources, and do they all land somewhere queryable? Merged-PR signals and human labels are the two most often stranded.

  • Which signals must be evaluated online, accepting that you have to name them in advance, and which can wait for a retrospective pass over stored traces?

  • What does a judge-model evaluation on every trace cost at your volume? The post's own answer is that it is expensive and that cheaper online evaluation remains an open research problem for them — which is a vendor admitting the economics are unresolved.

  • Who decides what a finding means and what changes? The post concedes someone still has to, and offers no evidence on how well the automation covers it.

  • What is your retention policy, and does your analysis window outlive it? An improvement loop over traces you have already deleted is not a loop.
