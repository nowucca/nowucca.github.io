TL;DR

Anthropic's The components of agent memory (Lance Martin, 6 Nov 2026), surfaced by Elvis Saravia's LinkedIn post, splits agent memory into four layers: transcripts, notes the agent writes, derived representations such as wikis, and a small injected layer loaded every session. An offline pass called dreaming reads transcripts to correct notes, build wikis, and promote or demote what gets injected.

The findings that matter for builders:

  • Memory helps strong models a lot, weak ones little. On a CL-Bench database task, memory lifted Opus 5 from 0.564 to 0.828 mean reward; Sonnet 4.6 only went from 0.330 to 0.364.

  • Say what memory is for, not how to use it. A fixed rule ("record only failures") cut Opus 5's memory gain by 0.234. Explicit read-then-test prompting nearly doubled Sonnet 4.6, so steering is for older models.

  • Less is more. In Pokemon Red, Sonnet 3.7 wrote 413 files and earned 1 badge; Fable 5 wrote 10 files (43K chars) and earned 4. Store what the environment won't tell you again: plans, tested rules.

  • Dreaming fixes wrong notes. A note corrected against the transcript got Claude past Mt. Moon; the uncorrected and no-memory runs never did.

  • Wikis pay off on cross-document questions, with search beside them. Wiki + search reached 61% vs 53% for search alone and saved about 20K tokens per question; on single-document lookups the wiki added nothing, and one wiki grew to 1.77x its corpus.

  • Keep the injected layer tiny. Claude Code's auto memory loads only the first 200 lines or 25 KB of MEMORY.md, as an index.

Saravia's own take: keep memory "extremely basic" (folders and files plus some episodic layer), and expect to keep upgrading it.

The memory hierarchy and dreaming

Memory here means knowledge Claude gains from experience and keeps between sessions as readable context. It excludes weight updates, in-context learning and compaction.

The session writes notes and logs transcripts; only the top layer is loaded automatically, the rest is read or searched when needed. Dreaming, borrowed from sleep-time compute (Letta and UC Berkeley) and the hippocampal replay analogy, runs offline and does four jobs: correct notes against transcripts, build representations such as wikis, promote a few items into injected context while pushing detail down, and fill gaps no single session could see (dangling links, duplicates, a missing index). It can also be aimed at a goal, for example organizing memory around the person an assistant serves.

Tradeoffs and failure modes

The article is candid that the design questions are open. The ones a builder has to decide:

  • When to write. In-session notes capture salience at the source but pull attention from the task. Dreaming moves the work offline, but its output isn't available until the pass runs.

  • Wrong notes are trusted. A note can be wrong at birth or drift as the world changes, and a later session will rely on it. Dreaming against transcripts is the fix, but checking every note is too expensive; target notes likely to change, or set cadence by access frequency.

  • Representations cost upkeep and can hallucinate. A wiki needs compute to build and maintain, can accumulate errors, and can grow past its source (the Borges map). Transcript search is a reasonable foundation on its own.

  • The injected layer is the expensive one. It costs tokens every call, carries any error into every session, and longer instruction files reduce adherence. Dreaming's main job at the top is pruning: push detail down and leave a link. A commenter on Saravia's post adds the caching angle: a small, stable injected prefix is nearly free under prefix caching, so churn there costs latency as well as tokens.

  • Hoarding. Writing everything turns memory into the task (Sonnet 3.7 spent 17 steps reorganizing files with no game actions).

  • Concurrent writers. Several agents editing one shared page overwrote each other and lost 28% of graded facts. Partition ownership: one writer per page.

  • Over-specified memory policy. Fixed rules about what to record cost strong models most of their gain.

  • Payback is unmeasured. Another commenter notes the 20K tokens saved per question has to repay the build and refresh cost; the article gives no cost per correct answer at realistic query and update rates.

Review checklist

Questions to ask of any agent memory design:

  1. Are raw transcripts kept and searchable? They are the ground truth every other layer is checked against.

  2. Is the injected layer bounded (lines or bytes) and written as an index that points down, not as content?

  3. Does memory guidance state the purpose and leave salience to the model, with procedure added only for weaker models?

  4. Does each stored rule say how it was verified, and are unconfirmed facts marked as such?

  5. Is there an offline pass that checks notes against transcripts, and is it targeted at volatile notes rather than everything?

  6. Is anything stored that the environment re-reveals every turn (state on screen, file contents, positions)? Drop it.

  7. Does any derived representation (wiki, graph) sit beside search rather than replace it, and is its size tracked against the source?

  8. Is the representation justified by the workload: cross-document synthesis, judgment or arithmetic, rather than single-document lookup?

  9. Does each shared page have one writer, with source terms quoted rather than summarized when exactness is graded?

  10. Is there a second pass for dangling links, duplicates and a missing index?

  11. Is the build and refresh cost compared against tokens saved per query at realistic volumes?
