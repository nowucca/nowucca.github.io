Source: Alex L. Zhang, Souradip Chakraborty and Omar Khattab (MIT CSAIL), Language Model Harnesses can be Compositional Generalizers, arXiv 2611.28298, 20 Nov 2026, highlighted on LinkedIn by DAIR.AI. It builds on the authors' earlier Recursive Language Model (RLM) work, including a July 2026 research post on short-to-long generalization with a 30B model.

The claim

Standard agent harnesses keep appending tool output, history and reasoning to the prompt, so as a task gets longer every model call sees an input less like anything it was trained on. The network is forced to generalize to that drift, which makes training for long-horizon tasks expensive. The paper argues for the opposite design: a neurosymbolic harness that keeps task data in a program environment and splits work into sub-calls, so each individual model call stays locally in distribution even when the overall task is new.

How an RLM harness works

  • Context offloading. The long input lives as variables in a code environment (a Python REPL in the RLM line of work). The root model inspects it with code instead of reading it all.

  • Programmatic sub-calls. The root model calls itself or sub-agents as functions on slices of the data; their outputs stay in program memory rather than being appended to the root prompt.

  • Effect. Tasks with different surface text but the same decomposition produce similar root trajectories, so a learned strategy transfers.

Results reported in the abstract

  • Length generalization. RLMs trained with RL only on short tasks generalize to tasks 2 to 64 times longer, while the same base model trained directly improves less.

  • Cross-domain transfer. Training on one domain transfers to new domains that share latent structure (for example the same aggregate, filter or rank pattern).

  • Surrogate harness training. For messy, complex tasks where full trajectories are expensive, they train individual calls inside the harness on easier synthetic environments with fake tools and fake sub-calls.

  • RLM-27B. Trained this way on synthetic data, it improves Qwen3.8-27B in the same RLM harness by 26.9% on average on hard long-context suites such as CTC-Bench and ExpertLongBench, using about 2x fewer inference tokens.

  • Composition. Harnesses can compose newly learned decompositions through recursive sub-harness calls.

Why it matters for system design

It moves part of the generalization problem from the weights to the control program, which a team can change and audit. The practical design rule is: keep each call's input looking like training data, and keep large state outside the prompt. It also suggests a cheaper training recipe: if long trajectories are too costly, train the per-call skills on short synthetic tasks first.

Tradeoffs and limits

  • Training is slower per sample. The earlier RLM post reported 1.5 to 3x longer training on similar-size tasks because of multi-step rollouts and sub-call waits; the advantage grows only as tasks get long.

  • Shortcut decompositions. If a short task can be handed whole to one sub-call, the harness may learn a shortcut that fails at length; decomposition prompts or process supervision may be needed.

  • Locality is a goal, not a guarantee. The root model can still pull task-specific data back into its context.

  • Evidence scope. Controlled benchmarks and a small number of base models; no production cost, latency or reliability data, and no controlled comparison against commercial coding agents.

  • Latency. Recursive calls add wall-clock time unless sub-calls run in parallel.

Failure modes to watch

  • Root prompts that slowly accumulate data anyway, reintroducing drift.

  • Sub-call outputs that are too large and get pasted back into the root context.

  • Synthetic surrogate environments whose fake tools behave unlike the real ones, so per-call skills don't transfer.

  • Reading short-task training reward as proof of long-task capability, which the paper shows is unreliable for direct training.

Review checklist

  • Does the harness keep large inputs and tool outputs in program state rather than in the prompt?

  • Can you show that a typical call late in a long task looks like a typical call early on?

  • Is there a held-out set at several times the training length?

  • Are surrogate environments validated against the real tools?

  • Is wall-clock and token cost tracked alongside accuracy?

  • Is there a guard against single-sub-call shortcuts?
