Kiran Prakash (Thoughtworks) argues on martinfowler.com (2026-11-10) that an agent which runs for weeks is a distributed system, so a durable execution runtime should absorb crashes, retries and long waits, while the harness keeps everything that needs business judgment.

The argument

The running example is a purchasing agent that keeps one SKU in stock. A replenishment takes weeks: it gathers quotes, drafts a purchase order, waits days for a manager's approval, places the order, then waits on the supplier. The agentic loop is ordinary (ask the model, run the tool it picks, repeat); what breaks it is time. A process restart, a flaky ERP call or a seven-day wait all kill an in-memory loop.

Durable execution fixes the generic part. The runtime writes each step's input and output to a log before the next step runs; a step is any call to the outside world (model call, ERP call, supplier message), and code between steps only touches local state. After a crash the program restarts from the top, recorded steps return their saved results, and the first unrecorded step runs for real. In the article's words, the runtime "keeps a record of the result of each step that interacts with the outside world" so completed steps are skipped and state is rebuilt from the record.

The second half is the useful part: durable is not the same as correct. "A persistent log records what the agent saw, not what actually happened." The runtime gives at-least-once retries, crash-safe waits and one workflow per entity. It cannot know that a timed-out call actually placed an order, that a quote went stale during a week-long wait, that the code changed under a running task, that the history has outgrown the context window, or that a supplier email is trying to steer the agent. Those stay with the harness, written as deterministic code around the model.

The prior art is old and the article names it: Write-Ahead Log, Event Sourcing, Actors and Erlang's receive ... after, Idempotent Receiver, Sagas, Optimistic Offline Lock, Parallel Change. The claim is that agents are distributed systems plus a non-deterministic component, and those patterns apply almost unchanged.

How it works

One entity workflow per SKU owns a child workflow per replenishment. Waits are logged timers, so they cost nothing while idle; the place-order step is where the harness re-checks facts and supplies the idempotency key.

Failure modes: runtime vs harness

The article's table splits nine problems into four the runtime solves with general primitives and five the harness must design for. Of those five, it calls two essential (they come from the domain) and three accidental (they come from durable execution or the model).

Tradeoffs and caveats

  • Runtimes disagree on rule changes. The author built the example on both Temporal and Cloudflare Workflows. After a rule change during the approval wait, Temporal let the old-rule order continue; Cloudflare's per-decision re-check left the PO as a draft. "We need to know how the runtime behaves before we deploy a change."

  • Replay costs grow with the log. A workflow still in memory woke in milliseconds. One rebuilt from its log took about 2 s on Cloudflare and under 0.1 s on Temporal, growing with log length. Snapshots or continue_as_new cap it.

  • Determinism is a contract, not a feature. Replay runs today's code against yesterday's log, so code between steps must rebuild the same state. The article never defines determinism formally; the versioning section is where it bites.

  • Versioning is permanent debt until drained. Old rule branches stay in code until no running workflow needs them, which for weeks-long workflows means weeks.

  • Cost scales with work, not wall-clock. Waiting workflows hold no compute, so many idle SKU agents are cheap. This is the economic case for the pattern.

  • Security is out of scope. Durable execution "doesn't help with any of them per se"; prompt-injection defenses are separate. The article's only defense is capability gating in code.

  • Narrow evidence. One worked example, Python only. Restate, Inngest and DBOS are named as having equivalents but not shown. No production numbers beyond the replay timings.

The conclusion is less technical: domain judgment decides tradeoffs such as cancelling an order vs supplier goodwill; systems of record conflict and are hard for agents to reach; and agents are only as good as their context, so data-product thinking matters. A passing mention of Thoughtworks' Agent/works platform is the only vendor note.

Review checklist for a long-running agent

  1. Is every external call (model, tool, message) a logged step, with no side effects in the code between steps?

  2. Does each side-effecting call carry an idempotency key that survives retries and replays, and does the receiver honor it?

  3. Is a timed-out or failed call treated as "unknown", with a way to discover the real outcome later?

  4. For each irreversible action, is there a compensating action and a rule for when the agent may use it?

  5. Are facts re-checked in code just before commit (price, stock, approval ceiling), not trusted from before a wait?

  6. Is there one owner per business entity, so two workflows cannot act on the same thing at once?

  7. Is every wait bounded by a timeout that becomes an event the agent can act on (chase, escalate, cancel)?

  8. Is the rules or code version recorded at workflow start, and do you know how your runtime replays old workflows on new code?

  9. Is history bounded (continue-as-new, snapshots), and is what the model sees curated separately from the durable log?

  10. Are approvals accepted only from an authenticated signal, never from text in the model's context, and are tools gated by state in code?

  11. Have you measured cold-replay latency at your expected log length?
