Sources: The Foundry Dev Pack is here (Microsoft Foundry Blog, Ignite, 2026-11-18); analysis by Rick Hightower, 2026-11-19.

What shipped

The Foundry Dev Pack became generally available at Ignite on 2026-11-18. One install command (winget, a Homebrew cask, or a Linux install script) sets up Microsoft's agent-building tools:

ComponentInstalledLoop it serves
Foundry CLI (azd ai)alwaysterminal and CI: init, provision, run, invoke locally, deploy, monitor, doctor
Microsoft Foundry Skillalwaysany compatible coding agent
Foundry Toolkitonly if VS Code is presenteditor: scaffold, F5 debug, Agent Inspector traces
Foundry pluginonly if the GitHub Copilot app is presentchat: Foundry Canvas beside Copilot

The CLI went GA earlier, on 2026-11-05. Microsoft states GA for the Dev Pack and the CLI but says nothing about the release status of the Toolkit, Skill or plugin.

Why the Skill is the interesting part

The Skill packages Foundry-specific knowledge and deterministic command-line workflows for creating, deploying, evaluating and troubleshooting Foundry agents. Microsoft names GitHub Copilot, Claude Code and Cursor as compatible hosts, plus "other coding-agent hosts". It steers the agent to az, azd, MCP tools and repository scripts.

The architectural point: a platform vendor has stopped shipping its operating knowledge only as docs or as a plugin for its own assistant, and instead shipped it as one portable skill aimed at every harness, rivals included. The skill is the unit of distribution; the bet is that whichever agent you use, the platform is what gets billed. The tools share project files, so you can scaffold in one surface and deploy from another.

The claim, and how to treat it

Microsoft says the skill helps agents avoid broad web searches and repeated trial and error, so they use fewer tokens and iterate faster. No measurements are published. The failure mode it targets is real: an agent pointed at an unfamiliar cloud platform guesses command names, searches the web and burns turns learning what one line of a skill could state.

Tradeoffs

  • Portability vs. control. One artifact for all hosts means less vendor lock-in at the agent layer, and more at the platform layer.

  • Deterministic workflows vs. flexibility. Prescribed command sequences reduce flailing but encode the vendor's preferred path, including which services it provisions.

  • Conditional installs. Integrations appear only when VS Code or the Copilot app already exist, so two developers running the same install can end up with different toolsets.

Failure modes and risks

  • A skill that runs commands runs them against your subscription. It arrives through whatever host you use, with your credentials already loaded. Treat it like code you are about to execute, not documentation.

  • Unpinned skills drift. If the skill updates silently, the commands your agent issues can change without review.

  • Pipe-to-bash install on Linux carries the usual supply-chain exposure.

  • Release-status ambiguity. The headline GA covers two of four components.

Review checklist before adopting a vendor skill

  • Read the skill file. Which commands is it willing to issue, and against which resources?

  • Pin the version and review diffs on update.

  • Run the agent with least-privilege credentials scoped to a dev subscription first.

  • Confirm which components are GA and which are preview.

  • Measure the claimed token and turn savings on your own tasks before rolling it out.

  • Check that your harness's approval rules still apply to commands the skill suggests.
