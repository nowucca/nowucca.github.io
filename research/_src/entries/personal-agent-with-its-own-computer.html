Nod's permission model, and the honest admission at the centre of it

An open-source desktop agent that drives a real browser against sites with no API — signing into supplier portals, downloading invoices, cancelling subscriptions and refusing the retention offer — is a security design problem wearing a convenience product's clothes. The interesting thing about this particular release is that its own documentation says so.

Nod, from n8n Labs, is a research preview under Apache-2.0 that runs on the user's own machine. Its own description: it "works in your apps and on any website, asks before it acts, and uses the AI provider you choose." The vendor's framing is that the agent "has its own computer" — a local sandbox and browser of its own rather than control of the user's desktop.

The licence choice is worth a sentence of its own, because it is not what you would predict: the company's primary product is distributed under a source-available "Sustainable Use License" rather than an OSS one. Nod is Apache-2.0. That is a deliberate and consequential difference for anyone who wants to fork or embed it.

The architecture, and a discrepancy in how it is described

It runs locally and keeps state locally: "Files, memory, and saved logins stay there." The repository describes the shape as "One Node process and a few Docker containers, all on the machine that runs Nod", with a Linux workspace sandbox container and a Chromium browser container. Model providers are the user's choice — an API key or a consumer chat subscription — and the user pays for inference directly, with a local open model as an option.

One thing to flag for anyone evaluating the isolation boundary: the announcement describes the sandbox as "a private virtual machine on your computer", while the repository describes containers. Those are materially different isolation guarantees, and the difference matters precisely in the threat model this product creates. Anyone deciding whether to point this at a financial portal should read the container configuration rather than either sentence.

For website work, the agent uses credentials the user has stored: "Your saved logins and cards are encrypted on your machine, and Nod enters them through private forms the model can't read." Keeping secrets out of the model's context is the right instinct — the model drives the form without seeing the value.

The permission model

This is the part worth studying, and it has three layers.

A separate check before consequential actions. "Before Nod sends, pays, posts or deletes anything you didn't ask for, a separate check confirms you asked for it." The repository states the rule more precisely: each app action, and each website step that can change something, is checked "against your request and rules. Anything they don't cover waits for your yes." So the authorisation unit is the user's stated request, and anything outside it blocks rather than proceeding.

That is the right shape. Note what it implies: the request has to be specific enough to be checkable, which pushes ambiguity into a prompt for confirmation rather than into a silent decision — and it is the same pattern as scoping an approval to an action and its arguments rather than to a session.

An explicit untrusted-data stance. "App, web, and browser results reach the model marked as data, not instructions", and, plainly, "A web page or an email can't give Nod orders." For an agent whose entire job is reading attacker-controllable web pages while holding the user's logged-in sessions, this is the central control, not a nice-to-have. A product in this category without that sentence in its documentation should not be installed.

An admission that the guard is fallible. "The permission check is itself a model and can make mistakes, which is why Nod asks when your words don't cover an action."

That sentence does more work than any benchmark in the announcement. A model-based policy check is a classifier, and a classifier has a false-negative rate; building the product as though it were a deterministic gate would be the actual error. The design response — fall back to asking the human whenever the request does not clearly cover the action — is the correct one, and it means the system's real safety property is the quality of the "does this cover it" judgement, not the existence of the check.

Spend as a second axis of consent. The agent checks in "once a task passes $5", and a monthly limit can be set. The announcement also notes early testers "found tasks cost more than they expected", which is the honest version of a cost disclosure. Treating money as a separate gate from permissions is sensible: an action can be fully authorised and still cost more than the user would have agreed to.

On the self-reported safety numbers

The repository reports "0 unsafe actions in 678 runs" and "98% tasks finished" from simulated tests with one named model from October 2026, and labels them itself: "Test results, not a guarantee."

Take the framing seriously and the numbers lightly. A zero in 678 simulated runs bounds the failure rate loosely at best, says nothing about an adaptive adversary, and was measured against a scenario set the vendor chose. The right reading is that they built a harness and ran it — which is more than most — and that a zero is a statement about the scenarios, not about the design. The useful follow-up question is how the number varies across model choices, since the guard is a model and the user picks it; a weaker guard model is a weaker product, and that variation is the thing a buyer most needs published.

Where it stops

Stated limitations are specific and credible: the agent stops when the laptop sleeps, so scheduled work only runs while the machine is awake (testers resort to an always-on machine or a server, with hosting on the roadmap); each installation has a single owner; and it cannot place phone calls. It is a research preview, and platform support outside macOS is marked preview.

The sleep limitation is the one with design consequences. An agent whose value proposition is unattended errands — watch a price, fetch the invoices monthly — cannot do unattended errands on the device most people own. That pushes serious use onto a machine that is always on, which in turn concentrates stored credentials on a host nobody is sitting in front of. Worth thinking through before setting one up.

Review checklist

Before letting an agent of this kind touch a real account:

  1. Read the actual isolation configuration rather than the marketing noun. Container or VM changes what a compromise reaches.

  2. Confirm, per input surface, that fetched content is handled as data. Test it with a page that contains instructions.

  3. Decide which actions must never be delegated regardless of what the permission model allows — payments, deletions, anything legally binding — and keep those on a human.

  4. Phrase tasks narrowly enough that the authorisation check has something to check against. "Handle my subscriptions" is not a request, it is a grant.

  5. Set the spend limit before the first run, not after the first surprise.

  6. Ask which model is running the permission check, and whether the vendor publishes guard performance by model. The guard's quality is a configuration choice.

  7. If scheduling matters, plan for the always-on host, and then plan for the credentials living on it.

  8. For a research preview, keep the blast radius to accounts you could afford to have misused, and re-evaluate when it leaves preview.

Related reading

The permission design here is the consumer-facing cousin of work on scoping agent authority at the infrastructure level — credential injection behind a supervisor, egress through a single checked channel, policy checked per request rather than per session. Reading them together clarifies which parts of this product are genuinely enforced and which are a model's judgement.

The treatment of an approval as something checked against a stated request, with anything uncovered waiting for a human, is the same principle as making an approval conditional rather than a bearer token; this release is a working example of that idea in a product.

And on the injection surface, the general literature on agent configuration and tool output as attack surface applies directly: an agent that reads arbitrary web pages while holding live sessions is the most exposed shape in the category.
