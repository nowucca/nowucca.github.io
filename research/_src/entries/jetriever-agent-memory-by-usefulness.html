The short version

Agent memory is usually retrieved like a search index. You embed or keyword-match the query, take a shortlist, and maybe rerank it. That fails when the memory that matters shares no surface features with the question. In the paper's canonical case, a user mentioned a nut allergy months ago and now asks for a macaron recipe. The query says nothing about nuts, so a similarity retriever never surfaces the allergy.

Jetriever drops the shortlist. For each query it scores every stored memory with a small LLM-derived decision model (Jev) for the probability that the memory helps produce a correct answer, then ranks the whole pool by that probability.

On InMind's 125 indirect-query tasks:

  • Jetriever puts the gold exchange first 84.8% of the time. BM25 manages 1.6% and MiniLM 0%.

  • End to end, the top five memories go to GPT-5-mini, and 76% of answers correctly apply the stored fact, against at most 16% for published retrieval and memory systems. Handing GPT-5-mini the gold memory directly scores 84%, so selection is close to the ceiling.

  • On a 60-question sample of MemoryAgentBench, the four-dimension average rises from 44.3% (ReFind) to 55.4%.

  • Retrieval cost averages about $0.008 per InMind query and $0.031 per MemoryAgentBench query.

How it works

  1. Store past exchanges as discrete memories. No embedding index is required for ranking.

  2. Score the full pool. For a new query, pair it with each memory and ask the decision model one question: would this memory contribute to a correct answer? The output is a calibrated probability, not a similarity score.

  3. Rank and truncate. Sort by probability and pass the top k (five in the paper) to the answering model.

  4. Answer with the selected memories in context.

The design bet is that usefulness depends on world knowledge (macarons contain almonds), and only a model with that knowledge can see the link. Vector distance can't.

The finding that matters most: recognising is not ranking

A controlled 20-question comparison separates two abilities:

  • Recognition. Jev and a general Qwen3.5-9B both find 90% of gold memories somewhere in their top 50. A BERT-based decision model finds 30%.

  • Ranking. At rank 1, Jev scores 85% and Qwen3.5-9B drops to 40%.

So a general LLM "knows" the memory is relevant but can't order it above merely plausible context. What wins is calibrated probabilities. For anyone tempted to use a general model as a reranker by asking it to score relevance from 1 to 10, that is the warning: knowing something is relevant isn't enough, because the scores also have to be comparable from one memory to the next.

Tradeoffs

  • Linear cost in memory size. Every query touches every memory. The reported per-query costs are low on benchmark-sized pools, but a lifelong memory with tens of thousands of items multiplies cost and latency. Expect to need a cheap prefilter (time window, user, topic) or caching of per-memory scores, and each of those reintroduces some of the recall loss the method set out to fix.

  • A model per decision. You now depend on a decision model's calibration. If it drifts, or is swapped for one that is poorly calibrated, ranking quality collapses even when recognition looks fine.

  • Benchmarks favour the method. InMind is built around indirect queries, where similarity is weakest. On direct-lookup workloads the gap over a good embedding retriever will be much smaller.

  • Top-k is still a cliff. The answer model sees five memories. A useful sixth is lost, and distractors in the top five still cost accuracy.

Failure modes to watch

  • Plausible-context flooding. Memories that look related crowd out the one that matters. Calibration is the defence, so measure rank-1 accuracy, not recall@50.

  • Stale or contradicted memories. Utility scoring doesn't know that a later exchange superseded an earlier one, such as an allergy later corrected. You still need versioning or recency handling.

  • Privacy and over-application. A retriever that connects distant facts will also surface sensitive ones in contexts the user didn't expect. Decide which memories may ever be applied implicitly.

  • Cost blowups. Without a budget, a large memory pool turns each query into thousands of model calls.

Review checklist

  • Is retrieval quality measured on indirect queries, where the needed memory shares no words with the question, and not only on lookups?

  • Do you report rank-1 accuracy and end-to-end application accuracy, alongside recall@k?

  • Is the scoring model's calibration tested, for example on a held-out set with known useful and decoy memories?

  • Is there a cost ceiling per query, and a stated prefilter strategy once the pool outgrows full scoring?

  • Are superseded memories marked so a high-utility but outdated fact can't win?

  • Is there a policy for which memories may be applied without the user restating them?

  • Is the oracle baseline (gold memory supplied directly) measured, so you know how much headroom selection has left?
