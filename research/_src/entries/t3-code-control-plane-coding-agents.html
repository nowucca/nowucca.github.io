What it is

T3 Code is an open-source local server plus desktop, web and phone clients that drives the coding-agent CLIs already installed and signed in on your machine: Claude Code, Codex, Cursor, OpenCode, Pi and any ACP-speaking agent, among others. It does not resell tokens; it rides your existing subscriptions.

  • Start a thread at your desk and approve the next tool call from your phone.

  • Switch models mid-thread, or let one agent hand a task to another (for example Claude to Codex).

  • Each thread can run in its own git worktree, with diff review, commit, push and PR in one step.

  • Remote access over the local network, Tailscale or the vendor's relay (T3 Connect).

Architecture in one paragraph

A single server process on the machine that owns the code spawns and supervises the agent CLIs, normalises their event streams into one thread model, and serves every client from that one source of truth. Approvals are just another event the client answers. This is the same shape as other agent control planes: the agent runs where the credentials and repo live, the UI is thin and can be anywhere.

The telemetry detail worth knowing

The project's own telemetry documentation says product events go to the vendor's ingest endpoint and on to PostHog, keyed to a hashed owner identifier. To count installs per person, the server reads identifiers from the agents' local login files (the Claude account UUID when logged in, the OpenAI user ID from Codex's token) plus the vendor account and a per-device random ID, and sends their hashes.

  • The hash is a plain, unsalted SHA-256 of the raw ID. That makes the value stable across machines and surfaces, which is the point, but it is pseudonymous rather than anonymous: anyone who already holds the raw ID can compute the same hash and link the events.

  • Events carry provider, model, reasoning effort, permission mode, results, durations and token counts; the docs state prompts, responses, file contents and tokens are excluded.

  • A separate relay diagnostics stream goes to Axiom and can include machine names and error text.

  • Opt-out is an environment variable (T3CODE_TELEMETRY_ENABLED=false) read by the server, or a managed policy for administrators. The desktop app reads it from your shell profile.

  • The post that surfaced this notes the settings screen labels the data anonymous; the documentation itself describes hashed account identifiers.

Tradeoffs

You gainYou accept
One UI and approval flow across many agent CLIsA third-party process that reads every agent's login files
Phone approvals for long-running workA remote path into a machine with repo and credentials
Cross-agent handoff in one threadBehaviour coupled to each CLI's event format, which changes often
Uses existing subscriptionsVendor telemetry on by default unless disabled

Failure modes

  • Approval fatigue on a small screen: approving shell commands from a phone invites rubber-stamping; keep dangerous-command policies in the agent itself.

  • Remote exposure: a misconfigured relay or LAN bind exposes an agent runner with write access.

  • Upstream drift: a CLI update can break event parsing mid-thread.

  • Identity leakage: stable hashed account IDs let the vendor (or anyone with the raw ID) correlate usage across devices.

Review checklist before rolling out to a team

  • Set the telemetry opt-out (or the managed policy) before first launch if your policy forbids third-party analytics.

  • Decide which remote mode is allowed: LAN only, Tailscale, or the vendor relay.

  • Confirm worktree-per-thread is on so parallel agents do not collide.

  • Keep each agent's own permission settings strict; the control plane does not replace them.

  • Pin versions of T3 Code and the agent CLIs together, and test upgrades.
