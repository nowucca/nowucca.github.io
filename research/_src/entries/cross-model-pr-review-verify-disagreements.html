Adhish Thite reviewed a 150-file, 9-commit PR by sending one read-only prompt to Claude, Codex and Gemini, letting each split the work across sub-agents, then having a separate synthesizer check every disagreement against the code instead of voting. The result was 41 verified findings (1 Critical, 10 High), several caught by only one model.

The pipeline

One orchestrator builds a single context bundle, three vendor models review it independently with their own sub-agents, and a separate synthesizer checks the disagreements against the code before anything reaches the fix run.

What the run produced

The three reviewers disagreed on the verdict, and the verified list ended smaller than the noisiest reviewer's. That is the point of the verify step: it removed false positives without discarding single-model finds.

In total 16 agents wrote about 170 KB of notes. The synthesizer dropped 2 false positives that came from misread docs, and downgraded one security warning after reading the middleware that already handled it.

Three bugs it kept were each caught by only one model:

  • A prefers-reduced-motion CSS rule that turned looping indicators into a 60 to 120 Hz strobe (an accessibility and photosensitivity bug, not a style nit).

  • A loading state that showed "$0 / sample mode" while the app was still making paid API calls, plus races on a concurrency cap and mismatched timeouts.

  • A failure handler that wiped metrics already completed, and missing graceful-close teardown.

The output was one markdown brief with an agreement score per finding (3/3, 2/3 or 1/3, all verified) and file:line links, handed to a separate parallel fix run. The reviewers never wrote to the repo.

Why it works and where it breaks

The value comes from decorrelated errors plus an evidence check, not from the number of agents. Three vendors' models miss different things, and each chose its own way to split 150 files, so coverage gaps rarely line up. Voting would then throw away exactly the findings that justify the cost: the solo catches. Checking each disagreement against the code keeps those and kills the hallucinated ones.

Design choices that matter:

  • Identical prompt and context for all reviewers. The orchestrator gathers the diff, CI results, open comments and repo rules once, so differences between reports come from the models, not from what each was shown.

  • Read-only by rule. No edits, commits or PR comments during review. Review and fix are separate runs, so a reviewer cannot "fix" its way past a finding and the brief stays auditable.

  • Verification targets disagreements and solo high-severity claims. Unanimous findings are cheap to accept; the synthesizer spends its budget where reviewers conflict.

  • Agreement score is reported, not used as the filter. A 1/3 finding that verifies stays in the list, labelled 1/3.

Failure modes and open questions:

  • The synthesizer is a single point of judgment. It is the same model family as one reviewer (Gemini 4 Neon) and as the orchestrator, so it may favour Gemini's reading. A synthesizer from a fourth family, or rotation, would be cleaner.

  • No human spot check is reported. As a commenter asked, nobody says how many 1/3 findings survived a human read, or whether a dropped finding was wrong to drop. Dismissals need the same evidence trail as acceptances.

  • Severity scales differ by vendor. One commenter noted a bug all three found but ranked differently. The synthesizer has to normalise severity against a shared rubric, or the Critical/High counts mean little.

  • Cost and latency are not given. Sixteen agents at High and xhigh effort on a 150-file diff is expensive. Worth it for a release-gating PR, not for routine changes.

  • The PR size is part of the problem. Small, scoped PRs reduce the need for this, and commenters asked why the change touched 150 files. The pattern is a backstop for unavoidable big diffs (migrations, framework upgrades, agent-written features), not a reason to stop splitting work.

  • Single anecdote. One PR, one run, author's own count. No recall is measured against known bugs, so this shows the workflow, not its accuracy.

The author credits T3 Code (Theo Browne's multi-agent coding GUI) for running Claude, Codex and Gemini side by side in one thread with mid-run steering. The pattern itself is tool-neutral: any harness that can call three CLIs, collect their reports and run a verifier would do.

Review checklist

Use this when setting up a cross-model review for a large diff.

  1. Reviewers run with no write tools at all (enforced by permissions, not only by the prompt).

  2. One context bundle for every reviewer: diff, CI status, open comments, repo review rules, and the same prompt.

  3. At least two model families among reviewers, and a synthesizer outside the reviewers' families if you can.

  4. Each finding has file:line, a claim that can be checked, and a severity on one shared rubric.

  5. The synthesizer checks every disagreement and every solo High or Critical against code or docs, and records why it kept, changed or dropped each.

  6. Agreement score is shown per finding but never used to drop a verified one.

  7. A human samples the 1/3 findings and the dropped findings before merge; the merger owns the result.

  8. Fixes run separately from review, and the fix run is reviewed again (at least on the touched lines).

  9. Track cost per run and hit rate per reviewer over time, so you know which model earns its seat.
