What it is

A single-binary static scanner (cargo install safe-anything or npx safe-anything .) with 74 regex-and-parser rules, each mapped to a CWE and an OWASP page. No config, no account, no upload; it exits non-zero on high or critical findings, so it drops straight into pre-commit or CI, and it emits JSON and SARIF for GitHub code scanning. It covers five familiar families (injection and XSS patterns in nine languages, leaked secrets and .env mistakes, mobile and container/IaC config, locked dependencies checked against OSV.dev) plus one that most scanners don't yet treat as first-class: the coding agent's own configuration.

The agent-setup rules

The argument is short: the files that decide what an agent may do are code, so check them like code. It reads .mcp.json, Claude Code settings, commands, agents, skills and hooks, CLAUDE.md, Codex's config.toml and AGENTS.md, Cursor and VS Code MCP files and rules, Gemini CLI settings, OpenCode config, and any SKILL.md. It also ships as an MCP server and a Claude Code plugin, so the agent can scan before committing, and the README's suggested workflow is to clone someone else's skill or MCP repo into a temp directory and scan it before copying anything into ~/.claude, .cursor or .codex.

Evidence offered

The author hand-read every finding on a small benchmark (offline release build, 2026-11-22): OWASP Juice Shop 67 findings with 2 to 3 false positives; DVWA 63 with about 4; express 0; flask 2 (both benign); modelcontextprotocol/servers 1 (pull_request_target); anthropics/skills 6 (local innerHTML, a deliberate shell=True); vercel-labs/agent-skills 0. Scans of about 1,200 files take tens of milliseconds. These are the author's own numbers and repos, not an independent evaluation, and the agent-setup rules have no comparable measured corpus.

Assessment for a staff engineer

  • The useful idea is the scope, not the engine. Agent config is now a privileged, executable surface (permissions, hooks, MCP launch commands, skills with file access) that sits outside what SAST, secret scanning and SCA traditionally look at. Treating it as a lintable artifact in CI is cheap and catches the most common self-inflicted mistakes: pre-approved shell, unpinned npx MCP servers, tokens committed in .mcp.json.

  • It is pattern matching, and says so. No data-flow tracing; a clean run means none of 74 known patterns matched. The prompt-injection and hidden-Unicode rules will catch only crude, literal payloads; a determined attacker phrases around a regex. Treat those as tripwires, not a defence.

  • It does not cover the runtime. The real risks in recent agent incidents were runtime: a poisoned dependency the agent installs, an MCP server whose tool descriptions change after install, credentials surfacing in traces. Pinning and least-privilege config reduce blast radius, but you still need sandboxing, egress control and credential brokering outside the agent.

  • Supply-chain irony. It is a day-old, single-maintainer tool that you would install via npx or as an agent plugin. Pin a released version (the CI example pins @v1.0.2) and review it the same way it asks you to review others' skills.

  • Where it fits in a stack: alongside a broader SAST (Semgrep or CodeQL), a dedicated secret scanner, and an MCP tool-poisoning scanner, as the fast pre-commit check for agent config specifically. Its overlap with established tools on code and secrets is wide; the agent-setup family is the reason to adopt it.

Takeaways

  1. Add agent configuration (.mcp.json, settings, hooks, skills, rules files) to the set of files your CI security gate inspects.

  2. Pin MCP servers to versions or digests; never commit tokens into MCP env blocks.

  3. Scan third-party skills and MCP servers before installing them, the same way you would vet a dependency.

  4. Keep the runtime controls; static config checks shrink the attack surface but don't stop a compromised tool at run time.
