Jake Van Clief's 108-second Facebook reel (2026-11-12) argues that the scarce input to AI-built software is settled human judgment, not code. His team argues a feature out in a meeting, files the transcript as markdown, folds the settled decisions into a versioned skill file in the repo, and only then points agents at it. The practice is real and visible on screen (a merged docs-only PR, "Vision skill 0.5.0"); the headline claim that the best features were the ones not pushed with AI is anecdote.

The workflow he shows

The loop runs judgment first and automation second. Agents never get to decide what the product should be; they get a file that says so.

  1. Argue it out. The team meets and argues the opinions behind a feature: why it is or is not good.

  2. Capture the argument. The meeting transcript goes into the team's knowledge structure as plain markdown ("just good old markdown files").

  3. Settle and fold. Settled decisions are folded into a skill file in the repo (on screen: .agents/skills/vision/SKILL.md), versioned like code (0.5.0) and changed by its own docs-only PR.

  4. Point the agents. Only then are agentic loops pointed at those ideas to build "the functions, the structures".

  5. Keep it current. Later meetings update the same skill, so every agent run reads the latest settled intent.

His framing: this automates "our intent, our judgement, our opinion" at scale, and that only pays off if the starting opinion is right, because "opinions have no metric of best". A slightly wrong starting opinion is amplified by however good the automation is. He also widens "AI" to any automation: agentic loops, knowledge harnesses and second brains are all automations for something specific.

Where it breaks

The loop moves the bottleneck from code to the quality and freshness of one markdown file. That file becomes the highest-leverage artifact in the repo and inherits every failure mode of a spec.

  • Transcript is not decision. Raw transcripts hold the losing arguments too. If agents read transcripts rather than the folded skill, they can build the rejected option. The reel's own PR folds only "settled decisions"; keep that separation explicit (transcripts as evidence, skill as the ruling).

  • Supersession. A skill "always informed by our meetings" grows by accretion. Without a rule for which decision wins, Nov 6 and Nov 20 can both be in force. Versioning the file (0.5.0) helps only if each version records what it replaced.

  • Unclear who settles. A meeting produces opinions; someone has to declare one settled. The reel does not say who, and the PR was authored by one engineer. That person is the product owner in practice.

  • Slow is not the same as right. "Opinions have no metric of best" cuts both ways: slowing down does not validate an opinion. The cheap check is a user signal (alpha feedback, usage) recorded next to the decision, which the reel mentions only in passing.

  • Drift from code. A docs-only PR changes intent without touching code. Something has to find the code that now contradicts the skill; otherwise agents build new work on the new intent while old work stays on the old one.

  • Context cost. A vision skill loaded on every run competes for context with the task. Keep it short, with links down to detail.

Tradeoff in one line: you trade raw throughput for fewer reversals. That pays off when features are cheap to build and expensive to unbuild, which is the regime agents put most teams in.

Review checklist for a decision-capture skill

  • Transcripts and the skill live in separate places, and agents load only the skill.

  • Every decision in the skill names its date, its source meeting and who settled it.

  • A superseded decision is removed or marked, and the version note says what replaced what.

  • Skill changes go through their own reviewed PR, with no code in the same PR.

  • After a skill change, something lists code and open PRs that contradict it.

  • Each product decision carries the user signal it rests on, or says it has none yet.

  • The skill fits on a screen or two, with detail linked, not inlined.

  • Open questions are listed as open, so agents do not settle them by building.
