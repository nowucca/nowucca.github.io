At Imprint, review latency rose as merge volume grew: p50 review time went from about 33 to about 77 minutes over two years. Will Larson describes a CI check that marks low-risk PRs as "small-change". An approve-or-ignore skill then reviews those PRs, and any escape is treated as a system defect (Irrational Exuberance, 17 Oct 2026). About 10% of changes qualify so far. He calls the problem not solved and says it is too early for results.

Eligibility (all must hold)

RuleThreshold
Diff sizeFewer than 1,000 changed lines
Automated reviewNo p1 or p2 findings from the ai-code-review bot
Author experience10 or more prior merged PRs in every affected service
Blast radiusFewer than N services: N = 1 in the frontend monorepo, 3 in the backend (a gRPC service plus the shared gateway)
Shared codeShared libraries and utility files are never eligible
Opt-outsA per-repo .small_change file excludes paths, such as money movement

Eligibility is a GitHub check set by the build, which humans can't edit. A label exists only for visibility and filtering.

The lighter path

  • Slack automation tags small-change PRs.

  • A review-small-change skill reviews open, non-draft small-changes. It approves only when every check passes and no sensitive area (payments, security) is touched. Its only options are approve or ignore. It never comments, to avoid "meat proxy" review, where one agent generates review comments for another to answer.

  • A review-pr-cluster skill reviews batches of PRs for common themes and suggests new verifications.

  • Social rule: an error that ships through small-change is fixed in the bot, the checks, CI/CD or the harness, never blamed on a person.

Why it matters

Review has four jobs at Imprint: knowledge sharing, catching errors, catching malicious changes, and compliance. Some repos require an independent human reviewer by documented control. small-change keeps those jobs where risk is real, and stops spending human attention where checks already carry the risk. Rollout took about two days of intermittent work.

Risks

  • The gate is only as good as the review bot and the verifications. That is weakest for software with low scale but high domain complexity, where incremental rollout gives little coverage.

  • Author-experience counts can be gamed or can lag a service's real ownership.

  • Compliance controls may still demand human review in some repos. Keep those repos out.

  • The cultural cost is real: this departs from how engineers learned to be good reviewers.

Review checklist for adopting it

  • Eligibility is computed by CI and can't be edited by people.

  • Thresholds are explicit and versioned, with per-path opt-outs.

  • Automation approves or ignores; it does not add comment noise.

  • Escapes create tooling work items, not reviewer blame.

  • You measure the escape rate of small-changes against normal reviews before widening the gate.
