Google's google-cloud-developer plugin keeps the always-loaded context small by bundling only 5 skills, one MCP server and one always-on routing rule, then fetching any of the 219 catalog skills over the network when a task needs one. Remigiusz Samborski presents it in a five-minute segment (4:13 to 8:22) of Google Cloud Tech's 27-minute episode "How Google engineers build AI agents in production" (published 2026-11-23). The claims below are checked against the plugin's files in google/skills, the launch blog and the Agent Skills spec; the segment's content comes from the post, the chapter list and the video description.

What the segment claims

  • Models trained on static data invent outdated SDK calls and guess CLI flags, so knowledge must be loaded live, not memorized.

  • Don't stuff "50 pages of rules" into AGENTS.md. Put workflows in SKILL.md folders and let progressive disclosure load them (discovery, activation, execution).

  • Keep a single skill when it stands alone. Bundle skills, MCP servers and rules into an Agent Plugin when they only work together.

  • Demo: google-cloud-developer in Antigravity with live docs, IAM and billing guardrails, and "150+ on-demand skills".

What is actually in the plugin (version 1.1.20, checked 2026-11-25)

The "150+ skills" are the public catalog, not the bundle: index.json listed 219 skills on 2026-11-25. Packaging follows the vendor-neutral Agent Plugins spec (agent-plugins.org), and the same plugin installs in Antigravity, Claude Code and Codex CLI.

How the context stays small

The Agent Skills spec defines three loads: metadata (about 100 tokens per skill, always), the SKILL.md body (under 5,000 tokens recommended, on activation) and scripts or references (only when used). The plugin adds a fourth level above those: catalog skills are not installed at all, so they cost nothing until the finder fetches one. The always-on cost is five descriptions plus the routing rule.

Guardrails are mostly instructions

"IAM and billing guardrails" means skill text plus a permissions recommendation. The README tells users to keep gcloud auth login, projects create, billing projects link and services enable behind an Ask prompt and to allow only a list of read-only commands. The enforcing layer is the host's permission mode. The "MANDATORY" blocks in the skill are advice a model can skip.

Tradeoffs and failure modes

  • Fetch-and-follow from main. The finder runs instructions pulled at run time from the repo's main branch. They are not pinned to the installed plugin version, so behavior can change under a fixed install, and a bad commit reaches every session. The skill insists on TLS and on rejecting non-JSON responses, but that protects transport, not content.

  • Stale sizing in the skill itself. The finder says the catalog is "about 75 KB". It was 161 KB on 2026-11-25, which makes the truncation it warns about more likely.

  • Routing at catalog scale. Selection rests on name prefixes and description matching across 219 entries. A commenter asked how overlapping triggers are kept apart. No answer was visible in the comments.

  • Network and sandbox needs. Dynamic discovery needs curl, jq and access to GitHub. Sandboxed sessions without them fall back to the five bundled skills.

  • Credential in the environment. The MCP server's API key is exported as DEVELOPERKNOWLEDGE_API_KEY, readable by anything the agent runs.

The rest of the episode

The chapters frame production agents as four layers: Learn (context maps, persistent markdown memory, skills), Guard (fast deterministic checks, git hooks, secret scanners, retry limits so agents cannot cheat to green tests, slopsquatting), Review (interactive PR summaries, repo walkthroughs, video QA of UI, audio reviews) and Score (evals of tool choice, trajectories, multi-turn memory and multi-agent handoffs).

Review checklist

  • Is the always-loaded set (descriptions plus always-on rules) measured in tokens, and does it have a budget?

  • Are remotely fetched skills pinned to a commit or digest, and logged with the run?

  • Do the CLI guardrails live in the permission config, not only in skill text?

  • Does the routing map name prefixes that match the real catalog, and is that checked in CI?

  • Can the agent say "I could not load that skill" instead of answering from memory?
