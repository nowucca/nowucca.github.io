What it is

Thinking Machines Lab's smaller sibling to Inkling 2 Small. It is a multimodal mixture-of-experts with about 26B stored parameters and 3B active per token. It takes text and images and supports a 1M-token context. Weights ship in mixed precision, with NVFP4 and MXFP8 experts, alongside a small DSpark drafter model for speculative decoding. It runs on day one in transformers, llama.cpp, MLX and SGLang. The blog does not state the licence; check the model card before use.

Architecture: looping instead of storing

  • 24 physical layers, 48 layer visits. Layers 0 to 5 run once, the core layers 6 to 17 run three times with shared weights, then layers 18 to 23 run once. Compute per token matches the much larger Small model's 48 visits, but the checkpoint stores half the layers at half the width (hidden size 2,304 against 4,608).

  • Cross-pass messages. Every pass through the core starts from the same input, the output of the first six layers. Each looped layer reads a learned message from the previous pass, and a small gate decides how much of its current input to forget and how much of the message to add. Each pass refines the previous one.

  • Attention mix. Each six-layer block has five sliding-window layers (1,024 tokens) and one full-attention layer. It uses grouped-query attention (24 query heads, 8 KV heads), learned relative position logits, an attention sink and an output gate.

  • Experts. The router picks 8 of 128 SwiGLU experts per token at each visit (Small picks 8 of 384).

  • Variable-loop research checkpoint. A separate artifact was trained to run 1, 2 or 3 passes, trading quality for speed at inference time. It has not been evaluated in depth.

Claims

The post reports state of the art in its class on the Artificial Analysis Intelligence Index v5. Against Gemma 4 31B, Muse Glimmer, Qwen3.8-27B and Nemotron 3.5 Super VL, it leads on 32 of 48 benchmarks. For coding it leads FrontierCode v2.0, ties Qwen3.8-27B on Terminal-Bench 4.0 and trails it on AutomationBench. The Hugging Face team's own hands-on impression is that it is at least comparable to Qwen3.8-27B, with more validation needed.

Why it matters

  • Memory, not compute, limits local models. Looping buys depth without storing more weights, which suits laptops and single GPUs where memory is the constraint.

  • A per-request speed dial. If variable-loop training holds up, one checkpoint could serve fast and careful modes by changing the pass count, much like reasoning-effort settings.

  • Open-weight competition at the small end remains strong even as the frontier gap stays open.

Tradeoffs and failure modes

  • Compute is not reduced. Looping saves memory but still runs 48 layer visits. Latency is roughly that of a deeper model, and the KV cache and convolution state are kept per visit, so long contexts still cost memory.

  • Quantization interplay. Shared weights are reused three times, so quantization error in the core compounds across passes. Test your quantized build, not only the reference weights.

  • New architecture, young kernels. Day-one support exists, but performance and correctness in llama.cpp and MLX builds will keep changing.

  • Vendor and partner benchmarks. The scores come from the release and launch partners. Wait for independent runs (see R078).

  • 1M context is a capability, not a guarantee. Five of every six layers see only a 1,024-token window, so long-range recall rests on the full-attention layers and should be tested.

Checklist before adopting it as a local coding model

  • Licence and acceptable-use terms on the model card.

  • Measured memory and tokens per second on your hardware at your quantization level.

  • Long-context recall on your own repositories, not only needle tests.

  • Agentic coding success on your own task set, compared with your current local model.

  • Whether the DSpark drafter actually speeds up decoding in your runtime.
