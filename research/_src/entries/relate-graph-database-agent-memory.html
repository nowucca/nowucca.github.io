TL;DR

Relate is SQLite for property graphs: a Rust, in-process, in-memory graph engine that speaks Cypher 25, persists to one .rl file or a directory, and can be served unchanged as Bolt, HTTP and MCP. For agent memory it removes the server you would otherwise run (Neo4j, a vector DB) and adds vector, full-text and spatial search on the same graph.

  • What it buys: zero infrastructure, one file per agent or per project, Neo4j driver and tooling compatibility, and an agent-facing surface designed to be hard to misuse (in-band row caps, structured retryable errors, a read tool that provably cannot write).

  • What it costs: the whole graph lives in RAM, one process owns the store, there is no general write-skew detection, and it publishes no benchmarks. It is an experimental Neo4j Labs project, v1.0 released 2026-11-11, one week after the repo was created.

  • Verdict: a strong default for a single agent's (or single developer's) local graph memory and for agent-built knowledge graphs of code and files. Not a shared, multi-writer memory service.

Source

The post is a five-sentence note by André Lindenberg (posted 2026-11-12): agent memory does not need a server; a graph can live in one file the agent uses, and the same store can run as an MCP server; the cost is that the graph must fit in RAM and one process owns it. The repo link, relatedb/relate, is in the author's first comment, which calls it a store for "memory or transactional filesystem".

The repo is a Neo4j Labs project under Apache-2.0, mostly written by Michael Hunger with Oskar Hane and others. It accepts issues, not pull requests. It carries 500+ numbered architecture decision records and SSH-signed releases.

Architecture

One engine, embedded in the caller's process, with many front doors. The live graph is held in RAM in a typed CSR (compressed sparse row) layout for traversal. Durability is a fsync'd write-ahead log plus one snapshot codec (Parquet shards or a readable JSON file). Commits are optimistic: conflicts are detected on element IDs and on unique/key constraint values at a commit-time serialization point.

The query language is Cypher 25: quantified path patterns, path selectors, schema DDL, 80+ functions, EXPLAIN/PROFILE and LOAD CSV. On top of the graph it adds vector properties with a SEARCH clause (top-K with pre-filtering), hybrid vector plus full-text search, R-tree spatial indexes, and pull/push of subgraphs to and from Neo4j or Aura. Conformance is measured by running the openCypher TCK and Neo4j's own Cypher suites on every ready PR, reported as coverage rather than enforced as a merge gate.

Agent-native design choices

The most transferable part of Relate is not the engine but how it treats an agent as the primary client. Each choice closes a specific way agents misread tool output.

  • Truncation is said in-band. Under a detected agent harness (or --agent-mode), a statement prints at most 100 rows and says so in the output, so a capped result never reads as complete. --max-rows lifts it.

  • Errors are data. In machine modes a failure prints {"error":{code, exit_code, kind, message, retryable}}, and exit codes separate usage (2), rejected statements (6), write conflict or locked store (5) and other failures (1). The agent can branch on whether a retry can help instead of guessing from text.

  • Read is provably read-only. The MCP surface is two tools, read_cypher and write_cypher. Each statement is classified with EXPLAIN before it runs, so read_cypher rejects any write or schema change and a host can auto-approve it. In read-only mode write_cypher is not offered at all.

  • The skill ships with the binary. relate skill install writes a versioned SKILL.md bundle (CLI flags, Cypher dialect, vector and spatial references, known gotchas) into every detected agent (Claude Code, Cursor, Codex, Gemini CLI, Copilot and others). It never overwrites a hand-written skill directory, and relate upgrade keeps it current.

  • Extensions get only Cypher. relate run <name> packages talk to the host over MCP stdio, and their only power is read/write Cypher. Shipped examples turn a directory tree (fs-to-graph, with full-text over file contents) or a git history (git-to-graph) into a graph.

  • Typos get a suggestion. An unknown flag answers with the nearest real one, which saves an agent a round trip.

Tradeoffs and limits

The project's own limitations page is unusually candid. The ones that matter for agent memory:

Failure modes

A graph store fixes the shape of memory, not its quality. The ways a Relate-backed memory goes wrong are mostly upstream of the engine.

  1. Schema drift by the agent. An agent writing Cypher freely invents labels and relationship types (:Fact, :Memory, :Note). Without schema DDL and constraints, recall queries silently miss half the graph.

  2. Stale facts stay authoritative. Nothing in the engine ages, versions or retracts a fact. Without a provenance edge (source, run, timestamp) and a garbage-collection pass, the graph is the memory-without-reconciliation failure R002 describes.

  3. Vector recall without structure. Hybrid SEARCH makes it tempting to treat the graph as a vector store with extras. The value of the graph is multi-hop recall; if every read is top-K similarity, a flat vector index is simpler.

  4. Lost writes under relaxed durability. everysecond can drop about a second of acknowledged writes on a crash, and snapshot everything since the last checkpoint. An agent that wrote a memory and moved on will not notice.

  5. The serve process becomes shared infra anyway. Once two agents or a dashboard need the same memory, relate serve is a server you run, with one process and no replication. The "no server" claim holds only for one owner.

  6. Auto-approved writes. read_cypher is safe to auto-approve; write_cypher is not. A host that approves both lets a prompt-injected agent rewrite or delete its own memory (MATCH (n) DETACH DELETE n).

When to use it

Use Relate when one agent or one developer owns the memory, the graph fits comfortably in RAM, and recall is genuinely relational (which file calls which, which decision superseded which, who said what about whom). Prefer Markdown files plus ripgrep when memory is small and mostly prose, and a server database when several writers share memory or it must outgrow one machine.

Review checklist

  • Is recall multi-hop? If every query is "top-K similar notes", a vector index or plain files are simpler.

  • Is there a declared schema (labels, relationship types, unique/key constraints) that the agent's skill tells it to use?

  • Does every fact carry provenance (source, run, time) and is there a reconciliation or expiry pass?

  • Is durability full for memory the agent will not re-derive?

  • Is only read_cypher auto-approved, with writes gated or in a separate read-only mount for untrusted runs?

  • Is the expected graph size measured against host RAM, with the logical capacity cap set?

  • Is telemetry off for private stores?

  • Is there an export path (Parquet/JSON snapshot, or push to Neo4j) in case the Labs project stalls?
