The problem

Quantum algorithms for useful chemistry or physics need circuits far too large to simulate classically or to run on today's processors. That breaks the usual automated-discovery loop (generate, run, score): you cannot execute the candidate to check it. The paper's move is to replace execution with proof. A candidate program counts only if a theorem prover accepts both that it meets a formal specification and what it costs.

Architecture

  • A Lean 4 library for quantum programs: circuits, gates, registers, a quantum Hoare logic with classical variables, and a resource-counting framework (qubits and operations), built on Mathlib and the QuantumInfo part of Physlib. A separate specs library holds problem statements and benchmark challenges; the discovered programs sit on a separate branch so the framework stays lightweight to depend on.

  • Human-set problems. Researchers write the formal specification for each target (what the circuit must compute) and supervise progress. The agents search for programs that satisfy it more cheaply.

  • Independent agent teams in parallel. Each team of Gemini 4 agents works a problem separately. A result enters a shared notebook (the paper says wikis) only after Lean verifies correctness and cost.

  • Periodic "conferences." Every four hours, agents from all teams meet to trade, debate and compare ideas, then return to search. Verified cost falls over the run as better ideas propagate.

The trust boundary is clear: the agents and the conference discussion are untrusted; Lean's kernel, the library's semantics, and the human-written specs are trusted.

Why it matters beyond quantum

This is the clearest instance yet of a pattern also seen in proof search and verified software: when you cannot test, verify. The general recipe is a formal spec plus a checker you trust, wrapped around a population of untrusted generators that share only verified results. The verifier is what makes scaled parallel search safe: wrong ideas can be discussed freely, but they cannot enter the shared state.

Two design choices are worth copying in non-quantum agent systems:

  1. Verified-only shared memory. Teams can talk about anything, but the notebook other teams build on admits only checked results. That stops one team's hallucination from contaminating the rest.

  2. Diversity then exchange. Independent teams explore different directions; scheduled exchanges spread the winners. This is an explicit exploration-exploitation schedule rather than one big shared context.

Failure modes and caveats

  • Spec risk is the main risk. Lean proves the program meets the spec under the library's semantics and cost model. A spec that omits a constraint, or a cost model that undercounts something real (the README says explicit costing of classical computation and control flow is the next milestone), yields verified-but-irrelevant wins.

  • Baselines matter. "Up to 290x" is relative to a specific prior construction of one routine; the big application gains are against named prior circuits. Whether experts would have found similar savings with comparable effort is not addressed in the blog or abstract.

  • Compute and agent counts are not stated in the blog or abstract.

  • Result is still far from hardware. These reduce resource estimates for future fault-tolerant machines; nothing ran on a quantum computer.

Review checklist for a proof-gated agent search

  • Who writes and reviews the specs, and are they in a separate trusted library from the search output?

  • Does the cost model cover every resource that matters in deployment?

  • Can anything enter shared state without passing the checker?

  • Are baselines the best known, and is the comparison under the same cost model?

  • Is the framework pinned (toolchain, Mathlib versions) so proofs replay?
