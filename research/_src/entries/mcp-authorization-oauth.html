Summary

Jean Lee's post (LinkedIn, 2026-11-12) is a correct primer on how an MCP client gets a token for a remote MCP server, but it describes registration the 2025-06-18 way. In the current spec (2025-11-25), Client ID Metadata Documents are the default for clients with no prior relationship, and Dynamic Client Registration is a fallback. The four principles it names (PKCE, audience binding, least-privilege scopes, no token passthrough) are all MUSTs or SHOULDs in the spec.

The framing matters for anyone building agent harnesses: MCP authorization is plain OAuth 2.1 with the MCP server as a resource server and a separate authorization server. Nothing in it is agent-specific except the problem it solves, which is a general-purpose client that can't know in advance which scopes a tool server needs.

Scope of the spec: authorization is optional, applies to HTTP transports, and does not apply to stdio servers, which take credentials from the environment. Most local MCP servers today are stdio, so this flow only covers remote, hosted servers.

The flow

The post's six steps, with what the 2025-11-25 spec actually requires at each.

StepPost saysSpec requires
1. ChallengeServer answers 401 with authorization details401 with WWW-Authenticate: Bearer resource_metadata="...", and SHOULD add scope= with the scopes needed. Clients MUST parse it.
2. DiscoverClient finds the authorization server and its metadataTwo hops. MCP servers MUST serve Protected Resource Metadata (RFC 9728), which names the authorization server; the client then reads that server's OAuth or OIDC metadata. Clients fall back to the well-known URI when the header has no URL.
3. RegisterClient obtains a client IDPriority order: pre-registered ID, then a Client ID Metadata Document (the client_id is an HTTPS URL the server fetches), then Dynamic Client Registration, then ask the user.
4. AuthorizeUser signs in; auth code flow with PKCEPKCE is MUST, with S256. The client MUST refuse to proceed if the metadata lacks code_challenge_methods_supported. Redirect URIs must be localhost or HTTPS and match exactly.
5. Get tokenCode exchanged for a token for that serverThe resource parameter (RFC 8707, the server's canonical URI) is MUST in both the authorization and token requests. Public clients MUST get rotated refresh tokens.
6. AccessToken sent with each request; server validatesAuthorization: Bearer on every HTTP request, never in the query string. Server MUST check the token's audience is itself. Missing scope at runtime returns 403 insufficient_scope with the needed scopes, which drives step-up authorization.

The step the post leaves out is step-up. Clients start with the scopes from the 401 (or all of scopes_supported, which is meant to be the minimum for basic use) and ask for more only when a 403 names them. That is how least privilege works in practice for a client that can't predict which tools it will call.

Where the post is thin or out of date

  • Registration. "The client obtains its client identifier" hides the biggest change in the 2025-11-25 spec. Client ID Metadata Documents replace Dynamic Client Registration as the default, because DCR let any client mint unlimited registrations and gave the authorization server nothing to verify. CIMD moves trust to the client's domain, which brings its own risks: SSRF when the server fetches the URL, and localhost redirect impersonation, where an attacker presents a real client's metadata URL with their own localhost redirect.

  • Token passthrough. The post says it "prevents misuse of client credentials". The spec's point is narrower: an MCP server that calls an upstream API must get its own token from that upstream, and MUST NOT forward the token the MCP client gave it. Forwarding breaks audit trails and makes the server a confused deputy.

  • Audience binding is only as strong as the authorization server. RFC 8707 support is uneven, so the spec requires clients to send resource and servers to validate the audience anyway, "to enable current and future adoption".

  • Confused deputy for proxy servers. An MCP server that fronts a third-party API with one static client ID MUST get user consent for each dynamically registered client. The post doesn't mention it, and it is the case most proxy-style servers fall into.

  • What authorization doesn't cover. OAuth scopes gate which server and coarse capabilities a token reaches. They say nothing about which tool calls an agent makes with that access, prompt injection through tool results, or per-call approval. Those are harness problems.

Failure modes and a review checklist

Failure modes the spec's security section names, mapped to the spec clause that prevents each:

FailureWhat goes wrongSpec defence
Token accepted by the wrong serverA token for server A works at server B that shares an authorization serverresource on every request; server checks audience

Localhost impersonationAttacker reuses a real client's metadata URL with their own localhost portShow the redirect host; extra warnings for localhost-only clients

Review checklist for an MCP server or client:

  • Server serves RFC 9728 metadata and sends resource_metadata plus scope on 401

  • Client sends resource (the canonical server URI) in both the authorization and token requests

  • Server rejects tokens whose audience isn't itself, including tokens from the same authorization server

  • Upstream calls use a separate token the server obtained itself

  • scopes_supported lists the minimum; extra scopes come through 403 insufficient_scope

  • Client refuses authorization servers that don't advertise PKCE

  • Registration follows pre-registered, then CIMD, then DCR; CIMD fetches are SSRF-guarded

  • Tokens are short-lived, refresh tokens rotate for public clients, nothing lands in a URL

  • stdio servers take credentials from the environment and are not treated as covered by this flow
