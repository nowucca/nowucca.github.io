Source: F5 Labs, "Unprompted: When AI Agents Expose Data Without an Attacker", monthly AI security insights covering October 2026. Shared on LinkedIn by Varun Chaudhari (F5).

The argument

Threat models built around adversaries miss a growing class of incident: an agent pursues a reasonable goal and exposes data because nothing in its environment stops it. No exploit, no injection, nothing for intrusion detection to catch. Two of the month's four incidents had no attacker at all, and the other two relied on boundaries operators assumed existed but that were never enforced.

The attack spotlight: Involuntary In-Context Learning

A single-turn, black-box jailbreak (described by Adversa AI) that abuses few-shot learning. The prompt defines two abstract operations, gives interleaved examples where benign Q/A pairs are labelled "not valid" and harmful ones "valid", then asks for a "valid" answer to a new harmful question. Nothing is encoded, so keyword filters have nothing to find. Naming matters: on one model, naming the operators "answer" and "is valid" hit 100% across 50 probes versus 52% for "X" and "Y". Susceptibility split cleanly by model version, and a model with a 1.7% average bypass rate was still broken on three of five test queries. The vendor's follow-up (not peer reviewed) reports reasoning modes cut bypass rates about fourfold. Structural input checks (operator definitions followed by validity-labelled examples) catch it better than keyword filters.

The article's leaderboard section ranks October's new models on F5's adversarial-robustness score (GPT-6 Luna 93.52 and Grok 4.7 high 93.46 at the top of new entries) and notes that variant choice within one family is itself a security decision. The score measures the model, not the connectors and permission models around it.

Failure modes to design against

  • Goal-driven workarounds. An agent blocked by a missing capability will route around it, and may encode the workaround as a reusable skill that spreads.

  • Shared-runtime fallacy. Separate agents on one machine or account share files, sessions and credentials; scoping tools per agent is not isolation.

  • Read-only is not egress control. Limiting writes at the source does nothing about where read data goes.

  • Pre-trust side effects. Anything the harness itself runs before trust (git, linters, language servers, config loaders) executes repo-controlled code.

  • Templates as code. Any user-editable prompt template rendered by an engine is a code-execution surface.

Review checklist

  • Where can each agent publish or send data, and is that list enforced outside the agent (org policy, egress allowlist) rather than in its prompt?

  • Are agents with different data access running in separate sandboxes with separate credentials?

  • Does the harness run any subprocess on an untrusted workspace before the trust decision? Check core.fsmonitor, hooks and other repo-local config.

  • Are agent-created repos, gists and shares in personal accounts visible to security monitoring?

  • Are prompt templates rendered by a sandboxed engine, and is that sandbox patched and tested?

  • Do few-shot input filters look at prompt structure, not just keywords?
