Sources: the Jetpack AppFunctions release page and the androidx.appfunctions API reference. There is no developer guide or overview linked from the release page, which is itself part of the finding.

Version 1.0.0 shipped stable on 18 November 2026, in three artifacts: appfunctions (core), appfunctions-compiler (a Kotlin Symbol Processing plugin) and appfunctions-testing. The library's own description of what it does is worth quoting exactly, because it is more precise than most second-hand accounts of it: it "allows apps to share functionality and data with AI assistants, enabling them to discover and execute tasks directly on the device to fulfill user requests".

This matters beyond Android. It is a platform answer to a problem that has so far had only application-level answers: how does a program expose its capabilities to an assistant it does not control? MCP solves it with a protocol over a transport that each side opts into. This solves it by making the operating system the broker — the app declares functions, the platform indexes them, and a caller asks the platform. The architectural consequence is that no network is involved, no server runs, and the trust boundary moves from a connection to an OS-mediated IPC call.

What the API surface tells you

No guide exists, so the reference's type names are the design document. They tell a coherent story.

Declaration is annotation-driven and compile-time. The package exposes AppFunctionDeclaration (renamed from AppFunction during the alpha series), AppFunctionSerializable for the types that cross the boundary, AppFunctionSignature, AppFunctionServiceEntryPoint, and an AppFunctionInstruction. The Gradle setup directs you to "Use Kotlin Symbol Processing (KSP) for the appfunctions compiler plugin", and release notes refer to "the generated file name" — so the schema a caller sees is generated from the code that implements it, not hand-maintained beside it. That is the right choice and the one most tool-exposure systems get wrong: a hand-written schema drifts from its implementation, and a drifted tool description is worse than a missing one, because the caller believes it.

Discovery is a query against a platform index. AppFunctionManager, AppFunctionSearchSpec (which gained a scope during the alphas), AppFunctionMetadata, AppFunctionPackageMetadata, and AppFunctionsChangeEvent for observing changes. A caller searches rather than being handed a static list, and can watch for the set changing — which is the correct model when the available tools depend on which apps happen to be installed, and change as the user installs and removes them. Most tool-calling systems assume a fixed tool list for the life of a session; this one cannot.

Execution is request/response with a typed error channel. ExecuteAppFunctionRequest, ExecuteAppFunctionResponse.Success and .Error, plus an exception hierarchy that is unusually specific: denied, disabled, not-found, invalid-argument, limit-exceeded, not-supported, permission-required, cancelled, and a system error. Distinguishing denied from disabled from permission-required from not-found is the difference between a caller that can act on a failure and one that can only report it — an agent told "not found" should search again, and one told "permission required" should ask the user. Few tool protocols make that distinction available at all.

And there is an AppFunctionTestRule in the testing artifact, which is a small signal that the team expected these to be tested like code rather than tried like features.

One other detail is worth noting precisely because of what it implies about the ecosystem: during the beta, a metadata field was renamed from description to instructions — the release note says this was "to align with MCP naming conventions". That is the only mention of MCP anywhere on these pages. The documentation does not say AppFunctions is built on MCP, compatible with it, or an alternative to it. It borrowed a name.

The gap, and it is the important one

For a mechanism whose entire purpose is letting one program invoke another's capabilities on a user's device, the documentation does not state who may call.

There are strong hints that an access model exists. An AppFunctionAccessLevel annotation was added during the alphas "to support access restriction setting". There is an AppFunctionState with a manager-level query for the states of functions, which replaced a simpler per-function enabled flag. There is an AppFunctionPermissionRequiredException and an AppFunctionDeniedException. So the pieces are there.

What is not on these pages: what the access levels are, who sets them, whether the user is asked, whether approval is per-app, per-function or per-call, whether any installed application holding a permission can enumerate and invoke another app's functions, or what the platform shows the user when it happens.

This is not a complaint about an incomplete API; the API looks thought through. It is an observation about what shipping stable means. A capability-exposure mechanism's security model is not an implementation detail to be documented later — it is the thing an app developer must understand before deciding to expose anything at all. An annotation named AppFunctionAccessLevel with no documented semantics is an invitation to pick a value by guessing, and the guess that gets picked under deadline is the permissive one.

Also unanswered on these pages: whether execution is synchronous from the caller's perspective, whether long-running operations are supported, whether the providing app's process must already be running, the minimum API level, and how a caller first discovers that any functions exist. registerAppFunction and a CallbackAppFunction are present but marked experimental, which suggests the dynamic and callback-driven cases are still being worked out.

Correcting the framing this usually gets

The account that circulates with this release says it enables "AI agents like Gemini" to interact with app capabilities. The documentation says "AI assistants", and names no assistant — not Gemini, not any other. Whether a particular assistant is a caller today is not established by these pages. The distinction is not pedantry: "Gemini can call your app" and "the platform exposes an interface that assistants may call" imply very different things about who you are trusting.

A review checklist before exposing app functions

  1. Find the access-control documentation before you annotate anything. If you cannot establish who may call a function and whether the user is asked, treat every function you expose as callable by any software on the device.

  2. Expose reads before writes. A search or lookup that leaks nothing is a safe first function; a create-or-modify function is a capability grant.

  3. Check what each error variant reveals. A not-found versus denied distinction is useful to a caller and is also an enumeration oracle; decide deliberately which failures are distinguishable.

  4. Treat the generated schema as public API. It is generated from your code, so a refactor can change what callers see — version it and watch it in review.

  5. Write the function description for a caller that will act on it literally, and keep it accurate about side effects. The field is the caller's only instruction.

  6. Assume the tool list is unstable. Functions appear and disappear with app installs; anything built on top needs to handle the set changing underneath it.

  7. Test the functions, not the feature. A test rule ships for this reason.

  8. Decide what a user sees when another program invokes your app's function, and do not assume the platform shows them anything.
