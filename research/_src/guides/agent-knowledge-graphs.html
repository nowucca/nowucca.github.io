Bottom line

Use grep and file reads as the baseline for giving an agent knowledge. Add a code graph, knowledge graph, ontology or vector index only after it beats that baseline on held-out questions from your own corpus, scored on answer correctness as well as on tokens and time. Enforce access control in the retrieval path the agent actually calls, and check each interface it can reach. Treat the published figures as early evidence, mostly measured by the people who built the tools.

The default these sources describe is lexical. Wavestone's source-code survey of eleven agent systems found that none uses vector-embedding code retrieval (R054-f1), and it recommends no code RAG unless it beats ripgrep plus tree-sitter on a held-out set (R054-f5). That survey reads source code and runs no head-to-head comparisons (R054-f1), and only part of the paper was read. In a separate study of agent memory, the authors gave the agent a regex search over a verbatim log of its own history, with no embeddings or index (R230-f1). After RL training, that setup had the highest mean accuracy across their five tasks, 66.4 percent against 56.3 for MemGPT-style memory (R230-f4). It was one 9B model and one trained run per strategy (R230-f6).

The code-graph evidence is thin and vendor-run, and CodeGraph's figures report tokens and cost rather than answer quality (R134-f2). CodeGraph's authors asked one architecture question on each of 7 repos, with Opus 4.8 and a median of 4 runs per arm (R134-f1). Against the same Claude Code setup with CodeGraph blocked (R134-f4), they report 88 percent fewer tool calls, 62 percent fewer tokens and 44 percent lower cost on average (R134-f2), and the claims extracted report no answer-correctness score for those runs. Graphify's only code benchmark is 6 questions on one repo, where its authors report 82.0 percent key-fact coverage against 70.8 percent for a grep and read baseline (R076-f3). Trail-code, which injects learnings seeded from past sessions and PR comments rather than a code graph (R199-f4), reports 33 of 50 SWE-bench Verified instances resolved against 27 of 50 without it, with one model, in its authors' own run (R199-f2).

Keep conversational-memory benchmarks separate from code. On LOCOMO, Graphify's recall lead over supermemory came with lower QA accuracy, though it scored above mem0 (R076-f1). Its recall at 10 was 0.497 against 0.149 for supermemory and 0.048 for mem0, and its QA accuracy was 45.3 percent against 49.7 and 27.3 (R076-f1). On LongMemEval-S, with 50 questions, it ties dense RAG at 76 percent (R076-f2). A retrieval lead did not give Graphify the best answers in those runs (R076-f1) (R076-f2). The retrieval-model results are the authors' own figures on public benchmarks such as BEIR and MMTEB (R261-f1) (R137-f1) (R171-f1), and none of those claims involves an agent.

Most entries here rest on READMEs or model cards, one is a LinkedIn post with no data (R204-f3), and "How this was made" says how much of each was read. Claims from thinly read sources carry less weight below.

Do

  1. Make grep and read the baseline you have to beat. Wavestone's survey found no studied harness using vector-embedding code retrieval (R054-f1), and its test for code RAG is a held-out comparison against ripgrep plus tree-sitter (R054-f5). Graphify's code benchmark used a grep and read baseline (R076-f3), and CodeGraph compared against the same harness with its tool blocked (R134-f4). Both rest on few questions, 6 on one repo (R076-f3) and one on each of 7 repos (R134-f1), and the claims do not say whether either set was held out.

  2. Score retrieval and answers separately, then report both. Graphify's LOCOMO recall was about three to ten times the comparison systems', while its QA accuracy was lower than supermemory's (R076-f1). GraphRAG Zero raised global assertion coverage from 53.4 to 57.4 percent over vector RAG (R127-f2), while vector RAG kept higher chunk precision (R127-f3). AutoRAGBench scores retrieval systems through five held-out small answering models, so that retrieval quality rather than the answerer is measured (R211-f1). A practitioner post also says to measure retrieval alone with recall at k before tuning chunk size, though it offers no data (R204-f1) (R204-f3).

  3. Read code-graph savings as tokens, time and cost on single questions. CodeGraph's averages hide wide per-repo spread: cost savings ran from 78 percent on Excalidraw to about even on Gin, while Gin and Django still used 52 and 41 percent fewer tokens (R134-f3). Its authors block the tool in the baseline arm; on an unblocked harness 26 of 28 baseline runs used it through Bash, and earlier published figures lacked the block (R134-f4). Trail-code, which injects learnings seeded from past sessions and PR comments rather than a code graph (R199-f4), covered on its own harness 162 runs on 2 repos at equal average correctness of 93 percent, and the push mode lost 3 correctness points on one corpus (R199-f1).

  4. Have the agent look things up rather than recall them. This is an analogy from a clinical-coding extraction task, not a retrieval-for-agents result. There, codes recalled from memory included 13 to 18 percent that exist in no release, and picking from 20 retrieved candidates scored about ten times higher, on 40 development documents over three runs (R039-f3). In a data-analysis benchmark, Opus 5.5's execution accuracy rose from 54.6 with schema only to 86.6 with search tools, in its authors' runs over 256 tasks (R070-f3).

  5. Give the agent search tools, and add file access only if it pays for its extra tokens. In that data-analysis benchmark, one retrieved document added at most 1.5K tokens for a 9 to 17 point gain, while file and CLI access cost 2.2 and 2.6 times the input tokens per correct answer of search tools without better accuracy (R070-f6). In PageIndex's README, native PDF input cost 2.1 times its retrieval at 52 pages and 16.6 times at 420 pages, with prompt caching excluded and few documents (R010-f4).

  6. Expect accuracy to depend strongly on the model and effort setting. On PageIndex's own financial-qa benchmark, Sonnet 5.5 ranged from 82.0 percent at high effort to 98.0 percent at max, a vendor-run figure (R010-f2). The top configuration reached 99.0 percent at 10.73 dollars per 100-question run, a vendor-run figure (R010-f1).

  7. Enforce access control in the retrieval path, and check what the policy covers. TrustGraph evaluates SHACL policies per node as Allowed, Filtered or Violation, with a per-request user context and audit events (R183-f1). Its README states that policy for REST, SPARQL and GraphRAG but does not state it for MCP, vector search or DocumentRAG, and the default is open mode with no policies (R183-f2). In OntoBricks, the MCP guide's machine-to-machine connection shares one service-principal identity for all users, so per-user access control needs OAuth user-to-machine (R256-f3). Omnigraph's MCP tools run the same Cedar action as its HTTP routes, so policy alone decides what an agent may run (R074-f1), and its release notes tell operators to keep an agent read-only by narrowing its policy and giving it its own credential (R074-f2). auto-ontology-mcp drops RBAC and PII detection (R028-f5) and stores datasource passwords in plain text (R028-f3).

  8. Know how each index stays fresh. auto-ontology-mcp does not watch files, so passages go stale unless the agent re-reads changed documents and saves them again (R028-f4). OntoBricks reads live rows only in Lakehouse view mode, and in table mode its Explorer and raw SPARQL can disagree until a full Build (R256-f2). CodeGraph runs a file watcher with a staleness banner and reconciles on connect (R134-f6).

  9. Guard agent writes to a graph store. Relate's opt-in safe mode refuses unlabeled CREATE and MERGE and MATCH without LIMIT, but it is off by default and never auto-detected (R055-f3). Relate keeps the whole graph in RAM in one process and has no general write-skew detection (R055-f4). TrustGraph's extraction rejects triples that violate domain, range and subclass constraints, though it is not a full OWL reasoner (R183-f3). No source here measures whether this changes agent outcomes.

  10. Keep provenance and confidence with what the graph returns. Graphify tags each edge EXTRACTED or INFERRED with a confidence tag and rates a path by its weakest hop (R076-f5). TrustGraph records provenance with PROV-O and writes retrieval traces to a named graph (R183-f3). No source here measures whether these tags change agent outcomes.

  11. Keep tool definitions small. auto-ontology-mcp's authors report that one toolset setting cuts the tool definitions the model sees from about 52,000 to about 12,000 characters (R028-f6). Relate caps agent-mode output at 100 rows with the truncation stated in-band and returns structured JSON errors (R055-f2). No source here measures whether this changes agent outcomes.

  12. Choose embedding and retrieval models on your own retrieval task, not a leaderboard average. blink-multilingual-64M's author reports an MMTEB v2 average of 51.60 against 48.37 for a truncated rival at 256 dimensions (R137-f1), yet its retrieval score is 47.52 against 47.62, so the gain lies outside retrieval (R137-f2). SPARSEUP-v2's authors report BEIR-15 nDCG@10 of 57.2 against 50.5 for SPLADE-v3 (R261-f1), but it leads only 5 of 10 beyond-BEIR sets on nDCG@10 (R261-f3). NeuML's Atto models are averaged over three small BEIR datasets (R171-f1), and the 110M reference baselines score above every Atto model (R171-f2).

  13. If an agent builds the retrieval pipeline, test it on data it never saw. In AutoRAGBench, 72 of 77 builds improved on development checks, yet the model with the largest median development gain ranked tenth on hidden tests (R211-f6). Every agent-built system retrieved slower on average than the reference, 0.50 to 2.01 seconds per question against 0.35, a figure excluded from the score (R211-f5).

Avoid

  • Reading retrieval recall as answer accuracy. Graphify's LOCOMO recall lead sits beside a lower QA accuracy than supermemory (R076-f1), and on LongMemEval-S it ties dense RAG (R076-f2). Both are conversational-memory benchmarks, not code (R076-f3).

  • Quoting figures nobody could find or reproduce. The 71.5x tokens-per-query figure for Graphify is not in its README and comes from a LinkedIn post that was not re-read (R076-f4). PageIndex's 63-question 10-K notebook figures could not be verified (R010-f7), and its FinanceBench 98.7 percent comes through the vendor's own product and cannot be reproduced from the repo (R010-f5). SPARSEUP-v2's 55.8 at 128 terms per document was not found in the card or paper text read (R261-f5).

  • Combining numbers measured under different setups. CodeGraph's +82 percent residual retrieval context comes from a different model, 3-turn sessions and 56 sessions, which its own doc calls not comparable to the README table (R134-f5).

  • Reading memory scaling as accuracy at scale. AtlasKV's authors report under 20GB of VRAM at 1 billion triples, but accuracy was tested only up to 10,000 triples (R160-f3) (R160-f2). Their own limits include a flattened graph that blocks multi-hop reasoning, and answer relevance was scored by GPT-4o (R160-f4).

  • Repeating superlatives the comparison table does not support. LACONIC-8B and LACONIC-3B score above SPARSEUP-v2 on BEIR-15, and LateOn ties it (R261-f2).

  • Treating practitioner advice as evidence. The chunk-size post is opinion with no data, and its related papers were not read (R204-f2) (R204-f3).

  • Assuming a policy covers interfaces the docs do not name. TrustGraph's README does not state policy for MCP or vector search (R183-f2), and OntoBricks' release notes and MCP guide describe different identities for graph tools (R256-f3).

  • Skipping the privacy and telemetry details in the docs. Graphify's README says no telemetry yet logs queries locally to a cache file (R076-f6). Relate's telemetry is on by default in the standalone CLI (R055-f6), and Trail-code's README discloses that seeding sends scrubbed past-session content to Anthropic under the user's login (R199-f4).

  • Turning a vendor feature into a design rule. Graphify's strict mode denies Read and Grep unless a graph query was made recently (R076-f6), and nothing here shows that forcing graph use improves answers. SelfGraph's answerability check (R159-f3) and txtai's GraphRAG notebooks (R106-f2) have no evaluation behind them.

How this was made

Twenty-two sources were used.

  • 16 in the knowledge and code graphs set: READMEs and project docs (R010 PageIndex, R028 auto-ontology-mcp, R055 Relate, R076 Graphify, R106 txtai, R134 CodeGraph, R159 SelfGraph, R183 TrustGraph, R199 Trail-code, R256 OntoBricks), a Microsoft Research story (R127), a paper (R160 AtlasKV), model cards and a vendor blog for retrieval models (R261 SPARSEUP-v2, R137 blink-multilingual-64M, R171 Atto), and a LinkedIn post with no data (R204).

  • 6 related sources from other sets, used where they bear on retrieval for agents, with R039 used only as an analogy: R054, a source-code survey, from multi-agent; R211 AutoRAGBench, R070 SynthCorp and R039, a clinical-coding extraction article, from evals; R230 GrepMem from context; and R074, Omnigraph release notes, from security.

A Sonnet model extracted 74 claims for the graphs set, each tied to a location in its source. Opus wrote this guide from those claims and the related claims.

For nine of these the original LinkedIn posts were not re-read, so their claims rest on the READMEs and docs.

  • R204 is a LinkedIn post with no data, and its linked papers were not read (R204-f3). It is cited only as practitioner advice.

  • R028, R055, R106, R159 and R183 publish no benchmarks (R028-f2) (R055-f6) (R106-f1) (R159-f1) (R183-f1), and R256's claims contain no benchmark figures (R256-f1). They are used for design and access-control practice, not as evidence that the approaches work.
