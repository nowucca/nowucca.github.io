pstack: a Cursor engineer's rigor playbooks for coding agents

The premise

Frontier models take shortcuts: they declare success because code compiles or because they say it works. pstack is a set of skills built to make one agent's work trustworthy enough that you can run several in parallel. The stated goal is less code of higher quality, not more output.

Architecture

  • One entry point. /poteto-mode reads the task, matches it to one of 22 playbooks, opens a todo list whose first items are the playbook's steps copied verbatim, and calls other skills as steps need them.

  • Playbooks by task type. Investigation (read-only), bug fix with runtime evidence, perf against a baseline, "hillclimb" (one metric, hypothesis loop, one commit per accepted win), runtime and trace forensics, feature, refactoring, prototype, visual parity, authoring a skill, blinded eval of a skill change, PR babysitting, shipping a verified stack, autonomous and autopilot runs, session pickup, pause safely, multi-phase plans, worktree cleanup, and opening a PR (run at the end of every other playbook).

  • Principles cited, not just listed. The skill groups principles (domain modelling, boundary and type discipline, idempotency, verification, delegation, meta) and requires the agent to name each principle that shaped a decision and the choice it changed, citing only principles it actually read that session.

  • Situational skills the mode routes to: /interrogate (different models try to break a diff, keeping only findings a run proves), /arena (N parallel attempts, take the best parts), /swarm (parallel workers, one report), /blast-radius, /benchmark-checklist, /tdd, /show-me-your-work (a committed decision log), verification-skill generators, including one for formal verification, and /correct, which mines history for repeated mistakes and fixes each at the highest level that works.

  • Multi-model by default. Roles map to models through a setup skill; review panels mix models from several vendors, and the most expensive model is reserved for when it is named or after repeated failures.

Notable rules

  • Prove It Works. Verify against the real artifact, not a proxy or "it compiles"; a self-report is not proof.

  • Encode Lessons in Structure. If you write the same instruction twice, turn it into a lint, metadata flag, runtime check or script.

  • Explain the Number. Before trusting a measurement, find what limits it.

  • Never Block on the Human for reversible work: proceed, present, let them correct.

  • No planning skill, on purpose. The author's position is that the best spec is code; the host's plan mode is available if wanted.

  • Replies label evidence as measured, inferred or guess, and never hand the human a check the agent could run.

Tradeoffs

  • Context weight. A large skill tree and verbatim playbook steps consume context; the skill itself has a rule to push bulk work to subagents.

  • No-plan stance suits engineers who think in code and small verifiable commits; it is a weaker fit for cross-team work where the plan is the coordination artefact.

  • Cursor-first. Some steps rely on Cursor-only features and are skipped with a note in other hosts; behaviour differs by harness.

  • Multi-model panels raise cost per task in exchange for adversarial review.

Failure modes to watch

  • Playbook mismatch. A task routed to the wrong playbook inherits the wrong evidence standard.

  • Principle citation as theatre. Requiring the agent to name principles can produce plausible citations; the "only cite what you read this session" rule mitigates but does not verify.

  • Autonomous merge playbooks ("land the stack even if CI flakes") need branch protection and review settings that match the trust you are granting.

  • Auto-update off by default in Claude Code means teams can silently diverge in pstack versions.

Review checklist for adopting a rigor skill pack

  • What counts as proof of done for each task type, and is it a real artifact?

  • Does the pack route bulk work to subagents to protect the main context?

  • Which playbooks can merge or push, and do your repo settings constrain them?

  • Is the version pinned across the team?

  • Do you have a project-local way to verify app behaviour, or does the pack need to generate one first?

  • Measure on your own tasks: fewer reverts and review findings, not just faster completion.
