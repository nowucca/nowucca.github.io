OntoBricks: an ontology over live warehouse tables, served to agents over MCP

Source: a LinkedIn post by André Lindenberg on databrickslabs/ontobricks (version 0.9.3, about 490 stars, Databricks License), with the repository's README, backend guide and MCP guide. It is a Databricks Labs project, not a supported Databricks product.

The problem it targets

The usual enterprise knowledge graph is a separate database loaded from the warehouse. It is a copy, as fresh as its last load, and it needs its own governance. Agents then reason over stale or out-of-policy data. OntoBricks puts the meaning (an OWL ontology) on top of the tables where the data already lives and serves the graph to agents from there.

Architecture

  • Ontology layer. Design classes and relations on a canvas, import standards (FIBO, CDISC, HL7 FHIR and others) or your own OWL, or let an LLM wizard detect entities from table metadata and parsed documents, then add relations, attributes and axioms. Runs append; locked entities are never renamed or removed. A pitfalls checker runs 19 structural and semantic checks.

  • Mapping layer. An LLM proposes SQL mappings from each class and relation to Unity Catalog tables, views or metric views. Mappings compile to W3C R2RML, and schema-drift warnings flag upstream renames and drops.

  • Graph layer. Triples are defined by R2RML views over the source tables. A pluggable backend per domain: Lakehouse (Delta triple views, no extra infrastructure), Lakebase Postgres (a synced table kept in step by a snapshot pipeline, plus an app table for reasoning writes, unioned behind one view), Neo4j, or no graph at all for ontology-only domains.

  • Reasoning and quality. OWL 2 RL inference, SWRL rules and SHACL shapes compiled to SQL; per-entity data-quality checks and business rules.

  • Agent surface. Each domain publishes chosen MCP tools (describe the ontology, find entities, traverse, check SHACL facets, trigger class actions), plus GraphQL and read-only SPARQL that shows the generated SQL.

  • Governance. Versioned domains with a DRAFT, IN-REVIEW, PUBLISHED lifecycle enforced on the server, one editor per draft, a review quorum and an append-only decision log. MCP tools run as the end user.

Freshness is per path, not per system

The post's key point is that "current" depends on which path a query takes. On the Lakehouse backend, SPARQL compiles to SQL over views and reads current rows. Explorer and MCP entity lookups use materialized search and adjacency indexes, which are snapshots refreshed on build. On Lakebase, the graph itself is a synced snapshot. An agent can therefore get a current answer from one tool and a stale one from another in the same session.

Tradeoffs

  • No copy, but query cost moves to the warehouse. Every SPARQL query becomes SQL on a warehouse; deep traversals over views can be slow or costly, which is why indexes and snapshot backends exist.

  • LLM-generated ontology and mappings are a starting point. They need human review; the lifecycle and append-only design help, but a wrong mapping produces confidently wrong triples.

  • Platform lock-in. It runs as a Databricks App on Unity Catalog, a SQL warehouse and Lakebase. Neo4j is the only off-platform backend.

  • OWL 2 RL and SWRL are a subset of reasoning. Rich ontologies imported from standards may use constructs outside what is inferred.

  • Labs status. No vendor support guarantees.

Failure modes to watch

  • An agent mixing a SPARQL answer (current) with an MCP lookup (index snapshot) and reporting an inconsistency as a fact.

  • Schema drift upstream silently emptying a class until someone reads the warning.

  • Over-broad MCP publication exposing classes or actions an agent should not reach; publication is per domain and should be minimal.

  • Class actions that trigger jobs from an agent without a human check.

Review checklist

  • For each MCP tool an agent uses, is it known whether it reads live rows or a snapshot, and how old the snapshot can be?

  • Are LLM-proposed mappings reviewed before a version is published?

  • Do MCP tools run under the end user's identity and Unity Catalog permissions?

  • Is the published tool set the smallest that serves the use case?

  • Are SHACL shapes in place for the facts agents rely on most?

  • Is warehouse cost monitored for agent-driven SPARQL?
