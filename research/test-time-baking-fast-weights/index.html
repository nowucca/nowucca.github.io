Test-time Baking: replacing a KV-cache with fast weights, and where the 23x stops being 23x

Published 2026-11-12Summarized 2026-11-28

Read the original

inference-efficiencykv-cachetest-time-trainingbenchmarksclaim-checkingrendering

Source: arXiv:2611.17331, "TTB: Test-time Baking for Efficient Rendering of Decoder-only View Synthesis Models", Lin, Hachiuma, Choe, Chen, Wang, Lin, Chiu, Liu and Sun (NVIDIA and National Yang Ming Chiao Tung University), v1 stamped 12 Nov 2026; project page. The project page's venue claim is discussed below.

What it actually does

The starting point is a decoder-only view synthesis model (DVSM) that renders novel views of a scene by attending, for every output view, across a cache of key/value tensors derived from the context views. That cache is the scene state. Its size grows with the number of context views, and every rendered frame pays attention against all of it. At 64 context views and 960p, the baseline runs at 1 frame per second.

TTB replaces each cross-view attention layer with a layer that holds a small fast-weight SwiGLU MLP. Once per scene, during reconstruction, the model runs an inner optimisation loop — three Muon steps against an MSE objective — that fits that MLP to reproduce what the cross-view attention layer would have output. The distinguishing design choice is the regression target: it is the attention layer's output, not the raw value tokens that test-time-training methods such as LaCT regress onto. Each context view contributes a camera-only "rendering" token as MLP input and a second token carrying RGB as the target.

After the bake, the paper's words are that "we no longer need to cache the KV; only the updated MLP fast weights are stored." Rendering becomes a fixed-cost forward pass through a fixed-size MLP: O(1) per view in the number of context views, where the baseline was O(V).

The outer loop matters architecturally. The model is trained end to end on DL3DV-10K from a DVSM checkpoint, and the rendering loss is backpropagated through the inner-loop bake. The fast-weight MLP is not bolted on at inference; the network is trained in the knowledge that it will be baked.

The numbers, and what they are numbers of

The headline is real and it is in the paper: "up to 23x rendering speedup," stated as 23x against DVSM and 2.3x against LaCT. Two qualifications change how it should be cited.

It is a ratio of integers from a table. On DL3DV at 960p over 140 held-out scenes, measured on a single A100, the reported frame rates are DVSM 4 / 2 / 1 and TTB 23 / 23 / 23 at 16 / 32 / 64 context views. The 23x is 23 divided by 1. Both operands are printed to the units place, so the true ratio sits somewhere in a wide band — and the speedup is 23x only in the regime where the baseline has already collapsed to a single frame per second. At 16 views the same table gives roughly 6x. The flat 23 across all three view counts is the actual finding, and it is a better headline than the ratio: TTB's render cost does not move when the scene gets bigger.

Reconstruction is slower, not faster. The bake is additional work. On the same benchmark, reconstruction takes 5.4 / 18 / 65 seconds against the baseline's 4.4 / 15 / 60. LaCT and the ablated TTB variant do it in 1.9 / 3.7 / 7.3. So this is a trade of one-time setup cost for per-frame cost, and the paper's own limitations note the setup side is quadratic in view count: "Its inner-loop cross-view attention also makes reconstruction quadratic in V, a drawback for single-shot scenarios." The method pays off for a scene rendered many times and loses for a scene rendered once.

Quality is lost at scale, and the configuration that recovers it is off by default. On DL3DV at 64 views, baseline PSNR is 31.11 and TTB is 30.20 — 0.91 dB down. At 32 views the gap is about 0.21 dB. At 16 views TTB is 0.14 dB ahead on PSNR while behind on both SSIM (0.849 vs 0.852) and LPIPS (0.177 vs 0.170), which is the signature of a method trading perceptual detail for pixel error. A second configuration using "local-duplicate" routing closes the gap (31.33 at 64 views, slightly ahead of baseline) but the paper states it is "turned off except stated otherwise," and the authors call it "a heuristic" whose learned version is future work. A "comparable quality" claim therefore rests on an off-by-default heuristic, not on the default configuration.

On two-view Re10K at 512x512 the method is at parity or marginally ahead (31.28 vs 31.17 PSNR). On in-the-wild captures at 64 views it splits: behind on Mip-NeRF 360 (24.49 vs 24.76), ahead on Free (26.05 vs 25.57) and Hike (23.77 vs 23.10). The pattern across all of these is that TTB's deficit appears where the scene state is largest.

Parameter counts, from the paper's own table: DVSM 163M, TTB 271M, the ablated TTB 244M, LaCT 379M. These are model sizes rather than runtime footprint. The project page's "85x smaller" claim concerns scene state rather than parameters, and its accompanying chart does not attribute its series unambiguously, so that figure should be treated as unconfirmed.

The structural idea worth taking

Stripped of the rendering domain, the pattern is: a cache whose size grows with input is replaced by a fixed-capacity function fitted to reproduce that cache's output. The cache is not compressed, evicted or quantised — it is distilled, once, into weights, and then discarded entirely.

That reframes a familiar cost curve. Where cache-based systems manage a growing state with eviction policies, paging and compression, this approach caps the state by construction and pays for the cap in fidelity. The fidelity cost is not uniform: it is near-zero when the cache was small and real when the cache was large, which is exactly the opposite of what a compression scheme does. Compression gets harder as state grows; distillation into fixed weights gets lossier as state grows, and the paper names this directly — quality "saturates at large V" because of "the fixed capacity of its fast-weight MLP."

The other transferable choice is the regression target. Fitting the attention layer's output rather than its inputs means the fast weights inherit whatever the attention had already computed, instead of having to rediscover it. The paper notes the target "can also be tokens from arbitrarily non-linear layers," which is the sentence that makes this more than a rendering trick.

Failure modes

  • Single-shot workloads. Reconstruction is slower than the baseline and quadratic in context size. Anything rendered once is strictly worse off.

  • Capacity saturation. Beyond some scene size the MLP cannot hold the state, and quality stops improving as more context is added. There is no reported point at which this becomes catastrophic, only the stated saturation.

  • Heuristic routing. The configuration that closes the quality gap is hand-designed and not learned. Its behaviour on scenes unlike the benchmarks is unknown.

  • Interpolation only. The authors state the method "is built on reconstruction rather than generation, interpolating within context views without extrapolating to unobserved viewpoints." It will not invent a view it was not shown from a nearby angle.

  • Scope. The base model baked is DVSM specifically, finetuned from its Re10K checkpoint with DINO injection. Nothing here has been shown to transfer to another architecture.

A venue claim that does not check out against the paper

The project page carries "NeurIPS 2026 · Spotlight" and repeats it in the page's own metadata. The PDF says only "Preprint." and carries no venue or designation anywhere in its body. The abstract page shows no comments field and no venue. The claim may well be accurate — a page updated after acceptance would look exactly like this — but it is single-sourced to the authors' own site and cannot be confirmed from the paper or from a conference listing. Cite it as the project page's claim, not as a fact about the paper.

A smaller discrepancy in the same area: the PDF is stamped 12 Nov 2026 while the abstract page gives a submission date of 2026-11-13.

Release

The project page offers code at github.com/NVlabs/DVSM, weights at huggingface.co/nvidia/DVSM, and an interactive demo at huggingface.co/spaces/nvidia/DVSM, described as running the full pipeline on one GPU with pose estimation in front of it. The paper itself links only the project page. None of the three artefact links is confirmed against a primary source, so treat the release as announced rather than verified.

Review checklist

For anyone evaluating a claim of this shape — a growing cache replaced by a fixed-size learned substitute:

  1. Is the headline ratio computed from rounded figures? Check whether either operand is printed to the units place, and whether the best ratio occurs only where the baseline has degenerated.

  2. What does setup cost, and how does it scale? A per-frame win financed by a one-time cost is only a win above a break-even frame count. Ask for that number.

  3. Which configuration produced the quality figures? If parity requires an option the paper describes as off by default, the default configuration's numbers are the ones that matter.

  4. Does the deficit grow with state size? For a fixed-capacity substitute it should. A paper reporting a constant deficit across state sizes has either not tested far enough or is measuring something else.

  5. Is the quality metric set consistent? PSNR ahead with SSIM and LPIPS behind is a real signal, not noise.

  6. Is the regression target the layer's input or its output? The output target is the stronger design and the one that generalises past the paper's domain.

  7. Is the venue designation sourced to anything but the authors' page? Check the paper and the conference listing before repeating it.

  8. What exactly is released, and does it resolve? Announced artefacts and available artefacts are different claims.
