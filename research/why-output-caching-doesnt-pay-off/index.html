Why caching model outputs doesn't pay off

Read the original

Source: Sean Goedecke, "Why output caching doesn't work", shared in his LinkedIn post, 2026-11-20.

The argument

Input (prefix/KV) caching is what makes multi-turn agent economics work. Agents also repeat themselves in their output: quoting code back in PR explanations, re-quoting evidence documents, echoing sample outputs for a human to check. Output tokens cost more than input tokens, because input is ingested in parallel while output is decoded one token at a time. So it seems tempting to "cache" outputs, for example by training the model to emit a reference like src/script.py:12-15 or a pointer into its own history, and letting the harness expand it.

Goedecke's conclusion is that this is mostly not worth doing, for an Amdahl's-law reason. In his own agent histories, only about 6% of output tokens are visible text. About 50% are reasoning tokens and about 44% are tool calls. Even an implausibly good scheme that removed two-thirds of visible output would save about 4% of output tokens.

He adds two supporting points, both stated with moderate confidence: frontier models probably don't loop much in their reasoning, and inference providers likely already exploit repetition through n-gram-based speculative decoding, which speeds up repeated spans without changing token counts.

Where the output-token savings actually are

The 94% that users don't see. That mostly depends on model capability: a stronger model reaches the answer with fewer reasoning tokens and fewer tool calls. This is why a model that is several times more expensive per token can be cheaper per task. Harness quality helps too, though he thinks harness advantages are easy to copy.

Engineering takeaways

  • Measure your own token mix before optimising. Break output into visible text, reasoning and tool-call arguments per session. The 6/50/44 split is one person's workload, not a law.

  • Tool calls are the biggest lever a harness controls. Edit tools that send diffs or find-and-replace instead of whole files already removed most of the old repetition; check that your tools don't make the model re-emit content it already wrote.

  • Price per task, not per token. Compare models on cost to a correct result on your own tasks.

  • Reference-instead-of-repeat is still a UX choice. Pointing to file:line can make answers shorter and easier to check; just don't sell it as a cost win.

Caveats and failure modes

  • The token split is anecdotal and agent-specific. Workloads that are mostly long-form generation (reports, code generation from scratch) have a much larger visible share.

  • Tool calls can contain hidden repetition, for example content drafted in reasoning and then re-emitted in a tool argument. The author flags this as unknown.

  • Reasoning-token counts are often opaque or summarised by providers, so the split is hard to verify on closed models.

  • Expansion schemes add risk: a harness that expands references can show the user content the model never actually checked.

Review checklist

  • Do we know our per-session split of visible, reasoning and tool-call output tokens?

  • Do any tools force the model to re-emit large existing content (whole files, full documents)?

  • Are model choices compared on cost per completed task?

  • Is input caching (the real lever) protected: stable prefixes, no timestamps in system prompts?
