shrink-anything: delete dead code, keep the cut only if your tests still pass

Source: the EL4CTEO/shrink-anything README, surfaced by a practitioner post the same day. MIT licensed, npm and crates.io, early repo. Benchmark numbers are the project's own.

The problem it names

Coding agents write code faster than anyone deletes it. Functions nothing calls, files nothing imports, packages nothing uses, assets nothing shows: the agent reads all of it on the next task, CI builds it, users download it. The framing that makes this more than a lint rule is the token one — every line removed is a line the agent stops reading. The README claims 46% fewer tokens to read on its demo app.

The mechanism

One command: shrink-anything go --agent claude -- npm test, where the part after -- is any command of yours that fails when the app is broken. Or step by step: scan (changes nothing), cut -- <check>, task --agent <cli> for the judgment calls, weigh dist, verify, undo, report, doctor.

The safety design is the interesting part, and it is the same shape as record-and-replay porting tools:

  • Your check is the oracle. A cut stays only if your command exits 0 and at least as many tests run as before — that second condition is what stops a deletion from silently removing test cases. A check that already fails is refused, because it can prove nothing.

  • Batch, then bisect. Cuts go in as a batch; if the check fails, the batch is split until the single breaking cut is found and put back alone. Every state left on disk has passed.

  • Parse before test. Each edited file goes through the language's own parser before the check runs, so syntax damage fails fast rather than as a confusing test error.

  • Tests are never edited, and undo restores files byte for byte.

  • What can't be proven isn't cut. Public methods, library exports, subclasses a framework may register, files in convention-loaded folders go to the agent with a reason, or sit behind --aggressive.

The README's own demo is the honest case: a test reaches a function through a name read from a data file, nothing in the code mentions it, the cut broke the test, and that one cut was put back.

The design choice: counting mentions instead of building a call graph. A count can only miss dead code, never invent it, and it behaves the same in every language. Every text file — HTML, Vue, Svelte, YAML, SQL, templates — is read for mentions, so a function used only from a template survives. Adding a language is one table entry describing comments, strings, block ends and definitions: about twenty lines.

This is a deliberate trade of recall for soundness, which is the right direction when the action is deletion. It also means the tool is weakest exactly where dynamic dispatch is heaviest — reflection, string-built names, dependency-injection containers — and that is where the test gate is doing all the work.

Failure modes to plan for

  • A weak test suite silently authorizes deletion. The proof is exactly as strong as the check. The README is explicit: a project with no tests gets a scan, not a cut you should trust. Coverage, not line count, is the gate on how aggressively to run this.

  • Flaky tests are the dangerous case, worse than failing ones: a flake during a batch sends the bisection after the wrong cut, and a flake on a passing cut keeps something that should have gone back. Run it on a green, stable suite.

  • Bisection cost. Splitting a failing batch means re-running the suite repeatedly; on a slow suite the loop is expensive, which argues for a fast subset as the check and the full suite as the final verify.

  • Assets served as-is. Files under public/ or static/ may be linked from outside the repo, so they need --aggressive — the one category where the test gate cannot see the dependency at all.

  • Library versus app. In a library, public names belong to users. The tool guesses from a published package.json, a lib.rs, the absence of package main, and says what it guessed; override with --lib or --app. Getting this wrong in a published library is an API break that no test catches.

  • The agent-assisted path is a different risk class. task --agent hands duplicates and public methods to a model and keeps its work only if the check agrees. The check is still the gate, but the diff is now a model's refactor rather than a deletion.

Review checklist before running it on a real repo

  1. Is the suite green and non-flaky right now? Run it twice.

  2. Does the check fail when the app is actually broken — not just when it fails to compile?

  3. Is this a library? If so, is --lib set, and are public exports the contract you think they are?

  4. Start with scan and read the list. Anything surprising on it is a sign the mention-counting missed a dynamic path.

  5. Keep --aggressive off for the first pass, and treat its output as a reviewed list rather than a commit.

  6. Review the resulting diff as a human change. "Tests passed" is the floor, not the review.

Integration

A Claude Code plugin, a built-in MCP server exposing eight tools (shrink_scan, shrink_cut, shrink_task, shrink_verify, shrink_undo, shrink_report, shrink_weigh, shrink_status), and a skill that teaches any agent the loop. --agent accepts any command that reads a prompt on stdin, and without it the task file is handed to whatever you use — a reasonable hedge against tying a build step to one vendor's CLI.
