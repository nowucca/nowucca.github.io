Warp's self-improving agents: feedback becomes a reviewed skill edit

TL;DR

Warp (terminal and agent platform; ~800K monthly developers, 400K+ Claude Code sessions a week inside Warp) makes its agents improve from human comments with two skills per agent. The base skill holds domain instructions for the task (PR review, issue triage, spec writing). A scheduled improver skill pulls accumulated human feedback from where people already work (PR and issue comments), compares what the agent did with how humans reacted, and opens a PR with the smallest edit to the base skill. A human reviews and merges it; the next run inherits it. Warp runs this across its open-source repo for review, triage and spec agents. The point for a staff engineer: this is self-improvement with the ordinary code-review gate as the acceptance test, not an automatic optimizer.

How it works

  • Why they built it. Their internal code-review agent produced noisy, unhelpful comments. Hand-rewriting the prompt from observed failures helped but did not scale; better AGENTS.md helped a bit. Diagnosis: feedback given to an agent dies with the session.

  • Inner (base) skill. File-based domain knowledge, run per task (on PR open, on issue filed via a GitHub Action).

  • Feedback. Anything from a thumbs-up to a written reason ("our convention for this kind of global is X"). Collected in place, with no extra submission step.

  • Outer (improver) skill. Runs on a schedule in Oz, Warp's orchestration platform, not per task. In the triage example it authenticates to GitHub, runs a Python script bundled with the skill to pull recent issues with feedback, writes a JSON summary, reads it back, finds the concrete signals, and proposes the smallest edit.

  • Gate. The edit is a PR with a description naming the signals that prompted it. Human review, approve, merge.

  • Worked example. The triage agent missed the ready to spec label; a maintainer commented on the issue saying what and why; the improver opened a PR adding "apply ready to spec when the issue describes a real problem even if the UI/UX shape is not defined".

Warp's authoring advice

  1. Write principles, not rules ("look for repeated code" beats exhaustive naming rules).

  2. Explain the why, so the agent can generalize.

  3. Make feedback effortless and capture it where work happens.

  4. Keep skills small; use progressive disclosure (reference files and bundled scripts).

  5. Detailed expert feedback beats volume of thumbs; volume still helps (thousands of reviews, hundreds of contributors).

  6. Invest in the improver: it is largely reusable across agents.

The article's sidebar adds: skills are procedural and changed deliberately, memory is auto-written and always changing, so don't conflate them; share a templated improver across many agents rather than one per agent; assume feedback will be wrong (sanity-check it, filter whose input counts, keep a human at filtering or final review); in verifiable domains build the verification harness first; elsewhere prefer deterministic evals against golden outputs and restrict feedback to domain experts; track global metrics (time to merge, contributor count, cost) and feed them back to the improvers.

Assessment

Strengths. Uses infrastructure every team already has (PRs, review, git history) as the update channel, so every change is diffable, attributable and revertible. Small edits keep blast radius low. Separating the improver from the worker is the same actor/critic split the research papers use, at near-zero cost.

What's missing. No numbers on whether agents got better: no before/after comment acceptance rate, no rejected-edit rate, no regression check. The merge gate is human judgment of the diff, not a replay of past cases, so an edit that fixes one issue can quietly break others (the failure mode R164 GUARD and R066 TRUST are built to catch). Feedback attribution and conflict handling (two maintainers disagree) are not described. Skill growth over time and pruning are not addressed (R221).

Failure modes to watch. Skill bloat from many small accretive edits; overfitting to the loudest commenter; reviewer fatigue turning the merge into a rubber stamp; adversarial or low-quality feedback on a public open-source repo becoming instructions (a prompt-injection path into a skill file); stale rules after the codebase convention changes.

Review checklist if you build this

  • Does every improver PR cite the specific feedback items (links) that justify it?

  • Is there a replay set of past cases the edited skill must still pass before merge?

  • Who is allowed to count as feedback (maintainers only on public repos)?

  • Is there a size budget for each base skill, and a periodic prune pass?

  • Are improver runs and their accept/reject outcomes logged so you can measure whether the loop helps?

  • Can a merged edit be traced back and reverted on its own?
