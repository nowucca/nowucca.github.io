A shared board instead of private messages: how /swarm structures a parallel agent team

Source: the /swarm page of the Google Antigravity documentation, as of 26 Nov 2026. Documentation only — no paper, no benchmark, and nothing measured. Treat everything below as a described design, not an evaluated one.

The shape

/swarm turns the conversation you are already in into a coordinator for a team of named agents. The coordinator names the swarm, splits the task into pieces that do not collide — the documentation's examples are one worker per file or per package — and adds a worker per piece (parser, api-tests, docs), or a numbered group such as fix-1 through fix-4 when the pieces are alike.

Three structural choices are worth separating out from the feature description, because they are the reusable part:

1. Every brief is public. A worker starts with a clean context in its own conversation, and its brief — what it owns, what it must not touch, and what "done" means — is posted to the shared board where every member can read it. Ownership is therefore common knowledge rather than private instruction, which is what makes "do not touch that file" enforceable by peers instead of only by the coordinator.

2. There are no private messages. Assignments, questions between workers, diff summaries and test results all go to one board with @name, @group or @all mentions. The documentation states the intent directly: workers do not message each other privately, so the whole team conversation stays in one place, in order. A single ordered log is the difference between a multi-agent run you can debug afterwards and one you can only re-run.

3. Verification is a role, not a step. The coordinator adds a @verifier for every two to four workers; it reads diffs, runs tests, and reports problems back to the worker that wrote the code, which fixes them. Review is inside the loop and addressed to the author, rather than being a final gate in front of the human.

The coordinator does no technical work itself — it hands out tasks, judges what comes back and reports, so it stays responsive while workers run. There is also a @monitor worker that sleeps while the swarm makes progress and posts only if every member has gone quiet before the work is done: an explicit deadlock detector, which is a failure mode most hand-rolled multi-agent setups discover the expensive way.

Idling, quota and the economics

The cost model is the most practically useful part. A member with nothing to do — a worker awaiting input, or the coordinator awaiting reports — goes to sleep on the board and consumes no tokens until a post mentions it. Three states: Active (running a turn), Waiting (asleep, free), Killed (removed permanently; the coordinator adds a replacement rather than reviving it).

Quota exhaustion is handled by pausing rather than retrying: the error appears once, and the member stays paused until a new board post, a model switch, or a direct message — it does not restart itself when quota refreshes. Pausing instead of retrying is the correct behaviour (a retry loop against a quota wall burns the remaining budget), but note the consequence: a paused member is a silently stalled branch of the work, and nothing resumes it automatically. That is precisely what the @monitor role exists to catch.

The documentation is candid about the bill: swarm is in preview, and "every worker is its own agent, so a swarm uses quota much faster than a single conversation."

Models and workspaces

Workers inherit the conversation's model by default. A different model can be requested per worker or for all of them ("run the verifier on a different model than the workers"), limited to models available in the picker, and a waiting worker can be moved to another model later while keeping its conversation — cheap workers with an expensive verifier is an obvious configuration this makes available.

Workspaces default to shared: all workers edit the same checkout. When several workers edit or build simultaneously, the coordinator can give each its own working copy. The detail that matters operationally: removing a worker deletes its working copy, so the coordinator has the worker land its changes first. A worker's uncommitted work lives only in a copy whose lifetime is tied to the worker — which is a data-loss shape worth knowing before you ask for workers to be cleaned up.

Where it sits among the alternatives

The same page compares four mechanisms, which is a more honest framing than a feature pitch, and its axes transfer to any such decision: what the thing is for, how the agents coordinate, the workspace model, how verification happens, the typical horizon, and the plan tier.

CoordinationVerificationHorizon

Swarm's slot is clear: tasks that split cleanly across independent files, packages or investigation tracks, on a horizon of minutes to hours. The guidance to take from the table is that the coordination mechanism should be chosen by how long the work runs and how much the pieces overlap — not by how impressive the topology sounds.

What is unverified

Everything quantitative. The documentation offers no speedup against a single conversation, no success rate, no cost comparison, no guidance on how many workers is too many, and no evidence behind either the one-verifier-per-two-to-four-workers ratio or the horizon bands. Parallel agent teams are also where the published evidence is weakest in general: the baseline that matters is one agent given the same total token budget, and no such comparison appears here.

The design is also only as good as the split. Every property above — non-colliding pieces, enforceable ownership, a verifier that can judge a diff in isolation — depends on the coordinator decomposing the task correctly on the first attempt, and nothing in the documentation describes what happens when it decomposes it wrongly, beyond killing workers and adding new ones.

Review checklist, if you are building the same thing

  • Is there one ordered log of all inter-agent traffic, or can agents talk privately? If they can, you cannot reconstruct a failed run.

  • Are ownership boundaries published to every member, or only told to the one agent they bind?

  • Is review a role addressed to the author, or a gate in front of the human? The second makes the human the fixer.

  • Do idle agents cost tokens? A waiting agent that keeps polling is the quiet way these systems get expensive.

  • On quota or rate-limit exhaustion, does a member retry, pause, or die — and does anything notice that it stopped?

  • Who detects a stall in which every agent is waiting for someone else? Name the component.

  • When workers get isolated working copies, what is the lifetime of an uncommitted change, and who guarantees it lands?

  • What is the matched-budget single-agent baseline, and has anyone run it?
