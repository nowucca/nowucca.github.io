Field guide: Durable execution

How to run agents that work for hours or days: sleeping and waking, restarts, retries and idempotency, code-owned versus prompt-owned loops, steering, sandboxes, identity and audit, and what incidents teach.

Claims read from the full papersUpdated 2026-11-25

Bottom line

Build a long-running agent as a series of short runs driven by a durable record of events, not as one process that must stay alive (R084-f1) (R084-f2). Let deterministic code own state, scheduling, locks, ordering and completion gates (R263-f2) (R044-f5), and meter money and time outside the model (R094-f3). Make every outside action safe to repeat, because a durable runtime will retry and cannot make a retry safe on its own (R035-f1) (R035-f2). Treat worktrees, shared runtimes and in-process hosts as organisation, not isolation, and keep credentials outside the agent (R263-f5) (R146-f1) (R146-f4) (R084-f4).

The sources make this case mostly through vendor guidance, project documentation and practitioners' accounts of their own builds, with little controlled measurement; the controlled study the guide leans on is a memory study on synthetic single-change services (R084-f6) (R094-f7) (R184-f10). Anthropic's guide describes an always-on agent as one that sleeps most of the time and wakes for short runs that receive an event, do the task and save what happened (R084-f1), but it gives no measured results, failure rates or named deployment (R084-f6). One practitioner account is one engineer's rewrite of his own 27,500-line harness, built from 11 to 21 November, after it failed on agent-owned state, self-grading, piled-up patches, hung processes, retry budgets and deadlocks (R263-f1). He moved state into deterministic code (R263-f2) and reports 137 verified commits in the first 24 hours on his own three repositories, while warning that many were diagnostic and that commit count is not the metric he trusts (R263-f3). A martinfowler.com article draws the line between runtime and harness duties, using a toy Python domain and the author's own runs (R035-f1).

The Microsoft outage in the set is not an agent failure (R232-f1). It is Microsoft's preliminary account, as relayed by The Register, of a months-old gateway defect that load testing on weaker hardware missed, which spread through the fleet within two hours, with more than 80% of servers unresponsive at the lowest point (R232-f1) (R232-f2). Applying it to agents is an analogy, and the headroom lesson drawn from it is a practitioner's inference, and Microsoft says the service had sufficient headroom (R232-f4).

Several of the durable-execution sources are LinkedIn or practitioner posts by the builders themselves, and one is a short video. "How this was made" lists how each was weighted, and claims from thin sources carry less weight below.

Do

  1. Model the always-on agent as short runs off a durable inbox. Anthropic's guide names five primitives around an unchanged agent loop: a durable event inbox with a fast-acknowledging handler, timers in their own store that a polling scheduler turns into inbox events, memory as files on durable storage, permissions and an outbox (R084-f2). It is vendor guidance with no deployment data or reference implementation (R084-f2). LangChain reports that more than 70% of runs of its managed proactive agents start from schedules rather than a prompt, a vendor-reported figure (R123-f3). Vercel's board shows what is missing without this layer: posting does not wake an idle agent, and wake-ups need your own runtime (R177-f3).

  2. Make the inbox, not the worker, the source of truth. The guide recommends that a new worker pick up the same event if one dies mid-run, that only one worker be active per inbox, starting with one inbox per user, that pending events be batched, and that events be deduplicated on source identifiers (R084-f3). These are recommendations the guide does not test (R084-f3). Rebuilding from the log can cost time on some platforms: in the Fowler article's toy runs, Cloudflare took about 0.1 s in memory and about 2 s rebuilt from the log, while Temporal took 14 ms in memory and under 0.1 s rebuilt from the log (R035-f4).

  3. Put idempotency in the harness, not the runtime. The Fowler article says a durable runtime handles a dead process, a failed remote call, repeated work on retry and concurrency, but cannot make a retry safe (R035-f1). Under at-least-once semantics the harness must keep the idempotency key, the PO number in its example, constant across attempts (R035-f2). Vendor documentation describes effects that repeat or outlive a call: the Copilot SDK says a retried storeMemory call can deliver the same memory twice (R146-f4), and Google's ADK v2.10.0 documentation says a client timeout stops polling while the backend request still runs and is billed with its output lost (R206-f4). The multi-agent guide covers the other harness duties the article lists (R035-f3).

  4. Bound retries and say which errors are retryable. An unofficial super-agent prototype adapted from DeepSeek's internal code, which its README calls research code that is not identical to the internal version (R021-f5), is designed to retry transient failures such as HTTP 408, 429 and 5xx three times with growing backoff, then hold a failed Ticket until a person's message, a later report or a retry ends the hold (R021-f4). ADK polls deferred calls with exponential backoff and raises after 5 consecutive failed reads (R206-f2). The MCP specification says clients acting for a user should attempt step-up authorization, with retry limits, when a server returns an insufficient-scope error (R062-f4). Relate returns structured errors with a retryable field (R055-f2). Hoyt's first harness burned retry budgets on network blips (R263-f1).

  5. Let deterministic code own state, scheduling and locks. Hoyt's rewrite uses SQLite leases and fences, one Git worktree per worker, detached process-group watchdogs, pre-landing health checks, targeted rollback and a tiered human admission policy, in place of agent-owned state and a fifty-step plan (R263-f2). That design is his own and not independently reviewed (R263-f2). Codemod's v2, a vendor alpha, moves the decisions about which projects to skip, which files each rule group sees and when to pause for approval into TypeScript, replacing 953 lines of launcher and YAML in one internal example (R173-f1) (R173-f5). The FairyClaw authors argue for keeping ordering, safety rules and completion gates in runtime code because prose instructions are suggestions the runtime cannot enforce, from one case study and no ablation (R044-f5).

  6. Checkpoint completed steps and keep results outside the sandbox. Iusztin's CodeClimb checkpoints completed steps in Inngest so a crash does not repeat paid work, stores commits and scores outside the sandbox, and pauses for up to three days without running sandboxes when credits run out (R094-f2). That is his description of his own setup, with no crash-injection test (R094-f2). Codemod's workflow reuses saved results from matching completed steps on resume, demonstrated on one example with no crash test (R173-f2). The kernel-search authors keep memory in an append-only SQLite archive outside the model that agents re-read after restarts (R129-f6).

  7. Write a recovery path that checks the world before repeating an action. In the DeepSeek prototype's design, on restart, running Assignments end with the status host restarted, and new ones start with a recovery note telling the Executor to check its directory, git history and GitHub before repeating any outside action, while sessions and pending messages survive (R021-f3). The Fowler article makes re-checking before commit after a wait a harness duty (R035-f3). In one memory study with synthetic single-change services, 94 of 97 runs that read back the stored state corrected an out-of-date write (R184-f5) (R184-f10).

  8. Version the rules a waiting run depends on, and decide what a deploy does to it. In the Fowler article's toy runs, a rule change during a wait left Temporal continuing under the old rule silently while Cloudflare failed and left the order as a draft (R035-f5). The DeepSeek prototype records the policy version in each Ticket's immutable Mandate (R021-f1), and kagent resolves an Agent to an immutable prepared revision (R093-f2). kagent's README does not say how long-running conversations receive urgent prompt fixes (R093-f4), and no source in this set describes a tested answer.

  9. Give each concurrent thread its own workspace and lease, but do not call that isolation. Nijholt runs 15 sessions on a normal day and up to 40 at peak, each one thread with its own Git worktree, by his own account of a tool he co-founded (R273-f1) (R273-f4). Vercel's board treats claims as time-limited leases, for example five minutes (R177-f1). Git Ontology Agent runs independent requests on their own branch and merges them back by claim type (R212-f3). Hoyt warns that worktrees isolate filesystems but not credentials, privileges or network (R263-f5). In one kernel-search run, evaluation rate rather than agent count limited scale (R129-f3).

  10. Treat steering a running agent as a design decision. Anthropic's guide lists three options for mid-run events, push to the next run, fold into the current run, or interrupt and restart, and recommends none (R084-f6). A deferred tool call ends the run and saves the session, and the answer arrives as an inbox event that starts a new run (R084-f4). Git Ontology Agent classifies each mid-task message as supplement, correction, independent, cancel or progress, asks the user when confidence is below 0.8 (R212-f2), and reopens only the claims that depend on a changed one (R212-f3). That README gives no accuracy figures for the classification (R212-f2). In the DeepSeek-derived prototype, a person's message reaching a Ticket through its own Subscription arrives with no new evaluation and can resume an ended Ticket under the same Mandate (R021-f1).

  11. Start proactive work in an observe mode. The DeepSeek prototype starts unrequested work in observe mode, which records what it would accept and accepts nothing, and its docs advise switching to auto only after reviewing the recorded decisions (R021-f2). The Claude Code team rolls out its commit gate in off, observe and enforce modes (R182-f2). The prototype's docs give no usage data for the modes (R021-f2).

  12. Use an independent checker and an outside test, not the agent's own grade. Hoyt's first harness let agents grade their own diffs generously (R263-f1), and his rewrite adds an independent fresh-context reviewer (R263-f2). Nijholt has three models review each diff with no model reviewing its own code (R273-f2). AWS built its emulator by having agents correct each test against real AWS first and then build until the emulator passed it (R080-f1). Google's Elephant-Goldfish plugin stops a review if the host cannot create fresh-context subagents (R017-f2). The verification guide covers checking in depth.

  13. Meter money and time outside the model. CodeClimb's metering proxy enforces 2.50 dollars per experiment, 15 dollars per night, 6 rounds and a 6-hour deadline by returning HTTP 402, reserves budget for the final test, and is backed by plateau detection, timeouts and a kill switch (R094-f3). Uber reports moving polling to a background agent because notification turns were about a third of spend in its 20 highest-spend sessions (R246-f7).

  14. Know where credentials and tool policy live. Anthropic's guide describes credentials injected by a proxy outside the agent environment (R084-f4). LangSmith's Tool Gateway, a public beta, puts MCP tools behind one URL with per-agent tool kits and per-call identity as the user or as the agent (R168-f1), and describes deny and approval policies, with deny policies available by contacting the team (R168-f2). Its only evidence is one unnamed retailer, with no latency, adoption or incident data (R168-f4). Omnigraph's release notes tell operators who serve MCP to check what each agent credential allows before upgrading, because agents now gain every tool their policy allows even if no flag was set (R074-f2). The security guide covers credential scoping.

  15. Decide what the record of a run keeps, and under whose identity. LangSmith traces each tool call with tool, server, user, outcome and duration but not payloads, and its organisation-wide audit log is Enterprise-only (R168-f3). Git Ontology Agent records every answer as a commit with its source commit, so a past reply can be replayed with git show, shown in scripted demo output only (R212-f4). Microsoft says agents from eleven named platforms get an Entra Agent ID, with rollout completing in December (R169-f1). OntoBricks shows how identity can drift: its tools are said to run as the end user, but one MCP connection shares a service-principal identity for all users (R256-f3). The two record designs fit together: Git Ontology Agent keeps the agent's own answers in its repository (R212-f4), LangSmith keeps tool-call metadata without payloads (R168-f3), and Cursor's incident shows the risk of stored traces that hold credentials (R195-f1).

  16. Test liveness, not just correctness. Hoyt's new engine hit a scheduler and planner deadlock around hour 20, which he then covered with a 3,456-state liveness test (R263-f3). His first harness had idle workers deadlock on duplicate readiness checks and hung child processes holding locks (R263-f1).

Avoid

  • Keeping control state in memory. In Iusztin's comparison of his own two builds, a LangGraph server crash wiped the in-memory metering proxy state and needed extra recovery logic, while Inngest kept workflow state outside the worker (R094-f5). He calls it a single-spec preference piece and says neither stack is universally better (R094-f7).

  • Calling a shared runtime or a worktree a sandbox. The Copilot SDK's default in-process host gives neither crash isolation nor a sandbox (R146-f1). Shell tools do not run through its sessionFs, and coding-agent mode on a shared server can expose the host filesystem (R146-f4). In Claude Code's experimental Code Mode, off by default, the sandbox covers shell commands only (R214-f1) (R214-f4). LocalAI's add-ons run as the operating-system user that runs LocalAI, and only its Sandbox isolates what it runs (R253-f4). Pydantic says its Agent Sandboxes are not a container or VM and are wrong for coding agents that install packages (R061-f4).

  • Sharing grants and session IDs across tenants. In the Copilot SDK, durable permission grants are shared by every session in the same sessionFs namespace, so applications must use distinct namespaces per tenant (R146-f3). Its guide requires unique session IDs with ownership checks before resume or delete (R146-f2).

  • Reading commit or session counts as quality. Hoyt says commit count is not the metric he trusts (R263-f3). Nijholt says lines of code are not a quality measure, and his statement that he cannot recall a recent run going badly wrong comes with no incident log (R273-f4).

  • Trusting old experience after a tool changes silently. In one study of synthetic single-change services and short tasks, with incomplete tool documentation after a silent change, out-of-date experience gave 23% success against 63% with none and 100% with valid experience, across 6 models and 12,488 episodes (R184-f1) (R184-f10).

  • Taking an announcement for a shipped control. Microsoft labels cross-agent debugging and Trace Analytics public preview while external-agent observability becomes generally available (R169-f2), and many items in both Microsoft posts are preview or announcement-only (R169-f4). Codemod's v2 is an alpha (R173-f5).

  • Assuming the incident playbook will work at fleet scale. In Microsoft's account, restored servers were immediately overwhelmed again, automated recovery was not designed for such a broad unresponsive state, and rollback was impossible because the defect was months old (R232-f3).

  • Claiming determinism for prompt-routed workflows. The reel that argues for markdown instruction routes gives no measurement and does not use the word deterministic (R015-f4).

  • Logging payloads you would not want copied. Cursor reports that an exposed vendor key let an attacker copy coding-agent traces, a small number of which held unredacted credentials (R195-f1). Cursor's post does not say whether traces were unredacted at capture (R195-f4).

How this was made

Thirty-two sources were consulted.

  • 14 in the durable execution set: vendor guides, docs, blogs and announcements (R084 from Anthropic, R146 the Copilot SDK, R173 Codemod, R168 LangChain, R169 Microsoft, R080 AWS), project repositories (R021, R212, R017), practitioners' first-hand posts about their own builds (R094 on LinkedIn, R263, R273), a news report of a vendor's preliminary incident report (R232) and a Facebook reel (R015).

  • 18 related sources from other sets, used only where they bear on durability: R035, R177, R214 and R218 from multi-agent; R044 and R182 from verification; R061, R062, R074, R093 and R195 from security; R055 and R256 from graphs; R123 and R184 from memory; R129 from self-improvement; R206 from serving; and R246 from context.

A Sonnet model extracted the claims, each tied to a location in its source. Opus wrote this guide from those claims and the related claims.

How each source was weighted:

  • R094's two LinkedIn posts are one author's account and no repository exists to check (R094-f1).

  • R015 is weak. It is a Facebook reel (R015-f1) used only as one practitioner's opinion, and its absences are not proof (R015-f4).

  • R021 is an unofficial prototype adapted from DeepSeek's internal code, which its README says is not identical to the internal version (R021-f1) (R021-f5).

  • R232 is a secondary report (R232-f1), and its figures are preliminary (R232-f2).

  • R035's numbers come from the author's own runs on a toy domain (R035-f1). R218 was requested for its durability notes, but none of its specific numbers could be verified (R218-f1), so it supports no claim here.

  • Vendor material, R084, R146, R168, R169, R173, R080 and R017, is used for practices and stated figures, not as independent evidence (R084-f6) (R146-f2) (R168-f4) (R169-f4) (R173-f5) (R080-f1) (R017-f1).

Checking the sources found several of our earlier entries wrong, overstated or unverifiable:

  • R084: our doc's "queue by default", the failure-mode list with its at-least-once wording, and the session rule are ours; the guide lists options and recommends none (R084-f6). The 78% figure matches but is Anthropic's own, on one unnamed benchmark with no method (R084-f5).

  • R094: our entry dropped the 6-round and 6-hour limits and the reserved final-test budget (R094-f3), the 50-user middle case where the cost crossover happens, and the caveat that the largest LangSmith case needs an Enterprise quote (R094-f6). "Rebuilt" overstated a comparison of two stacks on one spec (R094-f5).

  • R263: our entry left out the scheduler deadlocks and burned retry budgets (R263-f1), the 24 November update (R263-f4) and the warning that worktrees do not isolate credentials (R263-f5).

  • R173: the "hard part" sentence is from the LinkedIn text, and YAML already supported conditions, approvals and file selectors, so only the decision logic moved (R173-f4). Resume was shown on one example with no crash test (R173-f2).

  • R212: the nonrefundable-train point about side effects was our inference, not the README's (R212-f5). Corrections win only for assumptions, and findings take the later check (R212-f3).

  • R015: the "Copilot or custom GPTs were the wrong frame" wording could not be confirmed word for word (R015-f2), and the absence of "deterministic" could not be confirmed (R015-f4).

  • R021: a person's message through its own subscription resumes a Ticket without a new evaluation, so "context only, with no new authority" was partly wrong (R021-f1). The hourly liveness check was not found (R021-f5).

  • R146: our entry's "shell-heavy work to sandboxed sessions" was wrong; the guide routes compute-heavy work to cloud sessions and mentions no sandbox. Our entry also left out that grants are shared across sessions in one namespace (R146-f3) and that workflow agents need longer idle timeouts and explicit deletion (R146-f2).

  • R273: the 58 to 76% figure is against MindRoom's standard agent in a cited earlier study (R273-f3), and our entry left out that the author built the tool and gives no incident data (R273-f4).

  • R080: the 30,000-plus commit figure is from a LinkedIn post, not the AWS sources (R080-f2), and the README warns against security testing but does not mention IAM (R080-f4).

  • R232: "missing headroom" contradicts Microsoft's statement of sufficient headroom, and the gradual-admission lesson is the practitioner's wording (R232-f4). The 80% figure is the lowest point, not a two-hour figure (R232-f2).

  • R017: the repository lists eight skills, not seven, and the 30% critic hit rate was not checked (R017-f4). The cap is one re-audit per stage (R017-f1).

  • R168: the audit log is Enterprise-only and deny policies need contact with the team (R168-f2) (R168-f3).

  • R169: the Foundry egress rules, audit mode, idempotent handler replay and toolbox auth are not in either post (R169-f4), and several observability items are preview rather than generally available (R169-f2).

Those entries have been corrected at the source.
