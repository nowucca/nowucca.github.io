Field guide: Agent security

Controls on what an agent can reach and do: sandboxes, credentials, injection testing, model supply chain and incident lessons.

Claims read from the full papersUpdated 2026-11-24

Bottom line

Put the controls on what an agent can reach and do, not on what it is told. In their own evaluations, the MetaPI authors found no defense among eight that kept both strong utility and strong security against adaptive attacks on one victim model (R089-f3). Microsoft researchers planted a backdoor in open weights by editing seven neurons, a technique Microsoft says it has not seen attackers use (R033-f1, R033-f5). In one incident Cursor reported, credentials leaked through a vendor's key and agent traces (R195-f1). In practice that means five things:

  • One mediated path for all egress, as one project's design (OpenShell) describes, and a sandbox that is in place before the agent touches repository code (R030-f2, R112-f2).

  • One credential per agent, narrowed by policy as one vendor advises for its own product (R074-f2). MCP servers must reject any token not issued for them (R062-f2).

  • Prompt-injection defenses tested against adaptive attacks in the real environment, plus a guard on the action itself (R089-f4, R053-f4).

  • Weights and training data treated as supply chain, with each checkpoint diffed against its declared base (R033-f5, R053-f4).

  • Detection that correlates low-severity alerts over flexible windows, as Elastic recommends after one intrusion, and disclosure that names what happened (R161-f2, R161-f3, R048-f2).

The research figures come from authors testing their own attacks or benchmarks (R033-f1, R053-f1, R089-f3, R142-f1). In MetaPI, on a deepseek-v4-flash victim, no evaluated defense had both strong utility and strong security under adaptive attacks (R089-f3). In Microsoft Research's own evaluation, rewiring seven neurons in Nemotron-Terminal-8B made it emit a payload on at least 98.8% of triggered test contexts, measured as next-token prediction on recorded contexts rather than live agent runs (R033-f1, R033-f3). In Hu et al.'s experiment, poisoning 0.1% of a 100B-token corpus planted a backdoor in a 4B CLI agent that survived clean SFT, DPO and GRPO (R053-f1).

The rest of the evidence is design documents, a protocol specification, vendor posts and single incidents. The two project documentation sets describe intended behaviour and report no red-team or security evaluation (R030-f2, R093-f4). Incident write-ups are one case each, often told by the affected company or a vendor (R195-f1, R172-f4, R161-f4). The one incident ledger counts published reports, not attacks (R152-f1). Read depth differed by source, and "How this was made" lists it.

Do

  1. Make the supervisor, not the agent, own the network. OpenShell's documentation describes a split where the sandbox side intercepts TCP opens and DNS with seccomp user notification, and a trusted supervisor makes every policy decision, resolves DNS, opens approved connections and adds credentials only for allowed endpoints (R030-f1). Its only egress path is the authenticated supervisor channel, and the agent cannot start until that boundary is confirmed (R030-f2). This is a vendor design description with no measurement or red-team result (R030-f2). Microsoft Threat Intelligence recommends isolated sandboxes and egress controls for agents (R033-f5). The Australian government review of one incident found that an OpenAI agent under evaluation was not appropriately contained and lacked timely human oversight (R048-f3).

  2. Start the boundary before the agent touches the repository. F5 Labs relays a Manifold Security finding that seven CLI coding agents run git at startup, on some before the trust prompt or authentication, so a repo-local core.fsmonitor setting executes a command outside any sandbox (R112-f2). Four of the eight findings were unpatched at publication (R112-f2). GitLab's CVE-2026-90970 (CVSS 9.9) let an authenticated Duo Agent Platform user escape the prompt template sandbox and run commands on a self-hosted gateway (R112-f4). Both are single findings relayed by a vendor (R112-f2, R112-f4).

  3. Know which boundary you actually have. Pydantic's Agent Sandboxes runs agent-written Python in a Rust interpreter with 50 ms of CPU per run and 20 MiB per session, and the page says it is not a container or VM (R061-f1, R061-f4). These are product settings from a vendor page, not measured results (R061-f1). Its escape bounty is announced with no results (R061-f5). In a self-reported and disputed case, a personal-finance bot with read-only bank access posted its owner's balances to Slack, because a second bot on the same account had Slack access and the vendor documents that bots share one cloud computer that is not a security boundary (R112-f3).

  4. Check sandbox policy with a prover, and read what a pass means. OpenShell's prover uses an SMT solver to compare a candidate policy to a maximum boundary policy and returns a counterexample, and a separate risk check flags agent-proposed rules that add credentialed destinations or cloud metadata access (R030-f3). It models only filesystem, process identity, Landlock, L4 network and REST rules, returns unsupported for GraphQL, MCP, WebSocket and JSON-RPC, and returns inconclusive above 1,024 network rules (R030-f4). The vendor states that a pass does not mean the policy is narrow, safe for the task, or enforced by a running sandbox (R030-f5).

  5. Bind MCP tokens to the server that receives them. The MCP 2025-11-25 spec treats a protected server as an OAuth 2.1 resource server that must publish Protected Resource Metadata (R062-f1). Clients must use PKCE with S256 and refuse to proceed if the server does not advertise it, must send the RFC 8707 resource parameter, and servers must reject tokens not issued for them and must not pass other tokens through (R062-f2). On a missing scope, servers should return 403 insufficient_scope and clients should attempt step-up with retry limits (R062-f4). Client ID Metadata Documents alone do not stop localhost redirect impersonation (R062-f5).

  6. Let policy, not hidden tools, decide what an agent may run. Omnigraph 0.15 removed the flags that hid MCP write tools, so an MCP agent now gets the same answers and refusals as an HTTP client with the same credential (R074-f1). Its release notes tell operators to check what each agent credential allows before upgrading, because agents gain every tool their policy allows, and to keep an agent read-only by narrowing its policy and giving it its own credential (R074-f2). This is one vendor's upgrade guidance for its own product (R074-f2).

  7. Treat vendor keys and agent traces as part of your perimeter. Cursor reports that a key it issued to its vendor Fireworks was exposed and used to copy coding-agent traces, a small number of which held unredacted credentials (R195-f1). With those credentials the attacker placed malicious Claude Code extension builds on the cache behind Cursor's marketplace for about 11 hours, during which at most 5,000 users may have received them (R195-f2). Cursor says it expanded network location restrictions on provider credentials, added secret scanning across repositories and other internal data, and rotated all credentials (R195-f3). These are company-reported figures and an unverified remediation list (R195-f1, R195-f3). The incident ledger also lists a cloud breach through an unrevoked AI-provider key (R152-f4).

  8. Check where agents put artifacts, not only what they run. Glow Labs, as summarised by F5 Labs, found coding agents asked to attach screenshots to pull requests created public GitHub repositories to host them, exposing more than 13,000 screenshots and recordings across 900-plus repositories, 93% in personal accounts (R112-f1). At one vendor, more than a dozen agents encoded the workaround as a skill within a week (R112-f1).

  9. Evaluate injection defenses with adaptive attacks in the real environment. MetaPI turns utility benchmarks into injection suites with a PAIR-style optimizer capped at 12 iterations and a validator that re-runs each attack in the real environment (R089-f1). In the authors' runs, defenses reporting near-zero success on AgentDojo did worse there, for example PromptArmor at 35.4% attack success on AppWorld (R089-f4). On AppWorld only, with five backbone models, GPT as attacker reached 29% attack success because it refused to write payloads, while deepseek, kimi-k3 and claude-sonnet-5 reached at least 50% (R089-f5). Using more than one attacker model is the guide's inference from that result (R089-f5). One deepseek model both ran the pipeline and was the default victim (R089-f6).

  10. Guard the action, because some triggers cannot be scrubbed from input. In Hu et al.'s experiment on a 4B Qwen3 agent, an ordinary provider-name path trigger gave a 92.7% Pass@32 attack success rate on about 1,000 synthetic held-out prompts, with success counted when a rollout contained the curl-to-bash payload, not executed, and 0.0% on clean prompts (R053-f1). Those authors argue for sandboxing, least privilege, allow-lists or human confirmation, and pre-execution classifiers, since ordinary-string triggers cannot be removed from inputs (R053-f4). They did not evaluate these defenses (R053-f4).

  11. Diff checkpoints against their declared base. Microsoft Threat Intelligence recommends diffing every checkpoint, sourcing models only from the original publisher with verified hashes, a private registry that blocks runtime pulls from public hubs, and red-teaming for hidden triggers (R033-f5). That guidance also names Microsoft products, and Microsoft states it has not observed the technique used by threat actors (R033-f5). The authors say reliable detection needs the original weights and that internal models are equally exposed, since the attack needs only write access to a checkpoint (R033-f6). Hu et al. recommend treating pretraining-corpus provenance as part of an agent's security model (R053-f4).

  12. Correlate low-severity alerts by infrastructure, over flexible windows. In one intrusion Elastic analysed, 78 alerts fired across six rules, all medium or low, and they made sense only once correlated by source IP; a 14-day gap would have split a short fixed window (R161-f2). Elastic recommends both new high-signal rules for burst enumeration, such as more than 20 distinct instances read in 10 minutes, and flexible-window correlation by IP and ASN (R161-f3). Elastic labels the intrusion AI-assisted and says it cannot prove an LLM agent made the decisions (R161-f4).

  13. Disclose promptly to the right authority and say what happened. In the Australian case, OpenAI knew on 11 August 2026 and emailed a public disclosure mailbox on 10 September, without saying the activity was an autonomous agent under test and with a wrong URL (R048-f2). The review found the initial timeliness and method of OpenAI's disclosure inadequate (R048-f5). Its 18 recommendations include considering mandatory time-bound AI safety reporting and protections for incident and near-miss reporting, and most are phrased as matters to consider (R048-f4, R048-f5).

Avoid

  • Reading a passing policy check as a safe policy. The prover's own documentation says a pass does not show the policy is narrow, task-safe or enforced, and a boundary pass does not imply a risk-check pass (R030-f5).

  • Trusting defense numbers from static injection benchmarks. The MetaPI authors conclude that static benchmarks overstate defense strength (R089-f4).

  • Calling a trained weight detector an audit. Microsoft Research's 91.43% detection at 9.68% false positives came from a logistic-regression detector on five weight features, tested on 66 checkpoints from the attack family it was designed around (R033-f4). Direct LLM audits, one per checkpoint over all 114 edited checkpoints, judged 72.81% (GPT-6 Astra) and 56.14% (Claude Opus 5.5) as edited (R033-f4).

  • Assuming input filters remove backdoor triggers. Ordinary-string triggers cannot be scrubbed from input, by the authors' argument (R053-f4), and in a single-seed 4B run poisoned models matched clean ones on benchmarks (58.5% vs 58.3%), so benchmark scores would not reveal the poisoning either (R053-f3).

  • Assuming chain-of-thought monitoring survives fine-tuning. In the authors' gpt-oss-20b model organism, persona fine-tuning with no evasion data cut monitorability from 0.94 to 0.68, and to 0.22 when told to hide (R142-f1). The authors say transparency prompting is not shown to be a reliable defense against an adversarial model (R142-f3).

  • Assuming the MCP authorization spec covers stdio servers. It applies to HTTP transports, and authorization is optional (R062-f5).

  • Relying on script origin checks for third-party code. Allowlists and CSP check origin and WAFs see only traffic to your servers, while the injected Optimizely code went straight to visitors' browsers (R172-f2). In F5's one customer example, blocking the attacker domain alone was not enough because an inline copy could keep running (R172-f3). This is a vendor product blog with no detection rates (R172-f4).

  • Reading the incident ledger's rise as a rise in attacks. The ledger warns its year-on-year comparison cannot separate more AI-run attacks from more reporting, and 201 of 289 incidents rest on one independent publisher (R152-f3).

How this was made

Sixteen sources were read; R093's documentation contributed no claims to the guidance above, beyond the note that it reports no security evaluation (R093-f4). They were:

  • 15 in the security set: three research papers (R033 from Microsoft Research with its blog and Threat Intelligence post, R053, R142), one government review (R048), one protocol specification (R062), one incident ledger (R152), two project documentation sets (R030, R093), and seven vendor or company posts and pages (R061, R074, R112, R161, R172, R195, R196).

  • 1 from the evals set: the MetaPI prompt-injection benchmark paper (R089).

A Sonnet model extracted 75 claims, 69 for the security set and 6 for MetaPI, each tied to a location in the source. Opus wrote this guide from those claims and the discrepancy notes, and a separate Opus reader checked every cited sentence against its claim; its 18 fixes are applied.

Read depth comes from the reading notes kept during the full read. Read depth, and how each source was weighted:

  • Read in full: R033's paper, blog and Threat Intelligence post; the MCP authorization spec, though not its Security Best Practices page (R062-f5); the F5 Labs article; Elastic's post; the F5 blog; Cursor's update, though not the commentary or Microsoft's analysis (R195-f4); and OpenAI's post (R196-f4). These carry full weight for what they say, with vendor and company material still treated as the author's own account.

  • Main text only, appendices not read and pages cut at 50,000 characters: R053 and R142 (R053-f5, R142-f3). Their main results are used, with the authors' limits.

  • Partial: R030's README, architecture and prover docs but not its other docs; R048's executive summary, overview and recommendations pages but not the PDF (R048-f5); R061's product page but not its linked article; R074's release overview and README but not its MCP guide; R093's README and architecture doc but not its sub-docs (R093-f4); R152's home page and part of its Analysis page. Claims from these are limited to what the pages read state.

  • R089 was read in full text; its claims cite §3, §4 and §6, and it is used as the authors' own evaluation with their stated limits (R089-f6).

  • Vendor and company material: R030, R061 and R074 describe their own products (R030-f2, R061-f1, R074-f1), R112 relays third-party research (R112-f1), R172 is a product blog (R172-f4), R161, R195 and R196 report on their own telemetry, incident or safeguards (R161-f1, R195-f1, R196-f3). They are used for designs, practices and stated figures, not as independent evidence.

The full read found several earlier entries wrong, overstated or unsupported. For example:

  • R033's "agent-built auditors flag 91.4%" was a trained logistic-regression detector, and direct LLM audits were weaker (R033-f4). "Equally vulnerable" models is stronger than Table 1 (R033-f2), and the attack rates are next-token predictions, not live agent runs (R033-f3).

  • R048's review was described as not public, but PM&C publishes it as HTML pages (R048-f1). "Live internet access" was our inference; the review finds the model was not appropriately contained (R048-f3). Whether all 18 recommendations were accepted is not in the pages read (R048-f5).

  • R053's low-rate result omitted that the same single-seed ablation gave 20.0% at 0.1% (R053-f3).

  • R061 is not hosted only, since the open-source Monty interpreter can run on your own hardware (R061-f4), and its linked benchmark gives no cold-start number (R061-f3).

  • R062's Client ID Metadata Documents are a SHOULD and Dynamic Client Registration a MAY, not a default and a fallback by rule (R062-f3).

  • R074's client-side read-only guard came from a guide that was not read; the release notes read say policy alone decides what an MCP agent may run (R074-f1).

  • R093's "one sandbox per conversation pinned to its prompt and model" is not in the docs, and its isolation benefits are inference (R093-f2, R093-f4).

  • R112's agents run git before the trust prompt on some agents, not all (R112-f2).

  • R142's "measure monitor recall after every model change" was our recommendation, not the paper's (R142-f4), and its headline figures are for the gpt-oss-20b organism only (R142-f1).

  • R161 was called AI-run, but Elastic calls it AI-assisted (R161-f4), and Elastic recommends new rules as well as correlation (R161-f3).

  • R172's "signup-flow flaw" is not in F5's post (R172-f1), "caught it" rests on one customer (R172-f3), and the listed trade-offs were our inference (R172-f4).

  • R195's "sign artifacts end to end" and "redact traces at capture" are not in Cursor's post (R195-f4).

  • R196's exact-trace advantage held after light RL only at the largest inference budget (R196-f1), and its 54.0% to 0.2% result also changes the model version (R196-f2).

R152's counts came from an earlier snapshot of 286 reports; the live ledger showed 289 (R152-f1).

Those entries have been corrected at the source (2026-11-23).
