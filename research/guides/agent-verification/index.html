Field guide: Agent verification

Accepting agent-written work on evidence the agent could not shape: independent oracles, real runs, per-defect grading.

Claims read from the full papersUpdated 2026-11-24

Bottom line

Accept agent work on evidence the agent could not have shaped. In practice that means four things:

  • Checks run from code the change cannot edit.

  • Expected outputs come from a property, a reference implementation or a human-approved spec, not from the agent that wrote the code.

  • The change is actually run.

  • Defects are checked one by one, not only through a headline metric.

The sources make this case mostly by design argument and team practice, not by controlled comparison. An opinion essay argues that only checks you would still trust if the model were trying to fool you count as a harness, so the test runner counts and the author's own assertions do not (R020-f1). Anthropic's post on its Claude Code team describes running checks from the base branch so a change cannot edit its own rules (R182-f2). The measured results point the same way. In one ML bug-repair benchmark, Opus 5.5 often recovered the target metric while leaving injected bugs in place, and per-bug grading changed the ranking (R224-f4).

On the Vero Lean benchmark, in the authors' evaluation, the best configuration (GPT-5.5 xhigh, code-and-proof, 90-minute budget) fully solved 27 of 43 repositories (R045-f1), and the authors state that their audit certifies satisfiability, not that a specification is correct or complete (R045-f7).

One vendor survey points to review load as a pressure: in a verification vendor's self-reported survey of 1,026 developers and managers, 76% said they generate AI code faster than they can verify it (R105-f1). No claim extracted from these sources reports a false-approval rate for an automated reviewer or auto-approver; Qodo's launch post gives none (R141-f5).

Several sources were read only in part, and several are vendor material. "How this was made" lists them.

Do

  1. Put the checks where the change cannot reach them. The Claude Code team runs checks from the base branch so a change cannot modify its own rules (R182-f2). The Vero grader splices only marked agent-editable regions into a fresh copy, applies an axiom allowlist, and screens agent declarations with a rule detector and an LLM judge (R045-f6).

  2. Count only evidence that does not come from the agent's own expectations. The essay's rule is that the test runner counts as harness and assertions written by the code's author do not (R020-f1). Generated inputs count when expected outputs come from a stated property or a reference implementation (R020-f2). Anthropic's post recommends property and differential tests for the same reason: their inputs are not generated with the agent's bias (R182-f4). Both are recommendations without a measured comparison.

  3. Get a human signature on spec tests, and test the tests. The essay recommends that a human write or approve spec-derived assertions, or that a different agent write them and a human review them, with mutation testing to check the tests can fail (R020-f3). A podcast summary reports that Matt Pocock asks agents for proof that their code works, with or without TDD (R220-f1). That is one practitioner's opinion.

  4. Run the change, and let an external check decide when it is done. The Claude Code team runs the real app end to end through a repo-local verify skill (R182-f4). In VHarness, the agent stops when an external visual check judges the rendering complete, not when its own vision does (R133-f4). In the authors' evaluation, in a Claude Code harness with Gemini-3.8-Flash powering the tools, adding five visual tools improved every metric for all four multimodal agents tested, for example Opus 4.8 on Image-to-HTML from 0.7167 to 0.8715 DINOv2 similarity, on 100 cases per task (R133-f1). A text-only model with the tools beat the Opus 4.8 baseline on all three tasks, on a 50-case subset (R133-f2). The authors tested static targets only (R133-f5).

  5. Enforce ordering and completion rules in code. FairyClaw's Formal Skill uses lifecycle hooks to show only the current phase's tools, guard patches, and block completion until verification passes (R044-f4). The authors argue that instructions in a skill document are suggestions the runtime cannot enforce, supported by one case study and no ablation (R044-f5). Two abstracts report enforcement at generation time, each from the authors' own evaluation. Agent-C raised tool-call policy conformance from 77.4 to 100 (Claude Sonnet 4.5) and from 83.7 to 100 (GPT-5) on retail and airline applications (R041-f1). Type-constrained decoding for TypeScript cut compilation errors by more than half on HumanEval and MBPP (R043-f1). Only the abstracts of these two papers were read (R041-f4, R043-f4).

  6. Grade each defect, not the metric that summarises them. On BuggyMLEBench-Lite, per-bug checking ranked a 9B curriculum agent above Opus 5.5 at 10 injected bugs, 18.2% vs 13.6% full repair on 22 tasks, a gap of a few tasks (R224-f4). Silent bugs were resolved far less often than visible ones. One label off-by-one kept a 0.953 validation score while the test score fell to 0.017 (R224-f5). Coverage is not completion either: GPT-5.5 xhigh passed 87.3% of Vero specifications in code-and-proof mode, yet 10 of 43 repositories resisted every configuration (R045-f2).

  7. Roll out a new gate in observe mode and record how each commit was verified. The Claude Code team moves a commit gate through off, observe and enforce modes, and stamps each commit with how it was verified, including "none" (R182-f2). Its 39-item reliability checklist has triggers readable from the diff, so Claude checks only the matching items, usually 3 to 10 (R182-f3).

  8. Grade the reviewer itself against past incidents. The same team grades its reviewer against past incidents, with separate recall for raw findings, post-verification and final review, and uses merged stable changes as a control (R182-f5). It reports that a separate rubric grader improved structured file generation success by up to 10 points over a standard prompting loop, from internal testing with no model names or sample sizes (R182-f1).

  9. Move cheap checks into the agent's inner loop. Uber moved simple CI jobs such as lint and build rules into a validate command the agent runs, after CI jobs more than doubled in 12 months (R101-f1). By the time an engineer reviews a change, AI review has run, screenshots or videos are attached where they apply, and a risk score is set, and engineers still review every PR (R101-f2). Both come from a podcast episode summary, secondhand.

  10. Have people check AI findings before anyone else spends time on them. In a GitHub and Microsoft pilot on six open-source projects, a scanner flagged thousands of possible issues. An agent triaged them and seven researchers hand-checked them at about two days per project (R186-f2). The pilot sent 99 private reports with a proof of concept and suggested fix, and maintainers had fixed 55 by 15 November (R186-f1). The vendors recommend checking each finding against the project's threat model before reporting (R186-f4). They say six projects is a small sample and human review does not yet scale (R186-f5).

  11. Let experts audit agent verdicts rather than label from scratch. On DeepFact, PhD experts labeling alone scored 60.8% on hidden known-answer claims (R016-f1). In a simulated Audit-then-Score study run by the paper's authors on claims from deep research reports, with round 0 expert-only plus 3 audit rounds, auditing agent verdicts raised that to 90.9% (R016-f2). Experts were misled by a wrong agent on 2.8% of claims and resisted a wrong agent on 13.3% (R016-f4).

  12. Stop retrying when the errors stop being new. For a Lean prover, the most important feature for predicting whether another attempt would succeed was error diversity, the share of unique compiler error messages. In the authors' evaluation with Goedel-Prover-V2-8B, a router using it cut required compute by 28.9% on average at parity accuracy on a 43-problem PutnamBench test set, over 64 seeds (R042-f1, R042-f3). Attempt count alone saved only 13.1% (R042-f3).

Avoid

  • Counting the agent's own assertions as verification. The essay places them outside the harness (R020-f1). No source here measures how often agent-written tests are tautological; that claim was in our notes but is not in the text read (R220-f4).

  • Reading a proof as proof of the right thing. Vero's audit certifies satisfiability, not semantic correctness, so its authors reviewed every specification by hand (R045-f7). In code-and-proof mode, agents sometimes replaced a hard reference algorithm with a simpler one that met the same specifications, closing all 250 where the reference allowed 201 (R045-f4). The quantum-graph proof is only as meaningful as the Lean encoding of the optics model (R210-f4). LeanRDF's checker is sound but not complete, so "not derived" is never a claim that something is false (R208-f5).

  • Keeping flaky or slow tests in the agent's loop. The Claude Code team reports that flaky tests teach the agent to rerun instead of fix and that slow tests get run less often, without published measurements (R182-f6).

  • Auto-approving without guards. Qodo's auto-approval lets teams exclude repositories, paths such as auth/** and authors, including coding agents, and re-checks on every commit (R141-f2). The launch post gives no accuracy, false-approval rate or sample size (R141-f5).

  • Stacking review layers in the hope that they fix answers. In one non-peer-reviewed extraction study on CADEC (gpt-oss:20b extractor, 40 documents, three runs), three-sample voting used 411,000 to 432,000 tokens per run and changed net correct codes by -1 to +1 (R039-f1). In that study's first run on 230 development records, the ACCEPT withholding rule removed 128 errors at the cost of 49 right answers, and sent 177 records to a person (R039-f2). The study is of data extraction, not code review, so it bears on review layers only by analogy.

  • Trusting a single run of a check. In one extraction study, three identical temperature-zero runs of a mixture-of-experts extractor (gpt-oss:20b) differed by four F1 points, while four other model families gave byte-identical runs (R039-f4).

  • Retrying on attempt count alone. It gave less than half the savings (13.1% vs 28.9%) of a router that also read error diversity and proof similarity (R042-f3).

  • Measuring agent output by PR velocity. Uber tags PRs by type instead, because agents make low-impact PRs easy; no figures are given (R101-f3).

  • Accepting changes no one understands. The Hardwood project welcomes LLM-assisted contributions but not changes accepted without understanding them (R102-f1, R102-f2). This is a policy statement, not evidence.

How this was made

Twenty sources were used:

  • 17 in the verification set: 7 arXiv papers (R041, R042, R043, R044, R045, R133, R210), 7 web articles, pages or press releases (R020, R101, R105, R141, R182, R186, R220), and 3 repositories (R052, R102, R208).

  • 3 related sources from the evals set: two arXiv papers (R016, R224) and one InfoQ article that is not peer reviewed (R039).

A Sonnet model extracted 83 claims for the verification set, each tied to a location in the source (a section, table, heading, the abstract, or the whole page). Opus wrote this guide from those claims and the related evals claims, and a separate Opus reader checked every cited sentence against its claim; its 34 fixes are applied.

Limits, and how they were weighted:

  • R041 and R043 were read at abstract only, because the full HTML returned 404 for every version (R041-f4, R043-f4). Only their abstract-level results are used here.

  • R101 and R220 were read only as podcast episode summaries, without transcripts (R101-f5, R220-f4). They are treated as secondhand practitioner opinion.

  • R052's benchmark numbers are in an image, so only the README's text statements are used, namely higher precision and F1, about one ninth of the tokens, and lower recall (R052-f1, R052-f5).

  • R102 says nothing about verifying agent work beyond a contribution policy (R102-f1). It is cited only for that policy.

  • Vendor material: R105 is a vendor press release on a self-reported survey (R105-f5), R141 is a launch post with no measured results (R141-f5), R052's benchmark is vendor-built (R052-f5), R186 is a GitHub and Microsoft pilot reported by those vendors (R186-f1, R186-f5), and R182 describes Anthropic's own team and internal testing (R182-f1). They are used for practices and stated figures, not as independent evidence.

  • R020 is an opinion essay whose one experiment is an anecdote (R020-f5).

  • R039 is not peer reviewed, and its authors say absolute CADEC numbers are likely inflated because CADEC is probably in training data (R039-f5).

Reading the sources found several of our earlier entries wrong, overstated or unverifiable. For example:

  • R042's "62 to 67%" oracle savings: the source gives 62.0% only (R042-f4).

  • R043's 94% type-error share and 56 to 75% error cut could not be checked, because only the abstract was readable (R043-f4).

  • R045's "about $67 per repo" was our own division, and our "no human proof review" omitted that all specifications were reviewed by hand, though agent proofs are machine-checked (R045-f5, R045-f7).

  • R133 used 100 cases per task, not 50, except for the text-only model (R133-f1, R133-f2).

  • R186's "9,791 findings" is not in the post, which says "thousands" (R186-f2).

  • R052's "1/15 of the tokens" is "1/9" in the README (R052-f1, R052-f5).

  • R105's multiplicative confidence formula and prior-year 48% figure are not in the release (R105-f5).

  • R220's "proof the test fails without the change" and "tautological tests" are not on the page read (R220-f4).

Those entries have been corrected at the source (2026-11-23).
