Reliaburger: a container platform whose release gate is the product claim

A single-binary container orchestrator written in Rust, Apache 2.0, at version 0.3.2 (released 23 November 2026). It is interesting to a staff engineer for two reasons that have little to do with containers: it treats an AI agent as a first-class, leashed operator of the cluster, and it publishes its qualification pipeline as the thing you are meant to judge it by rather than its feature list.

Architecture

One binary per machine plus one CLI. The per-node daemon is bun; every operator-facing command is relish. Eight resource kinds cover the surface that a conventional Kubernetes stack assembles from thirteen projects: app scheduling, batch jobs, ingress, mTLS, service discovery, metrics, logs, a registry, GitOps and chaos testing all ship inside the binary.

The stated design choices: Raft for leadership, capped at seven voters; SWIM gossip for membership and propagation; eBPF for service discovery in the kernel, with no proxy on the request path. A whitepaper argues each trade-off with sources.

Agent affordances are not a wrapper added later. Every command emits JSON a script can consume, relish agent returns bounded answers, and relish mcp exposes read-only tools over MCP along with the exact source its binary was built from.

The agent control loop: lease, propose, approve, undo

Reading a cluster is unrestricted. Changing one is not. The documented sequence is:

  1. The agent takes a lease on the object it wants to touch (relish agent lease take app web --namespace shop).

  2. The agent proposes a change rather than making it (relish agent propose rollback web --namespace shop).

  3. The cluster records what the change would do.

  4. A human token, or a policy, approves it (relish proposal approve 17).

  5. The undo is a single command, shown before anything happens (relish undo 17).

Policies are declarative and match on the author of a proposal, so a cluster can deny any delete proposed by an agent while allowing the same delete from a person. That is the useful primitive: the authorisation decision keys on who proposed as well as what, which most infrastructure RBAC cannot express.

The project reports that across 30 recorded agent sessions, the coding agent changed nothing by itself. Read that as evidence the gate holds in the recorded cases, not as a security proof; the recordings are the vendor's own.

Release qualification as the headline

The pipeline, in the project's own order:

  1. Build and sign the candidate once.

  2. Install it the way a user would, from the signed artifact.

  3. Soak it: three VMs running apps, a volume writer, Redis, a log spammer and exporters while a fault harness breaks things every few minutes.

  4. Soak again with a job campaign and a node-level fault every cycle: about an hour on a compressed schedule, then eight hours on the full one.

  5. Any product fix invalidates the candidate. A new candidate starts every soak again.

The failure conditions are absolute rather than statistical: one lost write, one counter that goes backwards, or a certificate close to expiry fails the release. An upgrade walk moves every node to a signed soak build and back, with a power-off or leader kill mid-walk on alternate walks.

The honest part is the published cost of that gate. One release needed eight candidates because the soaks failed the first seven. That number is the most transferable thing in the whole project: it prices a no-exceptions release gate in candidates, not in sentiment.

Tradeoffs

Small surface, counted. The project publishes a line-count comparison: 202,730 lines of Rust in src/ against 2,134,280 lines of Go across a thirteen-project Kubernetes stack, counted with one tool, code lines only, tests, vendored and generated code excluded on both sides. That is 10.5x. The comparison document is unusually careful about its own limits — the ratio falls to 6.7x once two large projects are removed, the two sides are not feature-equivalent in either direction, Go is wordier than Rust so some of the gap is language, and "lines aren't bugs". A reader who quotes the 10.5x without those qualifications is quoting something the authors explicitly declined to claim. Note also that the Rust side was counted on an unreleased development branch, not a release.

Pre-1.0 honesty as a feature. The project states it is good enough for home labs and dev clusters and not for production until 1.0.0, which has no date, and that an upgrade may mean starting a fresh cluster. The 0.3.2 notes confirm this concretely: the wire protocol moved to version 61, so a 0.3.1 cluster starts afresh.

No measured agent-efficiency claim. The obvious comparison — tokens and wall-clock time for an agent doing the same task on this platform versus on Kubernetes — is marked not measured yet, with open issues standing in for results. That is the right way to leave a hole, and it is also the hole that matters most to the agent-operability pitch.

Failure modes to design against

  • A leash that only covers the documented path. Propose/approve/undo binds the agent that uses relish agent. An agent with a shell on the node and the operator's own token is outside the model entirely. Treat the lease and proposal flow as a convention enforced by token scope, and check that the agent's token is genuinely the restricted one.

  • Undo that is not an inverse. A one-command undo of a rollback is cheap; an undo of a change that already moved data, or that other changes have since been layered on, is a different problem. The published evidence covers a single numbered proposal in isolation.

  • Policy keyed on author kind. Useful, and also a single bit that something must set honestly. If an agent can obtain a token whose author kind is human, every author-kind policy evaporates.

  • Soak coverage is not production coverage. Three VMs with a fault harness for eight hours is a strong gate against lost writes and bad upgrades. It is not a gate against scale, multi-tenant noisy neighbours or a year of certificate rotation.

  • Fresh-cluster upgrades. A wire-protocol bump that requires starting over is tolerable in a home lab and disqualifying for anything with state you care about. This is the concrete reason the pre-1.0 warning should be taken literally.

Review checklist

For anyone evaluating an agent-operable control plane, including this one:

  • Can the system express "this actor may propose but not apply", and is the distinction enforced by token scope rather than by the client?

  • Is every mutating path covered by the proposal gate, including the shell?

  • Is the undo shown before the change, and is it an inverse or a best effort?

  • Does the project publish how many candidates a release took, not just that it passed?

  • Are the failure conditions absolute (one lost write fails) or statistical (99th percentile)?

  • Is the headline size or efficiency comparison counted on a released artifact, with the counting rules published?

  • Which of the vendor's numbers are from a released version, and which from a development branch?

  • For any throughput figure: which release, what hardware, what the unit of work was, how long the run lasted, and whether the figure is an average over the run.

Figures that could not be traced

Two figures circulating with this project could not be traced to its published documents: a host-job throughput of 29,350 jobs a second attributed to an October release, and a 25-of-25 power-cut and reboot result attributed to 0.3.2. The project's own current throughput claim is different — about 2.65 billion host-job tasks in one real day on three four-vCPU VMs for the published 0.2.8, roughly 30,664 a second on average — and its soak schedule describes a job campaign at more than 100 million jobs a day, a much lower rate for a different test. Treat the unlocatable numbers as unconfirmed rather than wrong, and quote the published ones.
