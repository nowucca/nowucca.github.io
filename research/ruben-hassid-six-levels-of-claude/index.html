TL;DR

A consumer-level setup guide in six "levels", from the same author as R004, four days later. Four of the six are reasonable defaults; two are worth knowing even at staff level, and both check out against Anthropic's own pages: thumbs up/down sends the whole conversation to Anthropic for up to 5 years and it may be used for training, and on Team and Enterprise, an owner turning memory off for the organization permanently deletes every member's memory. The model-switching advice is right for the wrong reason (it is a cache miss, not a "re-read"). The post contradicts itself on skills: delete yours, then install his, from a 33,971-skill email-gated library. It also quietly reverses R004's "default to Auto" in favor of a fixed Opus 5.5 on high.

What the post says

  1. Use the desktop app. It works with local folders without uploading files one by one, and it pulls you toward Claude Code.

  2. Don't choose a model each time. Default to Opus 5.5 on high, and don't switch mid-chat, because "Claude re-reads the entire chat" and burns tokens.

  3. Effort is Medium or High, nothing else. Medium for light work, High for most; Extra High mostly burns your usage limit.

  4. Delete your old setup. Clear the custom-instructions box and old skills, since they were written for older models. Give one goal, and end prompts with "Before you start, restate my goal in your own words."

  5. Ask for HTML, not a document. Add "Make it an HTML page" and "for [who will read it]". Claims there is then "no scope of making mistakes".

  6. Protect what you plug in. Never click thumbs up or down, since feedback may go to training. On a Team plan, leave memory on once it's on: if an owner turns it off, every member's memories are deleted permanently.

Then a 20-minute plan: install the desktop app, no settings, connect one tool, use Claude Code more, delete installed skills and add new ones, and visit his library.

1Desktop app beats the browserMostly rightLocal folder access and Claude Code remove the upload step. The trade-off it skips: the agent can now read and write your disk, so permission prompts and folder scoping matter (R006's permissions by blast radius).
2Don't switch models mid-chat; it "re-reads the chat"Right advice, wrong mechanismEvery turn already sends the whole conversation; prompt caching is what makes that cheap. Caches are per model, so a switch is a cold cache: the full history is billed at full input price once, and again on any switch back. The cost scales with conversation length. A second, quieter cost: the new model inherits a transcript shaped by the old one's style.
2bDefault to Opus 5.5 on highReasonable, unmeasuredSimple and stable, which also helps caching. It contradicts R004 (same author, 2026-11-04), which said to default to Auto. Neither post shows evidence.
3Medium or High effort onlyPlausible heuristicHigher effort spends more thinking tokens; whether it pays depends on the task. Long agentic or hard-to-verify work can repay Extra High by avoiding retries; no data is offered either way.
4Delete old instructions and skillsSame as R004, same gapPruning stale config after a model upgrade is sound, but wiping without a before/after eval also deletes project facts and rationale. Skills cost little until they trigger (only their descriptions sit in context), so the risk is a stale skill that triggers and overrides newer model behavior, not idle ones.

Takeaways for a staff engineer

  • Pin model and effort per conversation as cache hygiene. Choose up front; if a task needs a different model, start a fresh conversation with a short handoff rather than switching in place.

  • Treat the feedback button as a data-export path. For teams on consumer plans, write it into the AI usage policy: no thumbs on chats containing customer data, secrets or unreleased code.

  • Put the org-wide memory toggle under change control. It is a destructive, irreversible bulk delete behind a single setting; document it in the admin runbook and require a second person.

  • Version harness config instead of wiping it. Keep instructions and skills in a repo, re-audit them after model upgrades, and gate removals on a small eval (R005's quarterly re-audit).

  • Steal the restate-the-goal line. It costs one turn and catches the most expensive failure, solving the wrong problem.

Review checklist

  • Is the model and effort level chosen at the start of each long conversation, and not changed mid-thread?

  • Does the team's usage policy say when feedback ratings are allowed?

  • Who can change the organization's memory setting, and is that change reviewed?

  • Are instructions and skills versioned, with a dated reason for each rule?

  • Before deleting config, is there a before/after check on a few representative tasks?

  • Do prompts name the reader and ask the model to restate the goal?

  • Is local folder access limited to the folders a task needs?
