Beacon: cross-harness session capture distilled into reviewed agent memory

Beacon (Asymptote Labs, MIT, Go, about 3.6k GitHub stars) is an endpoint agent that records every coding-agent session across 25+ harnesses into one OpenTelemetry-shaped event log, then runs a human-gated loop that turns a few good sessions into Agent Skills any harness can load. The capture layer is the real product; the "self-improving memory" is an LLM-scored, agent-drafted, human-approved lesson pipeline.

How it works

The pipeline is seven stages; only the last three touch an agent's future behavior.

  1. Capture. Per-harness collectors (OTLP exporters, lifecycle hooks, transcript polling, plugins or extensions) record sessions, prompts and responses, tool calls, commands, file activity, approvals, MCP calls and token usage. Coverage is uneven: the README's own matrix shows Codex without file events, Cursor and Gemini CLI without tokens, VS Code partial. Browser extensions also capture claude.ai and ChatGPT chats; cloud agents (Claude Code, Cursor, Devin) and CI jobs (beacon ci exec) go through sandbox hooks or API polling to S3/GCS.

  2. Normalize. Everything lands in one OpenTelemetry-based event model, written by default to ~/.beacon/endpoint/logs/runtime.jsonl. An optional indexed history keeps 90 days locally.

  3. Browse. beacon traces (terminal) and a read-only local dashboard with per-session "lenses": sandboxed single-file HTML views such as diffs per file or an itemized token bill. Agents can write new lenses.

  4. Score. beacon memory evaluations run sends a bounded, redacted projection of each chosen trace to a hosted evaluator (TypeSafe "Jev" or SubQ, API key required, endpoint overridable). It returns probabilities only. A trace becomes a candidate when task_success is at least 0.50 and the mean score is at least 0.60.

  5. Draft. The beacon-memory-distill skill has the running agent read the candidate's source trace (user messages, tool calls, commands, results, approvals, errors) and write the lesson. The evaluator never writes lesson text.

  6. Approve. The user confirms, edits or rejects each draft; the skill forbids approving a placeholder body.

  7. Promote and recall. beacon-memory-promote installs an approved memory as .agents/skills/<slug>/SKILL.md; beacon-memory-recall fetches approved memory before a task through MCP (get_memory_context) or beacon memory list. Because the output is a plain Agent Skill, any skills-capable harness can load it, which is the cross-harness claim.

What is automated and what is human

The "self-improving" label oversells it: the loop is human-curated memory with an LLM triage step. One commenter on the post made the same point. That is a reasonable design, not a flaw, but read it as "assisted curation".

There is a no-evaluator path: skip scoring and let the agent read traces directly. In practice the expensive judgment (is this lesson true, general and safe?) stays with the human at step 6.

Defaults and data flow

The on-disk default is local, but the interactive installer preselects Beacon Cloud. Choosing it signs the machine in and starts forwarding to Asymptote Labs; Local is an explicit opt-out, and beacon endpoint disconnect reverses it. The confirm screen names the operator and capture mode, and there is a metadata-only privacy tier. Package, MDM and CI installs are noninteractive and account-free.

  • What the capture holds. Full prompts and responses, commands, file activity and approvals, plus browser chat if the extension is installed. Assume secrets pasted into a session end up in the log.

  • Dual market. Forwarding to Splunk, Sentinel, CrowdStrike LogScale, Datadog, Elastic, Wazuh and others, plus MDM install paths, says Beacon is also an AI-activity telemetry agent for security teams. Developers adopting it for memory are installing the same agent.

  • Lenses. The README warns the lens sandbox "cannot block every way a browser can send data out"; treat a third-party lens as code with read access to your traces.

  • Supply chain. Linux packages ship with checksums, a signed checksum file from 1.3.57, and GitHub build-provenance attestations; the quick-start still offers curl | bash and a "paste this into your agent" setup prompt.

Failure modes and tradeoffs

  • Lessons with no scope or expiry. An approved SKILL.md is a standing rule. Nothing records which repos, versions or task types it was meant for, or when to retire it. A commenter on the post argued the approval should record what the lesson may influence and refuse when applied elsewhere; Beacon does not do this. Pair it with a scheduled KEEP / FIX / DELETE pass (R036, R123).

  • Poisoned or wrong lessons. A session that "succeeded" by a wrong route, or one that read a prompt-injected file, can score well. The evaluator judges reusability, not truth; the human reviewer is the only check. Keep the evidence link (R040's point) so a lesson can be re-checked against the trace that produced it.

  • Misfiled memory. Many sessions have a null repository field, and Beacon then falls back to the current directory. The skill warns about it; a careless run files lessons under the wrong project.

  • Memory tax. Every promoted skill adds to what agents load. R059 and R036 found small, curated layers beat large ones; a pipeline that makes promotion cheap pushes the other way.

  • Cross-harness drift. A lesson drafted from a Claude Code trace names Claude Code tools and paths. It may read as nonsense, or as a wrong instruction, in Codex or Cursor.

  • Egress at two points. The evaluator call and Beacon Cloud forwarding both move session content off the machine. Both need consent per run or per install, but a team rollout makes them policy decisions, not individual ones.

  • Tradeoff worth having. One normalized trace format across harnesses is genuinely useful on its own: replay, token bills, audit and SIEM feeds, even if you never use the memory loop.

Review checklist before adopting

  • Install with Local chosen; confirm nothing forwards (beacon whoami, no endpoint connected).

  • Check the coverage matrix for your harnesses: which columns (file, tokens, approvals) are missing.

  • Decide whether trace content may go to the hosted evaluator, or use the no-evaluator path or a self-hosted compatible endpoint.

  • Grep a day of runtime.jsonl for secrets and decide retention.

  • Require every approved lesson to name its scope (repo, task type) and a review date, in the SKILL.md body.

  • Keep a link from each lesson to its source trace.

  • Cap the number of promoted skills per repo and review them on a schedule.

  • Treat third-party lenses as code with access to your traces.
