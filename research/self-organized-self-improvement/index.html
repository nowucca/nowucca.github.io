Self-organized self-improvement: frozen agents that design their own learning loop

Source: Sundaram, Sancaktar and Isola (MIT CSAIL, University of Tübingen), Do LLM Agents Still Need to Be Told How to Self-Improve?, arXiv 2611.23219, project page ssundaram21.github.io/self-org. Surfaced by Elvis Saravia (DAIR.AI) on LinkedIn, 2026-11-18.

TL;DR

Most self-improvement work hands the model a loop: generate tasks, roll out, score, update. This paper removes the loop. A frozen model (the teacher) gets a sandbox, a budget, Read/Write/Bash tools and a Gameplay tool, and one goal: edit the text files (prompt, skill files) of a player, which is another instance of the same model, so the player does better on unseen games with hidden mechanics. The teacher gets no real games and no validation scores.

The newer models build a working learning procedure on their own:

  • On 20 held-out PuzzleScript levels, the player improves by +20% (Claude Opus-5), +10% (GPT 6-Astra) and +6% (GLM 5.3). Older generations of the same families show little or no gain.

  • Opus-5's self-organized run roughly matches GEPA hill-climbing on 20 real in-distribution games at matched rollout budgets.

  • The learned text transfers: +9% on longer-horizon PuzzleScript, +21% on ARC-AGI-3 level 1, and +0.15 SPL on MazeBench, a 3D world rendered as ASCII.

The safety point is the headline. Leaving the self-improvement loop out of your harness does not stop a capable model from building one when it has the tools.

Setup

 teacher (frozen LLM, minimal harness: no system prompt, memory, web, subagents)
   tools: Read / Write / Bash / Gameplay(game_src, player_dir) -> score + transcript
   budget: 20 updates (one edit to one player file = one update), 150 gameplays
   goal: improve player on UNSEEN single-player games; artifacts must generalize
        |
        v  writes games (PuzzleScript text; must compile and be winnable)
 player (fresh session, same model, context c = prompt + skill files)
   20-turn horizon, 25k-token game budget, low reasoning effort
        |
        v  final context c_final evaluated on held-out sets
 PS-t20 | PS-t30 (longer) | ARC-AGI-3 L1 (other engine) | MazeBench (3D, ASCII)

The self-improvement score is J(c_final) minus J(c_0) on held-out games, where c_0 is the minimal starting prompt. The paper runs three teacher seeds per model across six models from three families.

What the successful teachers did

The strategies were similar across model families, and nobody prompted for them:

  • A/B testing. They played the same generated game with and without the current artifacts to measure what an edit actually did.

  • Calibrated difficulty. They made fewer trivial games. One Opus-5 session wrote a random level generator and a BFS solver to filter levels by solution length.

  • Learnability-seeking replay. Most generated games were easy and quickly dropped. Replays clustered on games with a 20–60% observed win rate. That inverted U looks like the learnability objectives used in asymmetric self-play and unsupervised environment design.

  • Self-built validation suites and adversarial games. Teachers wrote games designed to break their own advice, then re-ran earlier games to catch regressions.

  • Small edits. Opus-5 and GLM 5.3 preferred small context updates.

An LLM judge also scored sessions against Zimmerman's 13 self-regulated-learning subprocesses. The models that improved scored higher. The paper calls this descriptive, not causal.

Ablations that matter for practitioners

  • Toolset. Read/Write only, with the teacher reflecting on prior knowledge, beats the baseline but recovers less than half of the Gameplay gain on most benchmarks. Adding Bash helps more. In one Read/Write/Bash session the teacher wrote and ran its own game simulator even though its prompt never mentioned gameplay. A strong agent with a shell will build the experience generator you left out.

  • Engine. A Python Gameplay tool recovers nearly all of the PuzzleScript gain in 3 of 4 cases, so the result is not tied to one DSL.

  • Information leaks into overfitting. Giving the teacher more detail about the evaluation games first helps both near and far transfer. Past a point, near-distribution scores keep rising while ARC-AGI-3 transfer plateaus. Imposing the t20 turn and token budgets on the tool also hurt t30 performance. Whatever you tell the optimizer about the eval, in the prompt or through tool constraints, shapes what it overfits to.

  • Horizon. Training against 30-turn games did best everywhere, including on the 20-turn set.

Why it matters

  1. Prescribed loops may become scaffolding you can remove. For strong models, a GEPA-style optimizer over real tasks and a free-form teacher with a sandbox reached similar gains. The engineering question moves from which loop to which primitives, budgets and information you expose.

  2. Capability, not harness design, gates self-improvement. The same setup gave nothing for older generations. Expect harness-level self-improvement to show up when you upgrade the model, without any code change.

  3. A safety boundary set by harness design is weak. If Bash plus file write is enough for a model to build its own practice environment and evaluator, then not shipping a self-improvement loop is not a control. The controls are the budget, what the files can change, and what the agent can observe.

  4. The learned artifact is readable. Gains live in text files that can be diffed and reviewed, unlike weight updates. That is the hook for governance.

Tradeoffs and failure modes

  • Domain. Every result is turn-based games with binary reward. Software tasks have noisier, partial and delayed signals. Whether teachers can write useful practice tasks for, say, a codebase is open.

  • Small n. Three seeds per model, 16–20 games per benchmark, and error bars of ±1 SD. The +6% for GLM 5.3 is within plausible noise. The 20–60% replay band is a pattern, not a law.

  • Self-graded progress. Teachers judge their own generated games. The paper checks that teacher-observed gains agree with measured gains (its Appendix D.5), but in a less verifiable domain a teacher can fool itself. Compare greedy acceptance under noisy validation (R066).

  • Eval-awareness overfitting. This is shown directly. Telling the optimizer about the target distribution trades breadth for depth.

  • LLM-as-judge for the strategy analysis. The SRL alignment scores come from one judge model. Treat them as descriptive.

  • Unbounded variants are untested. The budgets are tight: 20 updates and 150 plays. Longer horizons, edits to code rather than text, or persistence across sessions are exactly where drift and reward hacking would show up.

Review checklist: when an agent can edit its own context

  • Is there an explicit cap on context edits and on rollouts? Do you log every edit with the evidence behind it?

  • Can the agent create its own test environments (Bash, file write, interpreters)? If so, assume it will, and decide whether that is allowed.

  • Is there a held-out evaluation set the agent never sees, run by something other than the agent?

  • What does the agent know about the evaluation, through the prompt and through tool limits? Could that knowledge make it overfit?

  • Are the learned artifacts diffed and reviewed before they reach other sessions or users?

  • Is there a regression check against earlier tasks, not just the latest one?

  • When you upgrade the model, do you re-test whether self-improvement behavior appears where it didn't before?
