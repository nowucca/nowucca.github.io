What it is

A browser simulator that steps an LLM server through its scheduling loop one iteration at a time. Requests with different prompt and output lengths arrive, go through prefill (reading the prompt) and decode (emitting tokens), and occupy KV-cache blocks. You can follow one request, pause and step, and compare policies side by side. The modes cover static versus continuous batching, whole versus chunked prefill, and reserved versus paged KV allocation, including what happens when KV memory runs short.

The concepts it makes visible

  • Prefill versus decode. Prefill processes many prompt tokens per step and is compute-bound; decode emits one token per request per step and is memory-bandwidth-bound. A single iteration can mix both, as the default example does: two requests emit one token each while a third reads six more prompt tokens.

  • Static versus continuous batching. In static batching the whole batch waits for its longest request. In continuous batching a finished request's slot is refilled immediately, so throughput rises and short requests are not held hostage by long ones.

  • Chunked prefill. A long prompt is read in chunks across several iterations so it does not stall streaming answers for everyone else. The cost is a slower time-to-first-token for the long request.

  • Reserved versus paged KV allocation. Reserving the maximum KV space per request wastes memory on outputs that end early. Paged allocation hands out fixed-size blocks on demand, which packs more requests in but needs a plan for when memory runs out (preemption, swapping or recomputation).

How to use it for teaching

  1. Start with static batching and one long request among short ones; ask learners to predict when the short ones finish.

  2. Switch to continuous batching on the same workload and compare the arrival timeline.

  3. Add a long document prompt with whole prefill, watch streaming answers stall, then switch to chunked prefill.

  4. Shrink KV memory and compare reserved with paged allocation to show why paging became standard.

Limits

  • Units are abstract tokens per iteration, not measured GPU time; it shows ordering and memory logic, not real latency.

  • No prefix caching, speculative decoding, or multi-GPU parallelism.

  • Built on a hosted no-code app platform; availability depends on that host.

Review checklist when reasoning about a real serving setup

  1. Is the workload prefill-heavy (long prompts, RAG, agents) or decode-heavy (long outputs)?

  2. Is continuous batching on, and what is the maximum concurrent batch size?

  3. Is chunked prefill enabled, and what chunk size trades time-to-first-token against stream smoothness?

  4. Is KV allocation paged, and what happens on memory pressure: preempt, swap or recompute?

  5. Are latency targets stated separately for time-to-first-token and inter-token latency?
